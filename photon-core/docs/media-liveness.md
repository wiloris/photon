# Живость поста как условие отдачи media

Спецификация среза «уборка C-2»: media мёртвого поста не отдаётся — каким бы
путём пост ни умер.

Решение — **ADR-056**. Здесь то, что из него следует для кода, и результаты
разведки, на которых оно построено.

Порядок написания записан честно: **спецификация написана ПОСЛЕ кода**, чего
метод проекта не предполагает. Разведка D1–D3 предшествовала и коду, и
решению, но текст спецификации появился следом за реализацией. Отмечено, чтобы
не выдавать задним числом соблюдение порядка, которого не было.

---

## 1. Проблема

Уборка C (ADR-055) убирает media **по событию** удаления поста. Live
acceptance показал, что событий приходит не на все посты: при каскадном
удалении треда `MessageHasBeenDeleted` приходит **только для корня**, а для
ответов — не приходит вовсе. Их media остаётся `AVAILABLE`: байты на диске,
объект скачивается по `media_id` любым, кто читает канал.

Тот же класс шире каскада: удаление из webapp, по REST, retention'ом сервера,
а также всё, что осиротело до появления уборки C, — события не порождают либо
породили его тогда, когда обрабатывать было некому.

---

## 2. Разведка: D1–D3

Три замера, выполненные **до** решения и до кода. Ни один не был предположением.

### D1 — обход треда после каскада: невозможен

```
ДО удаления:  104 getThread(root)  → ok: order=2 posts=2
ПОСЛЕ:        104 getThread(root)  → отказ "forbidden"
ПОСЛЕ:        104 getThread(reply) → отказ "forbidden"
```

Подтверждено и формой API: **у постов нет ни одного метода с `includeDeleted`**
— параметр существует только у каналов, ботов и property fields. Догнать
удалённые ответы перечислением нечем.

### D2 — одиночный ответ: событие приходит

Удаление **только ответа** (без каскада) даёт штатную уборку C: `702` по его
media отвечает `unavailable`, на диске `DELETED`, блоба нет, в журнале строка
уборки с `post_id` ответа. Значит дыра **ровно одна — каскад**, а не «ответы
вообще».

### D3 — различимы ли «пост удалён» и «вызов не удался»: да

Ключевой замер: от него зависела применимость всего решения.

| ситуация | что получает код плагина |
|---|---|
| пост жив | `post != nil`, `appErr == nil` |
| пост удалён | `appErr != nil`, **`StatusCode 404`, `id = app.post.get.app_error`** |
| RPC плагина мёртв | **`(nil, nil)`** — ни поста, ни ошибки |
| инфраструктурный сбой | `appErr` с 5xx |

404 снят через REST (`GET /api/v4/posts/{deleted}` → 404, живой пост → 200);
REST и Plugin API идут через один метод прикладного слоя, но это **косвенное**
свидетельство, и так оно и записано. `(nil, nil)` — не догадка: это
задокументированный в самом Bridge отказ транспорта Plugin API, ради которого
существует проверка `created == nil` в `createPost`.

**Попутная поправка.** Прежние редакции документов называли путь закрытия
«перехват `MessageWillBeDeleted` с обходом треда». **Такого хука не
существует**: в `public@v0.1.21` 43 хука, из `*WillBe*` — только
`MessageWillBePosted`, `MessageWillBeUpdated` и `MessagesWillBeConsumed`.
Пред-хука на удаление поста нет вовсе. Формулировка была предложена по
аналогии и не проверена; исправлена везде, где встречалась.

---

## 3. Решение

Не догонять событие, а **спрашивать при чтении**.

На `702` и `701`, если у объекта непустой `post_id`, опрашивается живость
поста. Пост мёртв → `unavailable`.

**Три исхода, а не два** — главное в контракте:

| вердикт | когда | что делает сервер |
|---|---|---|
| `PostAlive` | `(post, nil)` | отдаёт |
| `PostGone` | `appErr` с **404** | **гасит** |
| `PostUnknown` | `(nil, nil)`, 5xx, 403, оракула нет | **отдаёт** |

**Fail-open — правило, а не оговорка.** Мёртвым считается только 404. Любой
другой исход оставляет вопрос открытым, и объект отдаётся: отсутствие ответа
не является доказательством отсутствия поста. Иначе сбой RPC или упавшая база
гасили бы живые вложения — отказ, который снаружи неотличим от потери данных.

`PostUnknown` сделан **нулевым значением** намеренно: забытый или
неинициализированный оракул даёт самый безопасный исход.

Это **не уборка**: ни байты, ни состояние не меняются, диск не освобождается.
Меняется только ответ на чтение. Уборки B и D остаются открытыми.

---

## 4. Границы

Опрашивается **только прикреплённый** объект. У неприкреплённого (`STORED`)
`post_id` пуст, спрашивать не о чем, и он обязан оставаться читаемым — на этом
держится проверка N5, а сама брошенная загрузка обнаружима по пустому
`post_id` и возрасту (уборка A).

Живость спрашивается **после** `HasBytes()`: у объекта, уже переведённого
уборкой C в `DELETED`, ответ тот же, а вызов через Plugin API стоит денег.
Порядок здесь — про цену, не про смысл.

---

## 5. Находка реализации: 702 ходил мимо сервиса

Тест поймал её **до** живого прогона. `MediaHandler.getInfo` читал
`MediaStore` напрямую и держал у себя копию правила «байты доступны?». Пока
условие сводилось к хранимому состоянию, две копии давали один ответ — именно
поэтому уборка C через 702 работала. С живостью они разошлись бы **молча**:
`702` отдавал бы метаданные объекта, чей пост мёртв, а `701` по тому же
объекту отказывал.

Handler переведён на `MediaService.Info`; различение причин задаёт
`mediaErrorText`, то есть одно и то же на обоих путях.

---

## 6. Failure-oriented проверки

| # | проверка | падает на мутации |
|---|---|---|
| 1 | media мёртвого поста → `unavailable` на обоих путях | «живость не спрашивается» (поведение до ADR-056) |
| 2 | media живого поста отдаётся | «гасить всегда» |
| 3 | `PostUnknown` отдаёт объект | «`(nil,nil)` считать мёртвым», «5xx считать мёртвым» |
| 4 | сервис без оракула работает как прежде | — (защита совместимости) |
| 5 | `STORED` с пустым `post_id` не гасится, оракул не вызывается | «спрашивать живость и для пустого `post_id`» |
| 6 | `DELETED` не опрашивает оракул | «спрашивать живость до `HasBytes`» |
| 7 | `Attach` не ломается | — |
| 8 | `702` отвечает **ровно** `unavailable` | «отвечать `forbidden` на любую причину» |
| 9 | четыре исхода Plugin API → три вердикта | «любая ошибка = мёртв» |
| 10 | `PostUnknown` — нулевое значение | перестановка констант |

---

## 7. Живой прогон: N8 и N9

- **N8** — media ответа, удалённого **каскадом**: пост умирает молча,
  события нет. Сервер с работающей уборкой C и без живости проходит N6 и N7 и
  падает здесь — мутация двойника это подтверждает: при ней падает **только**
  N8.
- **N9** — объект, осиротевший **до появления проверки**. Идентификатор
  приходит флагом `-orphan-media`, а не зашит: прогон обязан оставаться
  переносимым. Без флага проверка объявляется `NOT EXECUTED`.

N9 существеннее N8 по смыслу: N8 создаёт сироту сама и проверяет механизм,
N9 берёт уже лежащую на сервере и доказывает, что закрыт **класс**, а не путь.

---

## 8. Измеренная цена

Замер изолирован: одно соединение, один момент, две серии по 30 вызовов —
`702` по `STORED` (оракул не вызывается) против `702` по живому посту
(вызывается).

| серия | медиана | p90 |
|---|---|---|
| без опроса живости | 204.5 мс | 316.5 мс |
| с опросом живости | 208.4 мс | 308.8 мс |

**Разница медиан — +3.85 мс.** p90 в пределах разброса. Абсолютная задержка в
этом прогоне выше, чем в утреннем (≈205 мс против ≈92 мс), **одинаково в обеих
сериях** — это стенд и сеть, а не оракул.

Цена платится на каждом чтении прикреплённого объекта. Она не платится:
у неприкреплённых, у уже `DELETED` и при выключенном оракуле.

---

## 9. Чего срез не делает — намеренно

- **не освобождает диск**: байты орфанов остаются на месте, `meta.json` тоже.
  Это уборки **B** (подметание) и **D** (TTL), обе открыты;
- **не убирает состояние**: `AVAILABLE` у осиротевшего объекта так и остаётся
  `AVAILABLE`. Наблюдаемо снаружи только по ответу `unavailable`;
- **не заводит** индекс `post_id → media_id[]`, планировщик, `EXPIRED`,
  quotas и `post_deleted` в push;
- **не трогает** `ports/*.go`, C ABI, protobuf, SDK, plugin runtime и
  `services/localfeed`.

**Чего зелёный прогон не докажет:** что орфаны перестали появляться (они
появляются — просто больше не читаются); что диск перестал расти; что 404 от
Plugin API тождественно 404 от REST — последнее снято косвенно и подтверждается
поведением, а не исходниками сервера.

---

## 10. Что осталось открытым

- **прямое подтверждение 404 в Plugin API**: измерено через REST, в коде
  плагина пока подтверждается только поведением N8/N9. Одна строка журнала при
  первом `PostGone` закрыла бы это точно;
- **удаление канала и удаление пользователя** — не проверялись ни разу.
  Предполагать их поведение по каскаду треда нельзя: ровно эта ошибка и была
  опровергнута разведкой;
- **треды глубже одного уровня ответов** — не проверялись;
- **стоимость на медленном хосте**: +3.85 мс измерены при RTT ≈200 мс, где
  добавка теряется в разбросе. На локальном клиенте доля будет заметнее.
