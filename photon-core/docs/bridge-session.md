# Bridge Session — спецификация (Phase 12.5)

Написана **до** кода, как `WIRE_FORMAT.md` перед `adapters/tcp` и `sandbox.md`
перед sandbox (`CLAUDE.md`, «Метод работы»). Нормативные утверждения — «обязан»,
«не должен»; всё остальное — обоснование.

Связанные документы: **ADR-034** (JSON на проводе, protobuf как схема),
ADR-026 п.7 (та же граница для C ABI), ADR-025/ADR-009 (владение протоколом),
ADR-020 (порты заморожены), ADR-011/013/016 (`ports.Transport`),
`adapters/tcp/WIRE_FORMAT.md` (образец жанра).

---

## 1. Зачем эта фаза существует

`Photon_Create` не подключается к серверу. Это выяснилось при discovery-проходе
перед Phase 13 и оказалось не «недоделкой в одну строку», а отсутствующим слоем:
между замороженным `ports.Transport` (умеет открывать стримы) и Dispatcher
(умеет исполнять action) нет ничего, что знало бы **протокол** — как
аутентифицироваться, в каком порядке слать фреймы, чем отличается `action`-режим
от `subscribe`, что делать при обрыве.

Phase 13 (Dispatcher) без этого слоя реализуема только в одном виде: Dispatcher
сам открывает стримы и сам пишет в них JSON. Это ровно та ошибка, от которой
предостерегает `CLAUDE.md` («Спецификация до кода… обратный порядок даёт
протокол, повторяющий возможности выбранной библиотеки, а не модель системы») —
только на уровень выше: получился бы Dispatcher, повторяющий форму транспорта.

Поэтому Phase 12.5 идёт **перед** Phase 13, а не после.

### Что эта фаза НЕ делает

- Не исполняет action'ы (это Phase 13) — сессия доставляет запрос и возвращает
  ответ, но не знает, что внутри payload'а.
- Не трогает `ports.Transport` и `adapters/quic`. Проверено при написании
  спецификации: порт покрывает потребность целиком (§7). Порты заморожены
  (ADR-020), и это шестой подряд компонент, который обошёлся без правки
  контракта.
- Не реализует сервер. Серверная сторона — `photon-quic-bridge` (Phase 14),
  отдельный репозиторий.
- Не вводит доменные сущности (`User`, `Post`, …) — Phase 12, отложена
  осознанно.

## 2. Нормативный wire-format

Источник истины — ADR-034. Здесь он повторён в объёме, необходимом для
реализации; при расхождении прав ADR.

Транспорт — QUIC, ALPN `photon-quic-v1` (совпадает с `defaultALPN` в
`adapters/quic` — проверено, менять нечего). Сериализация — **JSON**. Каждый
фрейм — одно JSON-значение, записанное `json.Encoder` (то есть с завершающим
`\n`); читается `json.Decoder` потоково. Длины фреймов на проводе нет:
границу задаёт сам JSON. Это не выбор Phase 12.5, а описание уже развёрнутого
сервера.

### 2.1 Handshake-стрим

Первый bidi-стрим соединения. Три фрейма, строго в этом порядке:

```
→ {"session_token":"<token>"}
→ {"mode":"action"|"subscribe","protocol_version":1}
← {"ok":true}                      | {"ok":false,"error":"<reason>"}
```

После получения ответа клиент **обязан** закрыть handshake-стрим (half-close
достаточно) и далее работать по этому же соединению другими стримами.
Соединение живёт; закрывается только стрим.

`protocol_version` — новое поле, см. §5. Развёрнутый сервер его не знает и
проигнорирует (Go `encoding/json` молча игнорирует неизвестные поля) — поэтому
добавление обратно совместимо.

### 2.2 Action-стрим

Отдельный bidi-стрим на каждый action. Два фрейма запроса, один ответа:

```
→ {"action":100,"resource":"PostResource"}
→ { ...payload... }                          // {} если payload'а нет
← {"ok":true,"data":<any>} | {"ok":false,"error":"<reason>"}
```

`data` не типизирована и может быть объектом, массивом или отсутствовать —
клиент `test_photon.go` специально приводит её через `interface{}`, потому что
жёсткое `map[string]interface{}` падало на ответах-списках (`getUsers`,
`searchUsers`, `getReactions`). Реализация **не должна** предполагать, что
`data` — объект.

### 2.3 Push-стрим

Только на соединении с `mode=subscribe`. Сервер открывает UniStream, один
фрейм:

```
← {"event":"posted","user_id":"...","data":{...}}
```

`event` — строка, не число (константы `PushEvent*` в
`photon-quic-bridge/server/protocol.go`). `user_id` пустой = широковещательное
событие.

### 2.4 Два режима — два соединения

`mode` фиксируется на соединение, а не на стрим. Клиенту, которому нужны и
action'ы, и push, требуется **два** соединения — именно так делает
`test_photon.go` (`conn` для action'ов, `subConn` для подписки). Реализация
не должна пытаться получить push по `action`-соединению.

## 3. Граница «схема ≠ провод»: интерфейс `Codec`

ADR-034 п.4 требует изолировать wire-format за интерфейсом, чтобы смена формата
была подменой реализации, а не правкой по всем вызовам.

Ключевое требование к форме интерфейса: **количество фреймов — деталь кодека, не
контракта**. JSON-кодек пишет запрос двумя фреймами (header + payload);
гипотетический protobuf-кодек написал бы одним `PhotonRequest`. Если интерфейс
объявить пофреймово (`WriteHeader`, `WritePayload`), это различие протечёт
наружу и смена формата снова станет правкой вызывающего кода. Поэтому интерфейс
объявляется **посообщенчно**:

```go
// Codec — сериализация Bridge-границы. Реализация по умолчанию и
// единственная сейчас — JSON (ADR-034). Вызывающий не знает и не может
// узнать, какой формат за интерфейсом: число фреймов, их порядок и
// разделители — целиком внутри реализации.
type Codec interface {
    WriteHandshake(w io.Writer, h Handshake) error
    ReadHandshakeAck(r io.Reader) (HandshakeAck, error)

    WriteRequest(w io.Writer, req Request) error
    ReadResponse(r io.Reader) (Response, error)

    ReadPush(r io.Reader) (Push, error)
}
```

### 3.1 Почему `Response.Data` — `[]byte`

`Data` объявлена как непрозрачный `[]byte`, а не `interface{}` и не
`map[string]any`. Причина — ADR-026 п.7: граница C ABI отдаёт клиенту
`payload_json`, то есть JSON. Значит:

- JSON-кодек возвращает срез исходных байт **без разбора** — ни одной лишней
  сериализации на пути, и `data` любой формы (объект, массив, `null`) проходит
  насквозь, что прямо требуется §2.2;
- не-JSON кодек (если он однажды появится) обязан конвертировать в JSON на своей
  границе, потому что этого требует ABI, а не потому что так удобнее сессии.

Тип `interface{}` вместо `[]byte` заставил бы JSON-кодек разобрать и собрать
ответ обратно ради того, чтобы вызывающий снова сериализовал его в JSON — три
лишних прохода на ровном месте и потеря точности чисел (`float64`).

### 3.2 Что запрещено

Кодек **не должен** экспортировать ничего, что раскрывает формат: ни
`json.RawMessage` в сигнатурах публичных типов, ни методов вида `AsJSON()`.
Проверяется тестом уровня «сломай правило и убедись, что тест падает» —
компилируемым тестом на то, что подмена кодека на фиктивный не требует правки
кода сессии (§8, T-9).

## 4. Вывод `resource` из action-кода

ADR-026 п.1 убрал `resource` из `Photon_SendAction`: на уровне ABI строка
избыточна, потому что action-код определяет ресурс диапазоном. На проводе
header-фрейм строку **требует** (§2.2). Значит сессия обязана её выводить:

| Диапазон | `resource` |
|---|---|
| 100–199 | `PostResource` |
| 200–299 | `UserResource` |
| 300–399 | `ChannelResource` |
| 400–499 | `EngramResource` |
| 500–599 | `FileResource` |
| 600–699 | `WallResource` |

Таблица не выписана по памяти: она подтверждена перекрёстной проверкой всех 48
вызовов `action(...)` в `test_photon.go` — клиенте, проверенном против живого
сервера. Каждая сотня отображается ровно в один `resource`, исключений нет
(`PostResource` 100–114, `UserResource` 200–210, `ChannelResource` 300–314,
`EngramResource` 400–405, `FileResource` 500–505, `WallResource` 600–602).

Требования:

- Код вне известных диапазонов **обязан** отвергаться до отправки в сеть, с
  ошибкой, отличимой от сетевой. На уровне ABI этому соответствует
  `PHOTON_ERR_INVALID_ACTION` (ADR-026 п.5).
- Проверка «код принадлежит `enum Action`» и проверка диапазона — **разные**
  проверки. Код `150` попадает в диапазон Post, но не существует в `enum Action`;
  он обязан быть отвергнут. Источник истины — `photonpb.Action_name`, как уже
  делает `photon-bindings/c/photon.go`.
- Каждый диапазон покрывается тестом (§8, T-8) — включая границы (100, 199,
  200, …), потому что ошибка на единицу здесь даёт молча неверный `resource`,
  который сервер отвергнет с невнятной ошибкой уже по сети.

## 5. `protocol_version` и механизм смены формата

ADR-034 п.5: запирает не формат, а отсутствие механизма смены. Механизм вводится
сейчас, формат — нет.

**Константа.** `ProtocolVersion = 1` — версия, которую клиент объявляет и
поддерживает. Одно число, не пара major/minor: `PHOTON_ABI_MAJOR/MINOR`
(ADR-026 п.4) версионируют ABI между Core и binding'ом, это другая граница и
другой темп изменений. Смешивать их в одно поле — источник ошибок.

**Отправка.** Клиент кладёт `protocol_version` в mode-фрейм (§2.1).
Развёрнутый сервер поле игнорирует — совместимость сохраняется.

**Приём и отказ.** Ответ на handshake может содержать `protocol_version`:

| Ответ сервера | Поведение клиента |
|---|---|
| поле отсутствует | принять, считать версией `1` — так отвечает развёрнутый сегодня сервер, и трактовать это как ошибку значило бы сломать работающую систему |
| `protocol_version == 1` | принять |
| `protocol_version != 1` | **отвергнуть** соединение с отдельной ошибкой `ErrProtocolVersion`, не пытаться работать «как получится» |
| `"ok":false` | отвергнуть с ошибкой сервера, версию не рассматривать |

Отказ **обязан** быть отличим от прочих ошибок handshake (`errors.Is`), а не
строкой в тексте — ровно по причине, изложенной в ADR-033: строковая
классификация ошибок в этом проекте уже дважды приводила к реальным дефектам.

Требование `CLAUDE.md` («тесты должны ловить нарушения») здесь означает: тест
T-5 обязан падать, если реализация начнёт принимать несовместимую версию.
Проверяется намеренной поломкой правила при разработке.

## 6. Жизненный цикл сессии

```
     Created ──Connect()──► Connecting ──ok──► Ready ──Close()──► Closed
                                │                │                   ▲
                                │ ошибка         │ обрыв             │
                                ▼                ▼                   │
                             Failed ──────────► Failed ──────────────┘
```

Правила, каждое из которых имеет тест:

1. **`Connect` идемпотентен по результату, но не по эффекту**: повторный вызов
   на `Ready`-сессии возвращает `nil`, не открывая второго соединения.
2. **`Close` идемпотентен полностью** и безопасен из любого состояния, включая
   `Created` и повторный `Close`. Прецедент прямой: double-free в
   `ipc.closeWith` (Phase 9) найден именно таким тестом.
3. **`Close` во время `Connect`** обязан прерывать `Connect`, а не ждать его
   завершения. Прецедент: вечное зависание `host.Stop` на неотвечающем плагине
   (Phase 9) — тот же класс.
4. **После `Close` сессия не воскресает**: `Do` и `Connect` возвращают
   `ErrSessionClosed`. Прецедент: воскрешение плагина после `Stop` во время
   backoff (Phase 9).
5. **`Do` на не-`Ready` сессии** возвращает ошибку, не подключается неявно.
   Неявное подключение внутри `Do` пришлось бы делать под общей блокировкой и
   превратило бы каждый первый вызов в непредсказуемо долгий.
6. **Отмена `ctx`** прерывает `Do`: вызывающий получает `ctx.Err()` сразу, не
   дожидаясь ответа сервера, и стрим закрывается на запись (half-close).

   **Полностью освободить стрим при отмене нельзя, и это ограничение
   замороженного порта, а не недоделка.** `ports.Stream.Close()` — half-close
   только пишущей стороны: `CancelRead`/`CancelWrite` порт намеренно не
   экспортирует (прямо сказано в комментарии `adapters/quic/quic.go` к
   `stream.Close`). Значит горутина, заблокированная на `Read`, остаётся
   заблокированной до ответа сервера или до закрытия соединения — освобождение
   ограничено временем жизни `Connection`, но не мгновенно.

   Фильтр ADR-020 применён и не пройден: это не «решается внутри адаптера»
   (адаптер и так делает единственно верное) и не ограничение библиотеки
   (`quic-go` умеет `CancelRead`) — это сознательное сужение порта. Расширять
   порт ради этого — отдельный ADR и отдельное решение, а не побочный эффект
   Phase 12.5. Здесь фиксируется как известное ограничение (§9).

**Реконнект в Phase 12.5 не реализуется.** Сессия сообщает об обрыве
(`Failed`), решение о переподключении принимает вызывающий. Причина: политика
переподключения — ответственность `services/autodial` (Phase 7, уже
реализована), и дублировать её здесь значило бы завести вторую политику,
расходящуюся с первой. Это записано как осознанный пропуск, а не забытый пункт.

## 7. Отношение к `ports.Transport` — правок не требуется

Проверено при написании спецификации, до кода:

| Нужно сессии | Есть в `ports.Transport` |
|---|---|
| открыть соединение | `Transport.Connect(ctx, Endpoint)` |
| handshake-стрим, action-стримы | `Connection.OpenStream(ctx)` |
| push от сервера | `Connection.AcceptUniStream(ctx)` — заведён ADR-016 **именно** под Subscribe в `photon-quic-bridge` |
| half-close после записи фреймов | `SendStream.Close()` |
| закрыть всё | `Connection.Close()` |
| ALPN `photon-quic-v1` | `adapters/quic`, `defaultALPN` — совпадает |

Ни одного пункта, требующего расширения порта. Фильтр ADR-020 («решается внутри
адаптера? ограничение библиотеки или потребность ядра?») не доходит даже до
второго вопроса.

Сессия работает через `ports.Transport`, **не** через `quic-go` напрямую —
в отличие от `test-client/test_photon.go`, который дёргает `quic.DialAddr` сам.
Тест-клиент таким и остаётся: он проверяет сервер, а не ядро, и его прямая
зависимость от `quic-go` — не образец для Core.

## 8. Тесты

Failure-oriented — обязательны (`CLAUDE.md`). Опыт Phase 9–11: три реальных бага
найдены тестами отказов, ни один не проявлялся при нормальной работе.

| # | Тест | Что ловит |
|---|---|---|
| T-1 | Handshake: порядок фреймов auth → mode → ack | Перестановка фреймов — сервер отвергнет молча |
| T-2 | Handshake: `ok:false` → ошибка, сессия не `Ready` | Продолжение работы по неаутентифицированному соединению |
| T-3 | Handshake: обрыв соединения между фреймами | Зависание на чтении ack |
| T-4 | Handshake: мусор вместо JSON в ответе | Паника/зависание на неразбираемом ответе |
| T-5 | **Несовместимый `protocol_version` → отказ** (§5) | Работа «как получится» с чужим протоколом |
| T-6 | Совместимая и отсутствующая версия → приём | Регрессия совместимости с развёрнутым сервером |
| T-7 | Action: два фрейма, затем ответ; `data` — объект, массив, `null`, отсутствует | Падение на ответах-списках (реальный баг тест-клиента) |
| T-8 | `resource` для каждого диапазона + границы + неизвестный код | Ошибка на единицу, молча неверный `resource` |
| T-9 | Подмена `Codec` фиктивной реализацией не требует правок сессии | Протечка JSON наружу интерфейса (§3.2) |
| T-10 | `Close` из каждого состояния, дважды | Double-free (прецедент `ipc.closeWith`) |
| T-11 | `Close` во время `Connect` | Зависание (прецедент `host.Stop`) |
| T-12 | `Do`/`Connect` после `Close` → `ErrSessionClosed` | Воскрешение после закрытия (прецедент backoff) |
| T-13 | Отмена `ctx` во время `Do` → возврат `ctx.Err()` не дожидаясь ответа, стрим закрыт на запись | Зависание вызывающего на неотвечающем сервере |
| T-14 | Параллельные `Do` по одному соединению — каждый в своём стриме | Гонка/смешение ответов |
| T-15 | Push: приём события; push по `action`-соединению не ожидается | Неверное предположение §2.4 |
| T-16 | `-race` на всём пакете | Гонки |

**Чем тестируется.** Фиктивный `ports.Transport` поверх `net.Pipe` — сессия
работает против него, не открывая сокетов. Ограничение честное и записанное:
`net.Pipe` не воспроизводит ни таймингов реальной сети, ни поведения QUIC при
обрыве — это ровно то, из-за чего Phase 9 и 10 не нашли три бага, найденных
Phase 11 на настоящих процессах. Поэтому:

- тесты T-1…T-16 проверяют **логику протокола**, и этого достаточно для их целей;
- проверка против **живого сервера** остаётся отдельным пунктом (§9) и не
  подменяется фиктивным транспортом.

## 9. Что останется непроверенным после Phase 12.5

Записывается заранее, как требует `CLAUDE.md` — «не дореализовывать молча»:

1. **Работа против живого `photon-quic-bridge`.** Полный репозиторий Bridge
   (`handler_*.go`, QUIC listener) в этом дереве отсутствует — здесь только
   четыре изменённых файла (`CLAUDE.md`). Владелец подтвердил, что репозиторий
   доступен и может быть положен рядом; до этого момента сессия проверена
   только против фиктивного транспорта.
2. **Использует ли сервер `HandshakeResponse.status` и `PhotonResponse.code`.**
   Из имеющихся файлов не видно — клиент их не читает (ADR-034, «Ограничение
   проверки»). Если сервер их шлёт, кодек их проигнорирует; это не ошибка, но
   должно быть подтверждено, а не предположено.
3. **Поведение реального QUIC при обрыве** — таймауты, порядок ошибок,
   `AcceptUniStream` на закрывающемся соединении. Фиктивный транспорт этого не
   воспроизводит.
4. **Полное освобождение стрима при отмене `ctx`** — невозможно через текущий
   `ports.Stream` (§6, п. 6). Горутина чтения живёт до ответа сервера или
   закрытия `Connection`. Это записанное ограничение, а не открытый пункт:
   закрывается только расширением порта, то есть отдельным ADR.

Пункты 1–3 закрываются одним шагом: прогон против развёрнутого сервера, когда
полный репозиторий Bridge будет рядом. До тех пор статус фазы — 🟡, а не ✅.
