# `ports` — контракты ядра: назначение, границы, правила адаптера

Документация пакета `photon-core/ports` за пределами doc-комментариев в коде:
последний незакрытый пункт Phase 1 (`ROADMAP.md`). Комментарии в файлах
отвечают на вопрос «что делает этот метод»; здесь — то, чего в них нет:
**границы между портами**, **зависимости между ними** и **чек-лист автора
адаптера**.

Источник истины о сигнатурах — сами файлы `ports/*.go`. Если этот документ
разойдётся с ними, прав код: расхождение по составу портов ловит
`ports/ports_doc_test.go`.

**Пакет заморожен как v1 (ADR-020).** Любое изменение существующего
контракта — только через новый ADR; добавление нового порта — тоже ADR, но
это не изменение замороженного (прецедент — `identityprovider.go`, ADR-022).
Девять портов прошли восемь адаптеров и сервисов без единой правки
контракта — это и есть проверка, ради которой заморозка вводилась.

---

## 1. Девять портов и что каждый решает

| порт | файл | отвечает за | НЕ отвечает за |
|---|---|---|---|
| `Storage` | `storage.go` | персистентность: транзакции, namespace, обход по префиксу | схему данных, сериализацию, кеш |
| `Transport` | `transport.go` | исходящее соединение и потоки внутри него | выбор адреса и переключение путей (это `services/autodial`), приём входящих соединений |
| `Identity` | `identity.go` | личность устройства: генерация пары, подпись, проверка | хранение приватного ключа (это `Storage` + `Crypto`) |
| `Crypto` | `crypto.go` | конфиденциальность: симметричный ключ, производные ключи, шифрование | подписи и личность (это `Identity`) |
| `IdentityProvider` | `identityprovider.go` | проверку внешнего OIDC-токена | сам OAuth-flow и вход пользователя (это `services/account` и клиент) |
| `P2P` | `p2p.go` | согласование прямого канала до появления адреса (NAT traversal) | обнаружение собеседника и доставку signaling-блобов |
| `Media` | `media.go` | разбор и уменьшение медиаданных | хранение байт (это `Storage`) и адресацию файлов (это Bridge) |
| `Notifier` | `notification.go` | доставку уведомления по уже известному адресу | соответствие «пользователь → адрес доставки» |
| `Authorizer` | `plugin.go` | право уже аутентифицированного вызывающего на действие | аутентификацию, жизненный цикл плагинов, IPC |

Разделения в правой колонке — не стилистика. Каждое из них уже один раз
предотвратило утечку: `Storage` без `bucket` (ADR-010), `Transport` без
`Listen` (ADR-012), `Identity` отдельно от `Crypto`, `Authorizer` без
IPC-вокабуляра (ADR-030, ADR-032).

## 2. Зависимости между портами

Пакет не импортирует ничего, кроме стандартной библиотеки, но типы одних
портов участвуют в контрактах других. Это единственный вид связи между ними:

- **`P2P.Session` встраивает `Transport.Connection`.** После установления
  P2P-канал неотличим от обычного соединения, поэтому `P2P` не дублирует
  `Transport`, а производит его результат другим путём установления.
  `Session` добавляет ровно один метод — `Peer()`: в P2P важно не только
  куда подключено, но и с кем (ADR-041).
- **`P2P.CreateOffer`/`AcceptOffer`/`CompleteSession` принимают
  `Identity.PublicKey`.** Узел идентифицируется той же криптографической
  личностью, что и везде в Photon, — отдельного типа «peer» нет
  (ADR-017/018).
- **`Authorizer.Authorize` принимает `Identity.PublicKey`**, а не
  `plugin_id` строкой. Субъекта устанавливает Runtime при запуске плагина;
  плагин в этом не участвует и подделать его не может (Phase 9, ADR-032).
- **`Crypto.DeriveKey(domain)` не связан со `Storage` namespace.** Совпадение
  слов не означает совпадения понятий: домен ключа — независимое понятие,
  и связывать их было бы ложной зависимостью.
- **`Notifier` не знает о `PublicKey`.** Соответствие «личность → адрес
  доставки» резолвит будущий Account/Profile-сервис ДО вызова `Notify`
  (ADR-019).
- **`IdentityProvider` не связан с `Identity`.** Похожие имена, разные
  концепции: `Identity` — локальная криптографическая личность устройства
  без сети, `IdentityProvider` — сетевая проверка внешней OAuth-личности
  пользователя. Поэтому claims живут в отдельном типе `ExternalIdentity`,
  а не переиспользуют имя `Identity` для другого смысла.

### Вспомогательные контракты

Не все интерфейсы пакета — порты. Семь из них описывают части контрактов
выше и отдельными портами не являются:

| контракт | файл | чья часть |
|---|---|---|
| `Connection` | `transport.go` | установленное соединение `Transport`; его же производит `P2P` |
| `Stream` | `transport.go` | двунаправленный поток внутри `Connection` |
| `SendStream` | `transport.go` | пишущая половина потока; `Close` — half-close, не закрытие приёма |
| `RecvStream` | `transport.go` | читающая половина потока |
| `ReadTx` | `storage.go` | операции чтения внутри `Storage.View` |
| `WriteTx` | `storage.go` | `ReadTx` плюс запись, внутри `Storage.Update` |
| `Session` | `p2p.go` | `Connection` плюс `Peer()` — результат согласования `P2P` |

Границы здесь такие же жёсткие, как у портов. `WriteTx` встраивает `ReadTx`,
а не дублирует его методы; `Session` встраивает `Connection`, а не копирует
её; `SendStream`/`RecvStream` существуют раздельно, потому что
однонаправленный поток — половина контракта, а не урезанный `Stream`
(ADR-016).

Ошибки — общие, в `errors.go`, по одному sentinel на различимый случай:
`ErrNotFound`, `ErrNamespaceNotFound`, `ErrCursorOutOfPrefix`,
`ErrDecryptionFailed`, `ErrInvalidKey`, `ErrUnsupportedFormat`,
`ErrSessionFailed`, `ErrRecipientUnreachable`, `ErrTokenInvalid`,
`ErrUnknownCaller`. Классификация — только через `errors.Is`, никогда
строковым поиском по тексту (ADR-033).

## 3. Чек-лист автора нового адаптера

1. **Реализовать интерфейс целиком.** Частичная реализация с паникой в
   недоделанном методе — не адаптер: потребитель ядра имеет право звать
   любой метод контракта.
2. **Добавить compile-time проверку** рядом с типом:
   ```go
   var _ ports.Storage = (*Storage)(nil)
   ```
   Она появляется вместе с первым адаптером каждого порта и не заменяется
   тестом: отсутствие метода обязано ломать сборку, а не прогон.
   Сегодня проверки есть у семи портов из девяти — нет у `Media` и
   `Notifier`, потому что у них ещё нет ни одной реализации.
3. **Пройти аудит ADR-011 (утечка реализации).** Ни одно имя в порте и ни
   одно понятие, вынесенное наружу, не должно называть библиотеку:
   `QuicConnection()`, `BoltTransaction()`, `PionAgent()`,
   `CreateBucketIfNotExists()` — плохо; `Connect`, `Update`, `OpenStream` —
   хорошо. Если адаптеру «не хватает» метода, это не повод расширить порт:
   сначала — решается ли внутри адаптера.
4. **Пройти аудит ADR-013 (форма от потребности ядра).** Источник
   требований — сценарии использования ядром, а не возможности выбранной
   библиотеки. Порт, повторяющий форму библиотеки, ломается на втором
   адаптере.
5. **Не расширять порт под адаптер.** Пакет заморожен (ADR-020): нужно
   изменение — сначала фильтр «решается внутри адаптера? ограничение
   библиотеки или потребность ядра?», и только потом ADR.
6. **Соблюдать семантику ошибок:** возвращать sentinel из `errors.go` там,
   где он определён, и не изобретать свой для того же случая. Ожидаемый
   отрицательный результат (`Verify`, `Authorize`) — это `(false, nil)`, а
   не ошибка; ошибка — только технический сбой.
7. **Уважать оговорки контракта, которые не проверяются компилятором.**
   Пример: `ForEachPrefixFrom` осмыслен только при упорядоченном обходе.
   Реализация без порядка выполнила сигнатуру формально и не выполнила по
   смыслу.
8. **Написать failure-oriented тесты** и проверить их мутацией: сломать
   правило и убедиться, что тест падает (CLAUDE.md, «Метод работы»).

## 4. Что считается нарушением при ревью порта или адаптера

Отказ на ревью, а не замечание:

- **имя из библиотеки** в сигнатуре порта или в типе, который порт отдаёт
  наружу (ADR-011);
- **метод, добавленный потому, что он есть у библиотеки**, без сценария
  ядра (ADR-013);
- **расширение замороженного контракта** без ADR (ADR-020), включая «просто
  ещё один метод» и «поле в существующую структуру»;
- **реализация в `ports/`.** Правило фазы: только интерфейсы, ни одной
  реализации (`ROADMAP.md`, Phase 1);
- **импорт чего-либо, кроме стандартной библиотеки, в `ports/`** — пакет
  обязан оставаться зависимым только от языка;
- **смешение ожидаемого отрицательного результата с технической ошибкой**
  (`Verify`, `Authorize` — `(bool, error)`, а не `error` вместо `false`);
- **строковая классификация ошибок** вместо sentinel'ов `errors.go`
  (ADR-033);
- **отсутствие compile-time проверки** у первого адаптера порта.

## 5. Состояние реализаций (на 2026-09-17)

| порт | реализации |
|---|---|
| `Storage` | `adapters/bbolt` |
| `Transport` | `adapters/quic`, `adapters/tcp`, `services/autodial` (сам реализует порт, оборачивая другие) |
| `Identity` | `adapters/ed25519` |
| `Crypto` | `adapters/aesgcm` |
| `IdentityProvider` | `adapters/googleoidc` |
| `P2P` | `adapters/pion` (вместе с `Session`) |
| `Authorizer` | `photon-plugin-runtime/permissions` (другой модуль — контракт живёт в ядре, реализация вне его, ADR-030) |
| `Media` | нет |
| `Notifier` | нет |

Отсутствие реализаций у `Media` и `Notifier` — не долг: порт написан под
будущую потребность, и первый адаптер появится вместе с ней. Его автору
и адресован раздел 3.
