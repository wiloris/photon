# Event Delivery — спецификация (Phase 15.5)

Написана **до** кода, как `WIRE_FORMAT.md` перед `adapters/tcp`,
`bridge-session.md` перед `services/session` и `p2p-session.md` перед
`adapters/pion`. Обратный порядок даёт слой, повторяющий возможности
выбранной библиотеки, а не модель системы.

Реализует ADR-045. Форма канала на границе ABI заморожена
(`photon-bindings/c/photon_core.h`, ADR-008) и здесь **не пересматривается** —
спецификация описывает внутреннюю модель, приводящую её в исполнение.

---

## 1. Зачем этот слой существует

Ядро не отправляет наружу ни одного события. Цепочка обрывается дважды, и оба
обрыва записаны в самом коде:

```
Bridge ──push──► session.AcceptPush()      ✅ реализовано, проверено вживую (Phase 12.5)
                       │
                       ✗ обрыв 1: dispatcher создаёт сессию только с Mode: ModeAction
                       │
                 dispatcher                ✅ наружу только SendAction и Close
                       │
                       ✗ обрыв 2: Photon_SetEventCallback запоминает колбэк,
                       │           вызвать его нечему
                 core.callback
```

Практическое следствие: клиент на C ABI не может узнать ничего, кроме ответа на
собственный вызов. Ограничение касается не только P2P (отвечающая сторона не
узнаёт о входящем offer), но любого сценария, где инициатива у сервера.

**Заголовок это фиксирует прямо:** «СОСТОЯНИЕ НА СЕГОДНЯ: ядро НЕ ОТПРАВЛЯЕТ НИ
ОДНОГО СОБЫТИЯ… Строить логику клиента на ожидании события нельзя — ожидание не
завершится». Первым событием там же назван `CONNECTED`, «вместе с фоновым
коннектором, который появится, когда появится push».

---

## 2. Что уже заморожено и здесь не решается

Из `photon_core.h`, в силе с момента появления первого события:

| свойство | формулировка контракта |
|---|---|
| один канал | все события — подключение, входящее сообщение, событие плагина, изменение хранилища, изменение сети — приходят одним колбэком |
| дискриминатор | `event_json` содержит поле `"type"` |
| имена типов | `CONNECTED`, `MESSAGE`, `PLUGIN_EVENT`, `STORAGE_CHANGED`, `NETWORK_CHANGED` |
| поток | колбэк может быть вызван из горутины, не связанной с потоком инициализации JNI; на Android обязателен `AttachCurrentThread` |
| владение `event_json` | невалиден сразу после возврата из колбэка; нужно сохранить — копировать внутри |
| `user_data` | обязан оставаться валидным до момента, когда `Photon_Destroy` вернёт управление |
| гарантия остановки | после возврата из `Photon_Destroy` колбэк не будет вызван ни разу, ни из какого потока; `Destroy` обязан дождаться завершения уже начатых вызовов |
| `Photon_Create` | сети не касается |

Сигнатуры не меняются. Единственное место, где буквальное требование
невыполнимо, — ожидание завершения колбэка, из которого `Destroy` и вызван;
этот случай разобран в §10.2 как явное исключение, а не обойдён молчанием.

## 3. Границы слоя

| делает | не делает |
|---|---|
| держит подписное соединение и поднимает его сам | не подписывается на конкретные каналы: подписка на Bridge — на всё, что адресовано пользователю (ADR-040) |
| принимает push и доставляет его колбэку | не разбирает `data`: доменные сущности принадлежат ENGRAM/Bridge |
| восстанавливает подписку после обрыва | не переподключает action-соединение: там повтор решает вызывающий (`action-routing.md` §3.4) |
| сообщает о состоянии подписки | не сообщает о состоянии action-соединения (§6.3) |
| гарантирует порядок и отсутствие потерь внутри Core | не гарантирует сквозной доставки: см. §9 |

## 4. Архитектура: второе соединение

`mode` фиксируется **на соединение, а не на стрим** (`bridge-session.md` §2.4):
«Клиенту, которому нужны и action'ы, и push, требуется два соединения…
Реализация не должна пытаться получить push по action-соединению».

Поэтому инстанс держит две независимые `session.Session`:

```
                     ┌─────────────── Dispatcher (один на PhotonHandle) ───────────────┐
                     │                                                                  │
   Photon_SendAction ─► sess (Mode: action)    ──── ленивое подключение по вызову ──────┼──► Bridge
                     │                                                                  │
   насос ◄─ AcceptPush ─ sub  (Mode: subscribe) ── фоновое подключение и восстановление ┼──◄ Bridge
                     │                                                                  │
                     │  ctx (на весь инстанс) · inflight (WaitGroup) · mu               │
                     └──────────────────────────────────────────────────────────────────┘
```

**Транспорт остаётся один.** `ports.Transport.Connect` можно звать повторно —
в адаптере QUIC каждый вызов делает `quicgo.DialAddr` и создаёт свой сокет; а
`Transport.Close` установленных соединений не закрывает (прямое требование
порта). Второй экземпляр транспорта означал бы второй набор общих ресурсов без
единой причины.

**Обе сессии закрываются до закрытия транспорта.** Порядок `Close` из
`action-routing.md` §9 сохраняется, шаг «закрыть сессию» просто выполняется
дважды.

## 5. Жизненный цикл насоса

### 5.1 Запуск — первый `Photon_SetEventCallback` с ненулевым колбэком

Отвергнутые точки запуска и причины (ADR-045 §2):

| вариант | почему нет |
|---|---|
| `Photon_Create` | прямо запрещено: «Create сети не касается» |
| первый `Photon_SendAction` | связывает события с действиями; клиент, который только слушает, не подписался бы никогда |
| безусловно из `New` | второе соединение каждому инстансу, включая те, кому события не нужны |

`Photon_SetEventCallback` — единственный вызов ABI, выражающий намерение
получать события, и заголовок называет его «единственный способ получать
события».

- **Первый вызов с ненулевым колбэком** запускает насос. Запуск идемпотентен:
  второй насос не создаётся никогда.
- **Повторный вызов с другим колбэком** заменяет адресата доставки; подписку не
  трогает.
- **Вызов с `NULL`** отцепляет адресата: насос продолжает работать, события
  отбрасываются. Тушить и поднимать подписку по установке и снятию колбэка —
  лишний путь с состоянием гонки, а выигрыш нулевой.
- **Вызов на инстансе без `endpoint`** насос не запускает: адресата нет, как и
  у `SendAction` (`ErrNoEndpoint`).

### 5.2 Приём

Насос — **одна** горутина на инстанс. Цикл:

```
подключиться (session.Connect) ──► эмитировать CONNECTED
   └─► AcceptPush(d.ctx) ──► событие ──► доставить колбэку ──► повторить
```

Регистрация в `d.inflight` происходит **под `d.mu` и только после проверки
`d.closed`** — общая дисциплина диспетчера, без исключений для долгоживущей
горутины. Иначе `Add` мог бы случиться уже после `Wait` в `Close`.

### 5.3 Остановка

Единственный способ остановить насос — отмена `d.ctx`, то есть
`Dispatcher.Close`, то есть `Photon_Destroy`. Подробности и доказательство —
§10.

## 6. Reconnect, backoff, `ErrConnectionLost`

### 6.1 Оборванная сессия не переиспользуется

Проверено по коду, а не выбрано по вкусу:

- `markLost` переводит только `Ready → Failed` и **не закрывает и не обнуляет**
  `s.conn`;
- `Session.Connect` из `StateFailed` **разрешён** (`StateFailed` не входит в
  switch ранних возвратов), и повторный `Connect` **перезаписал бы** `s.conn`,
  оставив прежнее соединение висеть навсегда;
- `Session.Close` терминален: `StateClosed`, `close(s.closeCh)`; воскрешение
  запрещено (`bridge-session.md` §6 п. 4).

**Правило: попытка восстановления — это `Close` прежней сессии и создание новой
через `session.New`.** Сессия одноразова относительно обрыва. Записано здесь,
чтобы не выяснялось утечкой дескрипторов.

### 6.2 Что считается обрывом

`AcceptPush` различает исходы, и цикл восстановления обязан различать их так же:

| исход `AcceptPush` | что означает | реакция насоса |
|---|---|---|
| `Push`, `nil` | событие принято | доставить, продолжить приём |
| `ctx.Err()` | **отмена вызывающим**; обрывом не считается | выйти из цикла |
| ошибка, `errors.Is(…, ErrConnectionLost)` | соединение потеряно | эмитировать `NETWORK_CHANGED`, уйти в восстановление |
| `ErrSessionClosed` | сессию закрыли снаружи | выйти из цикла |
| `ErrNotReady` | подписка ещё не поднялась | не может возникнуть в цикле: приём начинается после `Connect` |
| `ErrMalformedFrame` | сервер прислал мусор | событие пропускается, соединение не рушится |

Восстанавливать нужно **обрыв**, а не любое состояние, в котором приём
невозможен.

### 6.3 Политика восстановления

- Число попыток **не ограничено**: у подписки нет вызывающего, который решил бы,
  что пора прекратить. Исчерпание попыток означало бы тихо переставший работать
  канал событий — состояние, неотличимое для клиента от «событий нет».
- Ограничен **интервал**: экспоненциальный backoff с потолком, начиная с малого
  значения. Конкретные числа — конфигурация (§11), не контракт.
- **Пауза обязана быть отменяемой:** `select` по таймеру и `d.ctx.Done()`.
  Неотменяемая пауза заставила бы `Photon_Destroy` ждать её длину — та же
  ошибка, от которой защищает порядок `Close` (отмена строго до ожидания).
- Успешное восстановление эмитирует `CONNECTED` снова.

## 7. События первой версии

Эмитируются три типа. **Новых значений `type` не вводится**: отдельного
`DISCONNECTED` в замороженном перечне нет, и заводить его прежде, чем появился
потребитель, отличающий его от `NETWORK_CHANGED`, означало бы расширять ABI
(MINOR) без основания.

| тип | когда |
|---|---|
| `CONNECTED` | подписка подтверждена сервером — при первом подключении и после каждого восстановления |
| `MESSAGE` | каждое принятое push-событие |
| `NETWORK_CHANGED` | подписка потеряна; далее насос уходит в восстановление |

`PLUGIN_EVENT` и `STORAGE_CHANGED` **не эмитируются**: имена в заголовке есть,
источников в ядре нет.

**Область действия `CONNECTED` и `NETWORK_CHANGED` — только подписное
соединение.** Action-соединение подключается лениво, по вызову, и своего
фонового жизненного цикла не имеет; сообщать о нём событиями было бы обещанием
того, чего нет. Это прямое следствие §4: у инстанса два состояния связи, и
события описывают одно из них.

## 8. Нормативный mapping `session.Push` → `event_json`

### 8.1 Форма

```json
{"type":"CONNECTED"}

{"type":"NETWORK_CHANGED","state":"disconnected"}

{"type":"MESSAGE","event":"posted","user_id":"abc123","data":{ … }}
```

Правила:

- **`type` — всегда первое и обязательное поле.** По нему клиент решает, как
  разбирать остальное (требование заголовка).
- **`event`** — имя события **как оно пришло с провода**: `Push.Event`.
- **`user_id`** — `Push.UserID`; **опускается, если пуст** (см. §8.2).
- **`data`** — `Push.Data`, вставляемые **сырыми байтами**, без разбора и
  пересборки. То же свойство, что у конверта ответа (`bridge-session.md` §3.1):
  ядро не является участником доменной схемы и не имеет права её нормализовать.
  Поле опускается, если `Data` пуст.
- Клиент обязан **игнорировать неизвестные поля и неизвестные значения `type`**
  — иначе добавление типа в будущем сломает существующих клиентов.

### 8.2 Две ловушки провода, которые обязан учесть mapping

Обе найдены прогоном против живого Bridge и записаны в `bridge-session.md`
§2.3; повторяются здесь, потому что именно здесь на них наступят.

1. **`Push.Event` — строка, а не значение enum.** На проводе Bridge шлёт
   `{"event":"posted"}`; одиннадцать имён: `posted`, `post_edited`,
   `post_deleted`, `reaction_added`, `reaction_removed`, `typing`,
   `user_added`, `user_removed`, `status_change`, `channel_updated`,
   `new_unread_channel`. Схема `photon.proto` объявляет `EventType` как enum —
   это одно из расхождений «схема ≠ провод» (ADR-034). **Mapping не переводит
   строку в число и не проверяет её по списку**: неизвестное имя проходит
   насквозь, потому что ядро не обязано знать доменный словарь Bridge и
   отбрасывать событие из-за незнакомого имени значило бы терять его молча.
2. **`user_id` верхнего уровня обычно отсутствует.** Поле объявлено сервером с
   `omitempty`, и заполняет его ровно один хук из восьми — `status_change`. Для
   остальных, включая `posted`, идентификатор автора лежит **внутри `data`**.
   Комментарий «пустой = широковещание» неверен и опровергнут прогоном.
   **Mapping не подставляет ничего вместо пустого значения и не достаёт id из
   `data`** — он опускает поле.

### 8.3 Кодирование

- `event_json` — валидный UTF-8 JSON, C-строка с завершающим нулём.
- Строка принадлежит вызову колбэка и освобождается сразу после возврата;
  клиент, которому нужны данные, копирует их внутри (требование заголовка).
- `Push.Data` уже скопирован декодером (`json_codec.go`: срез смотрит в буфер
  декодера, переиспользуемый между вызовами, и потому копируется явно), так что
  насос вправе удерживать его на время сборки строки.

## 9. Доставка, очередь и backpressure

### 9.1 Синхронная последовательная доставка

Насос **сам** вызывает колбэк, не передавая событие ни в какую очередь. Отсюда
сразу два свойства, которые иначе пришлось бы обеспечивать отдельно:

- **порядок сохраняется** — события доставляются в порядке приёма;
- **колбэки никогда не параллельны** — второе событие не начнёт доставляться,
  пока не вернулось первое. Для стороны JNI это существенно:
  `AttachCurrentThread` в теле колбэка выполняется без конкуренции за один env.

Гарантии даются **в пределах инстанса**: два `Photon_Create` — два независимых
насоса, порядок между ними не определён. Это следствие правила «адресат — сам
`PhotonHandle`» (`action-routing.md` §8).

### 9.2 Пользовательской очереди в Core нет

Промежуточного буфера между `AcceptPush` и колбэком не существует. Медленный
клиент замедляет чтение из сети, и давление уходит в QUIC: очередь между
проводом и `AcceptPush` ограничена лимитом входящих uni-стримов (клиент задаёт
только `HandshakeIdleTimeout` и `KeepAlivePeriod`, остальное — умолчания
quic-go), а не безгранична. **Скрытой неограниченной очереди на пути нет** —
проверено по коду.

Любая ограниченная очередь в Core вводила бы потерю события, а «событие может не
прийти» — свойство, видимое клиенту, и обещать его нельзя мимоходом.

### 9.3 Сквозной гарантии доставки нет — и это свойство Bridge

| участок | гарантия |
|---|---|
| Core: насос, `services/session`, `services/dispatcher` | очереди нет, потерь нет |
| quic-go на клиенте | очередь ограничена лимитом стримов; давление доходит до отправителя |
| **Bridge, `PushRegistry`** | **буфер 64 на клиента, `select … default` — при переполнении событие роняется молча** |

`newPushClient` заводит `make(chan PushEvent, 64)`; `sendTo` и `Broadcast` пишут
в него неблокирующим `select` с пустым `default`. Комментарий в самом Bridge это
фиксирует и ссылается на `bridge-session.md` §9 п. 6 как на открытый пункт.

**Следствие, обязательное для слоёв выше: поток событий может иметь пропуски.**
Логика, построенная на событиях, обязана восстанавливаться явным действием и не
имеет права предполагать полноту потока. Для будущего signaling это означает,
что потерянный offer закрывается потолком согласования (ADR-044 §3), а не
повторной доставкой push.

### 9.4 Цена синхронной доставки

Колбэк, который не возвращается, останавливает поток событий своего инстанса и
задерживает `Photon_Destroy`. Это следует из замороженного контракта — заголовок
обязывает `Destroy` дождаться начатых вызовов, — а не является новым требованием
к клиенту.

## 10. Уничтожение

### 10.1 Обычный путь

`Photon_Destroy` под `c.mu` ставит `destroyed`, забирает диспетчер, обнуляет
поле, освобождает `lastError`, отпускает мьютекс и вызывает `disp.Close()`
**вне** `c.mu`. `Dispatcher.Close`:

```
1. closed = true под d.mu     → ни один Add больше невозможен
2. d.cancel()                 → будит насос из AcceptPush и из паузы backoff
3. d.inflight.Wait()          → возвращается только после Done() насоса
4. sess.Close(), sub.Close()  → обе сессии
5. tr.Close(), если транспорт свой
```

**Единственный барьер времени жизни — `d.inflight`.** Признак `destroyed`
барьером **не является и в этой роли не используется**: любая схема
«проверил → отпустил → вызвал» имеет окно, а закрыть его можно только вызовом
колбэка под мьютексом, что запрещено (§10.5). `destroyed` остаётся дешёвым
подавлением заведомо ненужной доставки во время остановки.

**Доказательство.** После шага 1 регистрация невозможна. Шаг 2 будит насос из
любого места ожидания: `AcceptPush(d.ctx)` передаёт контекст в
`conn.AcceptUniStream(ctx)`, адаптер QUIC отдаёт его quic-go как есть; пауза
backoff отменяема по построению (§6.3). Шаг 3 возвращается только после
`Done()`, то есть после выхода насоса; если в этот момент колбэк выполнялся,
`Wait()` дожидается его возврата — ровно то, что требует заголовок. К возврату
из `disp.Close()` горутины насоса не существует, и вызывать колбэк некому.

### 10.2 Реентерабельный `Photon_Destroy` — явное исключение

Прямая реализация дала бы дедлок: `Destroy` → `Close` → `Wait()` ждёт насос,
который стоит внутри колбэка, вызвавшего `Destroy`. Структурно это тот же
дефект, что Phase 11 нашла в публичном API SDK (дедлок `OnEvent`/`OnStop`), и он
числится дефектом API, а не ошибкой вызывающего.

Замороженное «дождаться завершения уже начатых вызовов» в случае самовызова
**невыполнимо логически**. Поэтому вводится исключение:

`Photon_Destroy`, вызванный из потока, в котором сейчас исполняется колбэк
этого же инстанса:

- помечает отложенное уничтожение и **возвращает управление немедленно**;
- ничего не ждёт, ничего не закрывает, handle не освобождает;
- фактическое уничтожение выполняет насос **после возврата из колбэка**.

**Что при этом НЕ утверждается.** К моменту возврата такого `Destroy` колбэк
**не завершён** — он и есть вызывающий; инстанс **не уничтожен**; handle **ещё
выделен**. Создавать видимость обратного запрещено. Гарантировано ровно одно:
новых вызовов колбэка не будет. Обращаться к handle после возврата нельзя, как и
после обычного `Destroy`.

**Порядок в насосе обязателен:** цикл выходит → `Done()` (снимая себя с
`d.inflight`) → и только затем уничтожение. Обратный порядок дал бы тот же
дедлок изнутри: `disp.Close()` ждал бы горутину, которая его и вызывает.

### 10.3 Определение потока колбэка

Различение опирается на идентичность **OS-потока**, а не горутины. «Горутина ==
поток» неверно, поэтому требования записываются явно:

- **Между двумя вызовами cgo горутина может быть перенесена на другой
  OS-поток.** Насос обязан выполнить `runtime.LockOSThread()` и не снимать
  привязку до выхода: без неё захваченный идентификатор не гарантированно
  принадлежит потоку, который исполнит колбэк. Плата — один выделенный OS-поток
  на инстанс, у которого есть подписка.
- Идентификатор захватывается **один раз**, при старте насоса после привязки, и
  публикуется под `c.mu`. Захват на каждое событие не нужен: поток зафиксирован.
- **Обратный вызов C → Go выполняется на том же OS-потоке**, поэтому
  `Photon_Destroy`, вызванный из колбэка, видит тот же идентификатор.
- Сравнение — **только `pthread_equal`**: `pthread_t` непрозрачен по стандарту,
  сравнивать его как число нельзя.
- Требуется `#include <pthread.h>` в cgo-преамбуле. Это непубличная сторона
  границы (`internal_cgo_types.h` объявлен не входящим в ABI); внешний
  `photon_core.h` **не меняется**.
- **Платформа.** Механизм POSIX. Windows потребует `GetCurrentThreadId`;
  bindings под Windows отсутствуют (нет toolchain) — отложенная работа, а не
  незамеченная.

**Остаточное ограничение, не ловящееся ничем.** Если колбэк порождает
собственный поток, вызывает `Destroy` оттуда и **ждёт** его завершения —
дедлок: `Destroy` из чужого потока идёт обычным путём и ждёт насос, насос ждёт
возврата колбэка, колбэк ждёт свой поток. Идентичность потока такой случай не
различает и различить не может. Записывается обязанностью вызывающего:
**`Destroy` из колбэка допустим только синхронно, в том же потоке.**

### 10.4 Конкурентные `Destroy`: teardown ровно один раз

Отложенное уничтожение удлиняет окно, в котором handle остаётся валидным.
Сегодня повторный `Destroy` отсекается занулением ячейки в
`releaseOpaqueHandle`; при отложенном пути зануление происходит позже, и второй
вызов доходит до проверки состояния.

**Правило: уничтожение выполняется ровно один раз, и им владеет тот, кто первым
перевёл инстанс в `destroyed`.** Признак завершения (`teardownDone`) закрывается
ровно однажды — тем, кто фактически выполнил уничтожение.

| вызов | поведение |
|---|---|
| первый, из чужого потока | выполняет уничтожение сам, закрывает `teardownDone`, освобождает handle |
| первый, из потока колбэка | помечает отложенное уничтожение, возвращается немедленно; уничтожение и `teardownDone` — на насосе |
| последующий, из чужого потока | уничтожения не выполняет; **ждёт `teardownDone`** и только затем возвращается — иначе вернул бы управление, пока колбэк ещё исполняется, нарушив гарантию для себя |
| последующий, из потока колбэка | возвращается немедленно; поток колбэка не блокируется никогда |
| после полного уничтожения | ячейка handle занулена, вызов не резолвится — no-op, как сегодня |

Handle и его `cgo.Handle` при отложенном пути сохраняются вызовом `Destroy` для
насоса: освобождает их тот же, кто выполняет уничтожение.

### 10.5 Колбэк не вызывается ни под одним мьютексом

`c.mu` берут `Photon_Destroy`, `Photon_SetEventCallback`, `Photon_GetLastError`
и `Photon_SendAction`, а также `setError`, который зовут все пути ошибок. Вызов
колбэка под `c.mu` вешал бы клиента на **любом** реентерабельном обращении к
Photon — включая рядовое «получил `MESSAGE` → отправил действие».

Порядок обязателен: под `c.mu` прочитать `callback`, `userData` и состояние,
отпустить мьютекс, вызвать. `d.mu` в момент вызова насос тоже не удерживает.

**Порядок захвата мьютексов: `c.mu` → `d.mu`, никогда наоборот.** Насос
удерживает не более одного за раз и ни одного во время вызова колбэка.

## 11. Конфигурация

Параметры восстановления приходят через `config_json`, разбираемый
`dispatcher.ParseConfig` (схема — доменное знание Core). Действующая форма —
объект `bridge` с полями `endpoint`, `session_token`, `connect_timeout_ms`,
`call_timeout_ms`, `keepalive_ms`, `tls`.

Добавляются параметры backoff подписки: начальная пауза, потолок паузы. Значения
по умолчанию обязаны существовать — инстанс, созданный минимальным
`config_json`, должен получать события без дополнительной настройки.

`keepalive_ms` уже имеет значение по умолчанию 15 с, выставленное по итогам
Phase 12.5: subscribe-соединение умирало через 30 с простоя, потому что
keep-alive не слала ни одна сторона. Для подписки этот параметр критичен —
тишина на ней есть норма, и без keep-alive обрыв неотличим от отсутствия
событий.

## 12. Диаграммы

### 12.1 Обычное событие

```
Bridge          sub-session         насос                    клиент (C)
  │                  │                │                          │
  │                  │   AcceptPush(d.ctx) ─────────────►         │
  │─── UniStream ───►│                │                          │
  │                  │─── Push{Event,UserID,Data} ──►│            │
  │                  │                │ c.mu: read cb,ud; unlock  │
  │                  │                │──── cb(event_json, ud) ──►│
  │                  │                │                           │ обрабатывает
  │                  │                │◄────────── возврат ───────│
  │                  │                │ event_json освобождён     │
  │                  │   AcceptPush(d.ctx) ─────────────►         │
```

Второе событие не начнёт доставляться, пока не вернулось первое (§9.1).

### 12.2 Обрыв и восстановление

```
насос                     sub-session                    клиент
  │  AcceptPush ──────────►│
  │                        │ conn.AcceptUniStream → ошибка
  │                        │ markLost: Ready → Failed
  │◄── ErrConnectionLost ──│
  │ cb({"type":"NETWORK_CHANGED","state":"disconnected"}) ──────►│
  │
  │ sub.Close()                        ← прежняя сессия одноразова (§6.1)
  │ session.New(Mode: subscribe)       ← НОВАЯ, не переиспользование
  │ ждать backoff:  select { <-timer ; <-d.ctx.Done() }
  │ Connect(d.ctx) ──► ok
  │ cb({"type":"CONNECTED"}) ───────────────────────────────────►│
  │ AcceptPush ──────────►│
```

При неудаче `Connect` — снова пауза, интервал растёт до потолка; число попыток
не ограничено (§6.3).

### 12.3 Обычный `Destroy`

```
поток клиента                       насос                     колбэк
     │                                │
Photon_Destroy                        │ стоит в AcceptPush(d.ctx)
     │ c.mu: destroyed=true; disp; unlock
     │ disp.Close():
     │   d.mu: closed=true            │        ← Add больше невозможен
     │   d.cancel() ─────────────────►│ AcceptPush → ctx.Err()
     │   d.inflight.Wait() ...        │ выход из цикла
     │                                │ Done()
     │   ◄── Wait вернулся ───────────┘ горутины нет
     │   sess.Close(); sub.Close(); tr.Close()
     │ releaseOpaqueHandle()
возврат ─► новых колбэков нет, исполняющихся нет
```

Если в момент отмены колбэк выполнялся, `Wait()` дожидается его возврата — шаг 3
не завершится раньше.

### 12.4 `Destroy` из колбэка

```
насос ──► cb(event_json, ud)
              │
              │ клиент внутри колбэка зовёт Photon_Destroy
              ▼
        Photon_Destroy: c.mu → inCallback && pthread_equal(self, pumpThread)
              │         → destroyed=true, deferred=true, сохранить handle
              │         → unlock, ВОЗВРАТ НЕМЕДЛЕННО (без Wait)
              ▼
        управление возвращается внутрь колбэка
              │  ← колбэк ещё исполняется, инстанс НЕ уничтожен, handle ЕЩЁ выделен
              ▼
        колбэк возвращается
              │
насос ◄───────┘ видит deferred → выходит из цикла → Done()
              → disp.Close() → releaseOpaqueHandle() → close(teardownDone)
```

Порядок «`Done()` раньше `disp.Close()`» обязателен: иначе насос ждал бы сам
себя.

### 12.5 `Destroy` во время backoff

```
поток клиента                       насос
     │                                │ sub.Close() выполнен, ждёт паузу:
     │                                │   select { case <-timer: ; case <-d.ctx.Done(): }
Photon_Destroy                        │
     │ disp.Close():                  │
     │   d.mu: closed=true            │
     │   d.cancel() ─────────────────►│ ветка <-d.ctx.Done() срабатывает СРАЗУ
     │   d.inflight.Wait() ...        │ выход из цикла, Done()
     │   ◄── Wait вернулся ───────────┘
     │   закрыть сессии и транспорт
возврат
```

Неотменяемая пауза заставила бы `Destroy` ждать её длину — ровно то зависание,
от которого защищает порядок «отмена строго до ожидания».

## 13. Ошибки

Наружу через канал событий ошибки **не транслируются**: `event_json` описывает
состояние и содержимое, а не отказы вызовов. Диагностика вызовов остаётся у
`Photon_GetLastError` и у конверта ответа (ADR-038).

Внутренние исходы и их обработка — таблица §6.2. Отдельно:

- **`ErrMalformedFrame`** отвергает **событие**, а не соединение: один битый
  фрейм не повод рвать подписку. Тот же принцип, что у неизвестного признака
  направления потока в `adapters/pion` (`p2p-session.md` §7).
- **`ErrModeNotAccepted`** при подключении подписки — отказ подключения, а не
  обрыв: сервер подтвердил не тот режим, и продолжать нельзя. Проверка `status`
  обязательна (`bridge-session.md` §2.4): подписчик, не читающий `status`,
  проходит handshake и уходит ждать push на соединении, где сервер UniStream не
  откроет.

## 14. Тесты и проверяемые свойства

### 14.1 Unit — без сети

- насос доставляет события **в порядке приёма**;
- колбэки **не параллельны**: второй не начинается до возврата первого;
- `event_json` собран по §8: `type` присутствует; `event` взят с провода как
  строка; `user_id` **опущен** при пустом значении; `data` вставлены **сырыми**
  и байт-в-байт равны принятым;
- неизвестное имя события проходит насквозь, а не отбрасывается;
- `NULL`-колбэк: события отбрасываются, насос жив;
- замена колбэка: доставка уходит новому, подписка не пересоздаётся;
- запуск идемпотентен: два `SetEventCallback` не создают второй насос;
- `ErrConnectionLost` → `NETWORK_CHANGED` → новая сессия → `CONNECTED`;
- **сессия после обрыва не переиспользуется** (создаётся новая);
- пауза backoff прерывается отменой контекста;
- `ErrMalformedFrame` пропускает событие, не рвёт подписку;
- `d.inflight` держит насос: `Wait()` не возвращается, пока насос жив.

**Проверка мутациями обязательна** для каждого свойства — по прецеденту
Phase 15, где именно мутация вскрыла регрессионный тест, остававшийся зелёным на
том самом дефекте, ради которого был написан.

### 14.2 Integration — два соединения

- action и подписка работают одновременно и независимо: обрыв подписки не мешает
  `SendAction`, и наоборот;
- уничтожение инстанса при живой подписке и вызове в полёте: обе сессии закрыты,
  транспорт закрыт, висящих горутин нет, `-race` чист;
- инстанс без `endpoint`: `SetEventCallback` насос не запускает.

### 14.3 Live E2E — против развёрнутого Bridge

- подписка поднимается, приходит `CONNECTED`;
- реальное событие `posted` доходит до колбэка, `data` не искажены;
- подтверждается ловушка §8.2: `user_id` верхнего уровня отсутствует;
- обрыв соединения приводит к `NETWORK_CHANGED` и последующему `CONNECTED`.

### 14.4 Обязательные failure cases

Без них фаза не закрывается:

1. **Колбэк вызывает `Photon_Destroy`** — процесс не виснет; уничтожение
   происходит после возврата колбэка; ровно один раз.
2. **Колбэк вызывает `Photon_SendAction`** — не дедлок (проверка §10.5).
3. **Два конкурентных `Destroy`** — teardown ровно один раз; второй возвращается
   не раньше завершения первого.
4. **`Destroy` во время паузы backoff** — возврат немедленный, без ожидания
   паузы.
5. **`Destroy` во время исполнения колбэка из чужого потока** — возврат только
   после возврата колбэка.
6. **Медленный колбэк** — события не теряются внутри Core и не переупорядочены.
7. **Сервер молчит после подтверждения подписки** — keep-alive держит
   соединение; отсутствие событий не принимается за обрыв.

## 15. Что останется непроверенным

Записывается заранее, чтобы не «дореализовывать» молча:

- **сквозная сохранность события при устойчивом отставании** — Bridge роняет
  молча (§9.3); измерить порог можно, но закрыть его этой фазой нельзя;
- **поведение на Windows** — механизм определения потока POSIX-специфичен,
  toolchain отсутствует;
- **Android/ART** — `AttachCurrentThread` в теле колбэка описан контрактом, но
  проверить его нечем (нет NDK и устройства);
- **много инстансов одновременно** — по одному OS-потоку на инстанс с подпиской;
  где это начинает мешать, не измерялось;
- **аварийный обрыв в отличие от штатного** — тот же открытый пункт, что
  остался от Phase 12.5 (`bridge-session.md` §9);
- **поведение при смене сети на мобильном** — интерфейс меняется, соединение
  рвётся; политика восстановления описана, но на мобильной сети не проверялась.
