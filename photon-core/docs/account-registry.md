# Server-side Account Registry — последовательность регистрации на CAS

Реализует **ADR-077** (носитель — Mattermost plugin storage, вариант A).
Написана **до** кода, как `bridge-session.md` перед `services/session` и
`p2p-messaging.md` перед `p2pmsg`.

Опирается на: **ADR-018** (формат и свойства `PhotonID`), **ADR-023**
(`(Provider, Subject)` — ключ поиска), **ADR-024** (схема `Account`),
**ADR-021** (корень доверия — внешний IdP). Сценарии — `account-device-flow.md`.

**`ports.Storage` здесь не участвует.** Многоключевой транзакции у Mattermost
Plugin API нет (ADR-077 §1.3), и ни один шаг ниже её не предполагает.

---

## 1. Что даёт носитель

Измерено по `plugin.API` v0.1.21:

| операция | семантика |
|---|---|
| `KVCompareAndSet(key, nil, v)` | **вставка при отсутствии**. `(true, nil)` — вставлено; `(false, nil)` — ключ уже есть; `(false, err)` — сбой БД |
| `KVCompareAndSet(key, old, v)` | замена, только если текущее значение равно `old` |
| `KVGet(key)` | значение либо **`nil` для отсутствующего ключа** (не ошибка) |
| `KVCompareAndDelete(key, old)` | удаление, только если значение совпало |

**`(false, nil)` отличимо от `(false, err)`** — это и делает протокол
возможным: «проиграл гонку» и «хранилище недоступно» требуют разных действий,
и смешение их было бы худшим дефектом этой спецификации.

Транзакций нет: `Transaction`/`Begin`/`Commit`/`Rollback` в `plugin.API`
отсутствуют.

## 2. Ключи

Именование следует уже принятому в `photon-quic-bridge` (`engram:{userID}:{key}`,
`engram_idx:{userID}`): строчный префикс, части через двоеточие.

| ключ | значение | что обеспечивает |
|---|---|---|
| `acct:{provider}:{subject}` | запись `Account` (JSON) | **единственность Account для одного `(Provider, Subject)`** |
| `pid:{photonID}` | `{provider, subject}` | **единственность `PhotonID` глобально** |

Два ключа, и каждый отвечает ровно за одну единственность. Третьего не
заводится: `pid:` уже содержит обратную связь `PhotonID → (Provider, Subject)`
как побочный продукт резервирования — не как функция поиска, которой ADR-077
не вводит.

Префикс `mmi_` зарезервирован Mattermost и не используется.

### 2.1. Запись `acct:`

```json
{
  "state":        "claimed" | "registered" | "linked",
  "provider":     "google",
  "subject":      "…",
  "email":        "…",
  "photon_id":    "000000000",        // отсутствует при state=claimed
  "login_name":   "engram-000000000", // отсутствует при state=claimed
  "mm_user_id":   "…",                // присутствует только при state=linked
  "created_at":   "…"
}
```

`state` — не украшение: именно он отличает частичные состояния §5 друг от
друга, и повторный вход ветвится по нему.

### 2.2. `login_name`

```
login_name = "engram-" ‖ photon_id
```

Детерминирован, выводится из `PhotonID` и потому уникален вместе с ним. Длина
16 при пределе Mattermost 64, состав — строчные буквы, цифры и дефис.

**Записывается в `acct:` РАНЬШЕ вызова `CreateUser`** — это единственное, что
делает создание пользователя повторяемым (§6, состояние C).

## 3. Последовательность

```
R1a  claim     CAS(acct:P:S, nil, {state:claimed})                 ──┐
R1b  allocate  CAS(pid:N,    nil, {P,S})            повтор при (false,nil)
R1c  register  CAS(acct:P:S, claimed, {state:registered, N, login}) │ R1
                                                                   ──┘
U    CreateUser(login_name)                                          внешнее хранилище
R2   link      CAS(acct:P:S, registered, {state:linked, mm_user_id})
S    CreateSession(mm_user_id)                                       внешнее хранилище
```

### 3.1. Почему claim идёт раньше allocate

Обратный порядок — сначала выделить `PhotonID`, потом занять `acct:` — теряет
идентификатор на **каждой** гонке двух одновременных входов одного
пользователя: проигравший уже зарезервировал свой `N`, а освобождать его
нельзя (ADR-077 §2.5).

При порядке «claim раньше» гонка разрешается **до** выделения, и в типичном
случае не теряется ничего.

### 3.2. Что считается успешным резервированием

**Только `KVCompareAndSet(pid:N, nil, {P,S})`, вернувшая `(true, nil)`.**

Ни генерация числа, ни запись в `acct:` резервированием не являются.
`photon_id` попадает в `acct:` исключительно после успешной вставки `pid:`
(шаг R1c строго после R1b) — поэтому запись аккаунта никогда не ссылается на
незарезервированный идентификатор.

---

## 4. Гонки

### 4.1. Два входа одного `(Provider, Subject)`

Разрешается **R1a**: `CAS(acct:P:S, nil, …)` возвращает `(true, nil)` ровно
одному вызывающему.

- **победитель** продолжает с R1b;
- **проигравший** (`false, nil`) перечитывает `acct:P:S` через `KVGet` и
  продолжает **по уже существующей записи**, ветвясь по `state` (§6). Он не
  начинает заново и не отменяет чужую работу.

Правило общее для всех шагов: **проигравший CAS перечитывает состояние и
продолжает с него; победитель продолжает свою последовательность.** Никто не
откатывает.

### 4.2. Два входа при выборе `PhotonID`

Разрешается **R1b**. Кандидат генерируется криптографическим генератором;
`(false, nil)` означает, что число занято — генерируется следующее. Предел
попыток обязателен (существующий `maxPhotonIDGenerationAttempts`), исчерпание
даёт `ErrPhotonIDSpaceExhausted`, а не бесконечный цикл.

### 4.3. Гонка на R1c — единственный источник осиротевшего резерва

Два входа, оба заставшие `state=claimed` (первый упал между R1a и R1c),
выделяют **разные** `N₁` и `N₂` — обе вставки `pid:` успешны, потому что
ключи разные. Затем оба выполняют R1c, и `CAS(acct:P:S, claimed, …)`
пропускает одного.

Проигравший оставляет `pid:N₂` **навсегда занятым и ни к какому аккаунту не
привязанным**.

**Это принято, а не упущено** (ADR-077 §2.5). Освобождение создало бы окно, в
котором тот же идентификатор выдаётся другому, — а именно это ADR-018
запрещает. Цена ограничена: осиротевший резерв возникает только при
одновременном входе одного пользователя в узком окне между R1a и R1c, и стоит
одного значения из 10⁹.

## 5. Частичные состояния

Состояние определяется парой «значение `acct:P:S`» + «существует ли
пользователь Mattermost», и **первое наблюдаемо всегда**.

| # | отказ после | `acct:P:S` | пользователь MM |
|---|---|---|---|
| **A** | — | отсутствует | нет |
| **B** | R1a | `claimed` | нет |
| **C** | R1c | `registered` | **неизвестно** — U мог успеть |
| **D** | R2 | `linked` | есть |
| **E** | S | `linked` | есть |

Состояние C намеренно не различает «U не вызывался» и «U выполнился, но R2
нет»: различать их по записи нечем, и протокол обязан вести себя одинаково —
см. §6.

## 6. Recovery matrix

Механизм восстановления **один** — повторный вход по `(Provider, Subject)`
(ADR-077 §2.4). Отдельной процедуры починки нет.

| состояние | что обнаруживает повторный вход | какие операции выполняет |
|---|---|---|
| **A** | `KVGet(acct:P:S)` → `nil` | R1a → R1b → R1c → U → R2 → S |
| **B** | `state=claimed`, нет `photon_id` | R1b → R1c → U → R2 → S |
| **C** | `state=registered`, есть `photon_id`/`login_name`, нет `mm_user_id` | **U идемпотентно** → R2 → S |
| **D** | `state=linked` | S |
| **E** | `state=linked` | S (новая сессия) |

### 6.1. Идемпотентный U

```
user, err := CreateUser({username: login_name, …})
если "уже существует":
    user, err = GetUserByUsername(login_name)
```

Работает потому, что `login_name` детерминирован и записан в `acct:` **до**
первого вызова U (§2.2). Осиротевший пользователь Mattermost всегда находим —
искать по `Email` было бы нельзя: ADR-023 исключает его как ключ, он может
отсутствовать и меняться.

### 6.2. Сессия — расходный ресурс

Состояния D и E различаются только тем, была ли выпущена сессия; протокол их
не различает и выпускает новую. Сессия не входит в идентичность, и повторный
выпуск ничего не нарушает.

## 7. Инварианты — что обязано быть доказано тестом

| инвариант | чем обеспечен | как проверяется |
|---|---|---|
| **I1.** Два разных Account не получают один `PhotonID` | `CAS(pid:N, nil, …)` истинна ровно для одного вызывающего; `photon_id` попадает в `acct:` только после неё (§3.2) | параллельная регистрация N пользователей → все `photon_id` различны |
| **I2.** Один `(Provider, Subject)` не получает два Account | `CAS(acct:P:S, nil, …)` истинна ровно для одного (§4.1) | параллельные входы одного пользователя → один `photon_id` у всех исходов |
| **I3.** Зарезервированный `PhotonID` не переиспользуется | `pid:` не удаляется **ни на одном пути** этой спецификации | после осиротевшего резерва (§4.3) повторная выдача того же числа отвергается |
| **I4.** Осиротевший пользователь MM разрешим | `login_name` детерминирован и записан до U (§2.2, §6.1) | прерывание между U и R2 → повторный вход находит того же пользователя, второй не создаётся |
| **I5.** Повторный вход идемпотентен | §6 — каждое состояние ведёт к одному и тому же конечному | двукратный и десятикратный вход дают тот же `photon_id` и тот же `mm_user_id` |
| **I6.** `(false, nil)` не смешивается с `(false, err)` | §1 | сбой хранилища не выглядит как проигранная гонка и не приводит к продолжению по несуществующей записи |

Каждый инвариант обязан быть проверен **мутацией**: снять соответствующий CAS
или заменить его на `KVSet` — тест обязан упасть. Зелёный тест, который
проходит всегда, хуже отсутствующего.

## 8. Что эта спецификация не вводит

- **поиск пользователя по `PhotonID`** — отдельное решение с отдельным
  потребителем (ADR-077 §4);
- **удаление аккаунта** — вводится правило (надгробие, ADR-077 §2.5), но не
  механизм;
- **регистрация устройства** — `RegisterDevice` поверх этого реестра,
  следующий шаг после него;
- **освобождение осиротевших резервов** — запрещено §4.3;
- **многоузловое развёртывание** — KV живёт в общей БД и работоспособен, но
  стоимость последовательности при нескольких узлах не измерялась
  (ADR-077 §5.2).

---

## 9. Что останется непроверенным

Записывается заранее, чтобы не «дореализовывать» молча:

- поведение при отказе БД Mattermost **между** шагами — воспроизводится только
  на стенде с управляемым отказом хранилища;
- фактическая стоимость последовательности при конкуренции — измеряется, не
  оценивается;
- исчерпание пространства `PhotonID` — 10⁹ значений, воспроизводится только
  подменой генератора.
