# Plugin Runtime — Threat Model

Модель угроз для `photon-plugin-runtime`. Написана **до** проектирования
lifecycle, манифеста и IPC — потому что от неё зависит, какие permissions вообще
допустимы и какие гарантии обязан давать sandbox.

Документ формулирует **security properties**, а не механизмы. `seccomp`, `cgroups`,
namespaces, Android-специфика — это способы достижения свойств, и они выбираются
при реализации под конкретную платформу. Требовать конкретный механизм на уровне
модели угроз означало бы привязать архитектуру к одной ОС.

---

## 1. От чего защищаемся

| # | Угроза | Защита | Комментарий |
|---|---|---|---|
| T1 | Вредоносный плагин (написан со злым умыслом) | **Да** | Основной сценарий: плагины — сторонний код |
| T2 | Скомпрометированный/подменённый плагин | **Да** | Подпись пакета обязательна (ARCHITECTURE.md: нет подписи → отказ в установке) |
| T3 | Ошибочный плагин (баг, не злой умысел) | **Да** | Отличается от T1 намерением, но не последствиями |
| T4 | Плагин читает данные другого плагина или ядра | **Да** | Изоляция данных — базовая гарантия |
| T5 | Плагин вызывает API без соответствующего permission | **Да** | Enforcement на стороне Runtime, не на доверии к плагину |
| T6 | Плагин пытается обойти IPC и обратиться к ядру напрямую | **Да** | Именно для этого нужна граница процесса, а не только Authorizer |
| T7 | Плагин получает произвольный доступ к файловой системе хоста | **Да** | Ограничение — свойство; механизм зависит от платформы |
| T8 | Плагин устанавливает произвольные сетевые соединения | **Зависит от permission** | Сеть — не запрещена абсолютно, а выдаётся как capability |
| T9 | DoS через CPU/RAM/IPC-флуд | **Да, насколько позволяет платформа** | Полнота гарантии платформо-зависима — см. раздел 4 |
| T10 | Плагин падает (крэш процесса) | **Да** | Runtime и ядро обязаны пережить падение любого плагина |

## 2. Что мы намеренно НЕ обещаем

Этот раздел так же важен, как предыдущий. Обещание безопасности, которое система
физически не может обеспечить, хуже отсутствия обещания: на него полагаются.

| # | Сценарий | Позиция |
|---|---|---|
| N1 | **Компрометация самого Plugin Runtime** | Вне зоны ответственности sandbox. Runtime — доверенная часть платформы; если он скомпрометирован, механизм enforcement скомпрометирован вместе с ним. Защита от этого — код-ревью, подпись сборок, обновления, но не sandbox |
| N2 | **Компрометация ОС** (root/kernel exploit) | Полностью вне модели. Ни одно свойство ниже не сохраняется при скомпрометированном ядре ОС |
| N3 | **Компрометация Photon Core** | Вне модели: плагинная система строится поверх ядра и не защищает от него |
| N4 | **Side-channel атаки** (тайминги, кэш, энергопотребление) | Не рассматриваются. Изоляция процессов их не устраняет |
| N5 | **Защита от самого пользователя** | Пользователь, установивший плагин и выдавший ему права, — источник решения, а не угроза. Runtime не защищает пользователя от его собственного осознанного выбора, только обеспечивает, что выбор осознанный (явный запрос прав) |
| N6 | **Гарантия одинаковой изоляции на всех платформах** | Уровень OS-изоляции различается — см. раздел 4. Photon-уровень гарантий одинаков везде, OS-уровень нет |

## 3. Базовый инвариант

> **Плагин не получает никаких возможностей только потому, что он запущен.**
> Каждая привилегированная операция проходит через capability/permission
> enforcement.

Практически:

```
Plugin
  │  "дай мне X"
  ▼
IPC
  │
  ▼
Runtime
  ├── identity      (кто вызывает)
  ├── manifest      (что плагин ЗАПРОСИЛ)
  ├── trust level   (какой максимум ему вообще доступен)
  └── policy        (что решил пользователь/политика)
        │
     Authorizer → ALLOW / DENY
```

### Манифест — это запрос, а не разрешение

Критично для правильного понимания модели:

```
manifest:
  requested:
    - network.connect
    - storage.read
```

означает **«плагин просит»**, а не **«плагин имеет»**. Окончательное решение
принимает Runtime на основании trust level и политики. Реализация, которая
трактует манифест как выданные права, ломает весь инвариант — это то же самое,
что позволить недоверенному коду самому определять свои привилегии.

## 4. Платформенная модель: два уровня гарантий

Уровень OS-изоляции принципиально различается между платформами, и модель обязана
это отражать честно, а не постулировать одну схему для всех.

```
Layer 1 — Photon          (одинаково на всех платформах)
  ├── capability / permission enforcement
  ├── IPC isolation
  └── lifecycle isolation (падение плагина не роняет ядро)

Layer 2 — OS              (различается по платформам)
  └── process / filesystem / network / resource sandbox
```

**Photon гарантирует Layer 1 везде. Layer 2 предоставляется настолько, насколько
позволяет конкретная платформа.**

### Linux Desktop

Потенциально доступно: отдельный процесс, namespaces, ограничения файловой
системы, лимиты ресурсов, сетевые ограничения.

Модель требует **свойство**, а не механизм. Например: *«плагин не должен получать
произвольный доступ к файловой системе хоста»* — а каким механизмом это
обеспечивается (namespaces, bind-mount, отдельный пользователь), решает
Linux-реализация Runtime.

### Android

Модель другая, и это не деталь:

```
Android OS sandbox
      │
      ▼
  ENGRAM process
      ├── Plugin Runtime
      │     └── Plugin
      └── Android permissions
```

Приложение уже изолировано ОС от других приложений — но плагин **внутри** процесса
приложения от него не изолирован. Нельзя автоматически обещать «каждый плагин
запускается в отдельном OS-процессе»: модель упаковки и процессов на Android
устроена иначе, и вариант запуска отдельного процесса на плагин требует отдельного
исследования (не решается на уровне этого документа).

**Следствие:** на Android Layer 2 может быть слабее, чем на Linux. Layer 1
(enforcement, IPC, lifecycle) обязателен одинаково. Что именно достижимо на
Android — открытый вопрос, требующий проверки на реальном устройстве с NDK
(сейчас недоступно, см. `photon-bindings/android/README.md`).

Обещать одинаковую изоляцию на обеих платформах, не проверив вторую, — ровно то,
чего этот документ должен избежать (см. N6).

## 5. Sandbox ≠ Authorization

Два разных механизма, решающих разные задачи. Смешивать нельзя.

| | Вопрос, на который отвечает |
|---|---|
| **Permission (Authorizer)** | «Имеет ли плагин право отправить сообщение?» |
| **Sandbox** | «Может ли плагин вообще обратиться к механизму отправки в обход Runtime?» |

Полная цепочка требует обоих:

```
Plugin
  ↓
Sandbox / process boundary    ← не даёт обойти Runtime
  ↓
IPC
  ↓
Authorizer                    ← решает, что разрешено
  ↓
Capability
  ↓
Photon Core
```

- **Убрать Authorizer** → изолированный, но всесильный процесс: sandbox не
  различает «отправить своё сообщение» и «прочитать чужой чат».
- **Убрать sandbox** → permission API обходится багом в Runtime или компрометацией
  плагина: если плагин делит адресное пространство с ядром, никакая проверка прав
  не помешает ему прочитать память напрямую.

Именно поэтому ADR-005 требует отдельный процесс, а не только проверку прав.

## 6. Trust levels

В ENGRAM будут плагины разного происхождения, и они не могут иметь одинаковый
потолок возможностей.

| Уровень | Источник |
|---|---|
| `official` | Подписан командой Photon |
| `verified` | Прошёл проверку в ENSTOR |
| `user-installed` | Установлен пользователем из известного источника |
| `untrusted` | Произвольный источник, без проверки |

### Trust ≠ Permission

Trust определяет **максимально доступный набор** capabilities, но не заменяет
Authorizer и не выдаёт права автоматически:

```
verified plugin
  requested: network.connect
  → DENY        (политика пользователя запретила сеть этому плагину)

untrusted plugin
  requested: chat.send
  → ALLOW       (пользователь явно разрешил)
```

То есть высокий trust не даёт прав сам по себе, а низкий не запрещает всё
автоматически. Trust — верхняя граница; финальное решение всегда за Authorizer с
учётом политики.

```
        ┌──────────────────────┐
        │    Plugin Process    │
        │      untrusted       │
        └──────────┬───────────┘
                   │
                  IPC
                   │
        ┌──────────▼───────────┐
        │   Plugin Runtime     │
        │   ├── Manifest       │  (запрос, не разрешение)
        │   ├── Trust          │  (верхняя граница)
        │   ├── Policy         │  (решение пользователя)
        │   └── Authorizer     │  (финальное ALLOW/DENY)
        └──────────┬───────────┘
                   │
              capabilities
                   │
        ┌──────────▼───────────┐
        │     Photon Core      │
        └──────────────────────┘
```

## 8. Что из этого следует для проектирования

Прямые требования к следующим шагам (lifecycle → manifest → IPC):

1. **Манифест** обязан различать «запрошено» и «выдано» — это разные состояния, а
   не одно поле (следует из раздела 3).
2. **IPC** обязан передавать идентичность вызывающего: без неё Authorizer не может
   принять решение (T5).
3. **Lifecycle** обязан определять поведение при падении плагина: T10 требует,
   чтобы ядро пережило крэш, значит рестарт/отключение/backoff — обязательная
   часть модели, а не опция.
4. **Permissions** должны быть capability-ориентированными (`chat.send`,
   `storage.read`), а не ролевыми («доверенный плагин») — иначе trust начнёт
   подменять авторизацию, что прямо запрещено разделом 6.
5. **Sandbox-требования формулируются как свойства** («нет произвольного доступа к
   FS»), а не как механизмы («использовать seccomp») — иначе Android-реализация
   окажется невозможной по формальным причинам (раздел 4).
