# Передача media: контракт первого вертикального среза

**Статус:** спецификация. Написана **до кода** — по методу проекта и по
прецеденту `WIRE_FORMAT.md`, `bridge-session.md`, `p2p-session.md`,
`event-delivery.md`.

**Что фиксирует:** провод, ошибки, жизненный цикл и границы ответственности для
среза `upload → STORED → attach → getFeed → download → SHA-256 verify`.

**Чего не фиксирует:** модель (ADR-048) и решения о кадрировании (ADR-049) —
они уже приняты и здесь **не переопределяются**, а конкретизируются до
исполнимого контракта. Всё, отнесённое ADR-048 §14 и ADR-049 §11 к следующим
шагам, сюда не входит.

---

## 0. Проверка на новый API поверх замороженного

Выполнена **до** написания остального. Контракт ниже пользуется ровно тем, что
уже есть:

```go
type Stream interface { SendStream; RecvStream }
type SendStream interface { io.Writer; Close() error }  // Close — half-close записи
type RecvStream interface { io.Reader }
```

- кадрирование §1 — `json.Encoder`/`json.Decoder` поверх `io.Writer`/`io.Reader`;
- граница тела §2 — `dec.Buffered()`, стандартная библиотека;
- `DoStream` §6 — нужны только `Write`, `Read`, `Close`;
- отмена §8 — **ничего не добавляется**: используется то же, что порт уже даёт,
  с теми же последствиями, что записаны в ADR-049 §5.

**`ports.Transport` не меняется.** Всё новое — уровня `services/`, где контракт
не заморожен.

---

## 1. Кадр медийного стрима

Один bidi-стрим того же action-соединения, три части подряд:

```
[ JSON header  ]\n     {"action": <код>, "resource": "media"}
[ JSON payload ]\n     см. §4
[ binary tail  ]       ровно body_length байт, без обрамления
```

Первые два кадра идентичны сегодняшним кадрам любого действия — медийный стрим
отличается **только наличием третьей части** и тем, что её наличие определяется
кодом действия, а не содержимым.

**Направление третьей части задаётся действием, а не переговорами:**

| действие | кто пишет тело | кто пишет ответ |
|---|---|---|
| `MEDIA_UPLOAD` | клиент, сразу после payload | сервер, после приёма тела |
| `MEDIA_DOWNLOAD` | сервер, сразу после ответного JSON-кадра | сервер, **перед** телом |
| `MEDIA_GET_INFO` | никто | сервер |

На скачивании порядок обратный загрузке: **сначала JSON-ответ, потом тело**.
Иначе клиент не смог бы отличить отказ от начала данных, не прочитав их.

---

## 2. Граница тела — правило чтения

Дословно по ADR-049 §2, воспроизводится обеими сторонами:

```
body := io.MultiReader(skipLeadingWhitespace(dec.Buffered()), stream)
```

где `skipLeadingWhitespace` съедает ведущие `space`, `\t`, `\r`, `\n`.

Обе половины обязательны:

- **без `dec.Buffered()`** часть тела остаётся в буфере декодера и теряется
  молча; при теле меньше буфера теряется **всё** тело, а SHA-256 совпадает с
  хешем пустой строки;
- **без пропуска пробелов** к началу тела приклеивается `\n`, который
  `json.Encoder` дописывает после каждого значения, а `json.Decoder` не
  потребляет.

Оба случая измерены (ADR-049 §2) и оба **тихие**: длина правдоподобна, поток
валиден, данные неверны.

---

## 3. `body_length` и валидация

`body_length` — **обязательное поле payload** для обоих направлений.

**Правило приёма, одинаковое у клиента и сервера:**

1. читать **ровно** `body_length` байт, не полагаясь на EOF и не полагаясь на
   half-close;
2. если поток закончился раньше — **ошибка `invalid`**, а не усечённый успех;
3. если после `body_length` байт в стриме есть ещё данные — их **не читать**;
   для приёмника они не существуют;
4. `body_length` сверяется с фактически прочитанным **до** проверки SHA-256:
   это дешёвый и ранний детектор обрыва.

**Пределы.** `body_length` обязан быть в диапазоне `1 … max_media_bytes`.
Значение вне диапазона отвергается **до чтения тела**, ответом `invalid`.
Конкретное `max_media_bytes` — параметр развёртывания, не константа протокола;
первый срез принимает его как настройку Bridge со значением по умолчанию.

Нулевое тело не поддерживается намеренно: пустой media-объект не имеет смысла,
а `0` как «длина не указана» превратил бы обязательное поле в необязательное.

---

## 4. Действия и payload

Коды — из диапазона, закреплённого ADR-049 §8 (`RESOURCE_MEDIA = 7`, 700+).
Канонические имена и точные номера появляются в `photon.proto` на шаге
реализации; здесь фиксируется **состав полей**.

**`MEDIA_UPLOAD` — запрос:**

```json
{ "channel_id": "…", "name": "photo.png", "mime": "image/png",
  "sha256": "<hex, 64 символа>", "body_length": 65536 }
```

`sha256` объявляется **до** передачи: он делает проверку целостности
двусторонней, а не только клиентской (§9).

**`MEDIA_UPLOAD` — ответ:** `{ "media_id": "…", "sha256": "…", "size": 65536 }`.

**`MEDIA_DOWNLOAD` — запрос:** `{ "media_id": "…" }`.
**Ответ:** `{ "media_id": "…", "sha256": "…", "size": …, "mime": "…", "name": "…", "body_length": … }`, затем тело.

**`MEDIA_GET_INFO` — запрос:** `{ "media_id": "…" }`. Ответ — те же метаданные
без тела и без `body_length`.

**Прикрепление к сообщению — не медийное действие.** Оно выполняется
существующим `createPost`, который получает **типизированное** поле
`photon_media` и строит `props` сам. Сырые `props` от клиента не принимаются:
это дало бы запись в чужие ключи (ADR-048 §3).

## 5. Ошибки и их различимость

**Существенное ограничение, которое надо знать до проектирования:** конверт
ответа несёт `{"ok": false, "error": "<строка>"}` — **машинного кода ошибки в
нём нет**. Поэтому различимость обеспечивается **фиксированным словарём строк**
для медийных действий. Добавление числового кода в конверт затронуло бы все
действия сразу и в срез не входит.

| строка | что значит | когда |
|---|---|---|
| `forbidden` | нет прав **либо** объекта не существует | до любой проверки жизненного цикла |
| `unavailable` | объект известен и доступен субъекту, но байтов больше нет | состояние `EXPIRED`/`DELETED` |
| `invalid` | запрос не соответствует контракту | плохая длина, обрыв тела, битый кадр, `sha256` неверного формата |
| `integrity` | принятые байты не сошлись с объявленным `sha256` | только на **приёме загрузки** сервером |

**`forbidden` объединяет «нет прав» и «нет объекта» намеренно** — это уже
принятое решение ADR-039 (`errForbidden` — «единственный отказ авторизации,
один и тот же»), и оно не переопределяется здесь. Различать их значило бы дать
пробовать существование чужих `media_id`.

**Почему `unavailable` при этом не является утечкой.** До него нельзя дойти, не
пройдя авторизацию: резолвер `objMedia` сначала разрешает `media_id` в канал и
проверяет право чтения канала. Субъект, получивший `unavailable`, уже имеет
право видеть этот объект — он узнаёт только, что байтов больше нет.

**`integrity` на клиенте наружу не уходит:** несовпадение хеша при скачивании —
локальный вердикт клиента, а не ответ сервера (§9).

## 6. `DoStream` — семантика вызова в ядре

```go
Session.DoStream(ctx, action int32, payload []byte,
                 body io.Reader, sink io.Writer) (Response, error)
```

Форма закреплена ADR-049 §4 и здесь не меняется.

- **загрузка:** `body != nil`, `sink == nil`. Вызов пишет header, payload и
  ровно столько байт из `body`, сколько объявлено в payload, затем читает
  JSON-ответ;
- **скачивание:** `body == nil`, `sink != nil`. Вызов пишет header и payload,
  читает JSON-ответ и, **если `ok == true`**, копирует ровно `body_length`
  байт в `sink`;
- **оба nil** — обычное действие; поведение совпадает с `Do`;
- **оба не nil** — ошибка вызывающего, ни один байт не отправляется.

**`Response` возвращается и при `ok == false`** — вызывающий обязан различать
«вызов не состоялся» (`error != nil`) и «сервер отказал» (`Response.OK ==
false`). Это то же разделение, что зафиксировал ADR-038.

**Кадрирование живёт в `Codec`.** `DoStream` не собирает кадры сам, сырой
`ports.Stream` наружу не отдаётся (ADR-049 §4). Правило §2 существует в одном
месте — иначе оно размножилось бы по вызывающим, а его нарушение тихое.

**Клиент обязан прочитать ответ, даже если его запись не удалась.** Сервер
может отказать до конца приёма тела (например, `forbidden`), и тогда его
завершение стрима прервёт незаконченную запись клиента. Настоящая причина
лежит в JSON-ответе; ошибка записи — следствие, а не диагноз. Клиент, который
вернёт ошибку записи, покажет пользователю «сбой сети» вместо «нет прав».

## 7. Успешное завершение

**Загрузка успешна**, когда выполнено всё:

1. сервер принял ровно `body_length` байт;
2. SHA-256 принятого совпал с объявленным в запросе;
3. объект записан в MediaStore и переведён в `STORED`;
4. клиент получил `ok == true` с `media_id`.

Отсутствие любого пункта — не частичный успех, а отказ; объект в этом случае не
становится видимым и подлежит уборке как брошенный.

**Скачивание успешно**, когда:

1. получен `ok == true` с метаданными;
2. принято ровно `body_length` байт;
3. SHA-256 принятого совпал с `sha256` из ответа.

**Частично полученное тело не является результатом.** Пока §7 не выполнен
целиком, у вызывающего нет файла — есть незавершённая передача.

## 8. Отмена и дедлайны

**Клиент.** Порт даёт `Close()` (half-close записи) и ничего больше — ни
`CancelRead`, ни дедлайнов (ADR-049 §5). Поэтому:

- отмена выражается отменой `ctx` и прекращением чтения;
- **соединение при этом остаётся исправным** — измерено: следующее обычное
  действие проходит за миллисекунды;
- брошенный стрим **продолжает существовать** до закрытия соединения либо до
  срабатывания серверного дедлайна. Клиент не может освободить его сам.

Это **записанное ограничение**, а не недоделка. Расширение порта — отдельное
решение по ADR-020, и в срез не входит.

**Сервер.** Обязан ограничивать медийный стрим **скользящим дедлайном**:
дедлайн сбрасывается перед каждым записанным или прочитанным блоком, поэтому
здоровая передача любого размера его не задевает, а зависшая упирается за
фиксированное время. Измерено на стенде: обе стороны освобождаются за время
дедлайна, горутина возвращается, соединение продолжает принимать обычные
действия.

**Бюджет стримов.** Передача занимает один из 100 конкурентных слотов
соединения (ADR-049 §6 с уточнением ADR-050). Число одновременных передач
ограничивается явно — на клиенте и на Bridge.

---

## 9. SHA-256

- **вычисляется потоково** обеими сторонами, по мере прохождения байтов;
- **на загрузке** сервер сверяет принятое с `sha256` из запроса: несовпадение —
  `integrity`, объект не сохраняется. Клиент, объявивший хеш, не может
  подменить содержимое незаметно;
- **на скачивании** клиент сверяет принятое с `sha256` из ответа. Несовпадение —
  локальный вердикт: файл не считается полученным;
- хеш — **content identity** (ADR-048 §10): ключ локального кеша и основание
  дедупликации. Изменение содержимого есть новый `media_id`, а не новая версия.

Собственный хеш обязателен, потому что Mattermost хеша не хранит и не отдаёт —
в `FileInfo` такого поля нет.

---

## 10. Файл целиком в памяти не собирается

**Требование контракта, а не свойство реализации.** Ни одна сторона не имеет
права держать тело целиком:

- запись и чтение идут блоками фиксированного размера;
- SHA-256 считается на лету;
- сервер пишет на диск потоково;
- `DoStream` принимает `io.Reader` и `io.Writer`, а не `[]byte`, — именно чтобы
  сделать обратное невозможным по сигнатуре.

Проверяется измерением пикового RSS на теле, заведомо превышающем окно
флоу-контроля. Измеренный ориентир: тело 200 МБ при пике около 13 МБ на обеих
сторонах.

## 11. Жизненный цикл в первом срезе

```
(загрузка принята) → STORED → ATTACHED → AVAILABLE
```

| состояние | смысл | переход |
|---|---|---|
| `STORED` | байты записаны и проверены; `post_id` пуст | результат успешной загрузки |
| `ATTACHED` | объект назван в `photon_media` живого поста | `createPost` с проверкой владения |
| `AVAILABLE` | объект прикреплён и байты доступны | нормальное состояние |

`EXPIRED` и `DELETED` определены ADR-048 §7; в первом срезе они **достижимы
только явной уборкой**, планировщика нет (ADR-049 §11). Поле `expires_at`
записывается при создании — иначе объект нельзя будет убрать, не додумывая
срок задним числом.

**`STORED` без перехода в `ATTACHED` — брошенная загрузка.** Она обнаружима по
пустому `post_id` и возрасту; уборка вызывается явно.

## 12. Границы ответственности

| | отвечает за | НЕ отвечает за |
|---|---|---|
| **Photon Core** | кадр и его границу на своей стороне; `DoStream`; сверку `body_length`; сверку SHA-256 при скачивании; различение «вызов не состоялся» и «сервер отказал» | хранение байтов; TTL; авторизацию; знание, что внутри тела |
| **Bridge** | приём и отдачу тела; сверку `body_length` и SHA-256 при загрузке; **авторизацию** через существующую машину `resolve → policy`; дедлайн стрима; построение `props` при прикреплении | содержимое файла; локальный кеш; политику клиента |
| **MediaStore** | байты, индекс, состояния, `expires_at`; ответ «объект есть/нет/недоступен» | протокол; авторизацию (даёт метаданные, решение принимает authz) |

**Авторизация остаётся одной точкой принятия решения.** Медийный путь ветвится
до `Dispatch`, потому что тот не видит стрима, — но политику обязан вызывать ту
же (`resolve → policy`, ADR-039). Две точки **вызова** допустимы; две точки
**решения** — нет.

**Core не разбирает домен.** Тело для него — непрозрачные байты, `photon_media`
— метаданные приложения. Это вариант C ADR-046 и §2 ADR-048; срез его не
ослабляет.

---

## 13. Что срез обязан доказать

1. байты не проходят через JSON ни в одну сторону;
2. ни одна сторона не держит тело целиком — по измеренному пику RSS;
3. SHA-256 сервера при приёме = клиентский = исходный;
4. `media_id` не является capability: чужой субъект получает `forbidden`, а не
   байты;
5. загрузка без прикрепления оставляет `STORED` с пустым `post_id` и
   обнаружима как брошенная;
6. `photon_media` доезжает до клиента обычным `getFeed`, тем же курсором
   `(UpdateAt, ID)`;
7. `unavailable` отличим от `forbidden` и от `invalid`;
8. стоимость измерена раздельно: локальная и сетевая.

---

## 14. Что этой спецификацией не решается

Возобновляемость и диапазоны; дедупликация; планировщик уборки; S3/MinIO;
локальный кеш и вытеснение; превью; хуки `MessageWillBePosted` /
`MessageWillBeUpdated`; медиа в C ABI и SDK; удаление media по удалению поста;
квоты диска; машинный код ошибки в конверте ответа.

Первые одиннадцать отнесены ADR-048 §14 и ADR-049 §11. Последний назван здесь
впервые (§5) и требует отдельного решения, потому что затрагивает конверт всех
действий, а не только медийных.
