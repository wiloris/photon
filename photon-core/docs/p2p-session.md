# P2P Session — спецификация (Phase 15)

Написана **до** кода, как `bridge-session.md` перед `services/session` и
`WIRE_FORMAT.md` перед `adapters/tcp`. Обратный порядок даёт протокол,
повторяющий возможности выбранной библиотеки, а не модель системы.

Реализует замороженный порт `ports/p2p.go` (ADR-020). Архитектура слоёв —
ADR-043 (путь B+: ICE + DTLS + SCTP, без `pion/webrtc`). Аутентификация —
ADR-041. Signaling — ADR-042. Жизненный цикл — ADR-044.

---

## 1. Зачем эта фаза существует

Порт `p2p.go` спроектирован в Phase 1 и заморожен, но **ни разу не реализован**.
Phase 15 начата до появления первого потребителя (клиент — Phase 16) намеренно:
цель — выяснить, реализуем ли контракт и непротиворечив ли он, пока поверх него
ничего не написано.

Проверка уже дала результат до единой строки кода: комментарий к `AcceptOffer`
содержал **два разных контракта в одном предложении** — методы «блокируются до
успешного завершения согласования **либо** возвращают ошибку». Первый адаптер
выбрал бы одно, второй другое. Устранено ADR-044.

**Чего эта фаза не производит.** Работающего сценария «два устройства через
интернет» — доставку signaling выполняет вызывающий, а его нет до Phase 16
(ADR-042). Фаза производит слой, готовый к этому.

---

## 2. Границы: что делает адаптер и чего не делает

| делает | не делает |
|---|---|
| сбор ICE-кандидатов, проверки связности, выбор пары | discovery: откуда взялся `PublicKey` peer'а, кто online |
| DTLS поверх выбранной пары | доставку `offer`/`answer` другой стороне |
| SCTP-ассоциацию и потоки поверх DTLS | выбор канала доставки и требования к нему |
| handshake ADR-041 и подтверждение `Peer()` | хранение peer'ов, контакт-лист, реестр устройств |
| приведение к `ports.Connection`/`ports.Stream` | шифрование поверх DTLS — его достаточно |

Наружу не проходит ни один тип Pion: только `[]byte`, `ports.PublicKey`,
`Session`/`Connection`/`Stream`, `Endpoint` (ADR-043 §0).

## 3. Три шага согласования

```
инициатор A                     вызывающий код               ответчик B
     │                                                            │
 CreateOffer(ctx, peerB) ──► offer []byte ──[любой канал]──► AcceptOffer(ctx, peerA, offer)
     │                                                            │
     │  ◄──[любой канал]◄── answer []byte ◄──────────────────────┤ + session (ещё не готова)
     │                                                            │
 CompleteSession(ctx, peerB, answer) ──► session                  │
     │                                                            │
     └──────────── ICE → DTLS → SCTP → handshake ADR-041 ─────────┘
                              │
                     Peer() подтверждён, потоки открываются
```

Аргумент `peer PublicKey` во всех трёх вызовах — **ожидание**, а не факт.
Он говорит адаптеру, с кем вызывающий намерен соединиться, и служит критерием
на шаге 7 §6: если handshake подтвердил другой ключ, согласование терминально
проваливается. Подмена этого правила на «вернуть тот ключ, который подтвердился»
превратила бы `Peer()` в источник неожиданностей для вызывающего.

## 4. Wire-format блобов offer/answer

**SDP не используется.** Он не нужен при выбранной архитектуре: `pion/sdp` в
графе зависимостей отсутствует (ADR-043). Формат — свой, минимальный,
описывается здесь и фиксируется адаптером; для порта блобы непрозрачны
(ADR-042).

Кодирование — JSON, по тем же соображениям, что в ADR-034: отлаживаемость и
отсутствие второго формата на границе. Блоб не является частью Photon-протокола
и в `photon.proto` не входит.

### 4.1 `offer`

```json
{
  "v": 1,
  "ice_ufrag": "...",
  "ice_pwd": "...",
  "candidates": ["candidate:...", "..."],
  "dtls_role": "server",
  "nonce": "<base64, 32 байта>"
}
```

### 4.2 `answer`

Та же форма плюс поле корреляции:

```json
{
  "v": 1,
  "in_reply_to": "<nonce инициатора из offer, base64>",
  "ice_ufrag": "...",
  "ice_pwd": "...",
  "candidates": ["candidate:...", "..."],
  "dtls_role": "client",
  "nonce": "<base64, 32 байта>"
}
```

`in_reply_to` нужен потому, что `CompleteSession(ctx, peer, answer)` обязан
понять, к какому именно согласованию относится ответ: к одному peer'у
допускается несколько одновременных сессий (ADR-044 §7), и без корреляции
второй ответ применился бы к первому согласованию. Значение сверяется с
ожидаемым; несовпадение — терминальный отказ, а не выбор «ближайшего»
согласования.

### 4.3 Правила

- **`v` — граница версии формата.** Несовпадение — терминальный отказ, а не
  попытка разобрать «как получится».
- **Роли нижних слоёв назначаются шагом согласования, а не выводятся из
  сети.** Инициатор (`CreateOffer`) — ICE controlling, DTLS `server`, SCTP
  server; отвечающий (`AcceptOffer`) — ICE controlled, DTLS `client`, SCTP
  client. Иначе обе стороны могут выбрать одну роль, и handshake не состоится
  по причине, которую в логах не видно. Поле `dtls_role` в блобе дублирует это
  правило явно, чтобы расхождение обнаруживалось при разборе, а не таймаутом.
- **Кандидаты передаются в блобе целиком.** Trickle ICE не поддерживается:
  порт даёт ровно два обмена, третьего канала для дозагрузки кандидатов у него
  нет. Следствие — задержка на полный сбор кандидатов; принято осознанно.
- **`nonce` в блобе — вход для transcript §5**, а не средство аутентификации
  самого блоба. Блоб не подписан: канал доставки недоверенный по построению
  (ADR-042), и подпись в нём создавала бы ложное впечатление защищённости.

## 5. Handshake ADR-041 — нормативный формат

Выполняется **после** установления SCTP, до выдачи `Peer()` и до открытия
прикладных потоков. Идёт по выделенному SCTP-потоку с фиксированным
идентификатором; прикладные потоки этот идентификатор не используют.

### 5.1 Channel-binding material

```
binding = ExportKeyingMaterial(label = "photon-p2p-channel-binding", context = nil, length = 32)
```

Экспорт RFC 5705 из состояния DTLS (`pion/dtls`, `State.ExportKeyingMaterial`).
Свойства, требуемые ADR-041 §4, выполняются буквально: значение одинаково у
обеих сторон, определяется ключевым материалом канала, не выводимо стороной,
не участвовавшей в handshake, и доступно до передачи прикладных данных.

**Сертификатные отпечатки как замена запрещены** (ADR-043 §2).

### 5.2 Transcript

Подписывается конкатенация с **явным кодированием границ** — прямое требование
ADR-037: там сказано, что отсутствие длины в `device-auth` есть свойство формы
с одним полем, а не принцип, и при появлении структуры из нескольких полей
границы обязаны кодироваться явно. Здесь полей пять.

```
transcript =
    "photon-p2p-auth:"                     доменный литерал (ADR-041)
  ‖ uint32be(len(initiator_pubkey)) ‖ initiator_pubkey
  ‖ uint32be(len(responder_pubkey)) ‖ responder_pubkey
  ‖ uint32be(len(initiator_nonce))  ‖ initiator_nonce
  ‖ uint32be(len(responder_nonce))  ‖ responder_nonce
  ‖ uint32be(len(binding))          ‖ binding
```

Порядок полей — **по ролям согласования**, не по тому, кто вычисляет. Обе
стороны строят одну и ту же байтовую строку.

Роли `initiator`/`responder` определены шагом: `CreateOffer` — инициатор,
`AcceptOffer` — отвечающий. Роль не зависит от DTLS-роли и не выводится из неё.

### 5.3 Обмен

Каждая сторона отправляет `{"pubkey": <base64>, "sig": <base64>}` и проверяет
встречное сообщение: `Identity.Verify(pubkey, transcript, sig)`.

Проверка успешна **и** `pubkey` совпал с ожидаемым `peer` из аргумента вызова —
только тогда `Peer()` возвращает значение.

### 5.4 Что каждая часть предотвращает

| часть | без неё |
|---|---|
| домен `photon-p2p-auth:` | подпись из `device-auth`/`plugin-sign` предъявляется как P2P-handshake (ADR-037) |
| явные длины | две разные пары полей дают одну байтовую строку |
| оба публичных ключа | подпись переносится в разговор с третьей стороной |
| свежие nonce обеих сторон | воспроизведение записанного ранее handshake |
| channel binding | MITM, терминирующий два независимых канала |
| сверка с ожидаемым `peer` | соединение с не тем, кого запрашивал вызывающий |

## 6. Состояния и жизненный цикл

```
        CreateOffer / AcceptOffer
                  │
                  ▼
           negotiating ──────► failed (терминально)
                  │              ▲
           ICE → DTLS → SCTP     │ отмена ctx, таймаут,
                  │              │ ошибка слоя, чужой ключ
              handshake ─────────┘
                  │
                  ▼
              established ──► closed
```

Согласно ADR-044:

1. **Блокирующая семантика.** Все методы `Session` — включая `Peer()`,
   `OpenStream`, `AcceptStream`, `OpenUniStream`, `AcceptUniStream` — блокируются
   до `established`, до терминальной ошибки либо до отмены переданного им
   контекста. Смешанный контракт запрещён.
2. **`RemoteEndpoint()` не блокируется** — это диагностика. До установления
   возвращает пустую строку, после — выбранную пару кандидатов в виде
   `local→remote`. Формат порт не специфицирует.
3. **Отмена.** `CreateOffer` — согласование не начато либо прервано, повтор
   допустим. `AcceptOffer` — выданная `Session` переходит в `failed`, `answer`
   недействителен. `CompleteSession` — согласование прервано. Отмена не
   закрывает экземпляр `P2P` и не влияет на другие сессии.
4. **Таймаут установления обязателен** и задаётся конфигурацией адаптера. Без
   него зависание неотличимо от медленной сети. Потолок покрывает согласование
   **целиком**, включая промежуток между `CreateOffer` и `CompleteSession`: там
   стоит доставка блоба чужим каналом (ADR-042), и ответ может не прийти
   никогда. Незавершённое согласование освобождается по истечении потолка, а не
   живёт до `Close()`.

### 6.1 Время жизни контекста — часть контракта

Прямое следствие п. 3, записанное отдельно, потому что ошибка здесь тихая.

Согласование продолжается **после возврата** из `AcceptOffer` и
`CompleteSession`, и живёт оно на контексте вызывающего. Значит привычная форма

```go
ctx, cancel := context.WithTimeout(parent, 10*time.Second)
defer cancel()
answer, sess, err := p2p.AcceptOffer(ctx, peer, offer)
```

**убивает сессию** на выходе из функции: вызов вернул `answer` и `Session` без
ошибки, а через мгновение сессия стала терминальной.

Смягчать это адаптеру запрещено. «Игнорировать отмену, если `Session` уже
выдана» означало бы, что отменить согласование нечем вовсе, — а п. 3 требует
обратного.

**Правило для вызывающего: один контекст на всё согласование, живущий до его
исхода.** Он же ограничивает ожидание блокирующих методов `Session`.
5. **`failed` необратимо.** Повторные вызовы возвращают ту же ошибку.
   Восстановление — новый `CreateOffer`.
6. **Повторный `CompleteSession`** — ошибка, не вторая сессия и не та же самая.
7. **Несколько сессий к одному peer'у** разрешены и независимы.
8. **Glare** — две встречные попытки дают две независимые сессии либо ошибку у
   одной или обеих. Тихого слияния нет.

## 7. Потоки поверх SCTP

`sctp.Stream` двунаправлен, как и DataChannel: нативных однонаправленных
потоков не даёт ни один рассмотренный кандидат (ADR-043 §3). Поэтому
`OpenUniStream`/`AcceptUniStream` — **соглашение поверх**, обязательное по
ADR-016.

Соглашение: первым байтом вновь открытого потока идёт признак направления.

```
0x01  двунаправленный  → отдаётся из AcceptStream
0x02  однонаправленный → отдаётся из AcceptUniStream, приём только
```

- Признак пишется **отправителем при открытии**, до прикладных данных.
- Принимающая сторона читает один байт и направляет поток в очередь
  `AcceptStream` либо `AcceptUniStream`. Неизвестное значение — поток
  отвергается, соединение не рушится.
- В однонаправленном потоке отправитель не читает, получатель не пишет.
  Нарушение — ошибка на стороне нарушителя, не протокольный сбой.
- `SendStream.Close()` — half-close: завершает отправку, приём не трогает.

Это тот же приём, что в `adapters/tcp`, где однонаправленность выражена флагом
кадра (`WIRE_FORMAT.md`). Разница: там своё кадрирование целиком, здесь один
байт поверх готового мультиплексора.

## 8. Владение ресурсами

| владелец | ресурс |
|---|---|
| экземпляр `P2P` | ICE-агенты согласования, STUN/TURN-клиент, конфигурация |
| `Session` | своя ICE-связность, DTLS-соединение, SCTP-ассоциация, потоки |

- `P2P.Close()` **не закрывает установленные сессии** — требование порта.
  Прекращает новые согласования; идущие завершаются ошибкой.
- Общий ресурс освобождается, когда закрыта последняя сессия.
- `Close()` идемпотентен: повтор — успешный no-op.
- `Session.Close()` закрывает свои потоки и слои снизу вверх; на другие сессии
  и на `P2P` не влияет.

## 9. Ошибки

Публичный контракт не расширяется: наружу — `ports.ErrSessionFailed`
(ADR-043 §8). «Direct не удался» и «peer недостижим вовсе» снаружи
неразличимы.

Внутренние причины сохраняются обёрткой для диагностики: не собрались
кандидаты, ICE не сошёлся, DTLS не установился, SCTP не поднялся, handshake не
прошёл, подтверждён не тот ключ. Различать их наружу — отдельное решение с
доказанной потребностью, а не побочный эффект реализации.

Ошибки контекста (`context.Canceled`, `context.DeadlineExceeded`) возвращаются
как есть и `ErrSessionFailed` не подменяются: отмена вызывающим — не отказ
согласования. Различать их обязан и шаг handshake: дедлайн, выставленный на
соединении, и таймер контекста срабатывают одновременно, но независимо, и
чтение успевает вернуть `i/o timeout` раньше, чем контекст сообщит о себе —
подменять этим отказ разбора нельзя.

**Отказ обязан быть немедленным там, где он уже известен.** Два случая, каждый
из которых иначе подменяется истечением потолка на противоположной стороне:

- `ForceRelay` без единого `turn:`/`turns:` адреса — отвергается **на
  построении** адаптера, а не оборачивается offer'ом без кандидатов;
- сбор, давший **ноль** кандидатов (TURN не ответил, учётные данные неверны,
  интерфейсов нет) — отказ на том же шаге, а не блоб, с которым согласование
  заведомо не состоится.

## 10. Тесты

### 10.1 Покрыто локально, без сети и второй машины

Список приведён в соответствие с реально существующими тестами по итогам
аудита перед коммитом. Прежняя редакция перечисляла ещё пять свойств в
настоящем времени («проверяется»), тестов под которыми нет; они вынесены ниже,
в отдельный список. Это тот же класс ошибки, что закрытый в этой же фазе в
`ARCHITECTURE.md`: документ описывал намерение как состоявшийся факт — с той
разницей, что здесь неверное утверждение касалось **доказательности самой
фазы**, а такое дороже всего.

Каждое свойство названо вместе с тестом, чтобы утверждение можно было
проверить, а не принять на слово.

| свойство | тест |
|---|---|
| контракт: `var _ ports.P2P`, `var _ ports.Session` | compile-time, начало `pion_test.go` |
| полный цикл двух агентов в одном процессе на loopback | хелпер `connect`, используется всеми сессионными тестами |
| bidi-потоки | `TestBidirectionalStream` |
| **обязательные uni-streams** (ADR-016) | `TestUniStream` |
| виды потоков не путаются между очередями | `TestStreamKindsAreNotMixedUp` |
| `Peer()` возвращает подтверждённый ключ | `TestSessionPeerIsAuthenticated` |
| подмена ключа в handshake — терминальный отказ | `TestPeerMismatchIsTerminal`, `TestExpectedPeerCheckIsIndependent` |
| подпись в чужом домене (`device-auth`, `plugin-sign`) не проходит | `TestForeignDomainSignatureDoesNotVerify`, `TestTranscriptIsDomainSeparated` |
| границы полей transcript кодируются явно | `TestTranscriptFieldBoundariesAreExplicit` |
| в transcript входят оба nonce и channel binding | `TestTranscriptBindsBothNonces` |
| битые блобы отвергаются разбором, а не таймаутом | `TestMalformedBlobs` |
| отмена `ctx` в `CreateOffer` и `AcceptOffer` | `TestContextCancellation` |
| отмена `ctx` в `CompleteSession` — до вызова и **после возврата** | `TestCancellationAbortsEstablishment` |
| отмена после возврата из `AcceptOffer` | `TestCancelAfterAcceptOfferReturnAbortsNegotiation` |
| отмена после возврата из `CreateOffer` освобождает согласование | `TestCancelAfterCreateOfferReleasesPendingNegotiation` |
| потолок на незавершённом согласовании | `TestPendingOfferDoesNotOutliveEstablishTimeout` |
| handshake подчиняется контексту (молчащий собеседник) | `TestHandshakeObeysContext` |
| повторный `CompleteSession` — ошибка | `TestRepeatedCompleteSessionIsError` |
| несколько одновременных сессий к одному peer'у | `TestConcurrentSessionsToSamePeer` |
| `P2P.Close()` не закрывает живые сессии; идемпотентность | `TestAdapterCloseKeepsEstablishedSessions` |
| ни один слой Pion не пишет в stderr вызывающего | `TestEveryPionLayerGetsSilentLogger` |
| `-race` на всём перечисленном | штатный прогон |

Плюс четыре теста relay-пути из §10.2.

**Не покрыто тестами.** Свойства заявлены спецификацией и реализованы, но
утверждений о них не проверяет ничто — при регрессии молчат все тесты:

- **half-close.** `SendStream.Close()` описан в §7 как завершение отправки без
  разрыва приёма; в коде это `sctp.Stream.Close()`. Что приём после этого
  продолжает работать, не проверяется;
- **параллельные потоки** — несколько одновременно открытых потоков в одной
  сессии;
- **воспроизведение записанного handshake отвергается.** Проверен *механизм*
  (оба свежих nonce входят в transcript, `TestTranscriptBindsBothNonces`), но
  не само свойство: записанный и предъявленный заново handshake ни один тест
  не отправляет;
- **glare** (ADR-044 §7) — встречное одновременное согласование. Ни две
  независимые сессии, ни отказ у одной из сторон не проверяются.

**Покрыто частично:**

- **таймаут установления.** Потолок на согласовании, ожидающем ответа, покрыт
  (`TestPendingOfferDoesNotOutliveEstablishTimeout`); потолок на самой фазе
  установления покрыт только на шаге handshake
  (`TestHandshakeObeysContext`) — зависание внутри ICE или DTLS тестом не
  воспроизводится;
- **`failed` необратимо** (ADR-044 §4). `TestPeerMismatchIsTerminal`
  наблюдает терминальное состояние двумя разными методами (`OpenStream` даёт
  `ErrSessionFailed`, `Peer()` даёт `nil`), но что повторный вызов **того же**
  метода вернёт ту же ошибку, а не начнёт согласование заново, не
  утверждается.

Расширять фазу ради этих тестов не стали сознательно: решение — привести
документ в соответствие с кодом, а не код в соответствие с документом.
Записано здесь, а не потеряно в истории обсуждения.

### 10.2 Relay-путь: проверяется локально, сетевых условий не доказывает

TURN-сервер поднимается **в том же процессе** (`pion/turn/v3`, уже
присутствовал в графе как транзитивная зависимость `ice`) на loopback.
Проверяется: `ForceRelay` исключает host/srflx **целиком** (а не понижает
приоритет — иначе на loopback победил бы host и прогон шёл бы мимо TURN),
аллокация проходит, выбранная пара действительно relay, по ней идут данные;
плюс два немедленных отказа из §9.

Это **путь**, а не traversal. Сервер свой, на loopback, сетевых условий нет
вовсе. Прежде `ForceRelay` был флагом, который не исполнял никто, — ровно то
состояние, ради предупреждения о котором §10.3 и написан.

### 10.3 Требует сети — и не смешивается с п. 10.1 и 10.2

- **real-network direct acceptance** — согласование между двумя хостами по
  настоящей сети, direct-пара. **Выполнен**;
- **TURN relay acceptance** — тот же прогон через **внешний** TURN, с
  принудительным исключением host/srflx-кандидатов. **Выполнен**;
- **полноценный symmetric-NAT сценарий** — узел за симметричным NAT, где
  direct невозможен по природе сети. **Открыт.**

Выполненное — две физические машины (локальная за VPN-туннелем и VPS с
публичным адресом), внешний coturn, доказательства с обеих сторон плюс
журнал самого TURN-сервера. Подробности и точные формулировки того, чем эти
прогоны **не** являются, — `adapters/pion/IMPLEMENTATION_LOG.md`.

Существенная деталь методики: direct-прогон шёл при **доступном** TURN, а не с
убранным из конфигурации. Relay-кандидаты были собраны обеими сторонами и не
были выбраны. Без доступного relay проверка «direct выбирается» не измеряла бы
ничего.

**Эти три — разные утверждения.** Прогон между машиной за домашним NAT и
хостом с публичным адресом является первым, может быть вторым при
принудительном relay, и **не является третьим**. Называть его «проверкой
обхода симметричного NAT» нельзя: если direct установился, relay не проверен;
если relay включён принудительно, проверен путь, а не сетевые условия.

Loopback из п. 10.1 доказывает протокол, п. 10.2 — relay-путь; traversal не доказывает ни то, ни другое. Это
тот же класс ошибки, что зелёный тест на фиктивном транспорте в Phase 12.5.

## 11. Что останется непроверенным

Записывается заранее, чтобы не «дореализовывать» молча. Это список **свойств
сети и рантайма**; свойства, не покрытые тестами при существующей реализации,
перечислены отдельно, в конце §10.1:

- поведение при потере сети посреди сессии (ICE-restart портом не выражен);
- одновременные сессии в количестве, где начинает мешать один ICE-агент;
- работа за симметричным NAT, если такого узла не окажется;
- мобильные сети и смена интерфейса;
- стоимость handshake и согласования — измеряется, не оценивается.
