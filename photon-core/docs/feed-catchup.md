# Догрузка после offline: сегменты и пропуски

**Статус:** спецификация. Написана **до** кода — Phase 12, второй вертикальный
срез. Первый срез (`localfeed`, «пролистать историю назад») закрыт коммитом
`440ee8d`.

**Сценарий:** «вернуться в канал после offline и увидеть новое, не получив ни
дубля, ни **молчаливого** пропуска».

---

## 1. Почему именно этот сценарий

Его назвал сам журнал первого среза
(`services/localfeed/IMPLEMENTATION_LOG.md` §4):

> Курсор оказался достаточен для чтения истории; водяной знак нужен для
> догрузки нового и остаётся неопределённым.

Три независимых довода за то, что он следующий:

1. **Уже оплачен.** `after` есть в `photon.proto`, реализован в обработчике
   Bridge и покрыт тестом `TestP12_FeedAfterUsesCursorAPI` — и **не используется
   ни одним потребителем**. Код без потребителя не доказан;
2. **Phase 15.5 оставила прямое требование.** В конверте push нет ни номера, ни
   версии, поэтому **пропуск нельзя обнаружить по потоку событий** — только
   сверкой с сервером. Сверка и есть этот срез. Без неё доставка событий
   остаётся «lossless не заявляется» и заявить будет нечем;
3. **Это первый сценарий, где локальная БД перестаёт быть множеством записей.**
   Пролистывание назад работало с любым подмножеством. Догрузка требует знать,
   **что именно известно** — иначе «между этими двумя сообщениями ничего не
   было» и «между ними я ничего не знаю» неразличимы.

---

## 2. Что меняется в границах

**Ничего замороженного.** Проверено по списку, а не по ощущению:

| граница | затронута | почему |
|---|---|---|
| `ports/*.go` | **нет** | используются `Put`/`Get`/`Delete`/`ForEachPrefix`/`ForEachPrefixFrom` как есть |
| `ports.Storage`, новые примитивы | **нет** | сегменты — обычная запись под своим ключом |
| C ABI | **нет** | срез не выходит за `services/` и `cmd/` |
| SDK, plugin runtime | **нет** | — |
| protobuf, Bridge | **нет ожидаемо** | `before`/`after`/`limit` уже есть; проверяется живым прогоном (§7) |

Поэтому **отдельного ADR не требуется**. `services/localfeed` объявлен
переписываемым свободно (ADR-046 §6.1, шапка пакета): пока паттерн доступа не
наблюдался, синхронизация не становится публичным контрактом. Решение о
заморозке принимается позже и отдельно.

## 3. Модель

### 3.1 Позиция

```
Position = (OrderKey int64, ID string)
```

Порядок **обязан совпадать с порядком обхода ключей**, иначе сравнение позиций
и обход разойдутся молча:

```
newer(a, b)  ⇔  a.OrderKey > b.OrderKey
              ∨ (a.OrderKey == b.OrderKey ∧ a.ID < b.ID)
```

Инверсия по `ID` не описка. Ключ записи —
`<channel> 0x00 <inv(OrderKey) BE> <ID>`; возрастающий байтовый обход даёт
`OrderKey` по убыванию, а при равном `OrderKey` — `ID` **по возрастанию**.
Значит в порядке «свежие первыми» среди одинакового `OrderKey` первым идёт
**меньший** `ID`, то есть он и считается более свежим. Ровно это и записано
выше.

### 3.2 Сегмент

```
Segment = [Oldest .. Newest]        // обе границы включительно
```

Смысл: **между `Oldest` и `Newest` локально лежит КАЖДАЯ запись, которая была у
сервера на момент выборки.** Это утверждение о полноте, а не о содержимом.

Канал описывается **списком сегментов**, упорядоченным «свежие первыми» и
непересекающимся. Между соседними сегментами — **пропуск**.

### 3.3 Хранение

Список сегментов канала — **одна запись** под ключом `<channel> 0x01`.
Пространство записей (`<channel> 0x00 …`) не задевается: байты разделителя
различаются, поэтому `ForEachPrefix` записей сегменты не видит.

Одна запись, а не запись на сегмент, выбрана осознанно: сегментов единицы,
операция всегда затрагивает список целиком (слияние), и одна запись даёт
атомарность внутри той же транзакции без согласования нескольких ключей.
Стоимость `O(#сегментов)` на разбор — измеряется (§6), а не предполагается.

## 4. Операции

### 4.1 `Ingest(channelID, block)` — записать блок и объявить, что он доказал

`Block` — результат **одного** ответа сервера:

```go
type Block struct {
    Records []Record   // порядок безразличен, Ingest упорядочит
    Anchor  *Position  // курсор запроса; nil = «с самых свежих»
    Dir     Direction  // DirNewest | DirAfter | DirBefore
    AtEnd   bool       // сервер вернул меньше запрошенного
}
```

Покрытие блока:

| `Dir` | сегмент блока | слияние |
|---|---|---|
| `DirNewest` | `[oldest(block) .. newest(block)]` | по **пересечению** позиций |
| `DirAfter` (якорь A) | `[A .. newest(block)]` | по **якорю**: A принадлежит известному сегменту ⇒ непрерывность доказана сервером |
| `DirBefore` (якорь A) | `[oldest(block) .. A]` | по **якорю** |

**Слияние по якорю сильнее слияния по пересечению**, и это главное свойство
модели. Ответ на `after: A` доказывает, что между `A` и верхом блока сервер
ничего не пропустил, — даже если блок и старый сегмент не имеют ни одной общей
записи. Пересечением такое не выводится.

**Асимметрия, принимаемая сознательно:** два сегмента, лежащие вплотную, но не
пересекающиеся и не связанные якорем, считаются **разделёнными пропуском**.
Пропуск может оказаться пустым — его закрытие вернёт ноль записей и сомкнёт
сегменты. Обратная ошибка — счесть непрерывным то, что непрерывным не
доказано, — даёт **тихую дыру** в истории. Направление ошибки выбрано в
безопасную сторону и проверяется тестом.

Пустой блок (`len(Records) == 0`) с якорем и `AtEnd` — законный случай и
означает «за якорем ничего нет»: сегмент якоря продлевается до верха канала,
пропуск закрывается.

### 4.2 `Page(...) → PageResult` — чтение, различающее «конца нет» и «дальше неизвестно»

```go
type PageResult struct {
    Records  []Record
    GapAfter bool   // за последней отданной записью — ПРОПУСК, не конец
}
```

Обход **останавливается на границе сегмента**. Прежняя сигнатура
(`[]Record, error`) удалена, а не оставлена рядом: вариант, не умеющий сообщить
о пропуске, — это ровно тот вызов, которым тихая дыра и попадает на экран.
Оставить оба значило бы оставить ловушку и надеяться на дисциплину.

### 4.3 `GapAnchor(channelID) → (Position, bool)`

Позиция, которую следует передать как `after`, чтобы закрыть **самый верхний**
пропуск: это `Newest` сегмента, лежащего **под** пропуском.

Не «самая свежая локальная запись»: она лежит **над** пропуском, и запрос от
неё вернёт то, что уже известно, оставив дыру нетронутой навсегда.

### 4.4 `Watermark(channelID) → (Position, bool)`

Самая свежая локальная позиция. Нужна для дозагрузки поверх верхнего сегмента,
а не для закрытия пропусков — это разные вопросы и разные ответы (§4.3).

## 5. Сценарий целиком

```
1. reopen           → getFeed(channel, limit)        → Ingest(DirNewest)
2. если пропуск     → показать маркер, не склеивать
3. закрыть пропуск  → getFeed(after: GapAnchor())    → Ingest(DirAfter)
4. повторять 3, пока GapAnchor не исчезнет
5. offline reopen   → только Page(), сети не касаться
```

Шаг 4 обязан **сходиться**: каждый ответ либо продвигает якорь, либо приходит
пустым с `AtEnd` и закрывает пропуск. Отсутствие продвижения — ошибка, а не
повод для ещё одной итерации; цикл имеет предел (урок ADR-047: цикл без предела
превращает дефект в зависание).

---

## 6. Что измеряется

Раздельно и без смешивания:

- **локально:** просмотрено/отдано на `Page` при наличии пропусков; стоимость
  `Ingest` в зависимости от числа сегментов; число сегментов после N reopen'ов
  без закрытия пропусков;
- **по сети:** время ответа Bridge на `getFeed` — **отдельной колонкой**,
  никогда не в сумме с локальным.

---

## 7. Что обязан показать живой прогон

Главный неизвестный факт, который нельзя вывести из кода:

> **С какого конца `GetPostsAfter` отдаёт записи** — ближайшие к якорю или
> самые свежие в канале?

Сходимость §5 шага 4 требует **ближайших к якорю**. Если Mattermost отдаёт
самый свежий конец, пропуск не закроется никогда, и это будет находкой о
Bridge, а не о Core. Проверяется прямым сравнением: закрыть пропуск шириной
больше одной страницы и посмотреть, какие именно записи пришли первыми.

---

## 8. Что НЕ входит

- **push и слияние с событиями** — Phase 15.5 доставляет события, но сверка с
  ними отдельный вопрос; здесь сверка идёт с ответом на запрос;
- **вытеснение и квоты** — сегменты растут, ограничение не вводится до
  наблюдения;
- **удаление записей** — `delete_at` в теле есть, но чистка ленты не входит;
- **несколько источников** — сравнение версий не делается, источник один;
- **обобщение на другие сущности** — по-прежнему один канал, одна лента.
