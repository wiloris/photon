# TCP Multiplexing Wire Format

Спецификация кадрирования для `adapters/tcp`. Зафиксирована **до** написания
кода, чтобы формат выводился из требований `ports.Connection`, а не из
удобства реализации или копирования QUIC.

## Зачем это нужно

`ports.Connection` (заморожен, ADR-020) обещает несколько независимых потоков
внутри одного соединения. QUIC даёт это нативно. TCP — нет: это один
непрерывный байтовый поток. Поэтому TCP-адаптер обязан построить
мультиплексор поверх сокета:

```
QUIC:                          TCP:
Connection                     Connection
├── Stream 1                    └── один байтовый поток
├── Stream 2                          ↓ framing
├── Stream 3                    ├── logical stream 1
└── UniStream                   ├── logical stream 2
                                └── logical stream 3
```

Порт при этом **не знает**, что под ним TCP — это принцип ADR-011/013.

## Принцип минимальности

Формат выводится из того, что порт реально требует, а не из полного набора
возможностей QUIC.

**Что порту нужно:**

| Требование порта | Следствие для формата |
|---|---|
| `OpenStream` / `AcceptStream` | кадр открытия bidi-потока |
| `OpenUniStream` / `AcceptUniStream` | тот же кадр + флаг направления |
| `Stream` как `io.Writer`/`io.Reader` | кадр данных |
| `SendStream.Close` = half-close (приём остаётся) | кадр «конец отправки» |
| `Connection.Close` закрывает всё | аварийное закрытие потока |

**Чего сознательно НЕТ** (есть в QUIC, но порт не требует):

- flow control windows (`WINDOW_UPDATE`) — см. раздел Backpressure ниже;
- приоритеты потоков;
- 0-RTT, миграция соединения, key update;
- datagram-режим;
- коды ошибок приложения в закрытии соединения (`Close() error` достаточно).

Добавлять это «на будущее» означало бы построить собственный протокол
вместо минимального кадрирования — прямое нарушение ADR-013.

## Формат кадра

Заголовок фиксированной длины — 12 байт, big-endian:

```
 0        1        2        3        4                8               12
 +--------+--------+--------+--------+----------------+----------------+
 | ver    | type   | flags  | rsvd   |   stream_id    |     length     |
 +--------+--------+--------+--------+----------------+----------------+
 |                          payload (length байт)                      |
 +---------------------------------------------------------------------+
```

| Поле | Размер | Описание |
|---|---|---|
| `ver` | 1 байт | Версия формата. Сейчас `1`. Кадр с другой версией → соединение закрывается |
| `type` | 1 байт | Тип кадра (см. ниже) |
| `flags` | 1 байт | Битовые флаги, зависят от типа |
| `rsvd` | 1 байт | Зарезервировано, обязано быть `0` |
| `stream_id` | 4 байта | Идентификатор логического потока |
| `length` | 4 байта | Длина payload. `0` допустим |

### Типы кадров

| Значение | Имя | Payload | Описание |
|---|---|---|---|
| `0x01` | `OPEN` | пусто | Открыть поток `stream_id` |
| `0x02` | `DATA` | данные | Данные потока |
| `0x03` | `FIN` | пусто | Отправляющая сторона завершила передачу (half-close) |
| `0x04` | `RESET` | пусто | Аварийное закрытие потока |

Неизвестный `type` → соединение закрывается (не игнорируется молча:
неизвестный кадр означает рассинхрон или атаку).

### Флаги

Для `OPEN`:

| Бит | Имя | Описание |
|---|---|---|
| `0x01` | `FLAG_UNI` | Поток однонаправленный (только от инициатора к принимающему) |

Для остальных типов `flags` обязано быть `0`.

## Нумерация stream_id

Обе стороны открывают потоки независимо, поэтому пространство ID разделено
по чётности — иначе два одновременных `OpenStream` с разных сторон
столкнулись бы на одном ID:

- **чётные** (`2, 4, 6, ...`) — открывает сторона, инициировавшая TCP-соединение (клиент);
- **нечётные** (`1, 3, 5, ...`) — открывает принимающая сторона (сервер);
- `0` не используется (упрощает отладку: `stream_id == 0` всегда ошибка).

Тот же принцип, что в QUIC и HTTP/2, и по той же причине.

## Жизненный цикл потока

```
        OPEN
          ↓
    ┌─────────────┐
    │    OPEN     │  оба направления активны
    └─────────────┘
       ↓        ↓
  FIN(local)  FIN(remote)      half-close: одна сторона закончила,
       ↓        ↓              другая продолжает передавать
    ┌─────────────┐
    │ HALF-CLOSED │
    └─────────────┘
       ↓        ↓
  FIN(remote) FIN(local)
          ↓
     ┌─────────┐
     │ CLOSED  │
     └─────────┘

RESET из любого состояния → CLOSED немедленно
```

Соответствие контракту порта:

- `SendStream.Close()` → отправляет `FIN`. Приём остаётся открытым — ровно
  то, что обещает порт («завершает отправку (half-close), не закрывая приём»).
- Получение `FIN` → `Read` возвращает накопленные данные, затем `io.EOF`.
- Получение `RESET` → `Read`/`Write` возвращают ошибку.
- `Connection.Close()` → закрывает TCP-сокет; все ожидающие `Read`/`Write`
  на логических потоках разблокируются с ошибкой.

## Backpressure

**Отдельного механизма нет — и это осознанно.**

Писатель логического потока держит мьютекс сокета на время записи одного
кадра. Если удалённая сторона не читает, TCP-окно закрывается, `Write` в
сокет блокируется, и вместе с ним блокируется писатель — backpressure
работает средствами самого TCP.

Ограничение этого подхода: медленный читатель одного логического потока
тормозит **все** потоки соединения (head-of-line blocking). Это неизбежное
свойство TCP как транспорта — именно поэтому TCP здесь **резервный**
транспорт, а основной — QUIC, где потоки независимы. Реализовывать
собственные flow-control окна поверх TCP означало бы строить второй QUIC,
не имея его главного преимущества (независимости потоков на уровне UDP).

Чтобы один писатель не захватывал соединение надолго, `DATA`-кадр
ограничен по размеру (см. ниже) — крупная запись режется на несколько
кадров, между которыми другие потоки получают доступ к сокету.

## Ограничения и защита от некорректных данных

Парсер разбирает **недоверенные** байты из сети, поэтому:

| Проверка | Реакция |
|---|---|
| `ver != 1` | закрыть соединение |
| неизвестный `type` | закрыть соединение |
| `rsvd != 0` | закрыть соединение |
| `flags` ненулевые для не-`OPEN` | закрыть соединение |
| `length > maxFrameSize` (64 KiB) | закрыть соединение, **не** аллоцировать буфер |
| `stream_id == 0` | закрыть соединение |
| `OPEN` для уже существующего `stream_id` | закрыть соединение |
| `DATA`/`FIN`/`RESET` для неизвестного `stream_id` | игнорировать кадр (гонка: поток мог быть закрыт локально, пока кадр был в пути) |
| `OPEN` с `stream_id` неверной чётности | закрыть соединение |

Ключевое: проверка `length` выполняется **до** выделения памяти. Иначе кадр
с `length = 0xFFFFFFFF` вызвал бы попытку аллокации 4 ГиБ — тривиальный DoS.

`maxFrameSize` = 64 KiB: достаточно, чтобы не резать типичные сообщения на
множество кадров, и достаточно мало, чтобы вредоносный кадр не выедал память.

## Что должно быть покрыто тестами

1. Frame encode/decode round-trip для всех типов
2. Один TCP-сокет → несколько logical streams, данные не перемешиваются
3. Параллельная запись из нескольких горутин (обязательно под `-race`)
4. Half-close: `FIN` → читатель получает данные, затем `io.EOF`
5. `RESET` → ошибка на обеих сторонах
6. Peer shutdown: закрытие TCP разблокирует ожидающие `Read`
7. Malformed frames: каждая строка таблицы выше
8. `length` за пределом → нет аллокации, соединение закрыто
9. Fuzzing декодера — парсер разбирает недоверенный вход
10. Совместимость с `ports.Transport`: те же тесты контракта, что у `adapters/quic`
