## Решено внутри адаптера

### PublicKeyOf без вычислений на кривой

**Потребовалось:** `ports.Identity.PublicKeyOf` — получить публичный ключ из приватного.

**Решение:** Приватный ключ Ed25519 в `crypto/ed25519` — 64 байта, где последние 32 байта уже являются публичным ключом (seed + public key, а не только seed). Извлечение — чтение среза, не пересчёт точки на кривой. `stded25519.PrivateKey.Public()` делает это за нас.

**Почему не потребовало правки порта:** контракт `PublicKeyOf` не обещает и не запрещает конкретный способ получения публичного ключа — адаптеру с другой схемой (например, где приватный ключ — только seed) пришлось бы явно вычислять публичный ключ, но сигнатура порта остаётся той же в обоих случаях.

### Единая ErrInvalidKey на все виды некорректной длины

**Потребовалось:** обработать некорректную длину приватного ключа (`PublicKeyOf`, `Sign`), публичного ключа и подписи (`Verify`).

**Решение:** `ports.ErrInvalidKey` уже существовал в `errors.go` (введён для Crypto port) и подошёл без изменений — сентинел общий для пакета `ports`, не привязан к одному порту.

**Почему не потребовало правки порта:** ADR по `errors.go` ("новая sentinel-ошибка только если вызывающий код должен принять другое решение") сработал ровно так, как задумано — не пришлось заводить `ErrInvalidPrivateKeyLength`/`ErrInvalidPublicKeyLength`/`ErrInvalidSignatureLength` по отдельности.

### PublicKeyOf возвращал срез с общим backing array с приватным ключом

**Потребовалось:** обнаружено при внешнем ревью — `priv.Public()` в стандартной библиотеке возвращает срез, указывающий на те же байты, что и сам приватный ключ (Ed25519: публичный ключ физически хранится как последние 32 байта 64-байтного приватного ключа).

**Решение:** `PublicKeyOf` копирует байты перед возвратом — тот же принцип, что копирование значений в `adapters/bbolt`.

**Почему не потребовало правки порта:** контракт `ports.Identity.PublicKeyOf` не специфицирует внутреннее представление ключей — только то, что возвращаемый `PublicKey` корректен и независим. То, что `crypto/ed25519` физически хранит их в одном массиве, — деталь конкретной реализации, полностью решаемая копированием внутри адаптера. Покрыто regression-тестом (`TestPublicKeyOf_ReturnsIndependentCopy`), потому что ошибка была бы "тихой" — до случайной мутации приватного ключа после вызова `PublicKeyOf` всё выглядело бы рабочим.
