# livecheck — ручной прогон против живого Bridge

**Не автотест.** В `go test ./...` не участвует и участвовать не должен:
требует развёрнутого `photon-quic-bridge` и действующего Session ID. Тест,
зависящий от внешнего сервера, либо делает прогон недетерминированным, либо
тихо пропускается — и тогда он хуже отсутствующего.

`package main`, а не `_test.go`, именно поэтому: `go test` его не подхватывает,
`go build ./...` — собирает, так что расхождение с API пакета сломает сборку, а
не останется незамеченным.

## Зачем

`services/session` тестируется против фиктивного транспорта на `net.Pipe`. Тот
не воспроизводит ни таймингов сети, ни поведения QUIC при обрыве — и это не
теория: первый же прогон этим инструментом нашёл две вещи, которых не находили
29 зелёных тестов (`docs/bridge-session.md` §9).

Тест-клиент Bridge (`test-client/test_photon.go`) проверяет **сервер** и ходит
в `quic-go` напрямую. Его прохождение не доказывает, что работает этот пакет:
это другая реализация того же протокола. Здесь всё идёт через
`ports.Transport`/`adapters/quic`, как положено коду ядра (ADR-020).

## Запуск

```sh
go run ./tests/livecheck -mode subscribe -session <Session ID>   # приём push
go run ./tests/livecheck -mode subscribe -session <ID> -trigger  # то же, push порождает сам
go run ./tests/livecheck -mode action    -session <Session ID>   # getMe, getMyChannels
go run ./tests/livecheck -mode lost      -session <Session ID>   # обрыв по idle-timeout
go run ./tests/livecheck -mode dispatch  -session <Session ID>   # через services/dispatcher
```

Код возврата — часть результата: любое нарушенное ожидание печатается как `❌`
и даёт выход с 1. Печать без ненулевого кода — тот же дефект, что зелёный тест,
проходящий всегда.

`-session` — **Session ID** (`Session.Id`), а не токен из `/users/login`. Имя
поля `session_token` на проводе историческое (§2.1). Значение живёт до логаута,
не дольше 30 дней, поэтому флаг, а не константа.

Прочие флаги: `-addr` (по умолчанию `vpn.wiloris.ru:4443`), `-keepalive`
(0 — как в проде), `-wait`, `-lost-window`, `-insecure` (только для
самоподписанных), `-trigger` (см. `subscribe` ниже).

## Режимы

| Режим | Что проверяет | Требует участия человека |
|---|---|---|
| `subscribe` | `AcceptPush`, разбор `Push`, значение `UserID` | нет с `-trigger`; без него — отправить сообщение в Mattermost |
| `action` | `Do`, положительный и отрицательный ответ | нет, обе операции читающие |
| `lost` | `ErrConnectionLost`, состояние, повторный вызов | нет — но сообщений слать НЕЛЬЗЯ, push отменит проверку |
| `dispatch` | `services/dispatcher`: подключение по требованию, переиспользование соединения, синглфлайт, конверт ответа, отказ сервера как `ok:false`, обрыв → `not_connected`, переподключение | нет, все операции читающие |

`dispatch` появился в Phase 13.5 и проверяет **другой слой**, а не тот же
другим способом: `action` гоняет `services/session` напрямую, `dispatch` — путь
`Photon_SendAction` целиком, кроме самой границы C. Саму границу C проверяет
`photon-bindings/c/livecheck_bridge.c` — отдельная программа против собранной
`.so`, см. `photon-bindings/c/README.md`.

### `-trigger`: подписка без человека

Прогон, требующий «отправьте сообщение руками», не повторяем: его нельзя ни
включить в регрессию, ни выполнить в другой среде. С `-trigger` инструмент
порождает push сам — открывает **второе** соединение в режиме `action` (push и
action на одном соединении не сосуществуют, §2.4), создаёт сообщение в
самопереписке (direct channel с самим собой) и удаляет его после приёма push.
Посторонних это не касается и следов не оставляет.

Первый запуск на свежем аккаунте может принять `channel_updated` вместо
`posted`: канал самопереписки создаётся тем же вызовом. На втором запуске канал
уже есть, и приходит `posted`.

### Чем `dispatch` доказывает свои утверждения

Транспорт обёрнут счётчиком подключений (`counting.go`). Без него два
утверждения фазы недоказуемы:

- «неизвестный код отвергается **без сети**» — быстрый ответ доказательством не
  является; доказательство в том, что счётчик остался нулевым. Мутация,
  переносящая проверку кода после `ensureReady`, оставляет ответ мгновенным и
  правильным по классу — и ловится только счётчиком;
- «второй вызов **переиспользует** соединение» — то же самое.

Счётчик **не** доказывает синглфлайт: `session.Connect` защищает себя сам, и с
убранным синглфлайтом подключение всё равно происходит один раз. Признак
поломки — `ErrConnectInProgress` у части параллельных вызовов; проверено
мутацией (убран синглфлайт → три вызова из четырёх падают, счётчик
по-прежнему 1).

Обрыв в `dispatch` — закрытие живого QUIC-соединения снизу, из-под сессии.
Соединение то самое, по которому только что шли вызовы; штатный idle-timeout
для этого не годится, потому что на сервере стоит `KeepAlivePeriod` (см. `lost`
ниже).

`lost` рассчитан на **штатный** idle-timeout: клиент keep-alive не шлёт, и если
сервер тоже не шлёт, обрыв приходит на 30-й секунде.

С включённым на сервере `KeepAlivePeriod` этот режим обрыва получать **не
должен** — вторая его роль — обратная проверка keep-alive. Три исхода
различаются явно, и `DeadlineExceeded` здесь **успех**, а не отказ:

| Вывод | Код | Что означает |
|---|---|---|
| `ErrConnectionLost` через ~30 с | 0 | сервер keep-alive не шлёт |
| `обрыва не было за N`, `state=ready` | 0 | keep-alive работает |
| `пришёл push` | 0 | проверка не состоялась, кто-то отправил сообщение |
| что-то ещё, либо `state != ready` | 1 | разбираться |

Проверка `state=ready` в успешном исходе не декоративная: она отличает «связь
жива» от «обрыв случился, но `AcceptPush` его не заметил и досидел до конца
окна». Второе означало бы дефект в `markLost` и выглядело бы точно так же.

Окно задаётся `-lost-window` (по умолчанию 150 с) и должно заметно превышать
idle-timeout.

Аварийный обрыв (потеря сети, убитый процесс) режим не воспроизводит; порядок
ошибок там может отличаться.
