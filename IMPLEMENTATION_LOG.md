# photon-quic-bridge — IMPLEMENTATION_LOG

Почему решения приняты именно так и что намеренно не сделано. Серверная
половина; всё, что относится к клиентскому слою сессии, — в
`photon-core/services/session/IMPLEMENTATION_LOG.md`.

Заведён задним числом: находки по серверу какое-то время лежали в логе Core,
потому что там шла работа. Место неверное — открывший этот репозиторий их там
не найдёт.

---

## Что это за репозиторий

Плагин Mattermost, выросший из `mattermost-plugin-starter-template`. Даёт
клиентам Photon транспорт QUIC поверх Mattermost API: handshake с авторизацией
по сессии, action-режим (запрос-ответ по bidi-стримам) и subscribe-режим
(push-события по uni-стримам).

Протокол ему **не принадлежит**: action-коды — алиасы на `enum Action` из
`photon-core/protobuf` (ADR-025). Core и Bridge — равноправные потребители
одного контракта, ни один не объявляет его самостоятельно.

`replace` на `photon-core` указывает на **относительный путь**
(`../photon/photon-core`): репозиторий собирается только когда лежит рядом с
`photon`. Ограничение записано комментарием в `go.mod`; снимается публикацией
`photon-core`, не раньше.

## Найдено разбором кода

### Выбор сертификата проверял существование, а не пригодность

`findCert` шёл через `os.Stat`. Порядок из трёх кандидатов (Caddy по домену из
`SiteURL` → любой домен в каталоге Caddy → `ServiceSettings.TLSCertFile`)
выглядел как отказоустойчивость, но ею не был: после выдачи процессу
Mattermost прав на обход каталогов Caddy `stat` проходит всегда, первый
кандидат выигрывает всегда, а нечитаемый или битый файл даёт отказ вместо
отката на следующий вариант.

Исправлено (`a6ac6ba`): промежуточной проверки нет вовсе, кандидаты
перебираются с немедленным `tls.LoadX509KeyPair`, первый успех выигрывает. Это
разом проверяет существование, права, разбор PEM **и совпадение пары
`.crt`/`.key`** — последнее до этого не проверялось нигде вплоть до подъёма
листенера.

Отбраковка каждого кандидата пишется `LogWarn` с источником, путями и
причиной. Молчаливое падение на следующий вариант и скрывало проблему прав:
оба пути через Caddy проваливались беззвучно, оставался третий, а при пустом
`TLSCertFile` — ни одного, и дальше срабатывала ловушка «`OnActivate`
возвращает `nil` при отказе TLS».

Скан каталога Caddy перечисляет **все** домены, а не первый попавшийся: если у
одного права не те, следующий должен получить свой шанс. Пары дедуплицируются,
чтобы домен из `SiteURL` не дал два одинаковых предупреждения.

### `certCache`: отложенный отказ плюс повтор на каждом handshake

Два разных дефекта в одной ветке кода, и путать их не надо.

**1. Отказ невидим, и это отложенный отказ, а не восстановление.** При
неудачном перечитывании кэш возвращал старый сертификат из памяти без единой
записи в лог. Снаружи всё продолжает работать — до первого рестарта, когда
старого сертификата в памяти уже нет: `getTLSConfig` возвращает ошибку,
`OnActivate` по своей отдельной ловушке всё равно возвращает `nil`, и плагин
числится активным без листенера. Реальный сценарий: Caddy продлевает
сертификат каждые ~60 дней и перезаписывает `.crt`/`.key` с правами `0600`,
после чего процесс Mattermost их не читает. Промежуток между причиной
(продление) и симптомом (падение на первом же сообщении после рестарта) —
недели. Исправлено: `LogError` с обоими путями, причиной и временем последней
успешной загрузки.

**2. `loadedAt` при ошибке не обновляется — и это НЕ блокировка повторов.**
Поле пишется только на успешной загрузке. При ошибке оно остаётся старым,
поэтому условие `time.Since(c.loadedAt) < 12*time.Hour` больше никогда не
выполняется, и **каждый** следующий `get()`, то есть каждый TLS-handshake,
заново берёт write-lock и заново читает файл с диска. Ошибочно было бы описать
это как «кэш заблокировал повторные попытки до рестарта»: повторы не
прекращаются, они происходят слишком часто. Цена — не отсутствие
восстановления (оно произойдёт сразу, как только права починят), а то, что все
handshake'и сериализуются на write-lock вокруг неуспешного файлового чтения,
пока проблема держится.

Второй пункт **намеренно не исправлен**: сам по себе он безвреден при
работающем сертификате (в норме ветка не достигается), а лечится либо
интервалом повтора при ошибке, либо счётчиком неудач — и то и другое добавляет
состояние, которое нечем проверить без единого теста на `server/` (см. ниже).

### Зелёный `go test` здесь не означает, что Photon чем-то покрыт

`go test ./server/...` проходит, и это легко прочитать как «тесты зелёные». Что
он на самом деле прогоняет:

| Тест | Что проверяет |
|---|---|
| `server/plugin_test.go` → `TestServeHTTP` | boilerplate-роут `/api/v1/hello` starter-template |
| `server/command/command_test.go` → `TestHelloCommand` | slash-команду `/hello` оттуда же |

Оба достались от шаблона и к Photon отношения не имеют. Из **17** файлов в
`server/` тестами не покрыт ни один значимый: `quic_listener.go`,
`dispatcher.go`, `push.go`, `hooks.go`, `api.go`, шесть `handler_*.go`.
`plugin_test.go` конструирует `Plugin{}` напрямую и до `OnActivate` — а значит
и до QUIC-листенера — не доходит вовсе.

Практическое следствие: **прохождение `go test ./server/...` не подтверждает
ничего из работы Photon.** Единственное, что этот прогон дал при переносе
ADR-025, — что новый module path не сломал компиляцию тестовых файлов.

## Найдено прогоном против живого сервера

Разбор кода этого не давал; см. также
`photon-core/docs/bridge-session.md` §9.

### Подписка умирала через 30 секунд простоя

Два независимых замера дали 30,5 с. Ни сервер (`quic.Config` без
`KeepAlivePeriod`), ни клиент (`nil`-конфиг) keep-alive не слали — эффективный
простой это `DefaultIdleTimeout` quic-go, 30 с.

Для action-соединения почти не проявляется: его держит трафик запросов. Для
подписки — наоборот, тишина и есть нормальное состояние, поэтому обрыв
наступает **штатно**, а не в аварии. Канал без сообщений полминуты роняет
соединение; сервер по `watchClose()` снимает клиента с регистрации, push
перестаёт доставляться, и приложению об этом не сообщает никто.

Поэтому `KeepAlivePeriod: 15s` (`b2c45b5`) — не настройка производительности, а
недостающая часть механизма подписки. 15 с это половина idle-timeout: при
потере одного keep-alive второй успевает дойти до истечения окна.

**Проверено на развёрнутом сервере, обратной проверкой.** До установки сборки с
`KeepAlivePeriod` прогон `photon-core/tests/livecheck -mode lost` получал обрыв
на 30-й секунде — воспроизводимо, дважды. После установки соединение пережило
150 с полного молчания, состояние осталось `ready`.

Форма проверки тут важнее результата: подтверждается **отсутствие** события.
Единственный способ это сделать — сначала получить событие воспроизводимо,
потом устранить причину и убедиться, что оно исчезло. Прямая проверка
(«keep-alive отправляется», видно в трассировке) подтвердила бы отправку
пакетов, но не то, ради чего всё делалось — что подписка перестала умирать.

### `user_id` верхнего уровня в push-событии обычно отсутствует

Поле объявлено с `json:"user_id,omitempty"` (`push.go:14`), а из **восьми**
хуков заполняет его ровно **один** — `status_change` (`hooks.go:98`). Для
остальных семи, включая `posted`, поле с провода исчезает; идентификатор автора
лежит в `data.user_id`.

Обещание `{"event":"posted","user_id":"...","data":{...}}` стоит в двух местах
— `server/protocol.go:23-24` и шапка `photon-core/protobuf/photon.proto:42` — и
для `posted` неверно в обоих. **Оба места не исправлены**: правка шапки
`photon.proto` — это правка Core, и делать её мимоходом из Bridge неправильно;
исправлены потребители (`bridge-session.md` §2.3 и комментарий в
`services/session/codec.go`, где утверждалось «пустой `user_id` =
широковещательное событие» — неверно).

Найдено прогоном: клиент печатал `user_id=<nil>` при полностью корректном
событии.

### `event` — строка, не enum

Подтверждено проводом: живой сервер прислал `"event":"posted"`, при том что
`photon.proto:146` объявляет `enum EventType`. Шапка `.proto` это уже
оговаривала (строки 46-47); теперь это факт, а не разбор. Тот же случай, что
`resource` и `status` — ADR-034: protobuf здесь схема, а не формат провода.

## Проверено и НЕ подтвердилось

Записывается наравне с находками: непроверенное предположение, отброшенное
проверкой, экономит время ровно так же, как подтверждённое.

### Action-код без обработчика

Проверялась гипотеза, что какой-то код `enum Action` не имеет обработчика в
`server/` — в частности `ACTION_UPDATE_WALL_POST`.

**Такого кода не существует.** `WallResource` — три кода (600 `GET_OR_CREATE_WALL`,
601 `GET_WALL_POSTS`, 602 `PUBLISH_WALL_POST`), все три имеют `case` в
`handler_wall.go`. Идентификатор `UPDATE_WALL_POST` не встречается ни в
`photon.proto`, ни в `protocol.go`, ни где-либо в этом репозитории.

Проверено систематически, а не только по Wall: **56** кодов в `enum Action`,
**56** алиасов в `protocol.go`, у **каждого** есть `case` в обработчике. Кодов
без алиаса нет, алиасов без обработчика нет.

## Известные особенности, не являющиеся дефектами кода

- **Порт `:4443` — константа** (`quic_listener.go:18`), не настройка. QUIC это
  **UDP**; в firewall нужен `udp/4443`.
- **System Console не управляет ничем.** `plugin.json` объявляет `DebugMode`,
  `configuration.go` — три поля, но `getConfiguration()` не вызывается нигде в
  `server/`. `SSEKeepAliveSec`/`ClientBufferSize` — остатки прежней
  SSE-реализации; буфер push-клиента захардкожен (`push.go:60`).
- **Буфер push — 64 события**, при переполнении события молча выбрасываются
  (`select/default` в `Broadcast`). Не проверено: требует всплеска событий и
  поднятого `net.core.rmem_max` на приёмнике, иначе потери на приёме
  смешаются со сбросом на отправке.
- **`plugin-linux-amd64` в корне репозитория — посторонний артефакт.**
  `Makefile` собирает в `server/dist/`; в бандл должен попадать оттуда.
- **`README.md` — неправленый boilerplate** starter-template. Про Photon, QUIC
  и сертификаты там нет ничего.
- **`make dist` тянет webapp** (`Makefile:278`), хотя webapp-бандл в
  `plugin.json` не объявлен. Бандл собирается вручную: бинарь в
  `server/dist/plugin-linux-amd64`, затем `plugin.json` + `assets/` +
  `public/` + `server/dist/` в каталог по `plugin_id` и `tar -czf`.

## Phase 14 — слой авторизации (ADR-039, ADR-040)

### Что было до

Ограничения доступа не существовало **как слоя**: `grep HasPermissionTo` по
`server/` давал ноль вхождений, `GetChannelMember` встречался трижды и все три
раза по существу операции, а не ради доступа. `Dispatcher.Dispatch` передавал
`userID` в handler, handler брал идентификатор объекта из payload и звал Plugin
API, который исполняется от имени сервера и прав вызывающего не проверяет.

Измерено на двух реальных аккаунтах, а не выведено: обычный пользователь читал
ленту и посты чужого приватного канала, скачивал **байты** файла по `file_id`,
писал на чужую стену, добавлял себя в закрытый канал, а поиск отдавал ему
содержимое чужой личной переписки. Mattermost на те же объекты отвечал ему
`403`.

### Форма решения и почему такая

`resolve(object) → policy(predicate) → handler`, вызов в `Dispatch` **до**
маршрутизации.

- **Проверка в `Dispatch`, а не в обработчиках.** `/api/v1/action` зарегистрирован
  без middleware (`api.go:15`) и ведёт в тот же `Dispatch`; проверка внутри
  обработчиков или в QUIC-слое оставила бы HTTP-вход открытым. Через него и
  снималась вся матрица.
- **Ни одного собственного права.** Каждое решение — вызов
  `HasPermissionTo/ToTeam/ToChannel` с константой `model.Permission*`. Причина
  не эстетическая: дефолты ролей администратор перенастраивает схемами, и
  захардкоженное правило разошлось бы с сервером при первой же смене схемы.
- **Скоуп — отдельный механизм, не замена проверки** (`scope.go`). Над
  невыборочным вызовом Plugin API никакое правило доступа утечку не чинит:
  скоуп находится внутри запроса. `SearchPostsInTeam` → `SearchPostsInTeamForUser`;
  каталог пользователей сужен командами субъекта.
- **`sanitize` — не авторизация** (`sanitize.go`). Какие поля видны, а не какие
  объекты доступны. Опции берутся у платформы (`Config.GetSanitizeOptions`),
  вычищает поля метод модели.
- **Push — отдельный ADR** (`push_router.go`, ADR-040). Предикат тот же
  `read(C)`, но вычисляется на каждого получателя, вход — событие хука, а
  стоимость — на каждое событие инстанса.

### Что намеренно не сделано

- **Кэш членства для push (вариант B ADR-040) не заводится.** Он означал бы
  собственное состояние о правах — ровно то, чего модель избегает, и промах
  инвалидации выглядел бы как утечка, а не как ошибка. Реализован вариант A.
- **`GetViewUsersRestrictions` не воспроизводится.** Функция не экспортирована
  в Plugin API; переписывать её у себя значило бы держать копию кода платформы.
  Вместо этого каталог сужен командами — сужение строго уже, чем у Mattermost
  (там к командам добавляются каналы субъекта), и следствие названо в
  `scope.go`: собеседник по личной переписке без общей команды в каталоге не
  появится.
- **`channel-member` как предикат не заводится.** Проверено на живом
  Mattermost 9.11: `pin`/`unpin` требуют `read(C)`, а не членства, и права с
  подстрокой `pin` нет ни в одной роли инстанса.

### Дефект, который нашёлся только на живом сервере

После развёртывания 0.4.0 выяснилось, что в `deletePost`/`updatePost` осталась
**прежняя проверка владельца**: `ownerSel` был добавлен в `authz.go`, но старый
код из обработчика не удалён — решение принимали оба места. Администратор с
`delete_others_posts` получал `forbidden: not the post owner`, то есть ровно тот
дефект, ради которого §3 ADR-039 и переписывался; заодно нарушался §7.3.

**Почему не поймали раньше** — существенно для метода:
`TestAuthzOwnerSelectorIsSelector` проверяет только таблицу правил и остаётся
зелёным при живом дефекте, а строка `a/102` в матрице целилась в собственный
расходный пост A, поэтому ветка «чужой пост у субъекта с правом» не
исполнялась ни разу. Тест был истинным и бесполезным для этого свойства.

Исправлено в 0.4.1: проверки сняты, добавлены тесты уровня handler'а через
настоящий `Dispatch` (мутация — возврат старой проверки — их роняет) и
недостающие строки матрицы.

### Развёртывание

`plugin.json` `0.3.0` → `0.4.0` → `0.4.1`, версия пишется в первую строку
Photon в логе (`plugin.go`). До этого версия не менялась при изменении слоя
авторизации, и после переустановки отличить сборку можно было только по
поведению. `server/manifest.go` генерируется `make apply` и в git не хранится
(`.gitignore:4`) — источник версии один, `plugin.json`.

Установка плагина и чтение лога сервера требуют `system_admin` по REST и
выполнялись владельцем; со стороны разработки сборка подтверждалась детектором
по поведению и QUIC-handshake.

1. **F6 — жизненный цикл сессии.** `GetSessionById` не проверяет ни истечение,

   субъектов. Правила есть и покрыты машинным тестом полноты; живое поведение
   не проверено, потому что каждое меняет постоянное состояние аккаунта. Ни
   PASS, ни FAIL.
3. **ADR-040, A vs C.** Выбор не сделан: нужен замер стоимости при 10 и 100
   подписчиках против задержки round-trip варианта C.
4. **Порядок веток `read(C)`** подтверждён только по исходникам — живой прогон
   его не различает.
5. **Буфер push на 64 события с молчаливым сбросом** — не тронут.

## Исчерпание кредита MAX_STREAMS (найдено 2026-09-08, исправлено)

Дефект, из-за которого **одно action-соединение переживало ровно 99 действий**,
после чего клиент вечно ждал открытия следующего стрима.

### Что было не так

`handleStream` разбирал два JSON-кадра, писал ответ и звал `stream.Close()`.
`Close()` закрывает **только сторону записи** — это прямо сказано в quic-go:

```go
// Close closes the send-direction of the stream.
// It does not close the receive-direction of the stream.
func (s *Stream) Close() error { return s.sendStr.Close() }
```

Кредит `MAX_STREAMS` возвращается только когда завершены **обе** половины
стрима (`Stream.checkIfCompleted` → `onStreamCompleted`). Приёмная половина
завершается либо чтением до EOF, либо `CancelRead`. Обработчик не делал ни
того ни другого: FIN клиента, который тот присылает уже после чтения ответа,
никто не читал.

Поэтому `DefaultMaxIncomingStreams` (100) вёл себя не как **конкурентный**
предел, а как **пожизненный для соединения**. Сотый слот занимает
handshake-стрим — отсюда ровно 99 действий.

### Как нашёлся

Не ревью и не тестом, а измерением при подготовке media-слоя: проверялся
бюджет стримов, и базовая линия «120 запрошенных → ровно 100 прошедших» три
прогона подряд не была похожа на конкурентный предел. Последовательное
открытие подтвердило: остановка на стриме №101.

Причина установлена на отдельном стенде, воспроизводящем это же кадрирование:
смена одной строки — сервер дочитывает стрим до EOF — и 150 последовательных
стримов проходят.

**Воспроизведено на живом Bridge 0.4.1** (только чтение, `getMe`):

| прогон | результат |
|---|---|
| 150 действий подряд | остановка на №100 |
| ровно 99 действий | все прошли |
| новое соединение после исчерпания | работает снова |

Дефект затрагивал **любого долгоживущего клиента**, включая
`photon-core/services/dispatcher`, который открывает стрим на каждое действие в
рамках одной сессии. Ни один прошлый live-прогон его не поймал: все делали
меньше сотни действий на соединение.

### Исправление

Одна строка в том же `defer`: `stream.CancelRead(0)`.

`CancelRead` завершает приёмную половину немедленно и **не может
заблокироваться**. Дочитывание до EOF решило бы ту же задачу, но повисло бы
навсегда на клиенте, не закрывшем свою сторону, — то есть заменило бы утечку
стрима утечкой горутины. Запрос к моменту `defer` прочитан полностью: протокол
— ровно два кадра, ответ уже отправлен.

### Чем доказано

`server/bugfix_streamcredit_test.go` поднимает **настоящий** quic-go и
**настоящий** `handleConnection`: дефект живёт в жизненном цикле стрима, и мок
транспорта его бы не воспроизвёл. Продакшн-код ради тестируемости не менялся —
тест сам биндит `127.0.0.1:0`.

| тест | до правки | после |
|---|---|---|
| 150 последовательных действий | **FAIL** на №100 | PASS, 0.11 с |
| 60 конкурентных действий | PASS — страховка от превращения пути в последовательный | PASS, 17 мс |
| 200 действий волнами по 50 | **FAIL** | PASS, 0.05 с |

Мутации: удаление строки, обход на успешном пути, замена вторым `Close()` —
**все три ловятся**.

### Живой acceptance после развёртывания

Развёрнутый бинарь сверен по sha256 с локальной сборкой — совпадает
побайтово; бандл сверен после передачи.

- **150** последовательных действий на одном соединении — все прошли, включая
  №100–150, без переподключения;
- **300** действий на одном соединении — все прошли;
- новое соединение после этого — работает;
- **160** конкурентных действий волнами по 40 — 0 сбоев, то есть путь не стал
  последовательным;
- **parity HTTP/QUIC** на `getMe` — ответы идентичны;
- журнал: 1275 записей `[Photon]`, **0 error, 0 PANIC**; процесс — 12
  дескрипторов, 7 потоков, RSS 21.5 МБ, без роста.

### Что это значит за пределами исправления

Предел в 100 стримов на соединение остаётся и после правки — теперь он
действительно **конкурентный**, а не пожизненный. Для будущего медийного слоя
это существенно: медийная передача занимает слот из тех же 100, и брошенная
передача держит его до закрытия соединения. Это записано в ADR-049 §6;
уточнение о том, что до этой правки предел был пожизненным, относится к
истории дефекта, а не к самому ADR.

## Props на границе plugin RPC (найдено 2026-09-09 живым прогоном, исправлено)

Дефект, из-за которого **первый же `createPost` с вложением сжигал
RPC-соединение плагина с хостом навсегда**, а сам плагин оставался снаружи
«здоровым».

### Что было не так

`createPost` клал в `Props` значение плагин-локального типа:

```go
post.AddProp("photon_media", refs) // refs — []MediaRef
```

`Props` — это `model.StringInterface`, то есть `map[string]any`. Plugin API
уезжает в хост через `hashicorp/go-plugin` поверх `net/rpc` с **gob**-кодеком
(`plugin/client_rpc_generated.go`: `apiRPCClient.CreatePost` шлёт
`Z_CreatePostArgs{post}`). gob кодирует значение, лежащее в интерфейсе, **по
имени типа**, и имя обязано быть известно ОБЕИМ сторонам. Хост регистрирует
шесть имён (`plugin/client_rpc.go`: `[]any`, `map[string]any`,
`[]*model.SlackAttachment`, `*model.AppError`, `*pq.Error`, …), и
плагин-локального среди них нет:

```
RPC call to CreatePost API failed: gob: type not registered for interface: []main.MediaRef
```

### Почему `gob.Register` не является решением

Регистрация процессо-локальна, а граница — межпроцессная. Зарегистрировав тип
у себя, плагин заставил бы **хост** декодировать имя `[]main.MediaRef`,
которого в хосте нет ни в одном пакете: отказ переехал бы с кодирования на
декодирование, то есть спрятался бы на шаг дальше от места, где его видно.

Второй довод сильнее первого и от gob не зависит: props хранятся в БД как
JSON, и любой их читатель — webapp, наш же `getFeed` — получает JSON-формы.
Записывая структуру, мы записывали бы то, чего при чтении не бывает.

**Свойство контракта.** После round-trip через JSON props состоят только из
`map[string]any`, `[]any`, `string`, `float64`, `bool` и `nil`; числа
декодируются как **`float64`** (точный диапазон до 2⁵³). Для `size` в
`photon_media` предел недостижим, но рассчитывать на `int64` при чтении props
нельзя. Место этого утверждения по смыслу — ADR-048 §3; он заморожен, поэтому
записано здесь.

### Последствие оказалось тяжелее самой ошибки

1. `Client.send` падает на `WriteRequest` **после** записи заголовка запроса —
   поток `net/rpc` десинхронизирован;
2. хост не разбирает продолжение и рвёт соединение; `input()` ставит
   **`client.shutdown = true` навсегда**, дальше всё — `ErrShutdown`
   (`connection is shut down`). Реконнекта у плагина нет;
3. сгенерированный клиент при отказе `Call` **только логирует** и возвращает
   `(nil, nil)`; проверка `appErr != nil` этого не видит, и следом идёт
   `created.Id` — разыменование nil;
4. паника ловится нашим `recover()` в `handleStream`, стрим закрывается без
   ответа — клиент получает `EOF` вместо конверта;
5. хост не замечает ничего: health-check шлёт `Control.Ping` по **отдельному
   control-стриму** (`go-plugin/rpc_client.go`), и тот жив. Плагин числится
   здоровым, а `authorizeSession` → `GetSession` → `ErrShutdown` →
   `unauthorized` на любое действие.

Невосстановимость — свойство стека `net/rpc` + go-plugin, **не** ошибка нашего
жизненного цикла. Наших ошибок две: отправили некодируемое значение и
разыменовали `nil` при неудавшемся вызове.

### Исправление

- `mediaPropsValue`: `json.Marshal(refs)` → `[]any`, и в `AddProp` уходит
  JSON-канонический вид;
- `created == nil` при `appErr == nil` — конверт `ok:false` вместо
  разыменования.

### Чем доказано

`server/media_rpc_test.go` проводит пост через **настоящую** пару `net/rpc` +
gob поверх `net.Pipe`, с аргументом формы `Z_CreatePostArgs`. Оракул
(`requireJSONCanonical`) требует, чтобы дальняя сторона восстановила значение,
зная **только** те типы, что уже знает, — это свойство сильнее кодируемости и
потому отвергает обе неверные починки.

| мутация | результат |
|---|---|
| вернуть `AddProp("photon_media", refs)` | падает: `gob: type not registered for interface: []main.MediaRef` |
| то же + `gob.Register([]MediaRef{})` | падает: `props.photon_media: тип []main.MediaRef не JSON-канонический` |
| снять проверку `created == nil` | падает: паника |

Прежний `media_attach_test.go` оставался бы **зелёным при всех трёх**: мок
передаёт `*model.Post` из горутины в горутину, сериализации там нет вовсе. Тот
же класс, что `TestAuthzOwnerSelectorIsSelector` в Phase 14 — тест истинный и
бесполезный для этого свойства.

### Живой acceptance после развёртывания

Развёрнутый бинарь сверен по sha256 с локальной сборкой (`9dcb472f…57ec`).
Полный медийный прогон: **30 проверок, PASS 28, FAIL 0, NOT EXECUTED 2**.
После `createPost` с вложением выполнено ещё 20 проверок; в журнале — **0
gob-ошибок, 0 паник, 0 `connection is shut down`**.

### Что осталось за рамками правки — намеренно

**`(nil, nil)` — форма общая.** В `server/` вызывается 43 различных метода
plugin API (без логирования), и любой при мёртвом транспорте вернёт нули без
ошибки. Правило: **защищать разыменования там, где результат фактически
используется**. Массовый рефакторинг всех вызовов сейчас не делается — он
тронул бы десятки файлов ради риска, который на большинстве путей не
реализуется, и несоизмерим с объёмом медийного среза.

**`unauthorized` при невозможности `GetSession`** — поведение fail-closed и в
этом верное, но диагностически неоднозначное: отказ авторизации неотличим от
отказа инфраструктуры, что живой прогон и показал. Развести их — отдельное
архитектурное решение: этот путь несёт на себе матрицу Phase 14.
