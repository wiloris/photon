# Phase 14 — findings discovery-прохода

Состояние на 2026-09-02. **Это findings, а не план и не спецификация.**
`ROADMAP.md` намеренно не менялся: переформулировка Phase 14 из «реализация
Bridge» в «Bridge authorization / access control» — отдельное решение, которое
принимается позже и здесь только подготавливается.

Разбор относится к коду **отдельного репозитория** `~/projects/photon-quic-bridge/`
(`main`, `ecdf475`). Ссылки вида `server/push.go:122` — на него, не на это
дерево.

Каждая находка помечена способом проверки. Различие существенно: часть
подтверждена прогоном против живого сервера, часть — только чтением кода, и
смешивать их нельзя.

## 1. Чек-лист Phase 14 описывает не то состояние

Записано: «QUIC listener · интеграция с Mattermost API · push-уведомления ·
handlers · исправление `getUsers` · исправление `searchUsers` · исправление
`getReactions`».

Фактически из семи пунктов **не открыт ни один**:

| Пункт | Состояние |

| QUIC listener | Есть, работает; проверен прогоном Phase 12.5 и 13.5, включая сквозной через `.so` |
| Интеграция с Mattermost API | Шесть ресурсов, 68 handler-функций |

### Три «исправления» — дефект тест-клиента, а не Bridge

Причина записана в самом клиенте (`test-client/test_photon.go:52-57`): поле
`Data map[string]interface{}` падало с ошибкой декодирования **на любом
списочном ответе** — `getUsers`, `searchUsers`, `getUsersByIds`,
`getReactions`. Клиент уже исправлен (`Data interface{}` + безопасное
приведение).

**Проверено прогоном** против живого сервера 2026-09-02, через
`services/session`: `getUsers (202)`, `searchUsers (205)`, `getReactions (112)`,
а также `getUsersByIds (206)`, `getFeed (101)`, `addReaction (110)`,
`engramStore/Query/Delete (400/401/402)`, `createPost/deletePost (100/102)` —
все возвращают `ok:true`. Работа по этим трём пунктам не требуется; требуется
исправление записи.

Класс ошибки тот же, что закрыт в Phase 13.5 дважды: **утверждение, которое
выглядит проверкой, но проверяет не то, что названо.** Здесь падение клиента
три раза подряд было записано как дефект сервера.

## 2. Что открыто на самом деле: разграничение доступа

Открытое в Bridge — не функциональность, а авторизация. Ниже по убыванию
последствий.

### 2.1 Push уходит всем подписчикам (по коду)

`PushRegistry.Broadcast` (`server/push.go:122-143`): при пустом `event.UserID`
событие уходит **каждому** зарегистрированному клиенту.

`UserID` заполняет **один хук из восьми** — `UserHasBeenStatusChanged`
(`server/hooks.go:98`). Остальные семь (`:20`, `:30`, `:44`, `:58`, `:71`,
`:84`, `:108`) отправляют событие без адресата, а `MessageHasBeenPosted`
(`:11-21`) кладёт в `data` результат `json.Marshal(post)` целиком — текст
сообщения, канал, автора.

Следствие по коду: любой клиент, прошедший handshake в режиме `subscribe`,
получает содержимое каждого сообщения инстанса, включая переписки, к которым
не имеет отношения.

**НЕ проверено на двух аккаунтах** — в распоряжении был один пользователь.
Это первая проверка, которую стоит поставить: второй аккаунт, подписка первым,
сообщение вторым в канал, куда первый не входит. До неё утверждение опирается
на чтение двадцати строк, а не на измерение.

### 2.2 Handlers не проверяют доступ (по коду)

`userID` доходит до каждого handler'а первым аргументом и используется
**только для логирования**:

- `getFeed` (`server/handler_post.go:100`) → `API.GetPostsForChannel` без
  проверки членства: любой `channel_id` читается по идентификатору;
- `downloadFile` (`server/handler_file.go:70`) → `API.GetFile` без проверки:
  любой `file_id`;
- `getUsers` (`server/handler_user.go:101`) → весь список пользователей
  инстанса с адресами почты (`Password`, `AuthData`, `MfaSecret` вычищены).

Plugin API Mattermost исполняется от имени сервера и прав вызывающего не
проверяет — значит проверка обязана быть в Bridge, и её нет.
`API.GetChannelMember` встречается в трёх местах из 68 handler-функций
(`server/handler_channel.go:373`, `:407`, `:435`), и все три — по существу
операции (`getUnreadForChannel`, `markAsRead`, `getChannelMember`), а не ради
разграничения доступа.

### 2.3 Контрпример в том же коде: EngramResource скоупит ключи

`server/handler_engram.go:125`, `:227`, `:268` — `kvKey := engramKey(userID, p.Key)`.
Один ресурс из шести изолирует данные по пользователю.

Это меняет формулировку задачи: приём в кодовой базе **известен и применён**,
просто не везде. Отсутствующее — не «не придумали как», а «не сделали», и
объём работы измеряется не исследованием, а перечислением мест.

### 2.4 Сессия проверяется один раз (по коду)

`API.GetSession` вызывается при handshake (`server/api.go:60` для HTTP-входа и
соответствующее место в `quic_listener.go` для QUIC). Дальше соединение живёт
без повторной проверки: подписка переживает логаут и отзыв сессии до обрыва
соединения. Для action-соединения окно короче, для подписки — сколько угодно
долго, теперь особенно, поскольку keep-alive держит её живой намеренно.

## 3. Дефекты, не относящиеся к доступу

### 3.1 Отказ TLS роняет плагин при первом же сообщении (по коду)

`OnActivate` (`server/plugin.go:75-81`): если `getTLSConfig` вернул ошибку,
пишется `LogError` и возвращается **`nil`**. Плагин считается активированным,
`p.quicListener` остаётся `nil`, а все восемь хуков безусловно зовут
`p.quicListener.Push(...)` — nil-разыменование, `recover` в хуках нет.

В `CLAUDE.md` это записано как ловушка развёртывания («сразу после активации
проверить лог»), и как совет по эксплуатации это верно. Но по существу это
дефект кода на три строки: либо `OnActivate` обязан возвращать ошибку, либо
хуки — проверять `nil`. Симптом («падает при отправке сообщений») отстоит от
причины («не нашёлся сертификат») настолько, что искать будут не там.

### 3.2 Настройки не читаются (проверено grep'ом)

`getConfiguration()` определён (`server/configuration.go:26`) и **не вызывается
ни разу** во всём `server/`. Переключатель `DebugMode` в System Console
(`plugin.json:18-29`) не делает ничего; `SSEKeepAliveSec` и
`ClientBufferSize` — остатки прежней SSE-реализации.

### 3.3 Буфер push на 64 события со молчаливым сбросом

`newPushClient` (`server/push.go:30`) — `make(chan PushEvent, 64)`;
`Broadcast` при переполнении уходит в `default:` (`:129`, `:139`), то есть
теряет событие без следа. Записано в `bridge-session.md` §9 п. 6 как открытое
после Phase 12.5; требует всплеска событий и подъёма `rmem_max`, иначе потери
на приёме смешаются со сбросом на отправке.

## 4. Что из этого — решение, а не работа

Два пункта нельзя закрыть правкой, потому что сначала нужно решение:

1. **Фильтрация push по членству в канале** (2.1). Цена — вычисление
   адресатов на каждое событие, на каждый хук; альтернатива — фильтрация на
   клиенте, что означает продолжать рассылать содержимое всем. Это ADR, а не
   деталь реализации.
2. **Видимость каталога пользователей** (2.2, `getUsers`). Отдавать ли всем
   всех и с какими полями — продуктовое решение мессенджера. Сейчас оно не
   принято, а получилось.

Остальное — перечислимая работа: проверки доступа по местам, `nil`-безопасность
хуков, чтение конфигурации, поведение при переполнении буфера.
