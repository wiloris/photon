# ARCHITECTURE.md

## Photon — платформенный движок для распределённых приложений

Версия документа: 1.0
Статус: Финальная архитектура зафиксирована

---

## 1. Философия

Photon — это не мессенджер, не кошелёк и не игра. Photon — это операционная система для приложений, работающих поверх единого ядра, которое отвечает за хранение данных, идентичность, транспорт, безопасность и расширяемость.

Главный принцип:

> Сначала строим Photon как платформенный движок. ENGRAM — первое приложение поверх него.

Это значит, что ядро проектируется так, будто его будут использовать десятки разных приложений — даже если сегодня существует только одно. Любая функциональность, специфичная для конкретного продукта (чат, кошелёк, игры), не может попасть в ядро. Она либо становится плагином, либо отдельным приложением поверх SDK.

Архитектура существует, чтобы через год не пришлось говорить: "надо переписать всё ядро".

## 2. Photon и ENGRAM: разделение ответственности

**Photon** — ядро платформы. Отвечает на вопросы: как хранить, как передавать, как проверять, кому доверять, как расширять.

**ENGRAM** — первое приложение поверх Photon. Отвечает на вопросы: что показывать пользователю, какой у продукта UX, какие фичи нужны конечному пользователю (чат, кошелёк, рулетка, игры).

Правило разделения: если функциональность может понадобиться другому, не связанному с ENGRAM приложению — она принадлежит Photon. Если функциональность специфична для продукта ENGRAM — она находится в ENGRAM или оформляется как плагин через Plugin SDK.

**Конкретные примеры (чтобы правило не оставалось абстрактным):**

- **Google OAuth** — не часть Core, а один из адаптеров `ports.IdentityProvider` (`adapters/googleoidc`). Это уже не гипотеза, а реализованный прецедент: `ports/identityprovider.go` не содержит слова "Google" нигде в сигнатурах, только в комментариях конкретного адаптера. Тот же путь для Apple/Microsoft/корпоративного OIDC — новый адаптер, не изменение порта.
- **YouTube-интеграция, криптокошелёк, платёжные адаптеры (ЮKassa, Т-Банк, обменники)** — плагины через Plugin Runtime (ADR-005, изолированный процесс) и `Authorizer` (`ports/plugin.go`), не часть Core. Ядро не должно знать о существовании ни одного конкретного плагина.
- **Фотоальбомы, аватары групп, любые Mattermost-специфичные возможности** — расширения `photon-quic-bridge` (или его преемника), не изменения Photon Core. Bridge — один из потребителей Photon Protocol (ADR-009), не место, откуда растут требования к ядру.

Проверочный вопрос тот же, что уже применяется к портам (ADR-011/013): если убрать конкретного поставщика/провайдера/функцию — останется ли Core осмысленным и полным? Если да — это правильно вынесено за пределы ядра.

## 3. Принцип Ports & Adapters (Hexagonal Architecture)

Ядро Photon построено по принципу портов и адаптеров.

**Ports** (`photon-core/ports/`) — только интерфейсы. Ядро описывает, *что* ему нужно (хранилище, транспорт, идентичность, крипто, медиа, p2p, плагины, нотификации), но не знает, *как* это реализовано.

**Adapters** (`photon-core/adapters/`) — конкретные реализации портов: bbolt для хранения, ed25519 для идентичности, QUIC/TCP для транспорта, pion для P2P.

Почему это важно:

- Реализацию можно заменить, не трогая бизнес-логику (например, сменить bbolt на другую БД).
- Ядро тестируется через моки портов, без реальной сети и диска.
- Разные клиенты (Android, Desktop) получают одно и то же поведение ядра независимо от платформенных деталей.

Схема зависимостей:

```
services/  →  ports/  ←  adapters/
```

Сервисы зависят от портов (интерфейсов), адаптеры реализуют порты. Направление зависимости всегда внутрь — к абстракции, никогда наружу.

### 3.1. Проверка на утечку реализации

Правило для любого типа, имени или метода в `ports/`:

> Если имя типа, метода или поля в `ports/` совпадает с названием конкретной библиотеки или технологии — оно не пройдёт ревью.

Плохо (утечка реализации конкретного backend'а или библиотеки в публичный контракт):

```go
CreateBucketIfNotExists("identity")   // bbolt
QuicConnection()                       // quic-go
BoltTransaction()                      // bbolt
PionAgent()                            // pion
OpenUniStream()                        // специфика QUIC-мультиплексирования
```

Хорошо (контракт описывает потребность ядра, а не возможности конкретной реализации):

```go
Namespace                              // не bucket, не table
Transport()                            // не QuicConnection
Session()                              // не Conn
PeerConnection()                       // не PionAgent
```

Практический тест перед тем, как добавить что-либо в `ports/`: если для этого имени пришлось бы писать `if backend == bbolt { ... } else if backend == sqlite { ... }` где-то в коде, использующем порт, — это утечка, и порт спроектирован неверно. Порт должен читаться так, будто первой реализации могло не быть ни одной — только потребность ядра, а не следствие того, с какой библиотеки начали разработку.

Пример эволюции: `ports/storage.go` изначально был написан по образцу bbolt (`bucket`, closure-транзакции), и при ревью (см. ADR-010 в `DECISIONS.md`) `bucket` был заменён на `namespace` именно по этому правилу — модель транзакций осталась, потому что оказалась переносимой, а вот `bucket` был реальной утечкой.

## 4. Почему ядро написано на Go

- Единый бинарник, кросс-компиляция под Linux/Windows/Android без сложной тулчейн-эквилибристики.
- Встроенная поддержка конкурентности (goroutines, channels) естественно ложится на транспортный слой и dispatcher, где нужно параллельно обрабатывать соединения, события и плагины.
- Хорошая экосистема для сетевых протоколов (QUIC, gRPC/protobuf), P2P (pion) и встраиваемых хранилищ (bbolt).
- CGO и c-shared сборки позволяют выдавать ядро как библиотеку через C ABI, что открывает путь к биндингам на JNI (Android) и Desktop-обёртки, без переписывания ядра под каждую платформу.
- Простая модель памяти и отсутствие скрытой магии — важно для кода, который будет жить и поддерживаться годами.

## 5. Устройство транспортного слоя

Транспорт реализован как адаптер (`adapters/quic`, `adapters/tcp`) над портом `transport.go`. Клиентский код никогда не работает с сокетами напрямую — только через интерфейс порта.

**QUIC** — основной транспорт: мультиплексированные потоки, встроенное шифрование, быстрый reconnect после потери сети (актуально для мобильных клиентов).

**TCP** — резервный транспорт на случай, если QUIC недоступен (блокировки, ограничения сети).

### Autodial Engine

Отдельный сервис (`services/autodial`), который определяет оптимальный маршрут подключения, проверяя доступность и оценивая качество каждого варианта по приоритету:

```
IPv6 QUIC → IPv4 QUIC → IPv6 TCP → IPv4 TCP → транспорт с маскировкой
```

Последняя ступень — транспорт с маскировкой трафика на случай, если все стандартные маршруты недоступны или заблокированы. Конкретный продукт здесь намеренно не назван: это **не элемент плана**, а роль в цепочке. Цепочка задаётся конфигурацией развёртывания (`TransportEntry`), поэтому любой такой адаптер добавляется в неё без правок `services/autodial` — и ровно так же исключается, если требование не подтвердится.

Autodial не встроен в транспортный адаптер напрямую — это отдельный сервис, который оркестрирует адаптеры транспорта, что позволяет менять логику выбора маршрута, не трогая сами протоколы.

## 6. Plugin Runtime

Ключевое архитектурное решение: **плагин не живёт внутри ядра**.

```
Photon Core → IPC → Plugin Host → Plugin
```

Плагины выполняются в изолированном процессе (Plugin Host), общаясь с ядром через IPC. Это даёт:

- Падение плагина не роняет ядро.
- Плагин не может напрямую читать память ядра или других плагинов.
- Права плагина определяются манифестом и проверяются на уровне IPC, а не на доверии к коду плагина.

Структура runtime (`photon-plugin-runtime/`): `manager` (жизненный цикл плагинов), `loader` (загрузка и валидация), `host` (изолированный процесс исполнения), `sandbox` (ограничение ресурсов и прав), `api` (мост к разрешённым портам ядра).

### Plugin SDK

Разработчики плагинов работают с `photon-plugin-sdk`, который предоставляет высокоуровневый API (`Storage()`, `Events()`, `Identity()`, `Network()`) и не даёт прямого доступа к внутренностям ядра. Каждый плагин описывает свои права явно в манифесте:

```json
{
  "id": "example",
  "version": "1.0",
  "permissions": ["storage", "network"]
}
```

Ядро обязано отказывать в доступе к любому ресурсу, не заявленному в манифесте.

### Правило направления зависимости

> Photon Core не знает о конкретных плагинах.

Зависимость всегда направлена снизу вверх и никогда наоборот:

```
Photon Core
      ↑
Plugin Runtime
      ↑
Plugin SDK
      ↑
Plugins
```

Ядро не импортирует код плагинов, не хранит списка "известных" плагинов и не меняет поведение в зависимости от того, какой плагин установлен. Всё специфичное для конкретного плагина живёт выше по цепочке — в Plugin Host и в самом плагине. Если в какой-то момент кажется, что ядру нужно "знать" о плагине — это сигнал, что функциональность спроектирована неверно, и её нужно переносить в Plugin Runtime или SDK, а не встраивать в ядро.

## 7. Bindings — единственная публичная граница: C ABI

`photon-bindings/c` — единственная публичная граница ядра. Ни один язык или платформа не вызывает Go напрямую.

```
Photon Core (Go)
        │
        ▼
photon-bindings/c   (единственный публичный ABI)
        │
 ┌──────┼──────────┐
 ▼      ▼          ▼
JNI   Desktop    Другие языки
```

- Android не вызывает Go напрямую.
- Linux не вызывает Go напрямую.
- Windows не вызывает Go напрямую.
- Любой язык работает только через `photon_core.h`.

Ядро не переписывается под каждую платформу — переписывается только тонкий слой моста (JNI, Desktop). Это гарантирует, что бизнес-логика (хранение, крипто, транспорт, плагины) идентична на всех платформах, и расхождения в поведении невозможны по построению.

Причина, по которой это правило жёсткое, а не рекомендация: как только один клиент найдёт способ обойти C ABI (например, через gomobile напрямую в Android, "ради скорости"), платформа перестаёт быть платформой — контракт расходится по клиентам, и дальнейшие изменения ядра нужно тестировать на каждом обходном пути отдельно.

**Статус ABI: проверенный, не только объявленный.** С момента реализации `photon-bindings/c` (Phase 5) C ABI перестал быть контрактом "на бумаге": все 12 функций реализованы поверх ядра, покрыты 32 тестами контракта (lifecycle, ownership, валидация action-кодов, ABI versioning), прогнаны под race detector и проверены на утечки двумя leak-check программами против реальной `.so`. Именно эта проверка поймала настоящий double free в `Photon_Destroy` — то есть ABI проверен не только на "работает в счастливом случае", но и на корректность владения памятью в граничных сценариях.

Практическое следствие для JNI (и любого следующего binding): слой `bindings/android` обязан вызывать `photon_core.h` через собранную `.so`, а не обращаться к Go-типам, внутренним пакетам `photon-core` или к `gomobile bind` в обход. Дословно:

```
Android / Kotlin
       │
       ▼
     JNI                    ← тонкий маршалинг, без бизнес-логики
       │
       ▼
  Photon C ABI (.so)        ← проверенная граница, ADR-020/026/027/028
       │
       ▼
  photon-core (Go)
```

Обходной вариант `Kotlin → JNI → внутренности Go` запрещён не из формализма: он обнулил бы всю проверку выше (double free, ownership, ABI version), поскольку та относится к границе `.so`, а не к Go-пакетам напрямую. Тот же аргумент применим к `bindings/desktop` и любому будущему binding на Rust/Swift/Python — все они переиспользуют одну проверенную границу, а не заводят собственную.

### 7.0. Минимальность ABI

Публичная поверхность `photon_core.h` держится намеренно маленькой — не отдельная функция на каждый ресурс (`Photon_GetUser`, `Photon_CreatePost`, ...), а фиксированный набор из семи функций: `Photon_GetABIVersion`, `Photon_Create`, `Photon_Destroy`, `Photon_SendAction`, `Photon_SetEventCallback`, `Photon_GetLastError`, `Photon_Free{String,Bytes}`. Вся ресурсная специфика (какое действие выполнить, что передать) идёт через `action_code`/`payload_json` внутри `Photon_SendAction`, а не через рост числа экспортируемых символов.

Это осознанный компромисс: удобство конкретного клиента (например, отдельная типизированная функция была бы приятнее в Kotlin) приносится в жертву поддерживаемости ABI на горизонте многих лет. Чем меньше публичных символов, тем меньше поверхность, которую нужно замораживать версией и тем реже приходится ломать её при эволюции ядра.

### 7.1. Ownership памяти

Правило: **любой объект, который создаёт Photon, уничтожается только Photon.** Не смешивать malloc/free вызывающей стороны с Go GC.

Для каждой функции, возвращающей выделенную память, обязательна парная функция освобождения:

```c
PhotonString* Photon_GetUsername(PhotonHandle*);
void          Photon_FreeString(PhotonString*);

PhotonBytes*  Photon_ReadFile(PhotonHandle*, const char* file_id);
void          Photon_FreeBytes(PhotonBytes*);
```

Если этого не сделать явно, вызывающая сторона (JVM, C++) рано или поздно попробует освободить память, выделенную Go-аллокатором, или наоборот — это не баг, а падение рантайма, которое тяжело воспроизвести и ещё тяжелее отладить постфактум.

### 7.2. Opaque Handles

Наружу никогда не передаются внутренние структуры Go. Только непрозрачные дескрипторы:

```c
typedef struct PhotonHandle PhotonHandle;
```

Снаружи не существует `PhotonCore*`, `Session*`, `Transport*` — вызывающая сторона не знает и не должна знать о внутреннем устройстве ядра. Всё, что у неё есть, — это `Handle` и набор функций `Photon_*`, принимающих его первым аргументом.

### 7.3. Единый Event Callback

Не десятки callback-ов на каждый тип события, а один:

```c
typedef void (*PhotonEventCallback)(const char* event_json, void* user_data);
void Photon_SetEventCallback(PhotonHandle*, PhotonEventCallback, void* user_data);
```

Замысел: все события — подключение, входящее сообщение, событие плагина, изменение хранилища, изменение сети — приходят единым потоком, различаясь по полю внутри `event_json` (`CONNECTED`, `MESSAGE`, `PLUGIN_EVENT`, `STORAGE_CHANGED`, `NETWORK_CHANGED`, ...). Разбор события — ответственность клиента. Это масштабируется лучше, чем растущий список отдельных callback-типов при добавлении новых событий.

**Состояние на сегодня: канал объявлен, но пуст.** Сигнатура заморожена вместе с остальным ABI (ADR-008), символ экспортируется, `Photon_SetEventCallback` принимает и запоминает колбэк — но ни одного события ядро пока не отправляет, потому что ни одного источника событий в нём не реализовано. Решение выше от этого не меняется: оно о форме канала, а не о сроке. Меняется только то, на что клиент вправе рассчитывать сегодня — ни на что: связь устанавливается первым `Photon_SendAction` (Phase 13.5), а не уведомлением. Точная формулировка контракта — в `photon-bindings/c/photon_core.h`, там же записано, когда появится первое событие.

Технический нюанс, специфичный для границы Go/JVM: вызов Go → C callback из горутины требует аккуратной работы с `cgo.Handle` для `user_data`, а на Android-стороне — корректного `AttachCurrentThread`/`DetachCurrentThread` в JNI, если колбэк прилетает не из того потока, в котором изначально инициализирован JNI env. Это частый источник нестабильных крашей, и на него стоит закладывать время отдельно от основной разработки bindings.

### 7.4. Ошибки: PhotonResult

Не строки, не отдельные коды на каждую функцию — единый enum результата:

```c
typedef enum {
    PHOTON_OK,
    PHOTON_TIMEOUT,
    PHOTON_INVALID_ARGUMENT,
    PHOTON_PERMISSION_DENIED,
    PHOTON_NOT_FOUND,
    // ...
} PhotonResult;
```

Плюс отдельная функция для диагностического текста:

```c
const char* Photon_GetLastError(PhotonHandle*);
```

Такой паттерн хорошо ложится на C, C++, Kotlin/JNI, Rust, Swift и Python FFI без адаптации под каждый язык отдельно.

### 7.5. ABI Versioning

Обязательное правило, а не опция:

```c
#define PHOTON_ABI_VERSION 1
int Photon_GetABIVersion(void);
```

Причина: ядро будет развиваться быстрее, чем все bindings синхронно. Без версионирования несовместимость ядра и биндинга проявляется как загадочный краш в проде. С версионированием — как явный отказ загрузки на старте:

```
Core ABI = 2
Bindings ABI = 1
      ↓
отказ загрузки
```

Каждый клиент обязан проверять `Photon_GetABIVersion()` при инициализации и отказываться работать при несовпадении мажорной версии, вместо того чтобы продолжать работу с непредсказуемым поведением.

### 7.5.1. ABI Freeze Policy

С момента, когда `photon_core.h` проходит ревью и помечается как **ABI v1 frozen**, действует отдельное правило, стоящее выше обычного процесса разработки:

> Любое изменение сигнатуры, поведения или семантики ownership любой функции из `photon_core.h` — это не обычный коммит, а событие уровня новой версии ABI.

Практически это означает:

- Изменение `Photon_SendAction(...)` (или любой другой экспортируемой функции) не может быть частью обычного PR "заодно поправил". Оно требует отдельного архитектурного обсуждения, фиксируется как решение (по аналогии с записями в этом документе), и только после этого — инкремент `PHOTON_ABI_VERSION`.
- Добавление новой функции в заголовок — тоже подпадает под это правило, а не только изменение существующей. Раздел 7.0 (минимальность) существует именно для того, чтобы таких добавлений почти никогда не требовалось.
- Пока `photon_core.h` не прошёл ревью и не зафиксирован как frozen v1 (см. `ROADMAP.md`, Phase 5), это правило не действует — до заморозки заголовок можно и нужно свободно дорабатывать по мере реализации `bindings/c`.

Смысл этого правила — сделать ABI самым консервативным элементом системы. Интерфейсы `ports/` внутри ядра могут эволюционировать относительно свободно на раннем этапе; публичный C ABI — нет, потому что его изменение синхронно ломает Android, Desktop и любые будущие биндинги одновременно.

### 7.6. Photon Protocol — общий контракт, а не деталь Bridge

`Photon_SendAction` работает через пару action-код/JSON-payload, зеркалящую схему, уже используемую в QUIC-протоколе (`photon-quic-bridge`). Здесь важно зафиксировать направление зависимости:

```
Photon Protocol
 (action-коды, payload/response-схемы, photon.proto)
       │
 ┌─────┴─────┐
 ▼           ▼
Core        Bridge
```

**Не** так:

```
Bridge
  │
  ▼
Core
```

Action-коды и схемы payload/response — это общий протокол платформы (`Photon Protocol`), от которого зависят и Core, и `photon-quic-bridge` как равноправные потребители. Core не должен зависеть от реализации bridge — иначе ядро платформы оказывается привязано к серверной интеграции с Mattermost, что прямо противоречит принципу из раздела 2 ("Photon не мессенджер").

**Практическое следствие:** формальное определение протокола (`photon.proto`, action-коды) должно физически жить в `photon-core/protobuf/`, а `photon-quic-bridge/server/protocol.go` — импортировать эти определения, а не объявлять их заново. На момент написания этого раздела action-коды объявлены непосредственно в `photon-quic-bridge/server/protocol.go` — это временное состояние ранней разработки, а не целевая архитектура. Перенос протокола в `photon-core/protobuf/` должен произойти до заморозки ABI v1, иначе `Photon_SendAction` в `photon_core.h` фиксирует зависимость на неверном уровне, и её придётся ломать при последующем рефакторинге.

**Что означает результат `Photon_SendAction` (ADR-038).** `PhotonResult` описывает исход **вызова** — дошёл ли запрос, пришёл ли ответ, разобрался ли он, — а вердикт самой операции живёт в конверте ответа (`ok`/`error`/`data`, зеркало `PhotonResponse` из `photon.proto`), который клиент получает через `response_out`. Ответ Bridge с `ok:false` — это состоявшийся вызов: возвращается `PHOTON_OK`, а причина отказа доходит до клиента телом ответа. Иначе и быть не может: кодов ошибок на проводе не существует (единственный тип ответа Bridge — `ok`/`data`/`error`), классификация по тексту запрещена (ADR-033), а заголовок запрещает устанавливать `response_out` при любом результате, кроме `PHOTON_OK`, — то есть любой код ошибки уничтожил бы единственный источник причины. Цена решения названа в ADR-038 явно: клиент, проверяющий только код возврата и не читающий `ok`, примет отказ за успех. См. `photon-core/docs/action-routing.md` §6.

## 8. P2P слой

**Состояние: порт реализован (Phase 15); открыт acceptance по настоящей сети.** `ports/p2p.go` прошёл тот же цикл, что и остальные восемь портов, и входит в заморозку ADR-020; `adapters/pion` реализует его **без единой правки контракта** — восьмой компонент подряд. Спецификация — `photon-core/docs/p2p-session.md`, написана до кода.

Прежняя редакция этого раздела утверждала обратное («реализован через `adapters/pion`… поддерживает ICE, STUN, TURN») и называла API `ConnectPeer()`, `CreateSession()`, `SendData()`, которого не существует ни в порте, ни где-либо в коде. Ошибка того же рода, что закрытая в Phase 14: документ описывал намерение в настоящем времени, и читающий считал бы слой готовым.

Порт определяет согласование, а не передачу данных:

```go
CreateOffer(ctx, peer PublicKey) (offer []byte, err error)
AcceptOffer(ctx, peer PublicKey, offer []byte) (answer []byte, session Session, err error)
CompleteSession(ctx, peer PublicKey, answer []byte) (Session, error)
Close() error
```

Метода «отправить данные» в порте нет намеренно: результат согласования — `Session`, которая расширяет `Connection` (`transport.go`) и добавляет `Peer() PublicKey`. После установления P2P-канал неотличим от обычного соединения, и данные идут через `OpenStream`/`AcceptStream`/`OpenUniStream` — те же, что у QUIC и TCP (uni-streams обязательны для всех адаптеров, ADR-016).

**Граница с транспортом.** `Transport` — dial на известный адрес; P2P — согласование **до** появления адреса. P2P не дублирует Transport, а производит его результат другим путём установления. Включение P2P в лестницу Autodial (раздел 5) отдельным решением пока не принято.

**Что порт сознательно не делает:** discovery (откуда взялся `PublicKey` собеседника, кто сейчас online) и доставку signaling-блобов другой стороне. Блобы непрозрачны для порта; их формат — дело адаптера, а доставка — дело вызывающего кода через любой уже существующий канал.

**Механизм обхода NAT зафиксирован ADR-043 — на уровне адаптера, а не контракта.** Путь B+: ICE + DTLS + SCTP из отдельных пакетов `pion`, без `pion/webrtc` и без SDP. До Phase 15 `pion` был назван в `p2p.go` лишь предположением, и решение принималось отдельным ADR — по правилу ADR-013 (порт проектируется от потребностей ядра, а не от возможностей первого адаптера) и ADR-011 (имя библиотеки не проникает в контракт; `PionAgent()` фигурирует в разделе 2 как пример того, что ревью не пройдёт). Наружу из адаптера не проходит ни один тип Pion.

**Аутентификация собеседника — ADR-041.** `Session.Peer()` возвращает **криптографически подтверждённый** ключ, а не тот, который передали аргументом: подписывается transcript с обоими публичными ключами, обоими nonce и channel binding (RFC 5705) из состояния DTLS, в собственном домене `photon-p2p-auth:` (ADR-037). Аргумент `peer` во всех трёх вызовах — намерение; подтвердился другой ключ — терминальный отказ.

**Что доказано и что нет.** Loopback-тесты доказывают протокол; локальные relay-тесты (TURN в том же процессе) — relay-путь. **Обход NAT не доказывает ни то, ни другое** — это отдельные утверждения (`p2p-session.md` §10.3). Из них выполнены два: direct-acceptance между двумя физическими машинами и relay-acceptance через внешний coturn, оба с подтверждением с обеих сторон. Открыт третий — **симметричный NAT**; выполненные прогоны им не являются: direct-пара установилась, значит условия direct допускали, а relay включался принудительно, то есть проверялся путь, а не сетевые условия.

Как и транспорт, P2P — адаптер, а не встроенная в ядро логика, поэтому его можно тестировать и заменять изолированно.

## 9. Безопасность

`photon-core/security/` — не опциональный модуль, а обязательный слой, через который проходит любое взаимодействие ядра с внешним миром (плагинами, клиентами, сетью).

**Решение:** security остаётся частью `photon-core`, а не выносится в отдельный репозиторий. Права доступа, проверка подписей и sandbox — это не надстройка над ядром, а часть того, что делает ядро ядром. Вынесение security в отдельный репозиторий создало бы риск версионного рассинхрона (ядро одной версии, проверки прав — другой) и позволило бы теоретически собрать ядро без security-проверок. Оба риска неприемлемы.

Компоненты:

- **permissions** — модель прав доступа (кто и к каким портам может обращаться).
- **signatures** — проверка подписей (плагины, обновления, идентичность пользователей на базе ed25519).
- **trust** — модель доверия между узлами и компонентами.
- **sandbox** — изоляция исполнения плагинов и ограничение их доступа к ресурсам.

Принцип: любой внешний код (плагин, входящее сообщение, обновление из ENSTOR) по умолчанию не доверенный, пока не пройдёт проверку подписи и прав.

### Принцип ENSTOR: доверие только через подпись

ENSTOR как магазин плагинов, расширений и приложений не доверяет пакетам по умолчанию:

```
ENSTOR → не доверяет пакетам → каждый пакет подписан
```

Отсутствие подписи — это отказ в установке, без исключений. Не "предупреждение пользователю", не "установка с пометкой небезопасно" — именно отказ. Проверка подписи выполняется на стороне клиента (через `security/signatures`), а не только на бэкенде ENSTOR, чтобы скомпрометированный или подменённый бэкенд не мог обойти проверку.

### 9.1. Device Trust Model

Photon не использует публичную PKI, клиентские X.509-сертификаты или собственный Certificate Authority для аутентификации клиента. Доверие пользователя строится исключительно на криптографической личности устройства (`Identity` port, Ed25519 — см. раздел 7, ADR-014).

Здесь принципиально разделены два разных вопроса, которые легко смешать:

- **Шифрование канала** — транспортный протокол (QUIC требует TLS 1.3) обеспечивает конфиденциальность и целостность байтов между узлами, независимо от того, кто на другом конце. Это забота `Transport` port и его адаптеров, не модели доверия.
- **Аутентификация клиента** — кто именно на другом конце — решается исключительно зарегистрированным публичным ключом устройства, а не сертификатом. TLS-сертификат сервера (даже полученный через Let's Encrypt/Caddy) не участвует в этом решении вообще — он аутентифицирует сервер перед клиентом на транспортном уровне, а не клиента перед сервером.

**Device Identity.** Каждое устройство при первом запуске генерирует собственную пару Ed25519 через `Identity.Generate`. Приватный ключ никогда не покидает устройство, не экспортируется автоматически, хранится средствами ОС (Android Keystore, Secret Service на Linux, DPAPI на Windows, Keychain на macOS — деталь конкретного `bindings/android`/`bindings/desktop`, не ядра). Публичный ключ регистрируется на сервере.

**Account.** Аккаунт существует отдельно от устройства. Один аккаунт — произвольное число устройств, каждое со своим ключом:

```
Identity Provider (сегодня Google, архитектура не привязана к конкретному)
        ↓
   Photon Account
        ↓
 ┌──────┼──────┐
Device A  Device B  Device C
```

**Авторизация.** Первичная авторизация — через внешний OAuth/OIDC Identity Provider. Сегодня это Google; архитектурно провайдер заменим (Apple, Microsoft, GitHub, корпоративный OIDC) без изменения остальной модели — по той же причине, по которой порты не называются именем конкретной библиотеки (ADR-011), архитектура доверия не называется именем конкретного провайдера. После успешной проверки сервер разрешает зарегистрировать новый публичный ключ устройства. Identity Provider — корень доверия для привязки устройства к аккаунту, не для шифрования трафика и не для самой криптографической личности устройства (та полностью определяется Ed25519-ключом, независимо от того, через какой IdP был создан аккаунт).

**Transport Authentication:**

```
Client → PublicKey → Challenge → Signature → Session Key
```

Сервер проверяет, зарегистрирован ли публичный ключ, отправляет challenge, проверяет подпись через `Identity.Verify`, создаёт временные сессионные ключи соединения. Долговременный device-ключ используется только для подтверждения личности, не для шифрования трафика напрямую.

**Device Management.** Аккаунт хранит реестр устройств: `DeviceID`, `PublicKey`, `Device Name`, `CreatedAt`, `LastSeen`. Удаление устройства из реестра немедленно останавливает приём подписей его ключа сервером — без отдельного протокола отзыва сертификата, потому что отзывать нечего: нет сертификата, есть просто запись в реестре, которую можно удалить.

**Компрометация ключа.** После отзыва устройства сервер перестаёт принимать подписи данного `PublicKey`. Существующие сессии этого устройства завершаются немедленно, не дожидаясь их естественного истечения — отзыв должен быть эффективен сразу, а не только для новых подключений.

**Переустановка приложения.** Переустановка (или сброс данных приложения) генерирует новую пару ключей — это всегда новое устройство с точки зрения модели, не восстановление старого. Старая запись в реестре остаётся до тех пор, пока пользователь не удалит её вручную. Явно фиксируется, чтобы не возникло соблазна впоследствии добавить "восстановление" приватного ключа через сервер — сервер физически не может это сделать, поскольку никогда не видел приватный ключ (см. ниже).

**Экспорт ключа.** Photon не предоставляет механизмов экспорта приватного ключа устройства. Это не ограничение конкретной реализации, а часть модели: если экспорт станет возможен, гарантия "приватный ключ никогда не покидает устройство" перестаёт быть архитектурным свойством и становится вопросом того, воспользовался ли пользователь этой опцией.

**Обязанности сервера.** Явное разделение — сервер никогда не генерирует ключи устройства, не хранит приватные ключи, не подписывает что-либо от имени клиента. Сервер только хранит зарегистрированные `PublicKey`, выдаёт challenge, проверяет подпись, отзывает доверие (удаляет запись из реестра). Любая функциональность, требующая от сервера операции с приватным ключом клиента, — по определению нарушение этой модели, а не деталь реализации, которую можно обсудить отдельно.

**Обязанности Identity.** `Identity` (`ports/identity.go`) отвечает исключительно за криптографическую личность устройства — генерация ключей, подпись, проверка подписи. Порт не знает про Identity Provider, аккаунты, реестр устройств, сервер или транспорт — ни один из этих терминов не встречается в его сигнатурах (проверено: 0 совпадений на "Google", "Account", "Device", "Registry", "OAuth", "TLS", "Certificate", "server" — см. `ports/identity.go`). Всё, описанное в этом разделе, — использование уже существующих примитивов `Generate`/`Sign`/`Verify` системой более высокого уровня (`security/trust`, будущий Account Service), а не расширение самого порта.

**Что отсутствует намеренно:**

- клиентские X.509-сертификаты;
- собственный Certificate Authority;
- ручное управление сертификатами устройств;
- экспорт приватных ключей между устройствами.

TLS-терминирующий прокси (например, Caddy) может присутствовать в инфраструктуре Bridge как обычный компонент транспортного шифрования — это не противоречит принципу, поскольку он не участвует в модели доверия к клиенту, только в шифровании канала до сервера.

**Влияние на уже принятые решения:** `Identity` используется без изменений — ADR-014, ADR-017, ADR-018 остаются в силе, `PhotonID`/`Account` по-прежнему не часть `ports/identity.go`. `Transport` не меняется — аутентификация происходит поверх уже установленного канала (см. раздел 7, `ports/transport.go`, заморожен ADR-020). Затрагивает `Bindings` (хранение приватного ключа средствами ОС), `photon-quic-bridge` или его преемника (реализация Transport Authentication), Developer Tools (область для управления устройствами). См. ADR-021.

## 10. Лицензирование

`photon-core` распространяется под **AGPL**. Это осознанный выбор:

- Гарантирует, что любые модификации ядра, используемые как публичный сервис, остаются открытыми.
- Защищает платформу от закрытых форков, эксплуатирующих открытый код без вклада обратно в проект.
- `photon-quic-bridge` (закрытая серверная часть) остаётся отдельным репозиторием именно потому, что серверная инфраструктура — не часть открытого ядра, и на неё AGPL-обязательства распространяются иначе.

SDK и bindings (`photon-sdk`, `photon-plugin-sdk`, `photon-bindings`) лицензируются отдельно, с более permissive лицензией, чтобы не создавать барьер для сторонних разработчиков, желающих строить приложения поверх Photon.
