# Архитектура Photon

Состояние первого публичного релиза. Документ описывает то, что есть в коде
этого репозитория; планы помечены как планы. Архитектура **не объявляется
завершённой**: ниже прямо перечислено, что ещё не сделано и где текущие
решения ограничивают будущие платформы.

## 1. Что такое Photon

Photon — платформа для клиентских приложений: ядро на Go (хранилище,
идентичность, криптография, транспорт, P2P, диагностика), единая граница
наружу — C ABI, поверх неё JVM SDK и инструменты разработчика, плюс среда
исполнения плагинов. Приложение работает с ядром через небольшой набор
функций C ABI и коды действий; сеть, хранилище и криптография скрыты за
портами ядра.

## 2. Слои и зависимости

```
приложение (JVM/Kotlin)          плагин (отдельный процесс)
        │ photon-sdk                     │ photon-plugin-sdk
        ▼                                ▼ IPC (не импорт)
JNI-мост (photon-bindings/jvm)   photon-plugin-runtime
        │                                │ coreops: операции поверх портов
        ▼                                ▼
C ABI (photon-bindings/c) ─────► photon-core
                                  ports ◄── adapters
                                  services
```

- **`photon-core` не знает о плагинах, Android, JVM и конкретных
  приложениях.** Внешние зависимости ядра: quic-go, pion, bbolt, protobuf
  (`photon-core/go.mod`). Единственная платформенная прослойка — перечисление
  сетевых интерфейсов на Android в `adapters/pion/androidsdk_android.go` под
  тегом `//go:build android`.
- **`photon-plugin-sdk` не имеет ни одной зависимости** (в `go.mod` нет
  `require`): плагин не может обойти runtime.
- **SDK и инструменты ходят в ядро только через C ABI**; второй реализации
  маршалинга нет.

## 3. Порты и адаптеры

Ядро построено по схеме «порты и адаптеры». Контракты — `photon-core/ports`
(`docs/ports.md`); они заморожены и меняются только отдельным решением.

| порт | реализация в этом репозитории |
|---|---|
| `Transport` (+ `Connection`, `Stream`) | `adapters/quic` (рабочий путь), `adapters/tcp` (адаптер есть, в рабочий путь не подключён — §5) |
| `Storage` | `adapters/bbolt` |
| `Crypto` | `adapters/aesgcm` |
| `Identity` | `adapters/ed25519` |
| `IdentityProvider` | `adapters/googleoidc` |
| `P2P` (`Session`) | `adapters/pion` — ICE + DTLS + SCTP без WebRTC-стека |
| `Authorizer` | реализует `photon-plugin-runtime` |
| `Media`, `Notifier` | контракты есть, отдельных адаптеров в этом репозитории нет |

Сервисы ядра (`photon-core/services`): `session` (сессия протокола поверх
транспорта), `dispatcher` (маршрутизация действий, события, жизненный цикл
инстанса), `diag` (журнал диагностики), `localfeed`, `outbox`, `media`,
`account`, `p2phost`, `autodial` (§5).

## 4. C ABI

`photon-bindings/c/photon_core.h`, версия ABI **1.0**, ровно 12 функций:
`Photon_GetABIVersion`, `Photon_Create`, `Photon_Destroy`,
`Photon_SendAction`, `Photon_SetEventCallback`, `Photon_GetLastError`,
`Photon_StringData`, `Photon_StringLen`, `Photon_FreeString`,
`Photon_BytesData`, `Photon_BytesLen`, `Photon_FreeBytes`.

Инстанс создаётся из JSON-конфигурации; вызовы — пара «код действия +
JSON-payload», ответ — JSON-конверт; события подписки приходят в один
колбэк. Состав символов и версия проверяются тестом
`TestABISurfaceUnchanged`. Добавление действий не меняет ABI.

## 5. Транспорт

Рабочий путь ядра сегодня — **QUIC** (`adapters/quic`, quic-go v0.48) к
одному endpoint из конфигурации. Адрес разрешается библиотекой quic-go
(`net.ResolveUDPAddr("udp")`): для имени с A- и AAAA-записями берётся первый
IPv4-адрес, и на другое семейство адаптер не переходит (вывод из кода, не
замер). Обрыв без закрытия соединения обнаруживается по таймеру простоя:
keep-alive 15 с + idle 30 с, то есть до 45 с.

**Autodial** (`services/autodial`) — реализованный и покрытый тестами сервис
выбора маршрута по лестнице

```
IPv6 QUIC → IPv4 QUIC → IPv6 TCP → IPv4 TCP → транспорт с маскировкой
```

но **к рабочему пути ядра он не подключён**: диспетчер создаёт QUIC-транспорт
напрямую. TCP-адаптер (`adapters/tcp`, собственный формат кадров —
`WIRE_FORMAT.md`) существует, но серверной стороны для него в этом релизе нет.
**Транспорта с маскировкой нет** — это зарезервированная ступень.

Какой путь ядро реально использовало, видно в журнале диагностики: событие
`transport.dial` несёт транспорт, семейство и фактический адрес
установленного соединения (§8).

## 6. Протокол и сервер

Сетевой протокол ядра — пара «действие + JSON» поверх QUIC-потоков; каталог
действий — `photon-core/protobuf/photon.proto`, сессия —
`photon-core/docs/bridge-session.md`.

**Протокол пока не нейтрален к серверу.** Он сложился вокруг первой
серверной реализации — плагина Mattermost («Photon QUIC Bridge»): в
`photon.proto` есть сущности Mattermost (`Post`, `Channel`, `Team`, `User`),
токен сессии по смыслу — Session ID Mattermost, а часть действий относится к
первому приложению на платформе (разговоры, друзья, профиль). Сам Bridge в
этот репозиторий **не входит**.

**Самостоятельной реализации сервера (Photon Server) в этом релизе нет.**
Для тестов транспорта есть только тестовый QUIC-сервер
`photon-core/tests/transportlab/bridgesim`. Нейтральный к серверу протокол и
Photon Server — направление развития (§10).

## 7. Плагины

`photon-plugin-runtime` запускает плагин отдельным процессом и общается с
ним по IPC (`docs/ipc.md`); манифест и права — `manifest`, `permissions`;
соответствие «операция → право» живёт в runtime, не в SDK; операции над
портами ядра исполняет `coreops`. Хост плагинов —
`cmd/engram-plugin-host`: запускает плагин по манифесту и корню пакета из
аргументов, хранит его данные в bbolt и исполняет его операции через
`coreops`; зависит только от адаптеров ядра и пакетов runtime. Назван по
первому приложению-потребителю, и это имя вошло в форматы данных
(пространство реестра `engram.host.registry`, префикс вызывающего
`engram-host:`, идентификатор по умолчанию `dev.engram.counter` в
legacy-режиме) — переименование изменило бы формат хранения, поэтому оно не
делалось. Пример — `examples/counter`,
`examples/greeter`; руководство — `docs/plugin-development.md`.

**Изоляция процесса плагина реализована только для Linux**
(`sandbox/linux.go`); на других ОС runtime собирается, но без изоляции
(`sandbox/none.go`). Часть мер изоляции не реализована сознательно — см.
`photon-plugin-runtime/docs/sandbox.md`.

## 8. Диагностика

Ядро ведёт журнал событий (`services/diag`): кольцевой буфер, номера `seq`,
курсоры, явное вытеснение, без аллокаций на запись. Наружу — действия
819 (снимок) и 820 (журнал) через `Photon_SendAction` и
`PhotonClient.diagnostics()` в SDK; C ABI для этого не расширялся. В журнал
не попадают payload вызовов, тексты сообщений, токены и ключи.

## 9. Инструменты разработчика

- `photon-devtools-core` — платформонезависимая часть: лента Inspector Live,
  снимок, журнал ядра, панель «Путь подключения» (чистый Kotlin поверх SDK).
- `photon-developer-tools` — консольный инструмент (Linux, JVM):
  `--inspector-live`, `--network-lab`, `--reconnect-lab`, `--performance`,
  `--protobuf-inspector`, `--storage-lab`, `--crypto-lab`, `--plugin-lab`,
  `--logging`. Лабораториям сети нужен сервер протокола (§6).

## 10. Платформы и направления развития

| направление | состояние |
|---|---|
| Linux (x86-64) | ядро, C ABI, JNI, SDK и инструменты собираются и тестируются |
| Android | ядро собирается под Android (NDK); упаковки (AAR) и среды Android-расширений в этом релизе нет — **план** |
| macOS, Windows | ядро и runtime компилируются (кросс-компиляция); C ABI и JNI на этих ОС не собирались и не проверялись — **план** |
| Photon Server | нет — **план**; предпосылка — нейтральный к серверу протокол (§6) |
| Autodial в рабочем пути, TCP-сервер, маскировка | нет — **план** (§5) |

Ссылки вида `ADR-NNN` в исходниках и документах ведут на внутренний журнал
решений проекта; в первый публичный релиз он не входит.
