# DECISIONS.md

## Architecture Decision Records — Photon Ecosystem

Этот файл фиксирует, **почему** архитектура устроена так, как описано в `ARCHITECTURE.md`, а не просто **как**. `ARCHITECTURE.md` — это текущее состояние системы; `DECISIONS.md` — история решений, которые к этому состоянию привели.

Формат записи: **Статус** → **Контекст** → **Решение** → **Последствия**.

Правило ведения журнала:

- Новая запись добавляется только для решений уровня "фундамент", а не для любой правки кода. Ориентир: если решение меняет то, как выглядит `ARCHITECTURE.md`, — это ADR. Если меняет только реализацию внутри уже принятой структуры — это не ADR.
- **Применение существующего правила — не новый ADR.** Если решение по конкретному порту сводится к "назвать по ADR-011" (например, `Identity` вместо `Ed25519Identity`, `Crypto` без упоминания AES, `Media` без упоминания ffmpeg) — это исполнение уже принятого правила, а не новое архитектурное решение. Новый ADR нужен только когда возникает вопрос, на который ADR-011 не даёт готового ответа (как в ADR-012 — не "как назвать", а "должен ли порт вообще поддерживать эту возможность"). Ориентир: если для объяснения решения достаточно one-line ссылки "см. ADR-011" — новый ADR не нужен, ссылки достаточно в комментарии кода.
- Записи не редактируются задним числом. Если решение пересматривается, добавляется новая запись со статусом `Superseded by ADR-XXX`, а старая помечается `Superseded`, но текст не переписывается — история должна быть читаема как есть.
- Нумерация ADR монотонно возрастает и никогда не переиспользуется, даже для отменённых решений.

## ADR-001 — Go как язык ядра

**Статус:** Принято

**Контекст:** Нужен язык для кроссплатформенного ядра (Linux, Windows, Android), способный компилироваться в единый бинарник, естественно работать с конкурентностью на транспортном и plugin-уровне, и предоставлять C ABI для встраивания в другие языки без переписывания бизнес-логики под каждую платформу.

**Решение:** Ядро Photon пишется на Go.

**Последствия:**
- Плюс: единая кроссплатформенная кодовая база, встроенная конкурентность (goroutines/channels) естественно ложится на транспорт и dispatcher, зрелая экосистема для QUIC/protobuf/P2P (pion) и встраиваемых хранилищ (bbolt), CGO/c-shared даёт путь к C ABI без второй реализации ядра.
- Минус: любой binding обязан работать через C ABI — GC и модель памяти Go не могут "просвечивать" наружу напрямую, отсюда требование opaque handles и явного ownership (см. ADR-004).
- См. ARCHITECTURE.md, раздел 4.

## ADR-002 — Ports & Adapters (Hexagonal Architecture)

**Статус:** Принято

**Контекст:** Ядро должно поддерживать замену конкретных реализаций (хранилище, транспорт, идентичность, P2P) без изменения бизнес-логики, и должно тестироваться без реальной сети/диска.

**Решение:** Ядро строится по принципу портов и адаптеров. `ports/` содержит только интерфейсы (storage, transport, identity, crypto, media, p2p, plugin, notification), `adapters/` — их конкретные реализации (bbolt, ed25519, QUIC/TCP, pion). Направление зависимости всегда внутрь — к абстракции.

**Последствия:**
- Плюс: замена реализации (например, bbolt на другую БД) не требует правок бизнес-логики; сервисы тестируются через моки портов.
- Минус: дисциплина обязательна — соблазн "быстро добавить логику прямо в адаптер" со временем размывает границу, если не следить за этим сознательно.
- Правило: новый порт заводится только когда существующие семь портов реально не покрывают потребность, и это решение фиксируется отдельным ADR, а не тихой правкой.
- См. ARCHITECTURE.md, раздел 3.

## ADR-003 — Photon как платформа, ENGRAM как приложение

**Статус:** Принято

**Контекст:** Без явного разделения ответственности продуктовая логика (чат, кошелёк, игры) со временем просачивается в ядро, и через некоторое время ядро становится непригодным для любого другого приложения, кроме первого.

**Решение:** Photon — платформенный движок (хранение, транспорт, идентичность, безопасность, расширяемость). ENGRAM — первое приложение поверх него. Правило разделения: если функциональность может понадобиться другому, не связанному с ENGRAM приложению — она принадлежит Photon; иначе — ENGRAM или Plugin SDK.

**Последствия:**
- Плюс: ядро остаётся пригодным для любого будущего приложения, не только ENGRAM.
- Минус: требует дисциплины при разработке ENGRAM — легче было бы "просто добавить в ядро", когда есть только один продукт и дедлайн.
- См. ARCHITECTURE.md, раздел 1–2.

## ADR-004 — C ABI как единственная публичная граница

**Статус:** Принято

**Контекст:** Ядро на Go должно быть доступно из Kotlin/JNI (Android), Desktop-клиентов и потенциально других языков. Без единой границы каждая платформа обрастает своим способом вызова ядра (gomobile для Android, что-то ещё для Desktop), и любое изменение ядра требует синхронной правки нескольких несовместимых интеграций.

**Решение:** `photon-bindings/c/photon_core.h` — единственная публичная граница. Ни один язык или платформа не вызывает Go напрямую, только через этот заголовок. ABI держится намеренно минимальным: `Photon_GetABIVersion`, `Photon_Create`, `Photon_Destroy`, `Photon_SendAction`, `Photon_SetEventCallback`, `Photon_GetLastError`, `Photon_Free{String,Bytes}` — вся ресурсная специфика идёт через `action_code`/`payload_json` внутри `Photon_SendAction`, а не через рост числа экспортируемых функций. Память — через opaque handles и явные `Photon_Free*` (что создал Photon, освобождает только Photon). Ошибки — через `PhotonResult` + `Photon_GetLastError`, не через специфичные для функции коды.

**Последствия:**
- Плюс: любой будущий binding (Rust, Swift, Python FFI) строится вокруг одного и того же контракта; ядро можно менять внутренне без синхронных правок во всех клиентах.
- Минус: минимальный ABI менее удобен для конкретного клиента, чем набор типизированных функций на каждый ресурс — это осознанная жертва в пользу поддерживаемости на годы вперёд.
- Требует ADR-007 (ABI Freeze Policy) как следствие: раз ABI единственный и минимальный, его изменение должно быть редким и осознанным событием.
- См. ARCHITECTURE.md, раздел 7, 7.0–7.4.

## ADR-005 — Plugin Runtime в отдельном процессе

**Статус:** Принято

**Контекст:** Плагины — код сторонних разработчиков, потенциально нестабильный или вредоносный. Если плагин выполняется внутри процесса ядра, его падение или нарушение прав может уронить или скомпрометировать всё ядро.

**Решение:** Плагин никогда не живёт внутри ядра. Схема: `Photon Core → IPC → Plugin Host → Plugin`. Права плагина заявляются в манифесте и проверяются на уровне IPC. Зависимость всегда направлена снизу вверх: `Photon Core ← Plugin Runtime ← Plugin SDK ← Plugins`; ядро не импортирует код плагинов и не хранит списка "известных" плагинов.

**Последствия:**
- Плюс: падение плагина не роняет ядро; плагин не может напрямую читать память ядра или других плагинов.
- Минус: IPC-граница добавляет накладные расходы по сравнению с in-process выполнением; требует отдельного тестового полигона (`tests/plugins/`: hello, crash, permission, storage, stress).
- См. ARCHITECTURE.md, раздел 6.

## ADR-006 — Security как часть ядра, а не отдельный репозиторий

**Статус:** Принято

**Контекст:** Права доступа, проверка подписей и sandbox можно было бы вынести в отдельный репозиторий/пакет, версионируемый независимо от ядра.

**Решение:** `photon-core/security/` остаётся частью `photon-core`, не выносится в отдельный репозиторий.

**Последствия:**
- Плюс: исключён риск версионного рассинхрона (ядро одной версии, проверки прав — другой) и риск теоретической сборки ядра без security-проверок.
- Минус: security не может релизиться/патчиться независимо от остального ядра — любой security-фикс требует релиза всего `photon-core`. Это принято как приемлемый компромисс, так как security и так пронизывает всё ядро (плагины, транспорт, ENSTOR-пакеты).
- См. ARCHITECTURE.md, раздел 9.

## ADR-007 — Photon Developer Tools как основная среда разработки

**Статус:** Принято

**Контекст:** Первый клиент ядра изначально задумывался как "debug client" — вспомогательный инструмент отладки. По мере проектирования выяснилось, что на нём фактически строится тестирование каждого компонента платформы (транспорт, storage, plugin runtime, protobuf, логи) ещё до появления ENGRAM.

**Решение:** Переименован из "Debug Client" в **Photon Developer Tools** — не вспомогательный инструмент, а основная среда разработки платформы, по роли близкая к IDE для Photon. Включает Dashboard, Network Lab, Storage Viewer, Crypto Lab, Plugin Lab, Protobuf Inspector, Logging, Performance.

**Последствия:**
- Плюс: явно фиксирует приоритет — Phase 16 (Developer Tools) не может считаться второстепенной задачей "когда будет время".
- Минус: увеличивает scope первого клиента по сравнению с минимальным debug-инструментом.
- См. ARCHITECTURE.md, раздел 7.7.

## ADR-008 — ABI Freeze Policy

**Статус:** Принято

**Контекст:** Публичный C ABI (ADR-004) — единственная граница между ядром и всеми клиентами разом. Без формального процесса изменение ABI со временем начинает происходить как побочный эффект обычных коммитов ("заодно поправил сигнатуру"), что синхронно ломает Android, Desktop и любые будущие биндинги.

**Решение:** После ревью `photon_core.h` помечается как **ABI v1 frozen**. С этого момента любое изменение сигнатуры, поведения или ownership-семантики любой функции из заголовка — событие уровня новой версии ABI, требующее отдельного архитектурного обсуждения и инкремента `PHOTON_ABI_VERSION`, а не обычный PR. До заморозки правило не действует — заголовок можно свободно дорабатывать по мере реализации `bindings/c`.

**Последствия:**
- Плюс: ABI становится самым консервативным элементом системы, в отличие от `ports/`, которые могут эволюционировать свободнее на раннем этапе.
- Минус: любая ошибка в дизайне API, не замеченная до заморозки, живёт в ABI дольше, чем аналогичная ошибка в остальном коде — это осознанная цена стабильности контракта.
- См. ARCHITECTURE.md, раздел 7.5.1.

## ADR-009 — Photon Protocol как общий контракт, не деталь Bridge

**Статус:** Принято

**Контекст:** На раннем этапе реализации action-коды и wire-структуры (`Response`, `HeaderFrame`, payload-типы) оказались объявлены непосредственно в `photon-quic-bridge/server/protocol.go`. Это создаёт риск, что ядро платформы окажется зависимым от конкретной серверной интеграции с Mattermost — то есть от одной из деталей реализации, а не от общего контракта.

**Решение:** Action-коды и payload/response-схемы — это **Photon Protocol**, самостоятельный контракт, физически определяемый в `photon-core/protobuf/` (`photon.proto`). И Core (через `Photon_SendAction`), и `photon-quic-bridge`, и любой будущий bridge (WebSocket, HTTP, mock/тестовый сервер) — равноправные потребители этого протокола. Ни одна из сторон не является его владельцем.

**Последствия:**
- Плюс: протокол можно реализовать другим транспортом (WebSocket bridge, HTTP bridge, mock-сервер для тестов) не меняя сам протокол и не трогая ядро.
- Минус: требует миграции — на момент принятия этого решения action-коды всё ещё физически объявлены в `photon-quic-bridge`, а не в `photon-core/protobuf/`. Это зафиксировано как блокер в `ROADMAP.md` (Phase 5) перед заморозкой ABI v1 (ADR-008): пока протокол не перенесён, `Photon_SendAction` в `photon_core.h` фиксирует зависимость на неверном уровне.
- См. ARCHITECTURE.md, раздел 7.6.

## ADR-010 — Storage port: Namespace вместо Bucket, схема только через Migrate

**Статус:** Принято

**Контекст:** Первый черновик `ports/storage.go` был написан по образцу bbolt: транзакции `View`/`Update` с колбэком, ключи внутри `bucket []byte`, явное `CreateBucketIfNotExists` в `WriteTx`. При ревью перед тем, как использовать этот интерфейс как образец для остальных портов, возникли три вопроса:

1. Должен ли `Storage` вообще знать о bucket'ах, или это деталь реализации bbolt?
2. Не станет ли понятие bucket искусственным ограничением, если появится другой backend (SQLite, Badger, Pebble)?
3. Не должно ли ядро оперировать более абстрактным понятием (namespace/collection), оставляя маппинг на bucket/таблицу/префикс — адаптеру?

Проверка по трём кандидатным backend'ам показала, что `bucket` — реальная утечка реализации: у Badger и Pebble нет встроенного понятия bucket (плоский keyspace, bucket эмулируется префиксом ключа), у SQLite bucket не мапится на таблицу один в один (таблица требует схемы столбцов, а не просто имени).

Отдельно проверена модель транзакций `View`/`Update` с колбэком — она осталась без изменений, так как оказалась не специфичной для bbolt: Badger реализует тот же паттерн API, а для Pebble/SQL-подобных backend'ов closure-style тривиально оборачивается в helper. Разделение `ReadTx`/`WriteTx` как разных типов даёт статическую гарантию (запись внутри `View` — ошибка компиляции), что признано полезным независимо от backend'а.

**Решение:**

- `Storage`/`ReadTx`/`WriteTx` оперируют `namespace string` вместо `bucket []byte`. Маппинг namespace → физическая структура (bucket в bbolt, префикс ключа в Badger/Pebble, таблица в SQLite) — целиком ответственность адаптера, не специфицируется портом.
- `CreateBucketIfNotExists` убран из `WriteTx` полностью. Единственный механизм, которым namespace "начинает существовать" — `Storage.Migrate`. Как это происходит физически внутри `Migrate` — решает адаптер; порт гарантирует только внешнее поведение: `Put`/`Delete`/`Get` в неподготовленный namespace возвращают `ErrNamespaceNotFound`, а не создают его неявно.
- Добавлен `ForEachPrefix` — не гипотетическое расширение, а отражение уже существующего в системе паттерна (Engram-хендлеры в `photon-quic-bridge` листят ключи по префиксу).

**Последствия:**

- Плюс: `adapters/bbolt` остаётся первым и самым естественным адаптером (namespace → bucket — тривиальный маппинг один в один), но порт не обязывает второй адаптер (например, будущий `adapters/badger` или `adapters/sqlite`) эмулировать понятие, которого в его модели данных нет.
- Плюс: принцип "схема управляется только миграциями" (согласованный ранее для bbolt-bucket'ов) сохранён и даже усилен — теперь он верен для любого backend'а, а не только для bbolt.
- Минус: `ForEachPrefix` как отдельный метод от `ForEach` — небольшое дублирование поверхности API (оба метода семантически частично пересекаются: `ForEach` эквивалентен `ForEachPrefix` с пустым `prefix`). Принято как оправданный компромисс ради явного, самодокументируемого вызова на стороне клиента порта.
- См. `ports/storage.go`, `ports/errors.go`.

## ADR-011 — Правило проверки ports/ на утечку реализации

**Статус:** Принято

**Контекст:** ADR-010 показал на конкретном примере (`bucket` → `namespace`), что порт, спроектированный "по образу первой выбранной библиотеки", со временем вынуждает вызывающий код разбирать случаи по backend'у (`if backend == bbolt { bucket } if backend == sqlite { table }`) — абстракция начинает течь. Это не одноразовая проблема `storage.go`, а системный риск для любого порта, написанного при наличии в голове одной конкретной реализации.

**Решение:** Для любого типа, имени или метода в `ports/` действует обязательная проверка перед принятием: совпадает ли оно по смыслу с названием конкретной библиотеки или продукта, а не с понятием уровня платформы.

Плохо (утечка реализации):
```go
QuicConnection()
BoltTransaction()
PionAgent()
CreateBucketIfNotExists()
```

Хорошо (понятие уровня платформы):
```go
Transport()
Session()
PeerConnection()
Namespace
```

Проверочный вопрос при написании или ревью любого порта: *"Если завтра появится второй адаптер на совершенно другой библиотеке — останется ли это имя осмысленным без изменений?"* Если ответ "нет" или "придётся объяснять через if" — имя или структура порта спроектированы неверно.

**Последствия:**

- Плюс: единообразная проверка, применимая к каждому из оставшихся портов (`transport.go`, `identity.go`, `crypto.go`, `media.go`, `p2p.go`, `plugin.go`, `notification.go`) без необходимости каждый раз изобретать критерий заново.
- Минус: требует дисциплины на ревью — проверка не автоматизируется линтером, полагается на осознанность при написании и чтении PR.
- Это правило процесса, а не архитектуры системы — оно не описывает компонент Photon, а описывает, как принимаются решения о дизайне `ports/`. Именно поэтому оно зафиксировано в `DECISIONS.md`, а не в `ARCHITECTURE.md`.

## ADR-012 — Transport port: только исходящие соединения (провизорно)

**Статус:** Принято

**Контекст:** При проектировании `ports/transport.go` по правилу ADR-011 интерфейс получился без протокольных/адресных утечек (`Connect`, `OpenStream`, `AcceptStream`, `OpenUniStream`, `AcceptUniStream`, `Close` — ни одного упоминания QUIC/TCP/IPv4/IPv6 в сигнатурах). Отдельно возник вопрос: должен ли порт поддерживать входящие соединения (Listen), раз Photon — платформа, а не просто клиентская библиотека.

На сегодня единственный реальный сервер (`photon-quic-bridge`) физически отделён от Core и слушает сам, вне этого порта; сценарии "узел одновременно клиент и сервер" покрываются отдельным портом `p2p.go`. Поэтому `Listen` в порт не добавлен. Но зафиксировать это как постоянное архитектурное решение было бы неверно — платформа в целом может через несколько лет обзавестись сценарием, где Core сам слушает входящие соединения (mesh-узел, встроенный локальный сервис).

**Решение:** `Transport` определяет только исходящие соединения (dial) на текущем этапе. Это явно провизорное ограничение, а не окончательный дизайн: добавление входящих соединений в будущем — предмет отдельного ADR, а не тихое расширение интерфейса задним числом.

**Последствия:**

- Плюс: порт остаётся минимальным и соответствует единственному сегодня реальному сценарию использования (Core как клиент).
- Плюс: явная формулировка "не добавляется без отдельного ADR" предотвращает как случайное разрастание интерфейса, так и ошибочное толкование текущего дизайна как постоянного запрета на серверную роль.
- Минус: если серверный сценарий понадобится раньше, чем ожидается, потребуется отдельный цикл ревью (новый ADR) прежде чем писать код — это осознанная цена, не случайная блокировка.
- См. `ports/transport.go`.

## ADR-013 — Порты проектируются от потребностей ядра, а не от возможностей первого адаптера

**Статус:** Принято

**Контекст:** ADR-011 даёт проверку постфактум — правильно ли названа уже написанная сигнатура. Но у `storage.go` (ADR-010) проблема была на уровень глубже названия: сама *форма* контракта (`bucket`, `CreateBucketIfNotExists`) была продиктована тем, что первый адаптер — bbolt, а не тем, что реально нужно ядру. Правильное имя на неправильной форме интерфейса ADR-011 не поймает: `RenameBucket()` в `EnsureNamespace()` не переименовать и не заметить, что сама операция лишняя.

**Решение:** При проектировании любого порта в `ports/` источник требований — сценарии использования ядром (`services/`, `Photon_SendAction` через C ABI, будущие плагины), а не то, что "удобно, раз первый адаптер уже выбран". Практически это означает: прежде чем писать метод порта, явно назвать сценарий ядра, который его требует (как `ForEachPrefix` был добавлен не гипотетически, а по наблюдаемому паттерну Engram-листинга) — а не переносить метод из документации/API первой библиотеки один в один.

**Последствия:**

- Плюс: защищает не только от плохих имён (это ADR-011), но и от лишних или неверно сформированных операций в контракте — цена ошибки в форме интерфейса выше цены ошибки в имени, потому что затрагивает не только адаптер, но и всех потребителей порта.
- Минус: требует на старте проектирования порта явно сформулировать сценарии использования, а не просто "обернуть" API первой библиотеки — это медленнее в моменте написания первой версии.
- Совместно с ADR-011 формирует полный чек-лист аудита порта: (1) форма контракта — от потребности ядра или от первого адаптера? (2) имена — не совпадают ли с конкретной технологией?
- Не требует новых ADR при простом применении к очередному порту (см. правило ведения журнала выше) — применяется как чек-лист, а не порождает отдельную запись на каждый порт.

## ADR-014 — Identity port: PrivateKey как []byte, а не opaque handle (провизорно)

**Статус:** Принято

**Контекст:** При проектировании `ports/identity.go` по ADR-013 (форма контракта — от потребности ядра) возник вопрос: представлять `PrivateKey` как обычные байты или как непрозрачный handle, аналогично `PhotonHandle` в C ABI (ADR-004)? Разница принципиальна для одного конкретного будущего сценария: аппаратное хранение ключей (HSM, Secure Enclave), где приватный ключ физически не может покинуть защищённый модуль — то есть `[]byte`-представление там в принципе невозможно, нужен handle, за которым скрыта операция "подписать, не показывая ключ наружу".

Phase 3 предполагает единственный адаптер — `adapters/ed25519`, программную реализацию без аппаратной защиты. Проектировать под HSM сейчас означало бы усложнять первый порт ради backend'а, которого нет даже в планах — то же рассуждение, что уже приводило к сознательному сужению scope в ADR-012 (Listen для Transport).

**Решение:** `PrivateKey`, `PublicKey`, `Signature` — именованные типы поверх `[]byte`. Это текущее ограничение, а не постоянное архитектурное решение. Если/когда появится потребность в аппаратном хранении ключей, представление `PrivateKey` меняется через отдельный ADR, а не тихой правкой сигнатур.

**Последствия:**

- Плюс: простой, идиоматичный для Go контракт, тривиально реализуемый `adapters/ed25519` без лишней косвенности.
- Плюс: явная фиксация границы (аналогично ADR-012) не даёт будущему разработчику принять `[]byte` за постоянное решение и молча "просто добавить" HSM-адаптер, ломая приватность ключа через `[]byte`.
- Минус: если HSM/Secure Enclave понадобится раньше, чем ожидается, `PrivateKey` меняет форму (bytes → handle), что breaking change для любого написанного к тому моменту кода поверх этого порта — осознанная цена простоты сегодня.
- См. `ports/identity.go`.

## ADR-015 — Transport: однонаправленные потоки как опциональная возможность

**Статус:** Superseded by ADR-016

**Контекст:** При ревью `transport.go` возник вопрос к `OpenUniStream`/`AcceptUniStream` в обязательном контракте `Connection`: применить к ним тот же тест ADR-011 — "останется ли интерфейс естественным для второго адаптера?" — и результат оказался неоднозначным. QUIC поддерживает однонаправленные потоки нативно. TCP — нет вообще; TCP-адаптер (Phase 6, реально запланированный, не гипотетический) и так обязан реализовать собственный слой мультиплексирования поверх одного сокета, чтобы удовлетворить `OpenStream`/`AcceptStream` — но требовать от него дополнительно эмулировать именно однонаправленность было бы формой контракта, продиктованной удобством первого адаптера (QUIC), а не потребностью ядра per se.

При этом сама потребность (получать push-события, не имея возможности ответить на том же канале) реальна и уже наблюдается в существующем коде (`photon-quic-bridge`, паттерн Subscribe). Вопрос не в том, нужна ли эта возможность ядру, а в том, должна ли она быть частью обязательного контракта `Connection`, который реализует каждый адаптер.

**Решение:** `OpenUniStream`/`AcceptUniStream` вынесены из обязательного интерфейса `Connection` в отдельный опциональный интерфейс `UniStreamConnection`, по идиоматичному для Go паттерну optional capability (аналогично `io.ReaderFrom`/`io.WriterTo`, `http.Flusher`/`http.Hijacker` в стандартной библиотеке). Адаптер, который умеет однонаправленные потоки нативно и эффективно (QUIC), реализует этот интерфейс дополнительно к `Connection`. Вызывающий код делает type assertion и, если адаптер его не реализует (TCP), использует обычный `Stream`, задействуя только одну его половину — функционально эквивалентно, но без typed-гарантии однонаправленности и без протокольной оптимизации QUIC.

**Последствия:**

- Плюс: `Connection` как обязательный контракт остаётся одинаково естественным для QUIC и TCP — ни один адаптер не обязан эмулировать то, чего в его протоколе нет.
- Плюс: QUIC не теряет реальное протокольное преимущество (меньше накладных расходов на канал, который никогда не используется в обратную сторону) — оно доступно через type assertion, а не убрано вовсе.
- Минус: вызывающий код (services/dispatcher), которому нужна эффективность uni-стрима, обязан явно обрабатывать оба случая (adapter реализует `UniStreamConnection` или нет) — не полностью прозрачно для потребителя порта.
- Минус: type-assertion-based опциональность — паттерн менее строгий на этапе компиляции, чем обычный обязательный метод интерфейса; ошибка "адаптер не поддерживает эту возможность" обнаруживается в рантайме (при неудачном assertion), а не на этапе компиляции.
- См. `ports/transport.go`.

## ADR-016 — UniStream возвращён в обязательный контракт Connection

**Статус:** Принято (supersedes ADR-015)

**Контекст:** При ревью ADR-015 был задан прямой вопрос по критерию ADR-013: это решение продиктовано реальной потребностью ядра или желанием сделать интерфейс максимально универсальным "на всякий случай"? Проверка по существу показала следующее.

TCP и Reality — не гипотетические, а реально запланированные адаптеры (два из пяти шагов autodial-лестницы, ARCHITECTURE.md раздел 5). У обоих действительно нет нативной поддержки однонаправленных потоков на уровне протокола. Однако ключевой вопрос не "поддерживают ли они uni-stream нативно", а "могут ли они его реализовать". Ответ — да, и почти без дополнительных затрат: TCP-адаптер и так обязан построить собственный слой мультиплексирования поверх одного сокета, чтобы вообще удовлетворить обязательный `OpenStream`/`AcceptStream` (в TCP нет и мультиплексирования как такового). Как только этот слой существует, пометить один виртуальный поток как однонаправленный — это соглашение внутри уже существующего собственного протокола кадрирования адаптера, а не требование к новой возможности сети, которой в TCP нет. То же верно для Reality, которая также работает поверх байтового потока.

Таким образом, барьер, из-за которого ADR-015 выносил `UniStreamConnection` в опциональный интерфейс, при ближайшем рассмотрении не является техническим барьером — это разница в объёме работы, которую TCP/Reality-адаптер и так обязан проделать для базовой многопоточности. Настоящей потребности в опциональности (a-la `io.ReaderFrom`, где часть реализаций `io.Writer` физически не может её предоставить эффективно) здесь нет.

**Решение:** `OpenUniStream`/`AcceptUniStream` возвращены в обязательный интерфейс `Connection`. Отдельный `UniStreamConnection` удалён из `ports/transport.go`.

**Последствия:**

- Плюс: устраняются оба минуса, зафиксированных в ADR-015, — вызывающему коду (services/dispatcher) больше не нужно обрабатывать два случая через type assertion; ошибка "адаптер не поддерживает" больше не может проявиться в рантайме, потому что перестаёт быть возможной в принципе — каждый адаптер обязан её реализовать.
- Минус: TCP/Reality-адаптеры обязаны реализовать собственное кадрирование для uni-потоков в рамках своего слоя мультиплексирования — но это входит в объём работы, уже необходимой им для базового `OpenStream`/`AcceptStream`, а не является дополнительной нагрузкой сверх того, что и так предстояло сделать.
- Процессный урок: тест ADR-013 ("это от потребности или от желания универсальности?") стоит применять не только к решению добавить возможность, но и к решению вынести её в опциональную — сама опциональность тоже может быть продиктована "на всякий случай", а не реальным техническим ограничением, и это стоит явно проверять, а не считать очевидным из одного факта "у протокола X нет нативной поддержки Y".
- См. `ports/transport.go`.

## ADR-017 — Photon ID: платформенный идентификатор, не часть Identity port

**Статус:** Superseded by ADR-018

**Контекст:** При обсуждении модели пользователя возник вопрос, куда должен относиться Photon ID — числовой публичный идентификатор пользователя/узла (формат `00 0000 0000`: два зарезервированных ведущих разряда + десять значащих, без привязки к телефону, email или иному внешнему идентификатору). Соблазн — добавить его прямо в `ports/identity.go`, рядом с `PublicKey`, поскольку Photon ID логически производится из публичного ключа.

Проверка по ADR-013 (форма контракта — от потребности ядра): `Identity` как порт нужен ядру для ровно четырёх операций — сгенерировать пару ключей, подписать, проверить подпись, получить публичный ключ из приватного (см. identity.go). Ни одна из них не требует знания о Photon ID. Присвоение, поиск, уникальность и отображение Photon ID — это не криптографическая операция, а операция состояния (запись `PhotonID ↔ PublicKey ↔ DisplayName` и её поиск), то есть бизнес-логика уровня `services/`, а не примитив уровня `ports/`.

**Решение:** Photon ID не добавляется в `Identity` port ни как метод, ни как тип. Разделение:

```
PrivateKey → (Identity.PublicKeyOf) → PublicKey → (будущий сервис) → PhotonID
```

- `Identity` (ports/identity.go) знает только про ключи и подписи — без изменений в уже написанном коде.
- Присвоение и хранение связи `PhotonID ↔ PublicKey` — задача будущего сервиса уровня `services/` (условно `services/account` или `services/profile`), построенного поверх уже существующих `Storage` (namespace вида `photon.accounts`, ключ — PhotonID, значение — профиль с публичным ключом) и `Identity` (для проверки подписей при операциях с профилем). Новый порт под это не заводится — существующих `Storage`+`Identity` достаточно.
- Формат Photon ID (при реализации упомянутого сервиса): 12-значный численный идентификатор, `00 0000 0000` — первые два разряда зарезервированы под будущее использование (например, шардирование/версионирование), остальные десять — значащий номер. Рекомендуемое представление — именованный строковый тип (`type PhotonID string`), а не целочисленный: строка сохраняет ведущие зарезервированные нули без ручного дополнения при каждом выводе; внутреннее хранение как числа (если нужна компактность в Storage) — деталь реализации сервиса, не часть публичного типа.

**Последствия:**

- Плюс: `Identity` остаётся минимальным и не приобретает знания о том, как устроена система пользователей платформы — при полной смене модели идентификаторов (например, отказ от числового Photon ID в пользу другого формата) `ports/identity.go` не меняется вообще.
- Плюс: явное отсутствие внешних идентификаторов (телефон, email) в модели соответствует уже принятому принципу автономности платформы (ARCHITECTURE.md, философия) — Photon ID никогда не был частью Identity именно потому, что не является криптографическим понятием.
- Минус: сервис `Account`/`Profile` пока не описан в `ROADMAP.md` как отдельная фаза — это открытый пробел, который следует закрыть до того, как ENGRAM (Phase 19+) станет зависеть от адресации пользователей по Photon ID.
- См. `ports/identity.go` (без изменений), `ROADMAP.md` (добавлена заметка о будущей фазе).

## ADR-018 — Photon ID: финальный формат и точка реализации (уточняет ADR-017)

**Статус:** Принято (supersedes ADR-017)

**Контекст:** ADR-017 зафиксировал границу ответственности (Photon ID — не часть Identity port), но оставил открытыми конкретику формата (12 цифр с зарезервированными разрядами) и точку реализации. При дальнейшем обсуждении формат уточнён и упрощён, а точка реализации привязана к конкретному будущему компоненту, а не к абстрактному "когда-нибудь".

**Решение — формат:**

- Photon ID — публичный постоянный идентификатор аккаунта.
- Длина: 9 цифр. Представление: `type PhotonID string`.
- Диапазон: `000000000`–`999999999`. Ведущие нули обязательны.
- `000000000` — валидный пользовательский Photon ID, не зарезервирован.
- Photon ID не содержит закодированной информации о пользователе (в отличие от рассматривавшейся ранее идеи зарезервированных ведущих разрядов — от неё отказались в пользу простоты: диапазон полностью плоский, без специальных подпространств).

**Решение — свойства:**

- Назначается один раз.
- Не изменяется после создания.
- Не переиспользуется после удаления аккаунта (удалённый Photon ID не возвращается в пул выдачи).

**Решение — граница ответственности (подтверждает ADR-017):**

Photon ID не относится к `Identity`. `Identity` отвечает только за криптографическую личность — ключи, подписи, проверку подписи (см. identity.go, без изменений). Связь:

```
PhotonID → Account/Profile → Identity
```

реализуется будущим Account/Profile сервисом поверх уже существующих `Storage` и `Identity` — новый порт под это не заводится.

**Решение — точка реализации:**

Реализация Photon ID откладывается до появления Account/Profile сервиса. Логическая точка: не Phase 2 (Storage — только фундамент хранения), не Phase 3 (Identity — остаётся исключительно криптографическим слоем), а после стабилизации обоих и при появлении потребности ENGRAM/сервисов адресовать пользователей — ориентировочно "Phase 3+", без закреплённого номера в `ROADMAP.md` до момента, когда Account/Profile перестанет быть гипотетическим.

До этого момента:
- отдельный порт для Photon ID не создаётся;
- `identity.go` не изменяется;
- `Storage` не получает специальной логики для Photon ID.

**Последствия:**

- Плюс: формат зафиксирован один раз (9 цифр) и не потребует миграции с 8 на 10 на 12 цифр — весь диапазон 000000000–999999999 доступен с первого дня, без зарезервированных подпространств, которые пришлось бы объяснять или высвобождать позже.
- Плюс: решение принято сейчас, когда контекст обсуждения свеж, но код появляется только вместе с реальным владельцем состояния (Account/Profile) — не раньше, что соответствует ADR-013 (форма контракта от подтверждённой потребности, не заранее).
- Минус: 9 цифр (10⁹ ≈ 1 млрд значений) — конечный ресурс без встроенного механизма расширения (в отличие от рассматривавшейся ранее схемы с зарезервированными диапазонами). Если пространство когда-либо начнёт исчерпываться, потребуется отдельное архитектурное решение (новый ADR) — вероятно, о переходе на больший формат для новых ID при сохранении старых, а не о простом "довыпуске" из резерва, поскольку резерва в этой версии решения не заложено.
- См. `ROADMAP.md` (заметка под Phase 3, обновлена ссылка на ADR-018).

## ADR-019 — Notifier: NotificationTarget вместо PublicKey

**Статус:** Принято

**Контекст:** При ревью `notification.go` `Notify` изначально принимал получателя как `PublicKey` (по аналогии с P2P `Peer`). При проверке обнаружено: push-системы (APNs, FCM, WebPush) не оперируют криптографическими ключами — они знают device token/registration token/endpoint. Связь `PublicKey ↔ адрес доставки push` оказалась той же по форме, что и `PublicKey ↔ PhotonID` (ADR-017/018): производные данные аккаунта, а не часть криптографической идентичности. Если оставить `PublicKey` в сигнатуре `Notify`, адаптер неизбежно должен был бы сам разрешать `PublicKey → push-токен`, то есть зависеть от каталога пользователей — размывая границу между `Notifier` и будущим Account/Profile сервисом.

**Решение:** `Notify` принимает `NotificationTarget` — уже разрешённый адрес доставки, непрозрачный для порта. Разрешение `PublicKey → NotificationTarget` происходит выше по вызову (Dispatcher → Account/Profile), не внутри `Notifier` и не внутри адаптера. `Notifier` не содержит ссылок на `PublicKey` и не зависит от каталога пользователей.

**Последствия:**

- Плюс: `Notifier` остаётся тестируемым и реализуемым без какого-либо Account/Profile сервиса — тестовый адаптер может просто получать `NotificationTarget` напрямую, не нуждаясь в разрешении идентичности.
- Плюс: единообразие с ADR-017/018 — уже второй случай, где "производный от PublicKey идентификатор" сознательно вынесен за пределы порта в будущий Account/Profile сервис. Закрепляет общий паттерн: любой порт, которому понадобится "адрес получателя" в форме, отличной от `PublicKey` (email, номер телефона нигде не используется, но сама форма проблемы та же) — по умолчанию не должен резолвить его сам.
- Минус: вызывающий код (Dispatcher) обязан явно резолвить `NotificationTarget` перед вызовом `Notify` — на один шаг больше, чем "передал PublicKey и всё сработало", но это осознанная цена сохранения границы.
- См. `ports/notification.go`.

## ADR-020 — Ports v1 Freeze Policy

**Статус:** Принято

**Контекст:** Все 8 портов (`storage.go`, `transport.go`, `identity.go`, `crypto.go`, `media.go`, `p2p.go`, `plugin.go`, `notification.go`) прошли полный цикл: ADR по спорным решениям → аудит на утечку реализации (ADR-011/013/016) → сборка → ревью → правки, а затем пакет целиком прошёл итоговую ревизию по чек-листу (единообразие комментариев, отсутствие ссылок на несуществующие ADR/адаптеры, обоснованность каждого `Close()`, консистентность именованных типов). За время проектирования почти все изменения были упрощающими (Plugin → Authorizer, PeerID не появился, PhotonID не попал в Identity, PublicKey убран из Notifier, лишние Close() убраны) — устойчивый сигнал, что границы ответственности найдены, а не подгоняются по ходу дела.

Это прямая параллель ADR-008 (ABI Freeze Policy для `photon_core.h`): там уже был сформулирован принцип, что публичный контракт, из-за которого синхронно ломается сразу много потребителей при изменении, должен быть самым консервативным элементом системы. `ports/` — ровно такой контракт: от него зависят все будущие адаптеры (Phase 2+), все future services/, и весь Photon Protocol/dispatcher поверх них.

Логическая цепочка, приводящая к этому ADR: ADR-011 (проверка портов на утечку реализации) → ADR-013 (форма контракта от потребности ядра, а не от адаптера) → восемь портов, спроектированных и отревьюированных по этим двум правилам → ADR-020 (заморозка результата). Freeze — не отдельное решение "с нуля", а следствие того, что ADR-011/013 уже отфильтровали большую часть возможных ошибок дизайна до этого момента.

**Решение:** Пакет `ports/` замораживается как публичный контракт v1. С этого момента любое изменение публичного контракта `ports/`, влияющее на его API или обязательства реализаций (изменение сигнатуры метода, добавление/удаление метода или типа, изменение семантики уже существующего поведения), — это не обычный коммит, а архитектурное решение, требующее нового ADR с явным обоснованием подтверждённой потребности (по образцу ADR-017→ADR-018: не "мелкое улучшение", не "пока всё равно никто не использует", а реальная необходимость, вскрытая при реализации адаптеров или сервисов). Это не распространяется на исправление опечаток, уточнение или расширение doc-комментариев без изменения самого контракта — такие правки остаются обычными коммитами.

Заморозка не означает, что пакет не может измениться никогда — как и ABI (ADR-008), она означает, что изменение перестаёт быть тихим и становится осознанным событием.

**Последствия:**

- Плюс: адаптеры (Phase 2+) и сервисы, которые будут строиться поверх `ports/`, получают стабильную основу — не нужно опасаться, что контракт уйдёт из-под ног в процессе реализации.
- Плюс: сохраняет тот же процесс, что уже доказал себя на всех 8 портах (включая случай ADR-015→016, где решение было пересмотрено после более глубокой проверки, не будучи "неприкасаемым") — заморозка не отменяет способность исправлять ошибки, а поднимает планку для изменений.
- Минус: любая недоработка в дизайне, не замеченная до заморозки, будет жить в контракте дольше, чем аналогичная ошибка в остальном коде — та же цена, что уже принята для ABI в ADR-008.
- **Важное разграничение (см. правило завершённости фазы, ROADMAP.md):** архитектурная заморозка — не то же самое, что закрытие Phase 1 по правилу "реализовано + тесты + документированы". Тесты и документация пакета `ports` всё ещё не выполнены — Phase 1 остаётся 🟡 до их появления, даже при замороженном контракте. Заморозка фиксирует **API**, не завершённость **фазы**.
- См. `ROADMAP.md`, раздел Phase 1.

## ADR-021 — Device Trust Model

**Статус:** Принято

**Контекст:** До этого момента модель аутентификации клиента нигде явно не была зафиксирована — обсуждались отдельные части (Identity как крипто-порт, PhotonID как платформенный идентификатор, ADR-017/018), но не то, как узел вообще доказывает серверу, что он — это он. Без явного решения здесь есть реальный риск постепенного дрейфа к клиентским X.509-сертификатам и собственному CA просто потому, что это привычный паттерн (Caddy/Let's Encrypt уже упоминались в контексте инфраструктуры) — а исправление такого дрейфа после того, как Transport/Bridge/Bindings/мобильные клиенты уже написаны под сертификатную модель, обошлось бы кратно дороже, чем зафиксировать решение сейчас.

**Решение — четыре принципа:**

1. Корень доверия для привязки устройства к аккаунту — внешний OAuth/OIDC Identity Provider (сегодня Google, архитектурно заменим на любой другой — принцип тот же, что ADR-011 применяет к портам: имя конкретного провайдера не должно быть вшито в модель).
2. Каждое устройство имеет собственную пару Ed25519, создаваемую через уже существующий `Identity.Generate` (`ports/identity.go`, без изменений).
3. Приватные ключи устройств никогда не покидают устройство — не экспортируются автоматически, хранятся средствами ОС (Keystore/Secret Service/DPAPI/Keychain).
4. Photon не использует клиентские X.509-сертификаты и собственную PKI для аутентификации устройств. TLS/QUIC остаётся исключительно транспортным шифрованием канала — вопрос, ортогональный вопросу "кому я доверяю", и сервер может продолжать использовать обычный серверный TLS-сертификат (включая инфраструктуру вроде Caddy) без противоречия принципу, поскольку это не механизм аутентификации клиента.

Подробное описание модели (Device Identity, Account, Transport Authentication challenge-response, Device Management) — см. ARCHITECTURE.md, раздел 9.1.

**Последствия:**

- Плюс: `Identity` port используется без изменений — ADR-014, ADR-017, ADR-018 остаются в силе; `ports/transport.go` не меняется (заморожен ADR-020) — аутентификация надстраивается поверх уже установленного канала, не встроена в сам порт.
- Плюс: отзыв устройства становится тривиальной операцией (удаление записи из реестра), а не протоколом отзыва сертификата — меньше движущихся частей, меньше инфраструктуры (не нужен собственный CA, OCSP/CRL и т.п.).
- Плюс: Identity Provider явно ограничен ролью "разрешить привязку нового ключа к аккаунту" — не становится точкой шифрования трафика и не участвует в криптографической идентичности устройства напрямую, что сохраняет автономность платформы (ADR-018: без привязки к телефону/email) на уровне устройства, даже при внешнем IdP на уровне аккаунта.
- Минус: вводит зависимость от внешнего Identity Provider для *создания аккаунта* (не для повседневной работы устройства) — это осознанный компромисс, а не случайная зависимость; при необходимости в будущем можно добавить альтернативные IdP или self-hosted OIDC без изменения Device Identity/Transport Authentication слоёв.
- Затрагивает будущую реализацию: `photon-quic-bridge` (или его преемник) — Transport Authentication; `bindings/android`, `bindings/desktop` — хранение приватного ключа средствами ОС; Developer Tools — область управления устройствами.
- См. ARCHITECTURE.md, раздел 9.1; `ROADMAP.md`, Phase 3.5.

## ADR-022 — Новый порт IdentityProvider (внешний OAuth/OIDC)

**Статус:** Superseded by ADR-023

**Контекст:** Реализация Device Trust Model (ADR-021) требует проверки внешнего OAuth/OIDC ID-токена при регистрации нового устройства (см. docs/account-device-flow.md, сценарии 1 и 3). `AccountService` (`services/account`, не порт — сервис поверх `Storage`+`Identity`) нуждается в способе проверить токен, не зная деталей конкретного Identity Provider. Это тот же класс задачи, что уже решён для `Notification`/`P2P` — внешняя система, поведение которой нужно ядру, но реализация которой должна быть подключаемой.

Рассматривалась альтернатива: не заводить порт, оставить проверку токена внутри `services/account` напрямую вызывающей библиотеку конкретного IdP. Отклонена — это зашило бы Google (или любой первый выбранный IdP) прямо в сервис, что прямо противоречит ADR-021 ("Google сегодня, архитектура не привязана к конкретному провайдеру"). Порт с одним методом устраняет эту зависимость тем же способом, что `Notifier` устраняет зависимость от конкретного push-провайдера.

**Решение:** Добавлен `ports/identityprovider.go`:

```go
type ExternalIdentity struct {
    Subject string
    Email   string
}

type IdentityProvider interface {
    VerifyIDToken(ctx context.Context, token string) (ExternalIdentity, error)
}
```

Аудит по ADR-011: ни Google, ни OAuth2/OIDC-специфичные термины (кроме самого "ID token" — формального термина спецификации OIDC, не бренда) не попали в сигнатуры. Аудит по ADR-013: единственный метод отражает единственную подтверждённую потребность (проверить токен, получить стабильный идентификатор пользователя) — не более.

Именование: возвращаемый тип назван `ExternalIdentity`, не `Identity` — несмотря на то, что так предложено в первоначальном наброске. `Identity` уже занято `ports/identity.go` (криптографическая личность устройства) и означает нечто принципиально другое — переиспользование имени для другого смысла создало бы путаницу именно там, где важна точность (Device Trust Model и так балансирует два разных понятия "личности": криптографическое и OAuth-based).

**Последствия:**

- Плюс: `services/account` не будет знать слово "Google" — так же, как `Identity` не знает слово "Ed25519" в своих сигнатурах, а `Notifier` не знает слово "APNs".
- Плюс: добавление второго IdP (Apple, Microsoft, корпоративный OIDC) в будущем — новый адаптер (`adapters/appleoidc` и т.п.), не изменение `services/account` или этого порта.
- Минус: это девятый порт в пакете, замороженном ADR-020 как "8 портов" по факту происхождения (Phase 1) — ADR-020 регулирует изменение существующего контракта, но по духу того же решения добавление нового порта тоже требует такого же обоснования, которое здесь и приведено, а не тихого расширения пакета.
- См. `ports/identityprovider.go`, `docs/account-device-flow.md`, ARCHITECTURE.md раздел 9.1, ADR-021.

## ADR-023 — ExternalIdentity: добавлен Provider (уточняет ADR-022)

**Статус:** Принято (supersedes ADR-022)

**Контекст:** ADR-022 определил `ExternalIdentity{Subject, Email}` и правило поиска `Account` по `Subject`. При ревью обнаружено: `Subject` (OIDC `sub`) гарантированно стабилен и уникален только *внутри одного конкретного IdP* — спецификация OIDC не гарантирует уникальность `sub` *между* разными провайдерами. Сегодня это не проявляется (единственный IdP — Google), но ADR-021 прямо заявляет "Google сегодня, архитектура не привязана к конкретному провайдеру" — то есть появление второго IdP (Apple, корпоративный OIDC) архитектурно ожидаемо, а не гипотетическая случайность. Без `Provider` в ключе поиска `Subject = "12345"` у Google и `Subject = "12345"` у Apple оказались бы неотличимы для `AccountService`.

**Решение:** `ExternalIdentity` дополнен полем `Provider string`:

```go
type ExternalIdentity struct {
    Provider string
    Subject  string
    Email    string
}
```

`AccountService` ищет/создаёт `Account` по составному ключу `(Provider, Subject)`, не по одному `Subject`. `Provider` — деталь адаптера (`"google"`, `"apple"` и т.п.), не enum/константа в порту — сам порт по-прежнему не знает о конкретных провайдерах (аудит ADR-011 проходит: `Provider` — название поля контракта, не значение, зашитое в сигнатуру).

**Последствия:**

- Плюс: `AccountService` корректен и для одного IdP, и для нескольких — не потребует правки модели данных при добавлении второго провайдера, только новый адаптер (`adapters/appleoidc` и т.п.), что и было целью ADR-022.
- Плюс: обнаружено и исправлено до реализации `services/account` — цена правки на этапе порта примерно нулевая; цена этой же правки после того, как `AccountService` и его Storage-схема уже написаны на одном `Subject`, была бы миграцией данных в проде.
- Минус: слегка увеличивает минимальный контракт `ExternalIdentity` (3 поля вместо 2) — принято как оправданное, поскольку `Provider` — не "на будущее", а немедленно необходимое поле уже для корректной семантики единственного сегодняшнего адаптера (Google — тоже провайдер, просто единственный).
- См. `ports/identityprovider.go`, `docs/account-device-flow.md`.

## ADR-024 — Account Service: схема хранения (PhotonID как первичный ключ)

**Статус:** Принято

**Контекст:** Перед реализацией `services/account` нужно было зафиксировать схему хранения. Первый черновик этого ADR ошибочно вводил отдельный внутренний `AccountID`, откладывая присвоение `PhotonID` на неопределённое будущее — это было написано без проверки уже существующей на тот момент работы (`docs/account-storage-model.md`, `services/account/model.go`, `service.go`) и противоречило её же более точному прочтению ADR-018: точка реализации `PhotonID` ("когда Account Service перестанет быть гипотетическим") — это ровно текущий момент, Phase 3.5, а не более поздний. Черновик исправлен до того, как был показан пользователю — переписан целиком, а не помечен Superseded, поскольку ошибочная версия не была частью согласованной истории решений.

**Решение — модель данных** (полное обоснование — `docs/account-storage-model.md`):

```go
type Account struct {
    PhotonID  PhotonID // первичный идентификатор, формат см. ADR-018
    Provider  string
    Subject   string
    Email     string
    CreatedAt time.Time
}

type Device struct {
    DeviceID  string // опаковый, для отображения/логов — не ключ поиска
    PhotonID  PhotonID
    PublicKey ports.PublicKey // ключ поиска при Transport Authentication
    Name      string
    CreatedAt time.Time
    LastSeen  time.Time
}
```

**Решение — Storage namespaces:**

| Namespace | Ключ | Значение | Назначение |
|---|---|---|---|
| `photon.accounts` | `PhotonID` | `Account` (JSON) | Основная запись аккаунта |
| `photon.accounts.by_external` | `Provider + "\|" + Subject` | `PhotonID` | Поиск аккаунта по `ExternalIdentity` при логине (ADR-023) |
| `photon.devices` | `PhotonID + "\|" + hex(PublicKey)` | `Device` (JSON) | `ForEachPrefix(PhotonID + "\|")` — список устройств аккаунта |
| `photon.devices.by_pubkey` | `hex(PublicKey)` | `PhotonID` | Обратный поиск для Transport Authentication и отзыва: дано `PublicKey` → чей это аккаунт |

Четыре namespace, не два "умных" — `ports.Storage` сознательно не поддерживает запросы за пределами namespace+key/prefix (ADR-010), поэтому под каждый способ поиска — отдельный namespace, а не денормализация ради денормализации.

**Решение — владение миграциями:** `services/account` зависит только от `ports.Storage`, `ports.Identity`, `ports.IdentityProvider` — никогда не импортирует конкретный адаптер (`adapters/bbolt` и т.п.) напрямую. `Migration.Up` в `adapters/bbolt` принимает `*bolt.Tx` — конкретный тип, не `ports.WriteTx` (создание namespace принципиально не выражается через generic `WriteTx`, см. ADR-010). Значит миграции, создающие эти четыре namespace, специфичны для конкретного адаптера и определяются композиционным корнем приложения (будущий `cmd/photon-core-server` или аналог), не внутри `services/account`. Тесты сервиса используют `adapters/bbolt` напрямую с локально определёнными миграциями — это нормально для тестового кода.

**Решение — Transport Authentication внутри Account Service:** `AuthenticateDevice` (challenge-response через `ports.Identity.Verify`) реализован в `services/account`, не в отдельном `services/dispatcher` — потому что и проверка регистрации/отзыва устройства, и проверка подписи обращаются к одному и тому же реестру устройств; разносить их по двум сервисам означало бы либо дублировать доступ к `photon.devices.by_pubkey`, либо вводить зависимость `dispatcher` → `account` ради одного вызова.

**Последствия:**

- Плюс: `PhotonID` присваивается один раз, при первом входе — совпадает с фактическим счётчиком времени жизни аккаунта, не требует отдельной миграции данных позже.
- Плюс: атомарность отзыва (удаление из `photon.devices` и `photon.devices.by_pubkey` в одной `Update`-транзакции) исключает рассинхрон между "виден в UI" и "принимается на Transport Authentication".
- Минус: генерация `PhotonID` требует проверки на коллизию (retry-цикл, ограничен `maxPhotonIDGenerationAttempts`) — с диапазоном в 10⁹ значений (ADR-018) коллизии редки, но не невозможны, и сервис обязан их обрабатывать, а не считать теоретическими.
- См. `services/account/`, `docs/account-storage-model.md`, `docs/account-device-flow.md`.

## ADR-025 — Photon Protocol перенесён в photon-core/protobuf (закрывает технический долг ADR-009)

**Статус:** Принято

**Контекст:** ADR-009 зафиксировал направление зависимости "Photon Protocol → {Core, Bridge}" как целевую архитектуру, но прямо указал, что на момент принятия action-коды и wire-структуры физически лежали в `photon-quic-bridge/server/protocol.go`, а не в `photon-core/protobuf/` — с явной пометкой "требует переноса до заморозки ABI v1". Phase 5 (Bindings) — точка, где `photon_core.h`/`Photon_SendAction` должны опираться на протокол, поэтому перенос стал блокером именно сейчас.

**Решение:**

1. `photon.proto` перенесён в `photon-core/protobuf/`, `go_package` указывает на `github.com/wiloris/photon-core/protobuf`.
2. Добавлен явный `enum Action` (40 именованных кодов, 100–602, плюс `ACTION_UNSPECIFIED`), которого раньше не было — номера полей `oneof` в `PhotonRequest`/`PhotonResponse` уже совпадали с action-кодами, но `protoc-gen-go` не генерирует Go-константы из номеров полей `oneof`, только из значений `enum`. Без этого enum перенести `ActionCreatePost = 100` и подобные из Bridge в Core было бы физически нечем заменить.
3. `photon-quic-bridge/server/protocol.go` — action-коды теперь не объявлены заново, а являются алиасами на канонический источник: `const ActionCreatePost = int(photonpb.Action_ACTION_CREATE_POST)`. Явный `int(...)` обязателен: `photonpb.Action` — отдельный тип (`int32`), а `action` в обработчиках Bridge — обычный `int`; без конверсии `switch` на разнотипных константах не компилируется.
4. Попутно исправлено: `go.mod` Bridge был всё ещё `github.com/mattermost/mattermost-plugin-starter-template` (не переименован со времён шаблона) — переименован в `github.com/wiloris/photon-quic-bridge`, обновлены внутренние импорты (`server/plugin.go`).

**Ограничение проверки:** полная сборка всего `photon-quic-bridge` в текущей рабочей среде не выполнена — Mattermost SDK (`github.com/mattermost/mattermost/server/public`) тянет десятки транзитивных зависимостей, недоступных без `proxy.golang.org` (сеть песочницы ограничена явным списком доменов). Что реально проверено:
   - Паттерн `const X = int(photonpb.Action_Y)` со `switch` на разнотипных константах подтверждён рабочим в изолированном мини-проекте, реально импортирующем `photon-core/protobuf`.
   - `protocol.go` и `plugin.go` синтаксически валидны (`gofmt -e` парсит без ошибок) и канонично отформатированы (`gofmt -l` пусто).
   - `photon-core` (включая новый `protobuf/`) собирается, тесты проходят, `go vet`/`gofmt -l` чистые — полная гарантия только на стороне Core, не Bridge.

Правильная проверка (`go build ./...` всего Bridge) должна быть выполнена на машине с доступом к обычному Go module proxy — это первый шаг перед мержем.

**Последствия:**

- Плюс: направление зависимости из ADR-009 наконец выполнено физически, не только на бумаге — `Photon_SendAction` (Phase 5) может ссылаться на протокол Core, зная, что Bridge — равноправный потребитель, а не источник.
- Плюс: `enum Action` даёт типобезопасные именованные константы, которых не было вообще ни в одном виде — раньше протокол был "правильным по совпадению" (числа в `protocol.go` и в `oneof` синхронизированы вручную, без гарантии).
- Минус: миграция Bridge проверена не полностью (см. ограничение выше) — риск, что при реальной сборке на полноценной машине найдётся мелкая нестыковка (опечатка в одном из 40 констант, пропущенный импорт) — принят осознанно, а не скрыт.
- См. `photon-core/protobuf/photon.proto`, `photon-quic-bridge/server/protocol.go`, ARCHITECTURE.md раздел 7.6.

## ADR-026 — Финальный аудит photon_core.h перед заморозкой ABI v1

**Статус:** Принято

**Контекст:** Перед официальной заморозкой ABI v1 (ADR-008 — ABI Freeze Policy) проведён последний архитектурный аудит `photon_core.h`, теперь опирающегося на перенесённый в Core протокол (ADR-025). Найдено и решено семь пунктов.

**Решения:**

1. **Экспортируемая поверхность** — подтверждена минимальной, без утечки доменной модели (`Photon_GetUser`/`Photon_CreatePost` и т.п. по-прежнему отсутствуют). Убран параметр `resource` из `Photon_SendAction` — после ADR-025 action-коды глобально уникальны и однозначно определяют ресурс по числовому диапазону (100-199 Post, 200-299 User, ...), отдельная строка избыточна на уровне ABI.

2. **Ownership** — добавлено явное правило для буферов, переданных ВНУТРЬ Photon (`payload_json`, `config_json`): собственность вызывающего до и после вызова, Core не хранит указатель после возврата — освобождать сразу после вызова безопасно. Раньше это подразумевалось, но не было сформулировано как отдельное, симметричное направлению `Photon_Free*` правило.

3. **Callback lifetime** — добавлена явная гарантия в `Photon_Destroy`: после возврата управления колбэк, установленный через `Photon_SetEventCallback`, гарантированно не будет вызван больше ни разу. `Photon_Destroy` обязан дождаться завершения уже начатых вызовов колбэка перед возвратом — не просто пометить handle невалидным.

4. **ABI Versioning** — заменено на `PHOTON_ABI_MAJOR`/`PHOTON_ABI_MINOR`, `Photon_GetABIVersion()` возвращает `uint32_t` в упакованном виде (`(MAJOR << 16) | MINOR`). MAJOR — breaking change, обязателен к проверке клиентом. MINOR — обратно совместимое расширение, клиент может игнорировать.

5. **Валидация action_code** — добавлен `PHOTON_ERR_INVALID_ACTION`, отдельный от `PHOTON_ERR_INVALID_ARGUMENT`: `action_code`, не входящий в `enum Action` (`photon-core/protobuf/photon.proto`), — самый частый и самый диагностируемый класс ошибки клиента, заслуживающий точного кода, а не общего "что-то не так с аргументом". Тест на это появится вместе с `bindings/c` (следующий шаг).

6. **Protobuf-граница** — подтверждено: `Core → Photon Protocol → Bridge` уже физически не зависит от Mattermost (ADR-025), что открывает путь к Telegram/Discord/Matrix Bridge на равных правах.

7. **JSON payload vs protobuf bytes** — решено в пользу **JSON** на границе ABI, с объяснением, почему это не противоречит переносу протокола в Core:
   - `photon.proto`/`photon.pb.go` остаются канонической схемой (источник имён полей, типов, action-кодов) — это не то же самое, что wire-формат на границе ABI.
   - Бинарный protobuf на ABI обязывал бы каждый bindings (JNI, Desktop, будущие Rust/Swift) линковать protobuf runtime своего языка ради единственного вызова `Photon_SendAction` — это утяжеляет ABI ровно там, где ADR-004 требует минимальности.
   - JSON поддерживается практически любым языком без дополнительных зависимостей и проще отлаживать на границе, где чаще всего всплывают самые трудноуловимые баги.
   - Внутри Core `payload_json` парсится через `protojson` (часть `google.golang.org/protobuf`) в типизированные proto-структуры, а не в generic `map[string]interface{}` — строгая схема сохраняется на стороне Core, не требуя её от каждого клиента.

**Дополнительно:** `Photon_Create` изменена с `PhotonHandle* Photon_Create(const char*)` (NULL при ошибке, без кода ошибки) на `PhotonResult Photon_Create(const char*, PhotonHandle**)` — раньше ошибка инициализации терялась, потому что `Photon_GetLastError` требует уже существующий `handle`, которого при ошибке создания как раз нет.

**Последствия:**

- Плюс: каждый из семи пунктов аудита либо подтверждён, либо исправлен до заморозки — не после, когда исправление уже было бы breaking change с необходимостью MAJOR-бампа.
- Плюс: JSON-решение снимает вопрос "почему не protobuf bytes", который иначе неизбежно всплыл бы после первого прочтения `ADR-025` кем-то новым в проекте.
- Минус: `Photon_Create` и `Photon_SendAction` меняют сигнатуру относительно черновика — любой уже написанный код (которого пока нет — `bindings/c` ещё не реализован) пришлось бы переписать; поскольку `bindings/c` не начат, цена правки сейчас нулевая.
- См. `photon-bindings/c/photon_core.h`.

## ADR-027 — Photon_Create: явная гарантия NULL на *handle при ошибке (уточняет ADR-026)

**Статус:** Принято

**Контекст:** ADR-026 изменил `Photon_Create` на `PhotonResult Photon_Create(const char*, PhotonHandle**)`, но исходная формулировка оставляла поведение `*handle` при ошибке неопределённым ("не трогается, не гарантированно NULL"). Это перекладывало на каждого вызывающего решение, безопасно ли вызывать `Photon_Destroy` после неудачного `Photon_Create` — реальный источник UB, если `*handle` в момент вызова содержит мусор со стека, а не осмысленный NULL.

**Решение:** При любом коде результата, отличном от `PHOTON_OK`, `*handle` гарантированно устанавливается в `NULL`. Вызывающему не нужно проверять `*handle` отдельно от `PhotonResult` и не нужно решать, можно ли уничтожать частично созданный объект — если результат не `PHOTON_OK`, `Photon_Destroy` вызывать не на чем и не нужно.

**Последствия:**

- Плюс: устраняет класс ошибок "вызвать `Photon_Destroy` на мусорном указателе после неудачного `Create`" — гарантия проверяема статически по контракту, не требует защитного программирования на стороне каждого bindings.
- Минус: требует, чтобы реализация `bindings/c` явно инициализировала `*handle = NULL` в начале `Photon_Create`, до любой точки возврата с ошибкой — небольшая, но обязательная дисциплина в самой реализации (появится как явный пункт теста ownership при написании `bindings/c`).
- См. `photon-bindings/c/photon_core.h`.

## ADR-028 — Атомарность Photon_Create и Photon_Destroy(NULL) как безопасный no-op (уточняет ADR-026/027)

**Статус:** Принято

**Контекст:** ADR-027 зафиксировал, что `*handle` гарантированно `NULL` при ошибке, но не сформулировал более сильное требование — что `Photon_Create` в принципе не может оставить систему в промежуточном состоянии ("частично созданный handle": часть ресурсов выделена, часть нет, `*handle` не установлен явно ни в валидный указатель, ни в `NULL`). Отдельно: `Photon_Destroy` не определял поведение при `handle == NULL`, что вынуждало бы каждый вызывающий код (и каждый будущий bindings) оборачивать вызов в проверку — особенно неудобно ровно в сценарии, для которого ADR-027 и вводился: безусловно передать `*handle` после неудачного `Photon_Create` дальше в `Photon_Destroy`.

**Решение:**

1. **Атомарность `Photon_Create`.** Контракт теперь явно бинарный: либо полная успешность (`PHOTON_OK` + валидный `*handle`, без утечек), либо полное отсутствие удерживаемых ресурсов (`*handle == NULL`, все промежуточные внутренние ресурсы освобождены до возврата). Требование к реализации: `*handle = NULL` — первая строка тела функции, до разбора `config_json`, до любого пути ошибки.
2. **`Photon_Destroy(NULL)` — безопасный no-op**, по аналогии с `free(NULL)` в стандартной библиотеке C. Не деталь реализации, а часть контракта.

Пункт 2 напрямую усиливает ценность ADR-027: раз `Photon_Destroy(NULL)` безопасен, а `*handle` после неудачного `Photon_Create` гарантированно `NULL`, вызывающий код может безусловно писать `Photon_Destroy(handle)` после `Photon_Create` независимо от результата, без ветвления на `if (handle != NULL)`.

**Последствия:**

- Плюс: устраняет ещё один источник defensive-программирования на стороне каждого bindings — конвенция `free(NULL)`-стиля уже знакома любому C-программисту, ничего нового изучать не нужно.
- Плюс: атомарность `Photon_Create` — конкретное, проверяемое тестом требование к `bindings/c` (тест ownership обязан включать проверку "после `Photon_Create` с намеренно некорректным `config_json` нет утечек ресурсов").
- Минус: обязывает реализацию `bindings/c` быть особенно аккуратной с порядком операций при инициализации (что явно и зафиксировано как требование к реализации, а не оставлено на усмотрение).
- См. `photon-bindings/c/photon_core.h`.

## ADR-029 — Security Layer: границы ответственности вместо четырёх пакетов

**Статус:** Принято

**Контекст:** Phase 8 была сформулирована как список каталогов из `REPOSITORY.md`:
`security/permissions`, `security/signatures`, `security/trust`, `security/sandbox`.
То есть как план «написать четыре пакета». Перед началом работы проведён аудит
фактического состояния кода, а не названий каталогов. Результат:

- **Подписи** — `Identity.Sign`/`Verify` (`ports/identity.go` + `adapters/ed25519`,
  15 тестов) не просто существуют, а реально используются: `services/account:230`
  выполняет через них challenge-response аутентификацию устройств.
- **Доверие к устройствам** — ADR-021 реализован почти целиком в `services/account`:
  Device Registry (`RegisterDevice`/`RevokeDevice`/`ListDevices`), Transport
  Authentication, namespaces `photon.devices`/`photon.devices.by_pubkey`, 18 тестов.
- **Контракт авторизации** — `ports.Authorizer` + `ports.Permission` существуют и
  заморожены (ADR-020), но **реализаций ноль** (проверено `grep` по всему
  репозиторию).
- **Sandbox** — отсутствует полностью (0 совпадений на `sandbox|isolat|process`).

Все четыре каталога `security/*` при этом содержат только `.gitkeep`.

**Решение:** Phase 8 переформулирована из «написать четыре пакета» в **Security
Foundation** — проверку того, что криптографическая идентичность, доверие к
устройствам и модель авторизации имеют единую основу и не дублируются. Конкретно:

1. **`security/signatures` не создаётся.** `Identity.Verify` — уже корректный
   криптографический примитив, работающий в продуктовой логике. Написать рядом
   второй механизм подписей означало бы создать конкурирующий API вместо
   переиспользования существующего. Будущая проверка подписей пакетов ENSTOR
   (ARCHITECTURE.md, «нет подписи → отказ в установке») — это *применение*
   `Identity.Verify` к конкретному формату, а не новый крипто-механизм, и
   относится к ENSTOR (Phase 19).
2. **`security/trust` не создаётся.** Device Trust Model (ADR-021) реализована в
   `services/account` — и это правильное место: реестр устройств есть состояние
   аккаунта (ADR-024), а не отдельный слой.
3. **Permission enforcement и sandbox переносятся в Phase 9,** где их субъектом
   становится Plugin Runtime. Permission без объекта, которому выдаются права, —
   абстракция; sandbox без процесса, который нужно изолировать, — тоже. В Phase 9
   оба получают реальное назначение в цепочке
   `Plugin → Manifest → requested permissions → Authorizer → Sandbox → IPC → Core`.

**Формулировка намеренно не «Phase 8 поглощена Phase 9»** — это было бы неточно и
запутало бы историю решений. Проблема была не в том, что фаза лишняя, а в том, что
её граница проведена по каталогам файловой системы вместо ответственностей. Две
области закрыты существующими механизмами, две перенесены туда, где у них есть
субъект.

**Последствия:**

- Плюс: не написан код ради закрытия пункта roadmap — ровно тот принцип, что уже
  применялся к `bindings/desktop` (deferred, а не переписан заново) и к форку
  `quic-go` (deferred с критерием возврата).
- Плюс: исключено дублирование, которое было бы трудно откатить: два механизма
  подписей или два реестра устройств рядом друг с другом расходятся со временем, и
  становится неочевидно, какой из них авторитетный.
- Минус: `REPOSITORY.md` перечисляет четыре каталога `security/*`, из которых два
  теперь заведомо не будут заполнены. Решается при работе над Phase 9 — когда
  станет ясно, нужны ли `security/permissions` и `security/sandbox` как отдельные
  пакеты или их место внутри Plugin Runtime; до тех пор удалять их преждевременно.
- См. `ROADMAP.md` (Phase 8, Phase 9), `ports/plugin.go`, `services/account`.

## ADR-030 — Граница ответственности: photon-core ↔ photon-plugin-runtime

**Статус:** Принято

**Контекст:** Аудит перед Phase 9 обнаружил противоречие в документах: `sandbox`
фигурирует одновременно в двух местах — `photon-core/security/sandbox/`
(REPOSITORY.md:69) и `photon-plugin-runtime/sandbox/` (REPOSITORY.md:104). Это не
вопрос расположения файлов, а вопрос границы ответственности: пока она не
зафиксирована, threat model и IPC-спецификация начнут протекать через неправильную
границу. Кроме того, ADR-029 отложил permission enforcement и sandbox в Phase 9,
не уточнив, в каком репозитории они живут.

**Решение — жёсткая граница:**

```
photon-core
│
├── ports/plugin.go
│     ├── Permission     (тип)
│     └── Authorizer     (контракт)
│
└── НЕ содержит: plugin runtime, sandbox, manifest parser, IPC implementation


photon-plugin-runtime          (отдельный репозиторий)
│
├── manifest      — парсинг и валидация
├── permissions   — реализация ports.Authorizer, политика
├── sandbox       — изоляция процесса плагина
├── ipc           — протокол ядро ↔ host
├── host          — процесс исполнения плагина
├── supervisor    — запуск, падение, перезапуск
└── lifecycle     — discover → validate → authorize → start → running → stop
```

**Важное уточнение про `ports.Authorizer`.** Его присутствие в `photon-core` не
означает, что ядро «знает про плагины». `Authorizer` — общий контракт
авторизации/capability, и его место в ядре допустимо именно потому, что ядро
определяет абстракции, а не конкретную плагинную систему. Его можно реализовать
поверх Plugin Runtime, встроенной политики или тестового адаптера — вообще без
плагинов (это прямо записано в комментарии `ports/plugin.go`).

Направление зависимости при этом сохраняется строго:

```
photon-core
      ▲
      │ implements ports.Authorizer
      │
photon-plugin-runtime  (manifest + policy + sandbox)
```

то есть `plugin-runtime → photon-core` есть, а `photon-core → plugin-runtime`
нет — ровно как требует ADR-005.

**Следствия для `photon-core/security/`** (уточняет ADR-029):

| Каталог | Решение |
|---|---|
| `security/signatures` | не создаётся — ответственность `Identity` |
| `security/trust` | не создаётся — ответственность `services/account` |
| `security/permissions` | не является реализацией: enforcement принадлежит runtime; в ядре остаётся только контракт `ports.Authorizer` |
| `security/sandbox` | **удаляется из архитектурной структуры `photon-core`** — sandbox изолирует процесс плагина, а плагин по ADR-005 не живёт внутри ядра |

Каталоги не удаляются физически прямо сейчас: сначала это решение, затем
синхронная правка `REPOSITORY.md` и структуры репозиториев — чтобы документ и
файловая система не разошлись на промежуточном шаге.

**Plugin Runtime ≠ Plugin SDK.** Разделение фиксируется здесь, до проектирования,
потому что оно определяет, кто кому доверяет:

```
Plugin SDK          ← с этим работает разработчик плагина
    ↓
  Plugin            ← сторонний код, недоверенный
    ↓ IPC
Plugin Runtime      ← часть платформы, пользователь ей доверяет
    ├── Host, Manifest, Authorizer, Supervisor, Sandbox
    ↓
Photon Core
```

SDK — библиотека для автора плагина. Runtime — то, что запускает пользователь и
чему доверяет как части платформы. Смешивать их нельзя: код SDK исполняется внутри
недоверенного процесса плагина, код Runtime — снаружи, и именно он принимает
решения о правах.

**Решение — `photon-plugin-runtime` не создаётся сейчас пустым скелетом.**
Сначала спецификации (threat model → lifecycle → manifest → IPC), затем скелет
репозитория. Тот же порядок, что уже сработал с `adapters/tcp`: `WIRE_FORMAT.md`
до кода, а не после.

**Последствия:**

- Плюс: Phase 9 явно перестаёт быть работой в `photon-core` — это снимает риск
  случайно втащить в ядро знание о плагинах, нарушив ADR-005 незаметно.
- Плюс: разделение Runtime/SDK зафиксировано до проектирования, а не постфактум —
  иначе легко получить SDK, который «немножко» принимает решения о правах.
- Минус: `REPOSITORY.md` требует синхронной правки (удаление `security/sandbox`
  из структуры `photon-core`), иначе документ противоречит этому решению.
- См. `ROADMAP.md` (Phase 9), `ports/plugin.go`, ADR-005, ADR-029.

## ADR-031 — Plugin SDK: клиент протокола, а не окно во внутренности runtime

**Статус:** Принято

**Контекст:** Phase 9 завершена: `photon-plugin-runtime` имеет работающий security
boundary (`manifest → permissions → authorizer → IPC → host → supervisor →
sandbox`, 196 тестов). Phase 10 — SDK для авторов плагинов. Основной риск этой
фазы не технический, а архитектурный: SDK — единственный компонент, который
физически исполняется **внутри недоверенного процесса плагина**, и любая
возможность, которую он открывает, автоматически становится доступна недоверенному
коду.

Соблазн, от которого нужно защититься заранее: сделать разработку плагина удобнее,
дав SDK прямой доступ к чему-то из runtime — «только для отладки», «только на
время разработки», «только чтобы запустить локально». Каждое такое послабление
обнуляет ровно ту границу, которую строила Phase 9.

**Решение — базовый принцип:**

> **SDK является клиентом уже существующего IPC-протокола и не знает внутренностей
> runtime.**

Что разработчик плагина видит:

```
Plugin SDK → IPC protocol → Plugin Host → Supervisor → Sandbox
```

Чего он не видит и не может достичь через SDK:

```
Plugin SDK → fork/exec → namespaces / seccomp / cgroups / ...
Plugin SDK → permissions.Policy (изменение собственных прав)
Plugin SDK → supervisor (управление собственным жизненным циклом)
Plugin SDK → photon-core напрямую (обход runtime)
```

**Практические следствия, обязательные к соблюдению:**

1. **`photon-plugin-sdk` не импортирует `photon-plugin-runtime`** — ни один пакет,
   даже `ipc`. Общими могут быть только определения протокола, и если такая
   потребность возникнет, они выносятся в отдельный минимальный пакет, а не
   импортируются из runtime.
2. **`photon-plugin-sdk` не импортирует `photon-core`** — плагин не обращается к
   ядру, он обращается к runtime, а runtime к ядру, проверив права на каждый
   запрос.
3. **SDK не имеет API для изменения собственных прав, состояния или жизненного
   цикла.** Отсутствие такого метода — не недоработка, а требование: манифест
   запрашивает, Authorizer решает, supervisor управляет.
4. **Никаких «режимов разработки», ослабляющих проверки на стороне runtime.**
   Удобство отладки достигается инструментами вокруг (тестовый хост, логи,
   Developer Tools), а не флагом, отключающим enforcement.

**Разделение ответственности целиком:**

| Компонент | Отвечает за |
|---|---|
| SDK | API для разработчика |
| manifest | декларация возможностей |
| permissions | что плагин просит |
| authorizer | что плагину разрешено |
| IPC | контракт взаимодействия |
| host / supervisor | выполнение и жизненный цикл |
| sandbox | enforcement на уровне ОС |

**Формулировка главного вопроса Phase 10** (чтобы проектирование шло от него, а не
от списка удобных функций):

> Как сделать разработку Photon-плагина максимально простой, **не позволяя SDK
> обходить security model runtime**?

**Последствия:**

- Плюс: граница, построенная в Phase 9, не может быть обойдена самым очевидным
  способом — «изнутри», через библиотеку, которую плагин и так линкует.
- Плюс: SDK можно переписать или заменить (другой язык, другая версия) без ревизии
  модели безопасности: он не является её частью, он её потребитель.
- Минус: часть удобств для разработчика окажется недоступна напрямую и потребует
  инструментов вокруг SDK (тестовый хост, эмулятор runtime). Это осознанная цена:
  инструмент можно сделать небезопасным для разработки и не поставлять в прод,
  а API в SDK — нельзя.
- См. `photon-plugin-sdk/README.md`, ADR-005, ADR-030,
  `photon-plugin-runtime/docs/ipc.md`.

**Phase 9 архивирована.** Зафиксированные ограничения sandbox (P3/P4/P5/P8 не
реализованы, Android-реализации нет) — часть архитектуры, а не долг к погашению.
Реализовывать их «ради полноты», без подтверждённого требования, не следует: см.
`photon-plugin-runtime/IMPLEMENTATION_LOG.md`, где для каждого записана причина.

## ADR-032 — Маппинг «операция → право» принадлежит runtime

**Статус:** Принято

**Контекст:** Обнаружено E2E-тестом при завершении Phase 10, а не ревью.
`docs/sdk-boundary.md`, раздел 4 описывал таблицу соответствия операций каталога и
требуемых прав. В реализации её **не существовало**: `ipc.Session` передавал
`m.Op` напрямую в `Authorizer` как имя права.

Практические последствия, которых никто не замечал:

- операция `storage.get` требовала право с именем `storage.get`, а не
  `storage.read` — то есть каталог операций и система прав жили в разных
  вселенных;
- `log.write`, заявленный как операция без права, не работал вовсе;
- unit-тесты `ipc` и `host` этого не видели, потому что сами использовали имена
  прав в качестве имён операций — и всё «сходилось».

Расхождение проявилось только когда SDK начал отправлять **настоящие** операции
каталога. Это иллюстрация того, что согласованность двух подсистем нельзя
проверить тестами, которые обращаются только к одной из них.

**Решение:** таблица «операция → право» живёт в `photon-plugin-runtime/ipc/operations.go`
— на **доверенной** стороне.

Причина не стилистическая. Если бы маппинг находился в SDK (или передавался от
плагина), недоверенный процесс мог бы объявить, что `storage.put` требует
`storage.read` — то есть сам определял бы стоимость своих действий. Плагин
сообщает **что** он хочет сделать; **чего это требует** решает runtime.

Три различимых исхода вместо двух:

| Случай | Ответ | Почему отдельно |
|---|---|---|
| Операция известна, требует права | `ALLOW` / `FORBIDDEN` | Обычный путь через `Authorizer` |
| Операция известна, права не требует | Исполняется | `log.write`: плагин должен уметь сообщить о проблеме, не получив ничего |
| Операция неизвестна | `UNSUPPORTED` | «Не знаю такой операции» ≠ «тебе нельзя». Отказ в правах на несуществующую операцию сбил бы SDK с толку при рассинхроне версий |

Дополнительно: `FORBIDDEN` теперь сообщает **право**, а не операцию — плагину
полезнее знать, чего просить у пользователя, чем повторение того, что он и так
отправил.

**Последствия:**

- Плюс: каталог операций и система прав стали одной согласованной моделью, а не
  двумя списками, случайно совпадавшими по именам.
- Плюс: добавление операции требует явного решения о том, какое право она стоит —
  забыть невозможно, потому что операция без записи в таблице отвечает
  `UNSUPPORTED`.
- Минус: таблица — ещё одно место, которое нужно обновлять при расширении
  каталога. Компенсируется тем, что пропуск обнаруживается сразу и внятно, а не
  тихой авторизацией по неверному праву.
- Урок для процесса: **спецификация, описывающая соответствие двух подсистем,
  требует теста, который проходит через обе.** Раздел 4 `sdk-boundary.md`
  существовал с самого начала Phase 10 и был написан правильно — но реализации не
  имел, и ни один unit-тест этого не показывал.
- См. `photon-plugin-runtime/ipc/operations.go`, `docs/sdk-boundary.md` раздел 4,
  `tests/integration/sdk_e2e_test.go`.

## ADR-033 — `ports.ErrUnknownCaller`: sentinel для «субъект не установлен»

**Статус:** Принято

**Контекст:** `ipc.Session` (`photon-plugin-runtime/ipc/session.go`) обязан
различать два разных исхода `Authorizer.Authorize`: субъект не установлен
(`UNAUTHORIZED`) и субъект установлен, но прав нет (`FORBIDDEN`) —
`ports.Authorizer.Authorize` возвращает `(bool, error)`, и различие
кодируется тем, что первый случай приходит как `error`, а второй — как
`(false, nil)`. Проблема в том, **какая именно** ошибка означает первый
случай: до этого ADR `ipc.Session` определял это строковым поиском —
`contains(err.Error(), "not a registered plugin")` — подстроки из текста
`permissions.ErrUnknownCaller`.

Это не новая находка: решение зафиксировано как осознанный компромисс в
`photon-plugin-runtime/IMPLEMENTATION_LOG.md` ещё при реализации `ipc` в
Phase 9, с явным условием возврата — «при появлении второй реализации
`Authorizer` стоит завести общий sentinel в `ports`». Условие наступило
раньше, чем предполагалось, и по другой причине: та же по природе
строковая классификация обнаружилась независимо в `host.classify()`
(`photon-plugin-runtime/host/host.go`) при работе над Phase 11 — там она
опаснее, чем в `ipc`. В `ipc.isUnknownCaller` ошибочная классификация
искажает только код ответа плагину (`UNAUTHORIZED` вместо
`INTERNAL_ERROR` или наоборот) — диагностическую точность. В
`host.classify()` та же по конструкции ошибка участвовала в решении,
восстанавливать ли процесс автоматически (`AutoRestartAllowed`) — а
текст ошибки, по которому шёл матчинг, в части случаев формируется из
данных, пришедших по проводу от самого плагина (`HelloPluginID`,
`HelloCapabilities`, тип сообщения). Строковый матчинг там уже
устранён (см. запись о находке в
`photon-plugin-runtime/IMPLEMENTATION_LOG.md`, раздел «Найдено
тестами») переходом на `errors.Is` и sentinel-ошибки `ipc`
(`ErrHandshakeFailed`, `ErrClosedDuringHandshake`). Оставлять `ipc`↔`permissions`
на прежнем строковом пути после этого — держать в системе ровно тот
класс хрупкости, который только что закрыли в соседнем месте.

**Решение:** добавить в `photon-core/ports/errors.go`, в ряд с уже
существующими `ErrTokenInvalid` (`IdentityProvider`), `ErrDecryptionFailed`
(`Crypto`) и другими sentinel-ошибками порта:

```go
// Plugin (Authorizer)
var (
	// ErrUnknownCaller — субъект не установлен: caller не
	// зарегистрирован ни с одним известным субъектом
	// (RegisterCaller не вызывался для этого PublicKey). Отличается
	// от (false, nil): тот означает «субъект известен, права нет»
	// (FORBIDDEN); эта ошибка означает «субъект неизвестен»
	// (UNAUTHORIZED) — то же разделение, что уже зафиксировано в
	// docs/ipc.md, раздел 5.
	ErrUnknownCaller = errors.New("ports: unknown caller")
)
```

Сравнение с `Identity.Verify` (`ports/identity.go`) объясняет, почему у этой
операции нет и не должно быть аналогичного третьего исхода. `Verify`
проверяет подпись, и вопрос устроен так, что «ключ неизвестен» не является
отдельным случаем: некорректный ключ уже покрыт `ErrInvalidKey`, а
структурно корректная, но неверная подпись — это `(false, nil)`, тот же
ожидаемый отрицательный результат, что и везде в системе (два исхода
исчерпывают вопрос «эта подпись принадлежит этому ключу?», технической
неопределённости о самом ключе там нет). У `Authorize` ситуация другая:
субъект может быть вообще не установлен — `RegisterCaller` для этого
`PublicKey` никто не вызывал, и это третий, отдельный от «есть право» и
«права нет» исход, которого структурно не существует у `Verify`, потому
что у `Verify` нет понятия «зарегистрированный вызывающий».

Прецедент прямой: `IdentityProvider` уже возвращает свою sentinel-ошибку
(`ErrTokenInvalid`) из этого же общего файла для той же цели — дать
вызывающему коду проверить конкретный исход через `errors.Is`, не
привязываясь к тексту сообщения конкретной реализации.
`permissions.ErrUnknownCaller` (`photon-plugin-runtime/permissions/authorizer.go`)
начинает оборачивать `ports.ErrUnknownCaller` через `%w`, сохраняя своё
публичное имя и сообщение для тех, кто уже проверяет
`errors.Is(err, permissions.ErrUnknownCaller)`; `ipc.isUnknownCaller`
переходит на `errors.Is(err, ports.ErrUnknownCaller)`.

**Почему это не нарушает ADR-020:** добавление sentinel-ошибки не меняет
ни одной сигнатуры `ports.Authorizer` и не создаёт обязательств для уже
существующих реализаций — `Authorize` и раньше возвращал `error` без
уточнения его конкретного значения, и реализация, не возвращающая
`ErrUnknownCaller` (то есть просто `(false, someOtherError)` для любой
технической невозможности принять решение), остаётся полностью
корректной с точки зрения контракта: `ports.Authorizer` не требует от
реализаций сигнализировать именно этот случай именно этой ошибкой, он
только даёт им общий способ сделать это, если он у них есть. Это
расширение словаря доступных ошибок порта, а не изменение метода,
типа или семантики уже существующего поведения — та же категория, что
уже фиксировалась ADR-020 как не требующая пересмотра заморозки самой
по себе (см. ADR-020, «не распространяется на... расширение
doc-комментариев без изменения самого контракта» — здесь по духу тот
же случай: контракт `Authorize(ctx, caller, permission) (bool, error)`
не меняется, меняется только то, что реализациям есть из чего выбирать
при сигнализации известного класса технической ошибки).

**Последствия:**

- Плюс: строковая классификация исчезает из двух мест сразу —
  `ipc.isUnknownCaller` и (уже случившийся отдельно) `host.classify`.
  Общий класс хрупкости («решение принимается по подстроке, а не по
  типу»), обнаруженный дважды за один день работы над Phase 11, закрыт
  полностью, а не наполовину.
- Минус: `permissions` (и любая будущая вторая реализация
  `ports.Authorizer`) теперь обязан возвращать именно
  `ports.ErrUnknownCaller` (прямо или обёрнутым) для случая «субъект не
  установлен» — иначе `ipc` снова не различит `UNAUTHORIZED` и
  `INTERNAL_ERROR`, только уже без строкового fallback, который раньше
  худо-бедно работал. Это новое обязательство, а не просто
  рекомендация, и оставаться словесным ему нельзя — ровно так осталось
  на словах предыдущее («при появлении второй реализации `Authorizer`
  завести sentinel»), пока не понадобилось само. Обязательство
  закрывается двумя тестами, оба через `errors.Is`, ни один — через
  наличие текста в сообщении: (1) в `permissions` — тест, что
  `Authorize` для незарегистрированного `PublicKey` возвращает ошибку,
  для которой `errors.Is(err, ports.ErrUnknownCaller)` истинно; (2) в
  `ipc` — тест, что при `Authorizer`, возвращающем
  `ports.ErrUnknownCaller`, сессия отвечает `UNAUTHORIZED`, а не
  `INTERNAL_ERROR`. Без первого теста `permissions` может незаметно
  перестать оборачивать sentinel при рефакторинге; без второго `ipc`
  может незаметно перестать его матчить — иначе расхождение между
  `permissions` и `ipc` снова обнаружится не тестом, а инцидентом,
  ровно как маппинг «операция → право» в ADR-032.
- См. `photon-plugin-runtime/IMPLEMENTATION_LOG.md` (запись об
  осознанном компромиссе `isUnknownCaller` и о находках `host.classify`/
  `ipc.handshake` за тот же день), `docs/ipc.md` раздел 5.

## ADR-034 — Wire-format Bridge-границы: JSON на проводе, protobuf как схема

**Статус:** Принято

**Контекст:** Ни один документ проекта не отвечал на вопрос «чем сериализуется
Bridge-граница». Хуже: единственный документ, который отвечал на него неявно,
отвечал **неверно**. Шапка `photon-core/protobuf/photon.proto` озаглавлена
`Wire protocol` и утверждает буквально:

```
//  Action stream (one stream per action):
//    Frame 1 → PhotonRequest
//    Frame 2 ← PhotonResponse
```

На проводе этого нет и никогда не было. Реальный формат зафиксирован в двух
местах, оба — рабочий код, а не черновик: шапка
`photon-quic-bridge/server/protocol.go` (серверная сторона) и
`photon-quic-bridge/test-client/test_photon.go` (клиент, проверенный против
живого развёрнутого сервера — см. `CLAUDE.md`, раздел про `photon-quic-bridge`).
Провод — JSON, ALPN `photon-quic-v1`:

```
handshake-стрим (bidi, первый на соединении):
  → {"session_token":"..."}          # фрейм 1
  → {"mode":"action"|"subscribe"}    # фрейм 2
  ← {"ok":true,...}                  # ответ, затем стрим закрывается
action-стрим (bidi, по одному на action):
  → {"action":100,"resource":"PostResource"}   # фрейм 1 — header
  → { ...payload... }                          # фрейм 2 (пустой объект, если нет)
  ← {"ok":true,"data":{...}} | {"ok":false,"error":"..."}
push-стрим (UniStream, сервер → клиент, только при mode=subscribe):
  ← {"event":"posted","user_id":"...","data":{...}}
```

Расхождение со схемой — не косметическое. Оно систематическое:

| `photon.proto` | Реальный провод |
|---|---|
| `PhotonRequest` — **одно** сообщение (`action` + `resource` + `oneof payload`) | **два** JSON-фрейма: header, затем payload |
| `Resource` — enum (`RESOURCE_POST = 1`) | строка (`"PostResource"`) |
| `PhotonResponse{ok, error, code, oneof data}` | `{ok, data, error}` — `data` нетипизирована, поля `code` нет |
| `PushEvent{EventType event_type, ...}` | `{"event":"posted"}` — строковое имя события (константы `PushEvent*` в `protocol.go`) |
| `AuthFrame`, `ModeFrame` | совпадают структурно (`session_token`, `mode`) |
| `HandshakeResponse{ok, error, status}` | клиент читает общий `{ok, data, error}`, `status` не использует |

То есть protobuf-схема описывает идеализированный типизированный протокол, а на
проводе — обобщённые JSON-конверты. Само по себе это не дефект: JSON выбран
осознанно. Дефект в том, что **нигде не записано, что схема — не провод**, а
`PhotonRequest`/`PhotonResponse` с их `oneof` выглядят ровно как wire-формат.
Первый, кто прочитает `.proto` (включая меня в новой сессии), реализует
`proto.Marshal(&PhotonRequest{...})` и получит соединение, которое сервер не
понимает.

Решение при этом уже принято — дважды, просто не для этой границы:

- **ADR-026 п.7** — для границы C ABI: JSON (`payload_json`), protobuf остаётся
  канонической схемой. Причина — не тащить protobuf-runtime в каждый binding
  (JNI, Desktop, будущие Rust/Swift) ради единственного вызова.
- **ADR-009 / ADR-025** — protobuf-схема принадлежит Core как общий контракт, и
  Bridge — её равноправный потребитель, а не владелец. Ни один из этих ADR не
  утверждает, что контракт обязан сериализоваться в protobuf-байты; ADR-025
  прямо называет `enum Action` целью переноса, потому что именно из него
  берутся Go-константы.

Для Bridge та же логика усилена ещё двумя фактами: это Mattermost-плагин, где
JSON — естественный формат всего окружения, и он **уже развёрнут и работает**.

**Решение:**

1. **Wire-format Bridge-границы — JSON.** `photon.proto` / `photon.pb.go` —
   каноническая **схема**: источник action-кодов (`enum Action`, ADR-025), имён
   полей, типов и структуры payload'ов. Схема и wire-формат — разные вещи, ровно
   как на границе C ABI (ADR-026 п.7). Второго wire-формата на этой границе не
   вводится.

2. **Шапка `photon.proto` исправляется.** Блок `Wire protocol` переписан: он
   описывает схему и её отношение к проводу, а не провод. Ссылка на этот ADR — в
   самом файле, чтобы вопрос не переоткрывался чтением схемы.

3. **`PhotonRequest`/`PhotonResponse` остаются в схеме.** Вопрос «не выкинуть ли
   их вовсе, раз они никогда не сериализуются» поставлен явно и проверен, а не
   решён по вкусу:

   - **Потребителей у них нет.** `grep` по всему рабочему дереву: вне
     `photon.proto`, сгенерированного `photon.pb.go` и текста ADR-025 они не
     упоминаются нигде — ни в Go, ни в Java/Kotlin. Генерации Java/Kotlin из
     `.proto` в репозитории вообще не существует (`option java_package` есть, но
     ни одного `*.gradle`, `buf.*` или `Makefile` нет); `Photon.kt` и
     `PhotonNative.java` принимают `actionCode` обычным `int` и ссылаются на
     `enum Action` только в комментарии. Единственный Go-потребитель пакета —
     `photon-bindings/c/photon.go`, и он использует только `photonpb.Action_name`.
     Технически удаление ничего не ломает.
   - **Но они несут информацию, которой больше нет нигде.** Номера полей в
     `oneof payload` равны action-кодам: `CreatePostPayload create_post = 100` ↔
     `ACTION_CREATE_POST = 100`. Это отображение «action → тип payload'а» не
     записано ни в одном другом месте проекта, и `protoc` проверяет его
     машинно — уникальность номеров полей внутри `oneof` нарушить молча нельзя.
     Удалив конверты, мы потеряли бы не «неиспользуемые сообщения», а
     единственную машинно-проверяемую запись о том, какой payload принадлежит
     какому action'у, оставив её жить в человеческой памяти.
   - **Они же — артефакт для смены формата** (п. 5 ниже). Если протокол однажды
     переедет на protobuf-байты, `oneof`-конверты — именно то, что для этого
     нужно; выбросив их сейчас, при возврате к вопросу пришлось бы
     восстанавливать отображение action → payload по всем 56 кодам вручную.

   Отображение проверено машинно при написании этого ADR, а не глазами: все 55
   номеров полей в `oneof payload` совпадают с реальными значениями `enum
   Action` (лишних номеров нет ни одного), 56-й код — `ACTION_GET_ME = 200` —
   payload'а не имеет закономерно (запрос «кто я» не принимает аргументов).
   `PhotonResponse.data` содержит 24 поля, все с номерами из `enum Action`,
   плюс `999` — общий `GenericResponse`.

   **Попутная находка, не правка ADR-025:** ADR-025 говорит про «40 именованных
   кодов, 100–602». Диапазон верен, число — нет: кодов **56**, и ровно столько
   же алиасов в `photon-quic-bridge/server/protocol.go`, то есть Bridge и схема
   согласованы, разошёлся только текст ADR-025. Запись ADR-025 при этом не
   редактируется — правило файла (см. конец документа) запрещает менять принятые
   записи; факт фиксируется здесь.

   Поэтому источник путаницы устраняется маркировкой, а не удалением: в
   `photon.proto` рядом с обоими сообщениями появляется комментарий, что они
   **не сериализуются на проводе** и служат схемой отображения action → payload
   (плюс заготовкой на случай п. 5). Удаление сообщений вернуло бы схему в
   состояние «правильная по совпадению», от которого ADR-025 её как раз увёл.

4. **Wire-format изолируется за интерфейсом** (реализуется в Phase 12.5). Слой
   сессии кодирует и декодирует фреймы через узкий интерфейс; вызывающий
   (Dispatcher, Phase 13) не знает, JSON там или protobuf, и не может это
   узнать, не нарушив границу типов. Это единственный пункт, который реально
   что-то стоит: без него смена формата — правка по всем вызовам, а не подмена
   одной реализации.

5. **Критерий возврата к вопросу «protobuf на проводе».**
   Пересматривать это решение до наступления **любого** из условий не следует:

   - появляется **первый сторонний клиент**, которого владелец проекта не
     контролирует (до Phase 16–18 все участники — свои, и формат меняется
     согласованной пересборкой обеих сторон);
   - измеренный — не предполагаемый — оверхед JSON становится значимым в профиле
     реальной нагрузки (наиболее вероятный кандидат — `UploadFilePayload` с
     `[]byte file_bytes`, который в JSON превращается в base64: +33% к размеру
     файла на каждый аплоад);
   - появляется bridge на языке, где JSON дороже protobuf'а, а не дешевле.

   Запирает **не формат, а отсутствие механизма смены** — поэтому механизм
   (п. 4 и версия протокола в handshake, Phase 12.5) вводится сейчас, а сам
   формат не меняется.

**Следствие, требующее внимания в Phase 12.5:** ADR-026 п.1 убрал параметр
`resource` из `Photon_SendAction` — на уровне ABI он избыточен, потому что
action-код однозначно определяет ресурс числовым диапазоном. На проводе же
header-фрейм строку `resource` **содержит и требует** (`{"action":100,
"resource":"PostResource"}`). Значит слой сессии обязан выводить её из
action-кода по диапазону (100-199 → `"PostResource"`, 200-299 →
`"UserResource"`, 300-399 → `"ChannelResource"`, 400-499 → `"EngramResource"`,
500-599 → `"FileResource"`, 600-699 → `"WallResource"`). Это не противоречие
между ADR — это ровно то место, где «схема ≠ провод» проявляется как код, и оно
должно быть покрыто тестом на каждый диапазон, а не написано по памяти.

**Ограничение проверки:** таблица расхождений выше выведена из четырёх файлов
`photon-quic-bridge`, физически присутствующих в этом дереве (`go.mod`,
`server/protocol.go`, `server/plugin.go`, `test-client/test_photon.go`), а не из
серверного пути чтения — `handler_*.go` и QUIC-listener живут в полном
репозитории Bridge, отдельном от этого (`CLAUDE.md`, тот же раздел). Поэтому
строки таблицы читаются как «клиент, работающий против живого сервера, посылает
и принимает именно это», а не как «сервер не принимает ничего другого». В
частности, использует ли сервер `HandshakeResponse.status` и
`PhotonResponse.code` в исходящих ответах, из имеющихся файлов не видно — клиент
их не читает. Проверить это — первый шаг Phase 12.5, когда полный репозиторий
Bridge будет положен рядом.

**Последствия:**

- Плюс: вопрос «чем сериализуется Bridge-граница» получает записанный ответ
  раньше, чем первая реализация клиента на нём ошибётся. Обратный порядок —
  реализация по неверной шапке `.proto` — стоил бы отладки на границе двух
  процессов, где, как отмечает ADR-026 п.7, баги ловятся хуже всего.
- Плюс: решение согласовано с ADR-026 п.7, а не принято отдельно — обе границы
  (C ABI и Bridge) держат один принцип «protobuf — схема, JSON — провод», и
  формулировать его второй раз для третьей границы уже не придётся.
- Плюс: `oneof`-конверты сохранены как машинно-проверяемое отображение
  action → payload — то, чего в проекте не было до ADR-025 и что легко
  потерять, приняв «неиспользуемое» за «ненужное».
- Минус: схема остаётся не полностью изоморфной проводу (таблица выше), и это
  сознательно **не** исправляется приведением `.proto` к JSON-структуре: схема
  описывает протокол в типизированном виде, провод — в конвертном, и попытка
  сделать их одинаковыми свела бы `.proto` к `map[string]interface{}`, потеряв
  всю его ценность. Цена — расхождение нужно держать в голове; отсюда
  требование п. 2 и п. 3 (маркировка в самом файле), а не только запись в ADR.
- Минус: `PhotonRequest`/`PhotonResponse` остаются кодом без потребителя —
  `photon.pb.go` генерирует для них полный набор методов. Принято осознанно:
  цена — размер сгенерированного файла, альтернатива — потеря отображения
  action → payload.
- См. `photon-core/protobuf/photon.proto` (шапка и оба конверта),
  `photon-quic-bridge/server/protocol.go` (провод, серверная сторона),
  `photon-quic-bridge/test-client/test_photon.go` (провод, проверенный
  клиентом), ADR-009, ADR-025, ADR-026 п.7, ROADMAP.md Phase 12.5.

## Как пользоваться этим файлом дальше

Когда реализация (Phase 0 и далее по `ROADMAP.md`) вскроет необходимость пересмотреть одно из решений выше — это нормально и ожидаемо, именно для этого документ существует. Процесс:

1. Не редактировать существующую запись.
2. Добавить новую запись с следующим номером, статусом `Принято`, и явной причиной пересмотра в разделе "Контекст".
3. Пометить старую запись `Superseded by ADR-0XX`.
4. Только после этого — вносить соответствующую правку в `ARCHITECTURE.md`.

Если за первые несколько фаз (`ports`, `bbolt`, `crypto`, `bindings/c`) не появится ни одной новой записи, кроме этой преамбулы — это будет хорошим подтверждением того, что архитектура была продумана достаточно, чтобы начинать разработку.
