# photon-plugin-sdk

Клиентская библиотека для авторов плагинов Photon.

**Подробное руководство разработчика —
[`photon-plugin-runtime/docs/plugin-development.md`](../photon-plugin-runtime/docs/plugin-development.md).**
Здесь только вход: что даёт SDK и почему он устроен именно так.

## Почему отдельный модуль, а не подпакет runtime

Разные trust boundaries (ADR-030):

```
Plugin SDK      ← исполняется ВНУТРИ недоверенного процесса плагина
    │
  Plugin        ← сторонний код
    │ IPC
Plugin Runtime  ← часть платформы, принимает решения о правах
    │
Photon Core
```

Код SDK живёт в недоверенном процессе. Импорт кода Runtime означал бы, что логика
принятия решений о правах компилируется внутрь того, кого она должна ограничивать.

**Зависимости:**

| Может | Не может |
|---|---|
| Стандартная библиотека | `photon-plugin-runtime` |
| (позже) кодогенерация IPC-протокола | `photon-core` напрямую |

Единственный канал связи с Runtime — IPC (`photon-plugin-runtime/docs/ipc.md`).

Плагин не обращается к ядру: он обращается к Runtime, а Runtime — к ядру, проверив
права на каждый запрос.

## Главный принцип (ADR-031)

> **SDK является клиентом уже существующего IPC-протокола и не знает внутренностей
> runtime.**

Разработчик плагина видит:

```
Plugin SDK → IPC protocol → Plugin Host → Supervisor → Sandbox
```

и никогда:

```
Plugin SDK → fork/exec → namespaces / seccomp / cgroups
Plugin SDK → изменение собственных прав
Plugin SDK → управление собственным жизненным циклом
```

Причина не формальная: SDK — единственный компонент, исполняющийся **внутри
недоверенного процесса плагина**. Любая возможность, которую он открывает,
автоматически доступна недоверенному коду. Граница, построенная в Phase 9, обходится
проще всего именно «изнутри» — через библиотеку, которую плагин и так линкует.

**Никаких «режимов разработки», ослабляющих проверки runtime.** Удобство отладки
достигается инструментами вокруг (тестовый хост, Developer Tools), а не флагом,
отключающим enforcement: инструмент можно не поставлять в прод, API в SDK — нельзя.

Ответ на вопрос «как сделать разработку простой, не позволяя SDK обходить
security model runtime» получился структурным, а не дисциплинарным: в `go.mod`
этого модуля **нет ни одного `require`**, и запрещённый импорт ломает сборку
раньше любого теста.

## Что даёт SDK

Один интерфейс `Plugin`, получаемый из `sdk.Connect`. Весь протокол — handshake,
корреляция запросов и ответов, доставка событий, ответ на остановку — делает SDK;
кадры IPC автор плагина не пишет.

| Группа | Методы | Требуемое право |
|---|---|---|
| Хранилище | `Storage().Get / Put / Delete / List` | `storage.read` / `storage.write` |
| Идентичность | `Identity().PublicKey / Sign / Verify` | `identity.read` / `identity.sign` |
| Шифрование | `Crypto().Encrypt / Decrypt` | `crypto.use` |
| Журнал | `Log` | не требует |
| Доклад о работе | `WorkComplete` | не требует |
| Жизненный цикл | `Connect`, `Run`, `OnEvent`, `OnStop`, `Close` | — |

**Права.** Манифест плагина их только **запрашивает**; выдаёт их вызывающий, а
runtime проверяет на каждый запрос (ADR-073). Право, указанное в манифесте, само
по себе ничего не открывает; отказ приходит как `ErrForbidden`.

**Завершение работы.** `WorkComplete` — доклад «текущая единица работы
закончена», а не остановка: решение о `STOP` принимает runtime, вызов повторяем,
и после него плагин продолжает работать (ADR-072).

**Две ловушки**, о которых стоит знать до первого плагина: `Run` должен быть
запущен до первого вызова API, а `OnEvent`/`OnStop` выполняются синхронно в его
потоке — блокирующий вызов SDK изнутри обработчика возвращает
`ErrReentrantCall`. Подробности и приёмы — в руководстве.
