Журнал начат с ADR-059. Более ранние решения пакета записаны в `README.md`

## ADR-059: реестр живых handle вместо `cgo.Handle` (2026-09-14)

### Почему

Первый прогон пакета под ASan остановился на `heap-use-after-free` в
`resolveOpaqueHandle`: конкурентный `Photon_Destroy`, законно начатый по
ADR-045 §7.3, читал ячейку, которую победитель уже освободил. Метку «уже
освобождён» (`0` в ячейке) можно прочитать только из освобождённой памяти —
механизм защищал ровно тем, что и было дефектом. Первая редакция исправления
(«удалить запись → `C.free`») проиграла переиспользованию адреса: вызов,
вошедший до конца окна, мог найти **чужой** объект на том же адресе. Отсюда
эпохи (редакция 2). Разбор семантики `active[e]` по всем экспортируемым
функциям нашёл дыру живости: отложенное уничтожение снимает handle на насосе,
вне экспортируемого вызова, и ячейка ждала бы вызова, которого может не быть.
Отсюда вторая точка прохода освобождения (редакция 3). Контракт окна —
`DECISIONS.md`, ADR-059.

### Что сделано

- `handle_registry.go` — реестр на чистом Go, без cgo: адрес → объект,
  `epoch`, `active[e]`, `retired`. Операции: `register`, `enter`, `exit`,
  `retire`, проход освобождения `reclaimLocked`. Аллокатор ячеек — параметр
  (`cellAllocator`): в рабочем коде `C.malloc`/`C.free` (`cCells` в
  `photon.go`), в тесте — контролируемый.
- `photon.go` — `cgo.Handle`, метка `0`, `resolveOpaqueHandle`,
  `releaseOpaqueHandle`, `coreFromHandle` удалены. Ячейка — только источник
  уникального адреса.
- Девять функций, принимающих handle, входят в эпоху первым действием и
  выходят через `defer`: `Destroy`, `SetEventCallback`, `GetLastError`,
  `SendAction` (через `enterCore`), `StringData`, `StringLen`, `FreeString`,
  `BytesData`, `BytesLen`. Ровно один поиск на вызов; повторных обращений к
  реестру по адресу вызывающего вне удерживаемой эпохи нет.
- Проход освобождения — в двух точках, с одним условием И5: на выходе вызова
  после `active[e]--` и в `retire` сразу после `epoch++`.
- `teardown`: `disp.Close()` → `close(teardownDone)` → `retire`. Прежний
  порядок освобождал ячейку до `close(teardownDone)`.
- `Photon_Create` и тестовый конструктор регистрируют инстанс одной функцией
  `registerCore`.
- `testsupport.go`: `tsCoreIsValid` — через пару вход/выход; добавлен
  `tsLookup` для тестов, которым нужен `*core` внутри окна.

### Что намеренно не сделано

- **Семантика `Destroy` не менялась**: первый, конкурентный, реентерабельный и
  отложенный пути — прежние (ADR-045).
- **`PhotonString`/`PhotonBytes`** идут через тот же реестр только как
  механизм. Окна конкурентного использования у них нет; `Free*` — ровно один
  раз; память по указателям из `*Data`/`GetLastError` эпохами не защищается.
- **Гонка ленивой инициализации `cachedCStr`/`cachedCData`** не устранена —
  существующее состояние, «нерешённое» ADR-059.
- **Объект другого типа в `Photon_Destroy`** по-прежнему снимается с учёта —
  отдельная задача. *(Закрыто позже: ADR-061, раздел ниже.)*
- **Комментарий `photon_core.h` (п. 6 ADR-059) не менялся**: заголовок
  заморожен, текущий текст решению не противоречит. *(Внесено позже, одной
  правкой заголовка вместе с ADR-061 — раздел ниже.)*
- **Тестовой точки остановки в рабочем коде нет**: поздний резолв закрыт
  свойствами механизма и модульным тестом реестра.

### Тесты

- `handle_registry_test.go` — 7 тестов механизма с аллокатором, отдающим
  освобождённый адрес следующему же `alloc` (LIFO): удержание адреса вызовом
  старой эпохи против переиспользования; снимающий вызов держит свою ячейку
  до выхода; снятие без активных вызовов освобождает сразу; отсутствие
  голодания; И7; И6; конкурентная проверка под `-race`.
- `events_test.go` — `TestEvents_DeferredTeardownReclaimsCellWithoutFurtherCalls`:
  реентерабельный `Destroy`, после него ни одного `Photon_*`, ячейка
  освобождена. Контролируемое перекрытие конкурентного и отложенного
  `Destroy` — удержанием `Close` подписки (`fake_transport_test.go`).
- Удалены тесты, закреплявшие поведение за окном: повторный ненулевой
  `Destroy`, вызовы на уничтоженном handle, доступ после `Free*` (C и JVM);
  проверка «`create → destroy → create` даёт разные адреса» — совпадение
  допустимо (п. 5.1).
- `leakcheck_handles.c` и раздел 6 `livecheck_events.c` — второй `Destroy`
  на handle убран.

### Мутации

| мутация | упавшие тесты |
|---|---|
| M1: нет прохода освобождения в `retire` | `TestRegistry_RetireWithoutActiveCallsReclaimsImmediately`, `TestEvents_DeferredTeardownReclaimsCellWithoutFurtherCalls` |
| M2: освобождение не смотрит на активные вызовы | `TestRegistry_OldEpochCallHoldsAddressAgainstReuse`, `TestRegistry_RetiringCallHoldsOwnCellUntilExit` |
| M3: нет проверки И6 | `TestRegistry_RegisterOnLiveAddressPanics` |
| M4: `>=` → `>` в условии И5 | `TestRegistry_OldEpochCallHoldsAddressAgainstReuse`, `TestRegistry_RetiringCallHoldsOwnCellUntilExit` |
| M5: освобождать только при отсутствии активных вызовов | `TestRegistry_NewEpochCallsDoNotStarveReclaim` |

Конкурентный тест реестра M2/M4 не ловит: поиск атомарен со входом, раннее
освобождение там не превращается в чужой объект. И2 и И3 мутациями не
проверялись — их нарушение недетерминированно.

### Что не проверено и не заявляется

- **LeakSanitizer.** В связке Go 1.22.12 / gcc 13.3 при завершении
  Go-процесса не срабатывает: пробник с заведомой утечкой завершился с
  `exit=0` без отчёта. Отсутствие отчёта LSan ничего не доказывает; утечки
  проверены только RSS-пробниками выше, и те не покрывают отложенное
  уничтожение и `PhotonString`/`PhotonBytes` (без Bridge эти пути из C ABI
  недостижимы) — их покрывают Go-тесты.
- **Переиспользование адреса под ASan** — не видно из-за карантина; доказано
  только модульным тестом реестра.
- **Накладные расходы мьютекса реестра** не измерялись. `leakcheck_handles`
  идёт ≈1 м 43 с, из них ≈1 м 18 с системного времени; сравнения с прежней
  `.so` нет.
- **Повторы конкурентных сценариев под ASan** — один проход, `-count=1`.

## ADR-061: типовая безопасность непрозрачных handle (2026-09-17)

### Почему

Реестр ADR-059 хранит адрес → значение и тип не различает, а приведение
проверяли не все функции. `Photon_Destroy` на значении не `*core` снимал
объект с учёта; `Photon_FreeString` и `Photon_FreeBytes` снимали **безусловно**
— проверка типа стояла только вокруг освобождения `cachedCStr`/`cachedCData`.

Худший достижимый исход: `Photon_FreeString(handle инстанса)` убирал инстанс
из реестра **живым** — `disp.Close()` не вызывался, насос событий продолжал
работать, `teardownDone` не закрывался, а handle больше не резолвился, поэтому
последующий `Photon_Destroy` промахивался. Утечка горутин и подписки, заметная
только по поведению. Читающие функции (`StringData`, `StringLen`, `BytesData`,
`BytesLen`) этого дефекта не имели: приведение у них уже проверялось.

В корректном C перепутать типы нельзя — три разные неполные структуры. Риск
живёт там, где типы стираются: JNI держит handle как `long`, у будущих FFI
целое число — обычная форма handle.

### Что сделано

- проверка типа вынесена **отдельным условием до `retire`** во всех трёх
  разрушающих функциях. Прежняя форма
  `if ps, ok := v.(*photonString); ok && ps.cachedCStr != nil` пропускала чужой
  объект дальше к снятию с учёта — в этом и состоял дефект;
- `Photon_Destroy` на строке или байтах, `Photon_FreeString` и
  `Photon_FreeBytes` на объекте другого типа — no-op; объект остаётся
  зарегистрированным и освобождается своей функцией;
- реестр остался **единым**: три отдельные карты рассмотрены в ADR-061 и
  отвергнуты, эпохи и инварианты И5–И7 общие по построению. Тип в записи не
  хранится — достаточно приведения;
- `photon_core.h` получил три группы комментариев **одной правкой**: поведение
  `Free*` и `Destroy` при чужом типе (ADR-061) и уточнение границы окна
  времени жизни (ADR-059 п. 6, отложенный пункт). Сигнатуры, коды
  `PhotonResult` и `PHOTON_ABI_MAJOR`/`MINOR` не менялись.

### Что намеренно не сделано

- **гарантии не расширены**: двойной `Photon_Free*` своего типа, вызов после
  закрытия окна и устаревший указатель на переиспользованном адресе остаются
  UB и тестами не закрепляются;
- **гонка ленивой инициализации `cachedCStr`/`cachedCData`** не исправлялась —
  отдельная известная область (ADR-059, «нерешённое»);
- **`releaseEventListener`** не трогался: контекст слушателя выделяет сам мост,
  в реестре его нет;
- **диагностики перепутанного типа нет**: ни одна из трёх функций не
  возвращает код, а `Photon_GetLastError` требует handle инстанса. Оставлено
  нерешённым в ADR-061.

### Тесты и проверки (2026-09-17)

`typesafety_test.go` — полная матрица «разрушающая функция × чужой тип» плюс
проверка по реестру. Каждый тест доказывает два шага: объект пережил
неправильный вызов и после него доступен своей правильной операции.

| № | вызов | чужой объект |
|---|---|---|
| 1 | `Photon_Destroy` | `PhotonString` |
| 2 | `Photon_Destroy` | `PhotonBytes` |
| 3 | `Photon_FreeString` | инстанс |
| 4 | `Photon_FreeString` | `PhotonBytes` |
| 5 | `Photon_FreeBytes` | инстанс |
| 6 | `Photon_FreeBytes` | `PhotonString` |
| 7 | все три | чужой вызов не снимает запись с учёта — проверка прямо по реестру |

| проверка | результат |
|---|---|
| `go test .` | 55/55 (было 48) |
| `go test -race .` | чисто |
| `go test -asan .` | чисто, отчётов нет |
| `go vet`, `gofmt -l` | чисто |
| мутации: удаление типовой проверки в `Destroy`, `FreeString`, `FreeBytes` | все три обнаружены |
| `.so` пересобрана, `leakcheck_handles` собирается против неё | да |

Мутация роняет по три теста каждая: две пары матрицы и проверку реестра.

### Известные хвосты — вне ADR-059

- `photon-bindings/jvm/README.md`, раздел «Сборка»: `javac` в шаге 4 не
  получает `PhotonEventListener.java` и падает на `cannot find symbol`;
  запуск `PhotonEventsTest` требует classpath с Java-классами, в README его
  нет.
- `gcc -Wall -Wextra` на `livecheck_events.c`: неиспользуемая `note()`
  (предупреждение было и до правки).
- `PhotonEventsTest`, проверка порядка: на первом создании self-DM лишний
  `MESSAGE` сдвигает сравнение — улучшение теста, если решим его делать.
- Отчёт по ходу работы называл `Photon.close()` неатомарным. Это неверно:
  метод помечен `@Synchronized`, проверка и установка `closed` атомарны.
  Хвостом не является.
