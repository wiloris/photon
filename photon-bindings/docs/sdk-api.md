# Photon SDK — спецификация публичной поверхности

Статус: **ПРИНЯТО И РЕАЛИЗОВАНО**, 2026-09-20. Phase 17.
§§1–10 — ADR-062; §4.1 — ADR-064; §11 — ADR-066.

Документ отвечает **только на вопросы, которые ADR-062 оставил открытыми**.
Направление задано ADR-062 и здесь не пересматривается.

**Написана до кода** — и код по ней написан. На момент написания (2026-09-18)
ни одного файла SDK не существовало: публичной поверхностью служил сам
JVM-мост, а каждый потребитель разбирал событие сам, регулярным выражением по
одному полю. Сегодня §§1–10 реализованы в `photon-sdk` (`99ad52f`), Developer
Tools переведён на этот API (ADR-062 п. 7), а аудит соответствия кода и текста
выполнен. Порядок «спецификация до кода» здесь соблюдён буквально, и запись
об этом оставлена как есть, а не переписана задним числом.

**C ABI этой спецификацией не меняется.** `PHOTON_ABI_MAJOR/MINOR` = 1/0,
экспортируемых символов по-прежнему 12, новых типов событий не вводится.

**Расширений после принятия два, и оба пришли отдельными решениями:**

- **§4.1** — секция `storage` в конфигурации, с **ADR-064** (локальная лента
  через `Photon_SendAction`), реализована вместе с ним и в ADR-062 п. 6 не
  входила;
- **§11** — типизированные примитивы локальной ленты (801/802/803), с
  **ADR-066** (2026-09-19). Он же адресно снял ограничение ADR-062 §6
  «ничего сверх этого» — для этих трёх примитивов и форм данных, которых они
  требуют, и ни для чего больше. Действие 800 остаётся сырым.

Прежняя редакция этого абзаца называла §4.1 **единственным** расширением;
с §11 это перестало быть правдой. Сигнатуры ABI не затронуло ни одно из двух:
`PHOTON_ABI_MAJOR/MINOR` = 1/0, символов 12.

## 0. Границы документа

### Закрыто ADR-062 — не пересматривается

- SDK — публичный Kotlin/JVM слой **поверх существующего** JNI-моста, а не
  второй мост;
- **D3**: один нативный колбэк, мультиплексирование слушателей на стороне
  SDK;
- **D5**: JSON на границе ABI, типизированная модель в SDK, доменных
  сущностей в Core не появляется.

> Расхождение, замеченное при написании: `jni-events.md` §8 всё ещё помечает
> D3 и D5 как открытые. Оно устранено ADR-062; правка того документа — за
> рамками этой спецификации.

### Non-goals

Документ **не**:

- дублирует валидацию `ParseConfig` — единственная проверка (отрицательные
  длительности, `dispatcher/config.go:157-172`) остаётся в ядре;
- вводит новые типы событий и не обещает `PLUGIN_EVENT` / `STORAGE_CHANGED`
  (`photon_core.h:318-320`: имена зарезервированы, источников в ядре нет);
- меняет правило «исключение — только на несостоявшийся вызов»
  (`PhotonException`, `Photon.kt:228`);
- выбирает **координаты артефакта и публикацию** — отложено ADR-051 и
  ADR-062 п. 8 (модуль, каталог и имя пакета решены в §7.3);
- проектирует миграцию Developer Tools на SDK.

## 1. Модель события

### Что даёт ABI

Канал отдаёт **одну строку**:

```c
typedef void (*PhotonEventCallback)(const char* event_json, void* user_data);
```
(`photon_core.h:367`)

Числового кода типа на ABI **не существует** — проверено машинно, ни одного
вхождения `PhotonEventType` / `PHOTON_EVENT_` в дереве. Тип события — это
строковое поле `"type"` внутри конверта (`photon_core.h:343`), и ядро пишет
его буквально так: `{"type":"CONNECTED"}` (`events.go:36-43`).

Эмитируются ровно три значения (`events.go:20-24`). Добавление четвёртого
**не является изменением ABI**: сигнатуры не меняются, версия остаётся 1/0.
Следовательно SDK, собранный сегодня, обязан работать с ядром, которое завтра
начнёт эмитировать `PLUGIN_EVENT`.

### Решение: sealed-иерархия с открытым дном

```kotlin
sealed interface PhotonEvent {
    val raw: String                 // исходный event_json, всегда

    data class Connected(override val raw: String) : PhotonEvent

    data class Message(
        val event: String,          // строка с провода Bridge, НЕ enum
        val userId: String?,        // обычно null: omitempty, один хук из восьми
        val data: String?,          // сырой JSON-текст, не разобранный объект
        override val raw: String,
    ) : PhotonEvent

    data class NetworkChanged(
        val state: String,          // сегодня единственное: "disconnected"
        override val raw: String,
    ) : PhotonEvent

    data class Unknown(
        val type: String?,          // null = строкового "type" получить не удалось
        override val raw: String,
    ) : PhotonEvent
}
```

**Нагрузка подтипов — ровно то, что есть на проводе, и ничего сверх.**
`Connected` не имеет полей, потому что ядро их не пишет. `state` и `event` —
строки, а не перечисления: словарь состояний ядра может вырасти, а `event` —
это вообще доменный словарь Bridge, который ядро намеренно не знает
(`events.go:50-53`). `data` остаётся текстом: разбор доменной формы
Mattermost в SDK — ровно та доменная сущность, которую D5 запретил.

`raw` присутствует у **каждого** подтипа, а не только у `Unknown`: это
единственное, что делает неизвестное событие пригодным к употреблению, и
страховка на случай, когда типизация чего-то не довезла.

### Гарантия расширяемости

> **Появление нового типа события в ядре не требует обновления SDK и не
> ломает существующий обработчик.** Неизвестное значение `"type"`
> представляется как `Unknown`; новый Kotlin-подтип при этом не возникает, и
> исчерпывающий `when` у потребителя остаётся исчерпывающим.

Это свойство выбрано сознательно и является главной причиной, по которой
подтипы для зарезервированных `PLUGIN_EVENT` / `STORAGE_CHANGED` **не
заводятся заранее**: их поля никем не наблюдались, и придуманная форма была
бы обещанием за ядро.

Обратная сторона названа явно, чтобы её не открыли заново: если когда-нибудь
потребуется **заставить** приложение обработать новый тип отдельной веткой,
это будет новое изменение API SDK (добавление подтипа ломает исчерпывающий
`when` на этапе компиляции) — отдельное решение, здесь не принимаемое и от
рантайма не зависящее.

## 2. Неизвестное и неразбираемое

### Два разных «неизвестно», которые нельзя смешивать

| Что неизвестно | Кому принадлежит словарь | Как представляется |
|---|---|---|
| значение `"type"` конверта | ядро, перечень в `photon_core.h:346-350` | `Unknown(type = "…")` |
| значение `MESSAGE.event` | Bridge, доменный словарь Mattermost | обычный `Message(event = "…")` |

Второй случай `Unknown` **не порождает никогда**. SDK не владеет словарём
Bridge и не обязан его знать — ровно по той причине, по которой его не знает
ядро. Смешение этих двух уровней — самая вероятная ошибка чтения §1, поэтому
она зафиксирована таблицей.

### Неизвестный тип доставляется, а не отбрасывается

Ядро принципиально не теряет незнакомое молча (`events.go:52-53`), а поток
событий и без того не полон: сервер роняет события при переполнении своего
буфера (`photon_core.h:333-337`, измерено — 165 событий, Phase 15.5).
Добавлять к этим пропускам пропуски по вине SDK значит ухудшать и без того
негарантированное.

### Неразбираемый конверт

Сегодня конверт собирает само ядро и валидирует `data` перед вставкой
(`events.go:65-67`), так что случай не должен наступать. Определённое
поведение всё равно обязательно — **исключение из парсера внутри нативного
колбэка пересекло бы границу JNI**, а это уже не вопрос удобства.

Нормативно: конверт, из которого **не удалось получить строковое поле
`"type"`**, доставляется как `Unknown(type = null, raw = <строка как есть>)`.
Случаев три, и все три дают один и тот же исход:

- строка не разбирается как JSON либо разбирается не в объект;
- объект разобран, но поля `"type"` в нём нет;
- поле `"type"` есть, но его значение не строка (`{"type":17}`).

Отдельного подтипа `Malformed` не вводится — потребитель различает случаи
проверкой `type`, а лишняя ветка `when` оплачивалась бы всеми ради случая,
который не должен наступать.

## 3. Слушатели

### Что уже гарантировано и не переопределяется

- доставка **синхронна и последовательна**: двух одновременных доставок не
  бывает (Phase 15.5, D1 в `jni-events.md`);
- поток — **любой**, в том числе не связанный с потоком инициализации JNI
  (`photon_core.h`, «граница Go/JVM»);
- после возврата из `Photon_Destroy` колбэк не будет вызван ни разу
  (`photon_core.h:302-308`).

Сегодня слушатель ровно один (`Photon.kt:123`), потребность в нескольких
зафиксирована документом (`jni-events.md:290-295`), но кодом ещё не
предъявлена: каждая лаборатория Developer Tools создаёт свой инстанс.

### 3.1. Изменение списка во время доставки — разрешено

Набор слушателей снимается **снимком** перед доставкой события. `add` / `remove`
из тела слушателя не бросают и на текущее событие не влияют.

Запрет («бросаем `ConcurrentModificationException`») отвергнут: «отписаться,
получив нужное событие» — основной сценарий, и его запрет заставил бы каждого
потребителя писать свою отложенную отписку.

### 3.2. Гарантия при отписке

> `remove(listener)` **не отменяет** доставку события, для которого слушатель
> уже попал в снимок. После возврата `remove` слушатель **не включается в
> новые снимки**.

Формулировка именно такая, а не «после того как доставка началась»: снимок
может быть снят раньше, чем дойдёт очередь до конкретного слушателя, и
внешний поток способен вызвать `remove` ровно в этом промежутке. Граница
проводится по снимку, потому что только она наблюдаема.

Сильная гарантия («после возврата не вызовется ни разу») отвергнута: она
означает ожидание внутри `remove`, а `remove` типично зовут **из самого
слушателя**, то есть изнутри идущей доставки — сильная версия даёт дедлок в
основном сценарии.

Реализация, естественно соответствующая контракту, — `CopyOnWriteArrayList`.

### 3.3. Порядок обхода — порядок регистрации

Не «не определён». Недетерминированный порядок невозможно проверить тестом, а
проект требует тестов, падающих при нарушении правила.

### 3.4. Исключение слушателя

Нормативно:

1. SDK перехватывает **`Throwable`**, а не `Exception`;
2. исключение одного слушателя **не прекращает** доставку остальным
   слушателям снимка — D4 обещает доставку, и отказ одного потребителя не
   вправе её отменить. Правило единое, `Error` исключением не является;
3. исключение **не пересекает границу JNI** ни при каких условиях;
4. перехваченное подаётся в
   `Thread.currentThread().uncaughtExceptionHandler` — **синхронно**, на
   потоке доставки, до вызова следующего слушателя;
5. SDK **никогда не устанавливает** default-обработчик и не заводит своего:
   установка глобального обработчика библиотекой была бы захватом ресурса
   приложения;
6. исключение самого обработчика ловится и **подавляется**; повторно тому же
   обработчику оно не подаётся;
7. `close()` из обработчика **допустим**.

Ниже — почему каждое из решений именно такое. Все ссылки на измерения — это
прогоны 2026-09-18 против локального фиктивного Bridge по настоящему пути
`Go → C ABI → JNI → JVM`.

**Почему `Throwable`, а не `Exception` (п. 1).** Мост ловит всё: `ExceptionCheck`
(`photon_jni.c:277`) истинен и для `Error`, после чего идут `ExceptionDescribe`
и `ExceptionClear`. Поэтому «ловим только `Exception`» **не означает**, что
`Error` дойдёт до JVM и убьёт поток, — он будет поглощён всё равно, только
мостом, с выводом в `System.err` и **без** доставки приложению. Единственный
способ отдать `Error` приложению — поймать его. Выбор здесь не между «скрыть»
и «не скрыть», а между «скрыть молча» и «сообщить».

**Почему доставка продолжается и после `Error` (п. 2).** Рассматривался
консервативный вариант: на `Error` прекращать обход остатка снимка. Отвергнут
по проверяемости: правило, действующее только под `OutOfMemoryError`, нельзя
честно проверить тестом — тест такого правила сам с высокой вероятностью не
переживёт условие, которое проверяет. Единое правило хуже в редком случае, но
не обещает того, что не может быть доказано.

**Почему `Thread.currentThread().uncaughtExceptionHandler`, а не
`getDefaultUncaughtExceptionHandler()` (п. 4).** Второе возвращает `null`,
если приложение ничего не поставило, и отказ стал бы **невидим совсем** — хуже
сегодняшнего положения, где мост хотя бы печатает трассировку. Первое
разрешается в обработчик приложения, когда он задан, и в `ThreadGroup`, когда
нет; `ThreadGroup` печатает трассировку в `System.err`. Измерено: с
установленным default-обработчиком три отказа дали ровно три вызова и ни
одного лишнего; без него в `System.err` пришло
`Exception in thread "Thread-8" java.lang.IllegalStateException: …`.

**Почему обработчик не привязывается к потоку.** Идентичность потока доставки
в JVM **не сохраняется между событиями**: мост делает `AttachCurrentThread` на
каждый колбэк и `DetachCurrentThread` после (`photon_jni.c:262-291`), поэтому
`java.lang.Thread` создаётся заново — измерено, три события дали три разных
`threadId`. Внутри одного события поток один и тот же. Отсюда же: `ThreadLocal`
на потоке доставки не переживает событие.

**Обработчик обязан быть быстрым (следствие п. 4).** Он исполняется **внутри**
пути доставки, очереди между насосом и потребителем нет намеренно
(`pump.go:21-23`). Измерено: обработчик, блокирующийся на 2000 мс, даёт паузу
между доставками ровно 2000 мс вместо 700 и снижает число принятых событий с
13 до 6 за девять секунд. Достаточно долгая блокировка приводит к потерям на
**сервере** — его буфер конечен (Phase 15.5, измерено 165 событий).

**Почему исключение обработчика подавляется (п. 6).** Отдать его мосту нельзя:
оно вышло бы из диспетчера и лишило бы события остаток снимка, то есть прямо
нарушило бы п. 2. Подавать его повторно тому же обработчику бессмысленно —
сломан ровно тот механизм, через который мы сообщаем о поломках.

**`close()` из обработчика (п. 7).** Дедлока нет: `Photon_Destroy`
реентерабелен, измерено — возврат за 25 мс, обработчик исполняется на потоке
доставки. Гарантия «после возврата из `Destroy` колбэков нет» соблюдается:
новых доставок не возникает. Но **остаток текущего снимка отрабатывает** —
отменить уже идущую доставку ядро не может и не обещает. Поэтому слушатель,
идущий следом и обратившийся к закрытому инстансу, получает
`IllegalStateException: Photon instance is closed` — и это **обычное исключение
слушателя**, которое идёт тем же путём п. 1–6. Цепочка конечна: повторный
`close()` идемпотентен.

**Публичная поверхность этого раздела — нулевая.** Ни нового типа, ни нового
метода: только зафиксированное поведение. Счётчик отказов доставки в публичный
API не вводится — он был бы обязательством навсегда (что считается отказом,
считаются ли `Error`, сброс, гонки) и задачу наблюдаемости не решает.
Добавление его позже — совместимое дополнение, как и собственный обработчик на
инстансе; обратное — удаление уже объявленного API — совместимым не бывает,
поэтому начинается с меньшего.

## 4. Конфигурация: форма

### Что есть на границе

Одна необязательная секция `bridge`, девять полей
(`dispatcher/config.go:113-129`). Значения по умолчанию живут в `withDefaults`
(15 с / 30 с / 15 с / 500 мс / 30 с); **ноль означает «по умолчанию»**, как и
отсутствие поля. Секция необязательна — `{}` законен. Developer Tools собирает
JSON руками в семи местах и использует восемь полей из девяти (`keepalive_ms`
не использует никто).

### Решение

Типизированный `PhotonConfig` с необязательной секцией `bridge`, зеркалящий
эту структуру и **ничего к ней не добавляющий**.

**Правило, которое важнее формы: SDK не повторяет значения по умолчанию.**
«Не задано» выражается как `null`. Иначе у умолчания появится два источника, и
они разойдутся при первой же правке ядра — молча, потому что оба значения
правдоподобны.

**Каноническая сериализация: не заданное поле не сериализуется вовсе.**
Хотя ядро трактует отсутствие и ноль одинаково, выбирается один вариант —
иначе два способа выразить одно состояние начнут означать разное при первой
попытке отличить «пользователь задал ноль» от «пользователь не задавал».
Минимальный `PhotonConfig` даёт `{}`.

**Валидации в SDK нет.** Отрицательная длительность уезжает в ядро и
возвращается как `PHOTON_ERR_INVALID_ARGUMENT` → `PhotonException`. Это ровно
граница из §0.

### 4.1. Секция `storage` (ADR-064)

Вторая секция конфигурации — **локальное хранилище инстанса**:

```kotlin
PhotonConfig(
    bridge = BridgeConfig(endpoint = "host:4443"),
    storage = StorageConfig(path = "/var/lib/engram/feed.db"),
)
```

**Отдельная секция, а не поле внутри `bridge`:** хранилище к Bridge отношения
не имеет, и класть его в чужую секцию значило бы связать локальную работу с
сетевой (ADR-064 п. 1.2).

**Секция необязательна, и её отсутствие — не ошибка.** У такого инстанса
просто **нет локального backend**: сетевые действия работают, локальные
отвечают отказом вызова (`PHOTON_ERR_NOT_CONNECTED`), как сетевое действие на
инстансе без адреса Bridge.

**Следствие для `create`, которое надо знать:** с этой секцией создание
инстанса **обращается к файловой системе** — хранилище открывается и
мигрируется внутри вызова. Свойство «`create` не подключает сеть» при этом
сохраняется: эти два свойства разные. Отказ открытия по годному пути даёт
`PhotonException` с кодом `PHOTON_ERR_INTERNAL`; негодная конфигурация —
`PHOTON_ERR_INVALID_ARGUMENT` (ADR-064 п. 1.6).

## 5. Единицы времени

На границе ABI — миллисекунды (`config.go:110-112`). В публичном API —
**`java.time.Duration`**.

Не `kotlin.time.Duration`: это value-класс, из Java он выглядит как `long` со
стёртым смыслом, а Java-потребитель у моста уже есть (26 Java-тестов в
`photon-bindings/jvm`).

**Последствие назвать явно:** `java.time` требует Android API 26+ либо
desugaring. Android в проекте отложен (нет NDK), но это ограничение **SDK**, а
не ядра, и записано до того, как о нём вспомнят на устройстве.

Конверсия одна, в точке сборки JSON: `Duration.toMillis()`. Округление вниз до
миллисекунды — документированное поведение, не дефект.

## 6. Поля вне схемы

Ядро игнорирует неизвестные поля **намеренно** (`config.go:139-142`): иначе
добавление секции для будущей подсистемы ломало бы старое ядро. Случай не
гипотетический — `storage_path` фигурирует в самом комментарии `ParseConfig`
как пример законного `config_json`, и в `wireConfig` его нет.

То, что ядро их игнорирует, **не отвечает** на вопрос, даёт ли SDK их
передать. Это отдельное решение, и оно принимается так:

> `PhotonConfig.raw(json)` — **альтернативный способ задать конфигурацию
> целиком**. Он не смешивается с типизированными полями одного экземпляра.

То есть законно

```kotlin
PhotonConfig(bridge = …)        // типизированный путь
PhotonConfig.raw("""{ … }""")   // всё, чего SDK ещё не знает
```

и не существует

```kotlin
PhotonConfig(bridge = …, raw = …)   // таких перегрузок нет
```

Смешивание отвергнуто по той же причине, по которой отвергнут вариант
«типизированный объект + карта прочего»: оно требует правил приоритета («что
если `raw` содержит `bridge`») и заводит второе место, где собирается JSON.

Запрет передавать такие поля вовсе отвергнут отдельно: SDK, физически не
способный передать поле, которое ядро принимает, вынуждает себя обходить — и
потребитель вернётся к сборке строки руками, то есть ровно к тому, что SDK
убирает.

`raw` документируется как **временный** путь: как только поле входит в схему
ядра, оно типизируется.

## 7. Вопросы, оставленные ADR-062 — закрыты

Все три. Ни один не закрывался рассуждением: 7.2 — двумя живыми прогонами,
7.1 — измерением, 7.3 — разбором существующей сборки.

### 7.1. Чем SDK разбирает и собирает JSON — ЗАКРЫТ 2026-09-18

**Решение: `kotlinx.serialization`, и только через tree-API.**

Три условия входят в решение и без них оно не действует:

1. **`@Serializable` и плагин компилятора не применяются.** Измерено: разбор
   конверта через `Json.parseToJsonElement` компилируется Kotlin 2.4.20 без
   единого плагина — привязки версии плагина к версии Kotlin у SDK не
   возникает.
2. **Автоматический object mapping не вводится** — ни рефлексивный, ни
   кодогенерируемый. Появление такого маппинга требует отдельного
   архитектурного решения, потому что это уже граница между JSON и доменной
   моделью, а её ADR-062 п. 5 провёл иначе.
3. **`MESSAGE.data` не проходит через `JsonElement.toString()`.** Подробности
   ниже — это не предосторожность, а измеренный факт.

**Почему не свой парсер.** Требуемый объём действительно мал: четыре
строковых поля верхнего уровня, одно поддерево дословно, девять полей на
запись. Ручная реализация чтения заняла 86 строк и прошла на вложенности,
массивах, `}` внутри строки и экранированной кавычке. Но публичная библиотека
становится владельцем этого кода навсегда — вместе с экранированием при
записи, поведением на битом вводе и всем, что добавит следующая правка
спецификации. Цена альтернативы измерена: **646 КБ** сверх обязательного
`kotlin-stdlib` (json 264 КБ + core 382 КБ). Для сравнения, `libphoton_core.so` —
**10.3 МБ** на одну архитектуру. Собственный JSON-код ради такой экономии —
плохая сделка.

**Почему именно эта библиотека.** Измерено на конверте с `1758181234567`,
целым за пределами double, `1.0` и `1e3`: дословность поддерева сохраняют
`kotlinx.serialization` и `gson`, **не сохраняют** `jackson-databind`
(`1e3` → `1000.0`) и `org.json` (`1.0` → `1`, плюс переставленный порядок
ключей). Object mapper здесь не нужен вовсе, поэтому `jackson-databind`,
`moshi` и рефлексивный путь `gson` дают больше, чем требуется. Между двумя
оставшимися выбран Kotlin-native.

**Про `data` — измеренное ограничение.** `JsonElement.toString()` **не**
является дословной передачей: он пересобирает текст и нормализует
форматирование. Проверено — `{"a": 1 ,  "b" : [1,  2] , …}` возвращается как
`{"a":1,"b":[1,2],…}`. Совпадение на плотном JSON, который шлёт ядро
сегодня, случайно и опираться на него нельзя. `data` обязан извлекаться как
исходный фрагмент строки; конкретный способ извлечения определяется при
реализации.

**Побочный факт, который стоит помнить при любой реализации:** у `gson` и
`jackson` разбор пустой строки не бросает исключения. Отсутствие конверта
поэтому определяется отсутствием `type`, а не только исключением — правило
§2 записано именно так и от библиотеки не зависит.

### 7.2. Способ наблюдения исключения слушателя — ЗАКРЫТ 2026-09-18

Решение и обоснования в §3.4. Закрыт двумя живыми прогонами на настоящем
пути доставки: доступность обработчика на присоединённом Go-потоке,
нестабильность идентичности этого потока между событиями, `close()` из
обработчика без дедлока, цена блокирующего обработчика.

### 7.3. Размещение — ЗАКРЫТ 2026-09-18

**Решение: отдельная сборка `photon-sdk`, пакет `dev.photon.sdk`, подключение
к Developer Tools композитной сборкой.**

```
photon-sdk/
├── settings.gradle.kts        ← свой корень сборки
├── build.gradle.kts
└── src/{main,test}/kotlin/dev/photon/sdk/…
```

Developer Tools подключает его через `includeBuild`, заменяя нынешнее прямое
подключение исходников моста (`build.gradle.kts:72-78`).

**Почему отдельная сборка, а не подпроект инструмента.** Подпроект оставил бы
корнем многопроектной сборки **потребителя**: платформенный модуль жил бы
внутри сборки своего клиента, и при выделении Developer Tools по критерию
ADR-051 SDK пришлось бы вынимать обратно. Композит сохраняет отношение
«инструмент — потребитель SDK» (ADR-062 п. 7) буквально, а будущее выделение
в отдельный репозиторий становится переносом каталога.

**Почему не корневая сборка на всё дерево.** В корне живут четыре Go-модуля и
Bridge с несовместимым toolchain (Go 1.22 против 1.24). JVM-сборка,
претендующая на корень, сделала бы его небезразличным к языку, ничего не
решив по существу.

**Почему `dev.photon.sdk`, а не `dev.photon.core`.** Последний занят мостом.
Общий пакет дал бы доступ к `internal`, но стёр бы границу, которую ADR-062
п. 2 проводит намеренно: мост — реализационная основа, SDK — публичная
поверхность.

**Что этим решением НЕ закрывается** (отложено ADR-051 и ADR-062 п. 8 и здесь
не переоткрывается): координаты Maven и публикация, тип артефакта для Android
(AAR требует Android SDK, которого в среде нет), кроссплатформенная упаковка
native, сборка под Android (NDK, ARM), система релизов. Сегодня реализуем
ровно один тип артефакта — обычный JVM-jar, и он **не самодостаточен**:
`.so` в него не входит, их получение остаётся задачей потребителя.

**Работа, которую решение делает обязательной и о которой легко забыть:** в
`photon-bindings/jvm` production-код и тесты лежат в одних каталогах
(`PhotonJniTest.java` рядом с `dev/photon/core/*.java`, два теста рядом с
`Photon.kt`) и сегодня исключаются по именам файлов. Переход на сборку с
обычной раскладкой `src/main` / `src/test` требует либо переноса этих файлов,
либо повторения списка исключений.

## 8. Время жизни клиента, колбэка и слушателей

Раздел описывает, как §3 соединяется с настоящим инстансом. Всё ниже
подтверждено живым прогоном 2026-09-18 на пути `Go → C ABI → JNI → JVM`
(14 проверок, 0 отказов).

### 8.1. Один нативный колбэк на клиента

**L1. Нативный колбэк устанавливается ровно один раз** за жизнь клиента — при
**первом** `addEventListener`. Не переустанавливается и не снимается.

Установка — единственный вызов ABI, выражающий намерение получать события, и
она **запускает подписку** (`photon.go:328-343`). Ставить колбэк в момент
создания клиента значило бы поднимать сеть тем, кто событий не слушает, — при
том что `Photon_Create` сети не касается по контракту.

**L2. После установки `addEventListener` и `removeEventListener` границы ABI
не пересекают** — это операции над списком в JVM.

Следствие, ради которого модель и выбрана: каждая установка слушателя на
стороне моста выделяет новый нативный контекст и `GlobalRef`
(`photon_jni.c:327-339`), освобождаемый отдельным вызовом по правилам очереди
`Photon.kt:70-112`. При одном колбэке эта механика исполняется один раз за
жизнь клиента, а не на каждое изменение набора слушателей.

**L3. Снятие последнего слушателя подписку не останавливает и колбэк не
снимает.** Останавливать её нечем: `NULL` в ABI лишь отцепляет адресата, а
подписка живёт до `Photon_Destroy` (`photon.go:334-336`, тест
`TestEvents_NilCallbackDropsWithoutStoppingPump`).

**L4. Доставка в пустой набор слушателей допустима.** Конверт разбирается,
обходить некого, ошибкой это не является.

### 8.2. Закрытие

**L5. `close()` во время доставки ждёт завершения текущего колбэка.** Вызов из
другого потока дедлока не даёт.

**L6. После возврата из `close()` слушатели не вызываются** — гарантия C ABI
(`photon_core.h:302-308`), а не SDK. Остаток текущего снимка при этом
отрабатывает (§3.4).

**L7. `addEventListener` после `close()` бросает `IllegalStateException`** —
**всегда**, независимо от того, устанавливался ли колбэк раньше.

Правило записано именно так, потому что без него поведение зависело бы от
истории вызовов: при L1 первый `addEventListener` упёрся бы в `check(!closed)`
моста (`Photon.kt:124`) и бросил, а последующий моста не касается (L2) и молча
добавил бы слушателя в мёртвый клиент. Добавление слушателя в закрытый клиент —
ошибка программиста: событий не будет никогда, а молчаливое согласие выглядело
бы как работающая подписка.

**L8. `removeEventListener` после `close()` — безопасный no-op**, в том числе
для слушателя, зарегистрированного до закрытия. Снятие — уборка; требовать
порядка «сначала отписаться, потом закрыть» значит заставлять каждого
потребителя оборачивать уборку в `try/catch`. Гарантия §3.2 после закрытия
выполняется тождественно: новых снимков не будет.

Асимметрия L7 и L8 намеренная: **добавить в закрытый клиент — ошибка, снять из
закрытого — уже сделано.**

**L9. `close()` очищает набор слушателей** — после возврата из
`Photon_Destroy`, не раньше. Порядок тот же, по которому мост освобождает
`GlobalRef` (`Photon.kt:149-160`): до возврата из `Destroy` доставка ещё
возможна. Иначе клиент, переживший приложение, удерживал бы его объекты через
диспетчер.

**L10. Повторный `close()` безопасен и ничего не делает** — идемпотентность
моста (`Photon.kt:144-147`).

### 8.3. Нативные библиотеки грузит приложение

**L11. SDK нативные библиотеки не загружает.** Это обязанность host-приложения:
`dev.photon.core.Photon.loadLibrary()` либо `loadFrom(absolutePath)` — так и
делает сегодня Developer Tools (`Main.kt`, `CryptoLab.kt`) вместе с
`-Djava.library.path` из своей сборки. Распределение ролей задано **ADR-051
п. 3** и здесь не пересматривается.

Автозагрузка внутри `create()` отвергнута по измеренной причине: после
`System.load(<абсолютный путь>)` последующий `System.loadLibrary("photon_jni")`
падает с `UnsatisfiedLinkError`, если имени нет в `java.library.path`
(проверено). То есть SDK, грузящий библиотеку сам, **ломал бы** уже работающий
путь тестов и десктопа, а `try/catch` вокруг загрузки прятал бы настоящие
отказы. Сверх того, автозагрузка требует решить, откуда берётся `.so` — это
упаковка и распространение, отложенные ADR-051 и ADR-062 п. 8.

Следствие, названное прямо: **jar SDK не самодостаточен** (§7.3), и методов
вроде `PhotonClient.loadLibrary` в публичной поверхности нет — они немедленно
потребовали бы решить тот же отложенный вопрос.

## 9. Действия: `sendAction`

```kotlin
public fun sendAction(action: Int, payloadJson: String): PhotonResponse
```

`action` — числовой код Photon Protocol, `payloadJson` — payload строкой.
Типизированного перечисления действий SDK не вводит: каталог живёт в
`photon-core/protobuf/photon.proto` и читается машинно из `FileDescriptorSet`;
своей копии нет ни у ядра, ни у Developer Tools (`Inspector.kt:132-150` —
«список, вписанный сюда руками, был бы второй копией истины»). Payload строкой —
прямое следствие D5 (ADR-062 п. 5).

### 9.1. Модель результата

```kotlin
public sealed interface PhotonResponse {
    /** Конверт ответа целиком, байт в байт. */
    public val raw: String

    /** ok:true. */
    public data class Ok(
        public val data: String?,
        override val raw: String,
    ) : PhotonResponse

    /** ok:false — вызов СОСТОЯЛСЯ, сервер отказал. */
    public data class Rejected(
        public val error: String?,
        public val data: String?,
        override val raw: String,
    ) : PhotonResponse

    /** Конверт без читаемого булева "ok". */
    public data class Unrecognized(override val raw: String) : PhotonResponse
}
```

### 9.2. Семантика

| Что произошло | Что получает вызывающий |
|---|---|
| `rc != PHOTON_OK` — вызов не состоялся | `dev.photon.core.PhotonException` (`Photon.kt:228`), ответа нет |
| `PHOTON_OK`, конверт `ok:true` | `PhotonResponse.Ok` |
| `PHOTON_OK`, конверт `ok:false` | `PhotonResponse.Rejected` |
| `PHOTON_OK`, `ok` не читается булевым, конверт не объект или не разбирается | `PhotonResponse.Unrecognized` |

Нормативно:

1. **`PHOTON_OK` означает только состоявшийся вызов ABI** — дошёл ли запрос,
   пришёл ли ответ, разобрался ли он. Вердикт операции живёт в конверте
   (ADR-038 п. 1–2).
2. **Отказ сервера исключением не является.** `ok:false` — нормальный ответ
   состоявшегося вызова.
3. **`raw` сохраняется без изменений** у всех трёх подтипов.
4. **`data` извлекается из исходного конверта без пересборки JSON** — то же
   правило и та же реализация, что для `MESSAGE.data` (§1, §7.1).
5. **`data` не типизируется** (ADR-062 п. 5).
6. **`error` не классифицируется по тексту** — передаётся как есть. Тип
   nullable: провод наличия поля не гарантирует.
7. **`Duration`/`nanos` в публичный результат не входят.**
8. **Отдельный `Outcome`/`CallResult` не вводится.**

### 9.3. Закрытый клиент

**`sendAction` после возврата из `close()` бросает `IllegalStateException`.**
Проверка принадлежит SDK, а не наследуется от моста (`Photon.kt:35` делает то
же самое): так контракт не зависит от того, сохранит ли мост своё правило, а
сообщение остаётся тем же, что у `addEventListener` (§8 L7). Обращение к
закрытому клиенту — ошибка программиста, и это та же логика, по которой L7
сформулирован «всегда».

**Вызов, начавшийся ДО закрытия и заставший его в полёте, отменяется и
завершается `PhotonException`** — `Photon_Destroy` прерывает висящий вызов
(тест `TestDestroy_CancelsInflightSendAction`, `photon_test.go:235-293`).
**Конкретный код отказа частью контракта не является:** тест ядра утверждает
только «не `PHOTON_OK`», и фиксировать здесь конкретное значение значило бы
обещать больше, чем проверено.

Проверка гонку не убирает и не обещает убирать — она делает определённым
сценарий «закрыли, потом позвали», а не «звали и закрыли одновременно».

### 9.4. Почему так

**Две оси ADR-038 выражены двумя механизмами, а не одним перечислением.**
Исключение отвечает на вопрос «состоялся ли вызов», `PhotonResponse` — «что
сказал сервер». `Outcome` из `photon-developer-tools/.../Outcome.kt:22-31`
сводит их в одну шкалу, потому что инструменту нужна единая колонка в отчёте;
это инструментальная модель, а не контракт API. В публичном API она заставила
бы проверять одинаково две разные по природе вещи.

**Типизированный `Rejected` закрывает цену, названную в ADR-038:** «клиент,
проверяющий только `rc` и не читающий `ok`, примет отказ за успех». С sealed-
иерархией такая ошибка невыразима — ветку обязан обработать `when`.

**`Unrecognized`, а не `Ok`.** Сегодняшний `classifyResponse`
(`Outcome.kt:52-53`) ищет регулярным выражением **только** `ok:false`, поэтому
испорченный ответ классифицируется у него как успех. Для инструмента это
терпимо, для публичного SDK — то же самое, что §2 запретил для событий.
Исключением испорченный конверт тоже быть не может: вызов состоялся и байты
есть, а исключение заявило бы обратное и ввело бы семантику, которой на проводе
нет.

**Одно исключение, а не два.** Используется существующий
`dev.photon.core.PhotonException` (`Photon.kt:228`) с полями `code`
(значение `PhotonResult`) и `nativeMessage`; он публичен и покрыт 26 Java- и
14 Kotlin-тестами. Своя иерархия означала бы либо второй тип на ту же причину,
либо обёртывание с потерей `code`. Следствие названо явно: публичная
поверхность SDK ссылается на тип из пакета `dev.photon.core`.

**`Duration` не входит.** `CallResult.nanos` (`Outcome.kt:34-40`) существует
ради Performance Lab, а не ради приложений. В публичном типе он стал бы
обязательством навсегда, включая ответ на вопрос «что именно измеряется — сеть,
JNI или разбор». Вызов синхронный, приложение измеряет его само. Добавление
позже — совместимое дополнение, по той же логике, по которой §3.4 отложил
счётчик отказов.

## 10. Что обязаны проверять тесты

Правило проекта: тест обязан падать при нарушении. Перечень ниже — не план
реализации, а список утверждений, каждое из которых проверяемо и каждое из
которых легко сломать «улучшением».

| § | Утверждение | Как ломается |
|---|---|---|
| 1 | неизвестный `"type"` даёт `Unknown`, а не исключение и не пропуск | добавить `else -> throw` в разбор |
| 1 | `raw` у каждого подтипа равен исходной строке байт в байт | пересобрать JSON из полей |
| 1 | `data` равен исходному фрагменту при произвольном форматировании внутри него | вернуть `JsonElement.toString()` |
| 2 | незнакомый `MESSAGE.event` остаётся `Message`, а не `Unknown` | сверить `event` со списком |
| 2 | неразбираемый конверт даёт `Unknown(type = null)`, исключение не улетает наружу | убрать try вокруг разбора |
| 3.1 | `remove` из тела слушателя не бросает и не влияет на текущее событие | заменить снимок на живой список |
| 3.2 | слушатель, снятый после снятия снимка, событие **получает** | снимать снимок лениво, поэлементно |
| 3.3 | порядок доставки — порядок регистрации | заменить список на множество |
| 3.4 | исключение одного слушателя не отменяет доставку остальным | не ловить исключение внутри цикла |
| 3.4 | перехватывается `Throwable`: `Error` из слушателя доходит до обработчика | сузить `catch` до `Exception` |
| 3.4 | обработчик получает ровно одно уведомление на отказ | подать ещё раз в `finally` |
| 3.4 | исключение самого обработчика подавлено и не подано повторно | убрать внутренний `try` |
| 3.4 | `close()` из обработчика возвращает управление и не даёт новых доставок | убрать `dispatcher.clear()` из `close()` |
| 3.4 | отказ слушателя на уже закрытом инстансе идёт тем же путём | подавать обработчику только первый отказ |
| 4 | не заданное поле отсутствует в JSON | сериализовать нули |
| 4 | SDK не подставляет собственных умолчаний | вписать 15 000 в `PhotonConfig` |
| 4.1 | секция `storage` сериализуется отдельно от `bridge` и без неё не появляется | положить путь полем внутрь `bridge` |
| 5 | `Duration` переводится в миллисекунды с округлением вниз | `toMillis` → `toSeconds * 1000` |
| 6 | `raw` и типизированные поля не смешиваются в одном экземпляре | добавить перегрузку с обоими |
| 8 | нативный колбэк ставится ровно один раз, при первом `addEventListener` | ставить при создании клиента; переустанавливать на каждом `add` |
| 8 | снятие последнего слушателя доставку не ломает: набор пуст, процесс жив | снимать колбэк, когда список опустел |
| 8 | `addEventListener` после `close()` бросает **независимо** от истории установки | проверять факт установки вместо флага закрытия |
| 8 | `removeEventListener` после `close()` не бросает | добавить ту же проверку, что у `add` |
| 8 | `close()` очищает набор слушателей и только после `Photon_Destroy` | очищать до вызова `destroy` |
| 8 | повторный `close()` безопасен | убрать флаг идемпотентности |
| 9 | `rc != PHOTON_OK` даёт `PhotonException` и НЕ даёт ответа | вернуть `Unrecognized` вместо исключения |
| 9 | `ok:false` даёт `Rejected`, а не исключение | бросать на вердикт сервера |
| 9 | `raw` равен исходному конверту байт в байт у всех подтипов | пересобрать конверт из полей |
| 9 | `data` равен исходному фрагменту при произвольном форматировании | вернуть `JsonElement.toString()` |
| 9 | конверт без булева `ok` даёт `Unrecognized`, а не `Ok` | считать успехом всё, где нет `ok:false` |
| 9 | текст `error` доходит без изменений и не отображается в коды | сопоставить текст коду ошибки |
| 9 | в публичном результате нет измерения времени | добавить `nanos` в `Ok` |
| 9 | `sendAction` после `close()` бросает и до моста не доходит | убрать `check(!closed)` из `sendAction` |
| 8 | в исходниках SDK нет `System.load*` — библиотеку грузит приложение | позвать `loadLibrary` внутри `create()` |

Отдельно: **отрицательной длительности SDK не проверяет** — тест обязан
доказывать, что ошибка приходит из ядра (`PHOTON_ERR_INVALID_ARGUMENT`), а не
из SDK. Это проверка Non-goal, и без неё дублирование валидации вернётся при
первом же ревью «а почему мы не проверяем ввод».

### Два свойства §3.4 — покрыты тестами репозитория (2026-09-19)

Пока их не было, эти две строки стояли в таблице выше и читались как заявка на
покрытие, которого не существовало; тогда они были вынесены сюда отдельно.
Теперь покрытие есть, и строки вернулись в таблицу:

- **`close()` из обработчика ошибок возвращает управление и не даёт новых
  доставок** — `close из обработчика ошибок возвращает управление и не даёт
  новых доставок`;
- **отказ слушателя на уже закрытом инстансе идёт тем же путём** — `отказ
  слушателя на уже закрытом инстансе идёт тем же путём`.

Оба проверяются без нативной библиотеки: шов `NativeSession` моделирует
**реентерабельный `Photon_Destroy`** — вызов из колбэка возвращается сразу, не
дожидаясь сам себя. Это свойство не выдумано для стенда: оно измерено **живым
прогоном 2026-09-18** на настоящем пути `Go → C ABI → JNI → JVM` (возврат за
25 мс, дедлока нет, новых доставок после возврата не возникло). Оснастка того
прогона в репозиторий не вошла, поэтому из дерева он по-прежнему не
воспроизводится — но поведение SDK поверх этого свойства теперь проверяется
при каждом `gradle test`.

Каждая проверка подтверждена мутацией: снятие `dispatcher.clear()` из `close()`
роняет 3 теста, обрыв доставки на первом отказе — 8, подача обработчику только
первого отказа — 2.

## 11. Локальная лента: типизированные примитивы (ADR-066)

Раздел добавлен **после** принятия документа и описывает второе его
расширение — первым была §4.1. Основание — **ADR-066**, принятый 2026-09-19;
он же адресно снял ограничение ADR-062 §6 («ничего сверх этого»), поэтому
поверхность выросла решением, а не по дороге.

**C ABI это не затрагивает:** `PHOTON_ABI_MAJOR/MINOR` по-прежнему 1/0,
символов 12, новых кодов результата нет.

### 11.1. Что типизировано, а что нет

| действие | код | поверхность |
|---|---|---|
| положить записи | 801 | `localFeedPut(channelId, records)` |
| залить блок | 802 | `localFeedIngest(channelId, block)` |
| позиция верхнего пропуска | 803 | `localFeedGapAnchor(channelId)` |
| **страница ленты** | **800** | **не типизирована**: `sendAction(800, payloadJson)` |

**800 остаётся сырым намеренно** (ADR-066 п. 3.6). Типизировать ли его —
отдельный вопрос, здесь он не решается. Практическое следствие: цикл догрузки
у вызывающего собирается из трёх типизированных вызовов и одного общего.

**`sendAction(action: Int, payloadJson: String)` сохраняется и устаревшим не
объявляется** (ADR-066 п. 3.5): он общий для всех действий, типизированы три.

### 11.2. Формы данных

Повторяют ADR-065 п. 2 один в один:

```kotlin
public data class FeedPosition(orderKey: Long, id: String)
public data class FeedRecord(id: String, orderKey: Long, version: Long, body: String)

public sealed interface FeedBlock {
    public val records: List<FeedRecord>
    public val atEnd: Boolean
    public data class Newest(records, atEnd) : FeedBlock
    public data class After (anchor: FeedPosition, records, atEnd) : FeedBlock
    public data class Before(anchor: FeedPosition, records, atEnd) : FeedBlock
}
```

Нормативно:

1. **`orderKey`/`version` — `Long`.** Значения выше 2^53 обязаны доезжать без
   искажения; разбор через число с плавающей точкой запрещён (ADR-065 п. 2.2).
2. **`body` — непрозрачный JSON-текст.** SDK схемы тела не вводит и содержимое
   не интерпретирует (ADR-062 п. 5). Разбирается ровно для вложения в дерево;
   незначащее форматирование при этом нормализуется, **значения — нет**: числа
   переносятся литералом, порядок ключей сохраняется.
3. **Негодный `body` — `IllegalArgumentException` до обращения к ABI.** Это
   нарушение предусловия вызова, того же рода, что обращение к закрытому
   клиенту (§9.3). Собственного типа исключения SDK не заводит.
4. **`atEnd` обязателен во всех трёх подтипах и умолчания не имеет.** «Сервер
   вернул меньше запрошенного» знает только тот, кто знал запрошенное;
   умолчание `false` молча превратило бы забытый параметр в утверждение.
5. **Порядок записей SDK не вычисляет и не перестраивает.**

### 11.3. Направление и якорь: противоречие невыразимо

Направление берётся **из типа блока**, отдельного поля не существует, и якорь
есть только у тех подтипов, где он обязателен. Пара «`Newest` + якорь» не
собирается, поэтому `ErrAnchorNotAllowed` через SDK недостижим.

Форма та же, что у конфигурации (§6): взаимоисключающие пути вместо одной
перегрузки с правилами приоритета.

**Это construction safety, а не валидация.** Фиксируется прямо, потому что
именно здесь легко ошибиться:

- **SDK не становится нормативным источником инвариантов.** Они живут в
  `services/localfeed` (ADR-065 п. 3);
- **Core остаётся единственным арбитром**, и его проверки не ослабляются
  оттого, что часть случаев стала невыразимой в Kotlin: до ядра доходят байты,
  а не типы;
- **malformed payload с провода ядро обязано отвергать** независимо от SDK —
  вызывающий на другом языке или другой версии ничем не ограничен;
- дублируется **один** инвариант и только формой «невыразимо», а не второй
  проверкой.

### 11.4. Результаты

У каждого действия — sealed-иерархия со ссылкой на исходный `PhotonResponse`.
Приём тот же, что у `PhotonEvent` и `PhotonResponse`: типизированная модель с
открытым дном.

**Второй таксономии конверта не заводится.** `ok:false` и неразобранный конверт
остаются различимы через `response`, потому что различает их уже
`PhotonResponse`; копировать сюда `Rejected`/`Unrecognized` значило бы завести
второе место, где описан один и тот же конверт.

```kotlin
FeedPutResult    : Stored(stored) | Unavailable
FeedIngestResult : Applied(семь полей) | Unavailable
FeedGapAnchor    : Found(anchor) | None | Unavailable
```

**Семь полей `Applied`** — `stored`, `segments`, `updated`, `unchanged`,
`stale`, `vanished`, `gapsClosed`. Отдаются **все**: отбор означал бы решение
за приложение, какие из уже посчитанных ядром чисел ему нужны.

Нормативно:

1. **`gapsClosed` — ЗНАКОВОЕ число.** Отрицательное значение законно и означает
   появление **нового** пропуска; приводить его к нулю запрещено. Прежний
   комментарий ядра утверждал, что отрицательным оно не бывает, и был
   опровергнут первым же живым прогоном.
2. **`vanished` — только сигнал.** Семантики удаления API не создаёт: ни
   метода, ни флага, ни имени, подразумевающего действие. ADR-054 и ADR-060
   (вариант A) не переоткрываются — автоматического удаления не происходит
   никогда.
3. **`stale` ошибкой не является** — это защита от переупорядоченной доставки
   (ADR-053).
4. **Отсутствие любого из семи полей даёт `Unavailable`, а не ноль.**
   Подставленный ноль неотличим от настоящего, и «поле не пришло» превратилось
   бы в «ничего не изменилось».
5. **`found:false` — это `None`, а не ошибка и не нулевая позиция.** Нулевая
   предложила бы закрывать пропуск от начала ленты.
6. **`GapAnchor` — производная от сегментов**, вычисляемая ядром при каждом
   вызове. Своего состояния SDK не заводит: persisted watermark не появляется,
   второго источника истины нет (ADR-066 §7).

### 11.5. Ошибки: канал не меняется

Отказ вызова приходит `PhotonException` — так же, как у `sendAction` (§9.2).

1. **Нового кода ошибки ABI нет.** Все семь инвариантов ядра приходят одним
   `PHOTON_ERR_INVALID_ARGUMENT`.
2. **Типизированных подклассов под причины `localfeed` не заводится.**
3. **`PhotonException.nativeMessage` структурированным контрактом ошибки НЕ
   является.** Текст туда доходит — это `Photon_GetLastError`, снятый в момент
   броска (ADR-063 п. 4), — но разбирать его для классификации нельзя
   (ADR-033). Публично остаются общий код и текст.
4. **Причины отдельных инвариантов не становятся стабильной типологией SDK.**

### 11.6. Цикл догрузки остаётся у вызывающего

**Catch-up живёт в приложении, не в SDK** (ADR-066 §9). SDK даёт примитивы;
последовательность запросов, повторение, сходимость и получение данных
транспортом — забота вызывающего.

Основания: полный цикл зависит от доменного отображения ответа Bridge, а
generic SDK не знает ни `Post`, ни ENGRAM; слоя синхронизации, планировщика и
сервисов в SDK нет, и цикл потребовал бы нового верхнеуровневого типа.

**В SDK не вводятся и этим разделом не предполагаются:** SyncEngine,
планировщик, repository-абстракция, оркестрация корутин, клиент Bridge.

Две защиты цикла переезжают вместе с ним и обязаны быть у вызывающего: предел
числа итераций и признак сходимости — «якорь либо продвинулся, либо пропуск
закрыт» (урок ADR-047: цикл без предела превращает дефект в зависание).

### 11.7. Граница ответственности

> **Core гарантирует внутреннюю согласованность принятого утверждения, но не
> истинность утверждения Caller о полноте серверного диапазона.**

> **SDK не превращает это утверждение в гарантию полноты.** Типизированный
> конструктор блока делает противоречивую комбинацию невыразимой — и только;
> «собралось в Kotlin» не означает «диапазон полон».

> **Вызывающий отвечает за истинность своей серверной выборки и за `atEnd`.**

### 11.8. Что обязаны проверять тесты (продолжение §10)

| Утверждение | Как ломается |
|---|---|
| каждый примитив уходит своим кодом действия | перепутать 801/802/803 |
| номера совпадают с `photon.proto` | изменить код в SDK, не сверившись с каталогом |
| `Long` переживает значение выше 2^53 при сборке и при разборе | подставить число с плавающей точкой |
| `gapsClosed` остаётся отрицательным | «нормализовать» в ноль |
| отсутствие любого из семи полей даёт `Unavailable` | подставить ноль вместо отсутствия |
| `found:false` даёт `None` | вернуть `Unavailable` или нулевую позицию |
| у `Newest` нет якоря ни как поля, ни в payload | добавить nullable-якорь |
| 800 не типизирован | завести `localFeedPage` |
| `sendAction` не устарел | пометить `@Deprecated` |

Проверено мутациями: **8 запущено, 8 убито** (2026-09-20).
