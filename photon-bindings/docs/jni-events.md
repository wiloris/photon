# JNI Event Bridge — спецификация

Контракт моста событий между `Photon_SetEventCallback` (C ABI v1.0) и
слушателем на стороне JVM.

**Написана до кода.** Реализации нет: `photon_jni.c`, `PhotonNative.java` и
`Photon.kt` сегодня не содержат ни одного упоминания `SetEventCallback` —
проверено машинно, ноль вхождений в трёх файлах. Мост линкует ровно семь
C-символов, и события среди них нет.

**C ABI этой спецификацией не меняется.** `Photon_SetEventCallback` в
заголовке существует с Phase 15.5; мост его не использует — это пробел
биндингов, а не пробел ABI. Новых экспортируемых символов не появляется
(`ROADMAP.md`, Phase 16, «Public API constraint»).

**Зачем сейчас.** На событиях стоят Dashboard и Logging первого настоящего
клиента: состояние подписного соединения снаружи наблюдаемо **только** через
`CONNECTED` / `NETWORK_CHANGED`. Без моста эти разделы Phase 16 стоят на
слое, которого нет.

## 1. Что уже гарантирует C ABI — и что здесь не решается

Всё перечисленное **заморожено** и мостом не переопределяется. Мост обязан
эти свойства сохранить, а не переизобрести.

| гарантия | источник |
|---|---|
| Первый ненулевой `Photon_SetEventCallback` **запускает подписку**; повторный вызов заменяет адресата; `NULL` отцепляет адресата, подписку не останавливая | `photon_core.h`, «Единый Event Callback» |
| Все события идут **одним каналом**; тип различается полем `"type"` в `event_json`. Сегодня эмитируются `CONNECTED`, `MESSAGE`, `NETWORK_CHANGED`; `PLUGIN_EVENT` и `STORAGE_CHANGED` зарезервированы, источников нет | там же; ADR-045 |
| **Порядок сохраняется**, и **колбэки никогда не параллельны**: насос вызывает колбэк сам, второе событие не начинает доставляться, пока не вернулось первое | `event-delivery.md` §9.1 |
| Колбэк **не вызывается под мьютексом ядра**: `c.mu` отпускается до вызова, `d.mu` в этот момент не удерживается | §9.1, строки про порядок захвата |
| `event_json` **принадлежит вызову** и невалиден сразу после возврата из колбэка | `photon_core.h` |
| `user_data` обязан оставаться валидным **до возврата из `Photon_Destroy`** | там же |
| После возврата `Photon_Destroy` колбэк **гарантированно больше не будет вызван** — ни разу, ни из какого потока; `Destroy` дожидается уже начатых вызовов | `photon_core.h`, гарантия для Event Callback |
| `Photon_Destroy`, вызванный **из потока исполняющегося колбэка того же инстанса**, помечает отложенное уничтожение и возвращается немедленно — явное исключение, иначе дедлок | `event-delivery.md` §10.2 |
| Поток событий **может иметь пропуски** при устойчивом отставании клиента: сервер роняет события при переполнении своего буфера (измерено: 165). Сквозной доставки нет | `photon_core.h`; §9.3 |
| Колбэк, который не возвращается, **останавливает поток событий своего инстанса и задерживает `Destroy`** | §9.4 |

**Мост не имеет права ослабить ни одно из них.** В частности, он не имеет
права превратить «пропуски возможны» в «доставка гарантирована», добавив
собственную очередь с повторами.

## 2. Что добавляет слой JNI

Ровно четыре вещи, и ни одной сверх:

1. **присоединение потока к JVM** — колбэк приходит из горутины Go, у которой
   нет `JNIEnv`;
2. **владение ссылкой на слушателя** — `GlobalRef` и момент его освобождения;
3. **перевод `const char*` в `String`** — с учётом того, что `event_json`
   невалиден после возврата;
4. **политика исключения**, вылетевшего из JVM-слушателя: в Go его пробросить
   нельзя.

Всё остальное — свойства ядра, проходящие сквозь мост без изменений.

## 3. Жизненный цикл

### 3.1 Установка

```
Kotlin: photon.setEventListener(listener)
   → PhotonNative.setEventListener(handle, listener)      // Java native
      → photon_jni.c: NewGlobalRef(listener)              // владение начинается
        Photon_SetEventCallback(h, &bridge_cb, ctx)       // ctx — наш контекст
```

`ctx` — структура моста, а не сам `GlobalRef`: в ней хранятся `JavaVM*`,
`GlobalRef` слушателя и `jmethodID` метода доставки. `JavaVM*` берётся один
раз, `GetJavaVM` из потока установки; `jmethodID` вычисляется там же и
кэшируется — искать метод на каждом событии значит выполнять поиск по
классу в горячем пути.

### 3.2 Замена и отцепление

`setEventListener(newListener)` обязан: создать новый `GlobalRef`, атомарно
подменить его в `ctx`, освободить **старый**. `setEventListener(null)` —
`Photon_SetEventCallback(h, NULL, NULL)`, затем освобождение `GlobalRef`.

**Опасность, ради которой это выписано отдельно:** освободить старый
`GlobalRef` раньше, чем гарантировано, что доставка с ним не идёт прямо
сейчас, — это use-after-free на стороне JVM. По принятому D1 доставка
синхронна и не параллельна, поэтому безопасный момент существует и достижим
без очередей; конкретная дисциплина (атомарная подмена и освобождение вне
идущей доставки) — предмет реализации, а не нового решения.

### 3.3 Уничтожение

```
Photon_Destroy(h)
   → ядро дожидается начатых вызовов колбэка (гарантия C ABI)
   → возврат
   → только теперь мост освобождает GlobalRef и ctx
```

Порядок обязателен и не подлежит оптимизации: `GlobalRef`, освобождённый до
возврата `Destroy`, может быть использован уже начатым колбэком.

## 4. Поток, `AttachCurrentThread` и `DetachCurrentThread`

Заголовок C ABI прямо предупреждает: колбэк **может быть вызван из горутины,
не связанной с потоком, в котором инициализирован JNI env**, и требует
`AttachCurrentThread` перед обращением к JNI и `DetachCurrentThread` по
завершении, если поток не был присоединён ранее.

Отсюда нормативные правила моста:

1. **Никогда не кэшировать `JNIEnv*`** между вызовами. Кэшируется только
   `JavaVM*`; `JNIEnv*` получается на каждый вызов через `GetEnv`, и лишь
   при `JNI_EDETACHED` выполняется присоединение.
2. **Присоединять только если поток не присоединён**, и отсоединять **только
   если присоединили мы**. Отсоединить чужой поток — сломать вызывающего.
3. **Никогда не вызывать `DetachCurrentThread` для потока, который присоединил
   не мост.**

Режим присоединения решён (**D2**, §8): `AttachCurrentThread` при
`JNI_EDETACHED` перед вызовом и `DetachCurrentThread` после — **только если
присоединил этот же вызов**. `AttachCurrentThreadAsDaemon` не используется,
постоянное присоединение потока доставки не используется.

## 5. Владение `GlobalRef`

| момент | действие |
|---|---|
| установка слушателя | `NewGlobalRef` — владение переходит к мосту |
| замена слушателя | новый `NewGlobalRef`, атомарная подмена, `DeleteGlobalRef` старого — **не раньше** момента, определяемого D1 |
| отцепление (`null`) | `Photon_SetEventCallback(NULL)`, затем `DeleteGlobalRef` |
| `Photon_Destroy` | `DeleteGlobalRef` **строго после** возврата из `Destroy` |
| поток доставки | `LocalRef` на строку события освобождается **до** возврата из колбэка |

Локальные ссылки, созданные внутри колбэка (`NewStringUTF` как минимум),
обязаны освобождаться явно: поток может быть присоединён надолго, и в этом
случае автоматическая очистка локального фрейма не наступит до отсоединения.

### 5.1 Накопление контекстов при замене — измеренное свойство, а не догадка

Замена слушателя **не освобождает прежний контекст немедленно**, и это
вынужденно: `Photon_SetEventCallback` не даёт дождаться уже НАЧАВШЕЙСЯ
доставки со старым `user_data`, а другого момента синхронизации ABI не
предоставляет. Освобождение сразу после подмены было бы гонкой, то есть
use-after-free на стороне JVM.

Следствие, измеренное тестом: **N замен за жизнь инстанса удерживают N
контекстов и N `GlobalRef`** до `close()`. Проверено на 200 заменах — до
`close()` живы все 200, после — ни одного. Рост ограничен числом замен, а не
числом событий, и полностью снимается уничтожением инстанса.

Оставшийся риск честнее назвать, чем спрятать: интерфейс, меняющий слушателя
часто (например, на каждом переходе экрана), накапливает `GlobalRef` в
пределах жизни инстанса. У JVM таблица глобальных ссылок не бесконечна.

**Безопасный момент раннего освобождения существует и выводится из
контракта**, но не реализован: доставки строго последовательны и никогда не
параллельны (§9.1), поэтому как только НОВЫЙ слушатель получил хотя бы одно
событие, всякая доставка со старым контекстом уже завершилась. Механизм,
использующий это наблюдение, — отдельное решение, а не деталь реализации:
он требует перехвата первого события в обёртке. **Здесь он не принимается.**

## 6. Последовательная доставка и запрет вызова под мьютексом

Ядро уже гарантирует, что колбэки не параллельны и вызываются вне `c.mu` и
`d.mu` (§9.1). **Мост обязан не испортить это в обе стороны:**

- **не добавлять собственный мьютекс, удерживаемый во время вызова JVM.**
  Если мост берёт свой замок для чтения `ctx`, он обязан отпустить его до
  `CallVoidMethod`. Иначе рядовое «получил `MESSAGE` → отправил действие»
  из слушателя упрётся в замок моста — тот же дефект, что §9.1 разбирает
  для `c.mu`, только этажом выше;
- **не превращать последовательность в параллельность.** По принятому D1
  доставка идёт синхронно на потоке доставки, поэтому гарантия переходит как
  есть; любой будущий отход от этого (исполнитель, очередь) ломает и её, и
  опознание реентерабельного `Destroy` по идентификатору потока.

**Реентерабельность обязана работать.** Слушатель имеет право из тела
колбэка вызвать `sendAction`, `lastError`, `setEventListener` и `close` того
же инстанса. Для `close` действует §10.2 — отложенное уничтожение с
немедленным возвратом.

## 7. Исключение внутри JVM-слушателя

Исключение из `CallVoidMethod` **нельзя пробросить в Go**: вызывающий —
C-функция, вызванная из горутины. Оставить его невычищенным тоже нельзя:
следующий JNI-вызов в этом потоке упадёт с «pending exception».

Нормативно: мост **обязан** после каждого вызова слушателя проверить
`ExceptionCheck` и очистить состояние (`ExceptionDescribe` + `ExceptionClear`
либо только `ExceptionClear`), после чего **вернуться нормально** — поток
событий обязан продолжиться.

Судьба самого факта исключения решена (**D4**, §8): исключение фиксируется в
логе, состояние очищается, доставка продолжается, слушатель **не
отцепляется**. Молча проглотить и не оставить следа нельзя — сбойный
слушатель выглядел бы как работающий.

## 8. Архитектурные решения

D1, D2 и D4 закрыты реализацией моста; D6 закрыт ADR-051.
**D3 и D5 остаются открытыми.**

### D1. Модель потока доставки — ПРИНЯТО: синхронно

**Синхронная доставка непосредственно на потоке доставки C ABI.** Никакого
исполнителя JVM и никакой очереди в мосте. Переход на другой поток — включая
UI-поток Compose — ответственность **верхнего слоя**, а не моста.

Следствия, которые теперь нормативны:

- порядок и «колбэки никогда не параллельны» переходят из ядра как есть,
  без новых механизмов;
- backpressure сохраняется: медленный слушатель тормозит поток событий и
  задерживает `Destroy` — это уже свойство C ABI (§9.4), а не новое
  требование;
- «после возврата `Destroy` колбэков не будет» остаётся верным без
  дополнительной синхронизации, потому что между ядром и слушателем нет
  ничего, что могло бы пережить `Destroy`.

Решение подтверждается фактом из §8.1: реентерабельный `Photon_Destroy`
опознаётся сравнением **идентификаторов OS-потока**. Исполнитель JVM увёл бы
колбэк на другой поток и сломал бы это опознание — вариант с очередью был
несовместим с уже замороженным поведением, а не просто дороже.

### D2. Режим присоединения потока — ПРИНЯТО: attach/detach на каждое событие

#### Что установлено чтением кода

| вопрос | ответ | источник |
|---|---|---|
| откуда приходит событие | **единственная горутина доставки на инстанс** — `Dispatcher.pump`; `sink` вызывается только из неё | `services/dispatcher/pump.go` |
| применяется ли `LockOSThread` | **да**, первой строкой горутины насоса, с `defer runtime.UnlockOSThread()` | `pump.go:67-68` |
| зачем | «поток доставки обязан быть стабильным: потребитель за границей ABI определяет реентерабельный `Photon_Destroy` сравнением идентификаторов OS-потока, а между двумя вызовами cgo горутину может перенести на другой поток» | комментарий там же; `event-delivery.md` §10.3 |
| может ли один OS-поток доставить несколько событий подряд | **да, всегда**: все события одного инстанса доставляются с одного и того же потока | следствие `LockOSThread` |
| может ли доставка мигрировать между потоками | **нет** в пределах жизни насоса. Насос запускается **один раз** (`pumpStarted`), переподключения происходят **внутри** его цикла, а не перезапуском горутины | `pump.go`, `StartEvents` |
| сколько таких потоков в процессе | **по одному на инстанс**: N хэндлов — N разных залоченных потоков | там же |
| виден ли мосту конец потока доставки | **нет**. `onStop` (`finishDeferredTeardown`) исполняется той же горутиной до `UnlockOSThread`, но это внутренняя точка `photon-bindings/c`; **C ABI не имеет сигнала «поток доставки завершился»** | `photon.go:360`, `pump.go:70-75` |

#### Что из этого следует нормативно

1. **Присоединять можно один раз на поток доставки** — поток стабилен, это
   доказано, а не предположено;
2. **`JNIEnv*` всё равно нельзя кэшировать между вызовами**: стабильность
   потока не делает `JNIEnv*` переносимым, и правило §4 остаётся в силе;
3. **Отсоединиться в момент завершения потока мост не может** — сигнала нет.
   Это не пробел реализации, а свойство нынешнего ABI;
4. **Поток не умирает вместе с насосом.** `UnlockOSThread` вызывается через
   `defer`, поэтому OS-поток **возвращается в пул** Go, а не завершается.
   Присоединённый к JVM и не отсоединённый поток остаётся присоединённым,
   будучи переиспользованным Go под произвольные горутины.

#### Решение — ПРИНЯТО: B1, присоединение и отсоединение на каждое событие

Нормативно:

- перед вызовом слушателя текущий поток доставки присоединяется к JVM через
  **`AttachCurrentThread`**, если он ещё не присоединён (проверяется `GetEnv`,
  присоединение выполняется только при `JNI_EDETACHED`);
- после возврата из слушателя выполняется **`DetachCurrentThread` — только
  если присоединение выполнил именно этот вызов**. Поток, присоединённый не
  мостом, не отсоединяется никогда;
- **`JNIEnv*` не кэшируется** между вызовами; кэшируется только `JavaVM*`;
- **`AttachCurrentThreadAsDaemon` для этого механизма не используется**;
- **постоянное присоединение потока доставки не используется**;
- **мост не создаёт ни исполнителя, ни собственного потока доставки**;
- **порядок, синхронность и поток доставки остаются ровно теми, которые
  гарантирует C ABI** — мост их не переопределяет ни в одну сторону.

Обоснование. Поток доставки принадлежит **пулу Go**: `UnlockOSThread`
вызывается через `defer`, поэтому после завершения насоса поток не умирает, а
возвращается в пул и может быть переиспользован под произвольные горутины.
Постоянное присоединение к JVM нарушило бы корректный жизненный цикл при
повторных create/destroy и накапливало бы присоединённые потоки — по одному на
каждый когда-либо созданный инстанс. B1 такого жизненного цикла не заводит и
корректна для уже существующей модели.

### D3. Модель слушателя

Один слушатель на инстанс (замена вытесняет прежнего — так устроен C ABI) или
список подписчиков на стороне Kotlin, мультиплексируемый одним C-колбэком.
Второе удобнее для Dashboard, где на события смотрят несколько панелей, но
вводит в биндинги диспетчеризацию, которой в ABI нет.

### D4. Судьба исключения слушателя — ПРИНЯТО

Исключение **фиксируется/логируется**, pending exception **очищается**,
доставка **продолжается**. Сбойный слушатель **не отцепляется
автоматически** — это отдельное решение, и семантика сверх C ABI сейчас не
добавляется.

### D5. Форма события на стороне Kotlin

Сырая `String` с JSON (буквально то, что даёт ABI) против разобранного
sealed-класса. Второе удобно, но вносит в биндинги знание о доменных типах,
которое ядро намеренно не имеет: `data` проходит сырыми байтами (§8.1
event-delivery, ADR-025/034).

### D6. Где живёт мост — ЗАКРЫТО ADR-051

`photon-bindings/android` оказался не Android-специфичным: он собрался
обычным `cc`, а `Photon.kt` уже несёт `System.load` «для desktop-JVM».
Вопрос решён **ADR-051**, а не этой спецификацией: каталог переименован в
`photon-bindings/jvm/` как **общий JVM-мост**, дублирующий
`photon-bindings/desktop/` не создаётся. Платформенные различия (хранение
приватного ключа средствами ОС — ADR-021) получат свой подкаталог тогда,
когда для них появится код.

**D3 и D5 остаются открытыми** — к размещению моста они отношения не имеют.

## 9. Правила безопасности

### 9.1 Use-after-free

- `event_json` не сохраняется: строка JVM создаётся **внутри** вызова, до
  возврата в ядро;
- `ctx` живёт до возврата из `Photon_Destroy` — это прямое требование к
  `user_data` в C ABI;
- `GlobalRef` освобождается **после** `Destroy`, а при замене слушателя —
  не раньше момента, гарантирующего отсутствие идущей доставки (D1).

### 9.2 Callback after destroy

Запрещён контрактом C ABI. Мост **не добавляет** собственной защиты в виде
флага «уничтожен» — вместо этого обязан не создавать путей, обходящих
гарантию: не ставить доставку в отложенную очередь, которая переживёт
`Destroy` (это прямое следствие выбора D1).

### 9.3 Конкуренция

- `setEventListener` может быть вызван из любого потока и **одновременно с
  идущей доставкой**: подмена ссылки обязана быть атомарной;
- `close`/`Destroy` может быть вызван из любого потока, в том числе из потока
  доставки (§10.2);
- две операции над одним инстансом из разных потоков — нормальный режим:
  существующие тесты уже гоняют 8 потоков × 500 циклов create/send/destroy.

## 10. Требования к тестам

Контракт считается подтверждённым, только если тесты **падают** при его
нарушении. Ниже — что обязано быть проверено; мутации для каждого пункта
подбираются при реализации.

**Функциональные:**

1. установка слушателя запускает подписку — событие `CONNECTED` доходит до
   Kotlin;
2. `event_json` доезжает как валидная строка с полем `type`;
3. замена слушателя: события идут новому, старый больше не вызывается;
4. `null` отцепляет слушателя, подписку не останавливая.

**Отказные (обязательны — именно они находили дефекты в Phase 9–11):**

5. **исключение из слушателя** не роняет процесс, не оставляет pending
   exception и **не останавливает поток событий**: следующее событие приходит;
6. **`close()` из тела слушателя** — возврат немедленный, дедлока нет
   (§10.2);
7. **после `close()` слушатель не вызывается ни разу** — ни из какого потока;
8. **медленный слушатель**: доставка следующего события не начинается, пока
   не вернулся предыдущий (проверка «не параллельны»);
9. **`setEventListener` из другого потока во время доставки** — нет гонки на
   `GlobalRef`;
10. **порядок**: N событий подряд приходят в порядке отправки.

**Структурные:**

11. `nm -D libphoton_jni.so` — среди неопределённых символов только
    `Photon_*`, ни одного `go.`/`runtime.`/`_cgo` (правило уже действует и
    проверено на десктопе);
12. добавление `Photon_SetEventCallback` **не меняет** `photon_core.h`:
    `PHOTON_ABI_MAJOR`/`MINOR` остаются `1`/`0`.

**Средой:** тесты идут на десктопной JVM (JDK 21 Temurin, Kotlin 2.4.20).
Ложное «пропущено» здесь опаснее падения: слой годами не запускался именно
потому, что тесты нечем было выполнить.

## 11. Что эта спецификация НЕ определяет

- расширение C ABI — новых символов не появляется;
- разбор `data` события: домен принадлежит ENGRAM/Bridge;
- очередь, повторы и гарантию сквозной доставки: их нет в ядре, и мост не
  имеет права создавать их видимость;
- структуру каталогов `photon-bindings` (D6);
- UI: переход на поток Compose — следствие D1, а не отдельный механизм.
