# ROADMAP.md

## Официальный roadmap Photon + ENGRAM

Как пользоваться этим документом: перед началом любой работы открой текущую фазу, найди первый невыполненный пункт, реализуй его, отметь `[x]`, переходи к следующему. Не начинай следующую фазу, пока не закрыта текущая, если явно не указано иное.

Статус фазы: 🔲 не начата · 🟡 в процессе · ✅ завершена

**Правило завершённости.** Фаза считается завершённой только тогда, когда одновременно выполнено три условия:

- ✔ реализована
- ✔ покрыта тестами
- ✔ документирована

Отметка ✅ не ставится по факту "код написан и вроде работает". Пока не выполнены все три пункта — статус фазы 🟡, а не ✅. Это правило дисциплинирует разработку и не даёт roadmap врать о реальном состоянии проекта.

## Legacy / Existing Components

Часть работы была выполнена ещё до формализации этого roadmap. Чтобы документ отражал реальное состояние проекта, а не выдавал уже сделанное за будущую задачу, такие компоненты фиксируются здесь отдельно, а не как "невыполненная" фаза.

- **Protobuf Protocol** (`photon.proto`, `photon.pb.go`) — базовая схема протокола уже существует. При переходе к Phase 12 задача — не создать эти файлы с нуля, а свести их к финальному списку сущностей (`User`, `Message`, `Channel`, `File`, `Plugin`, `Event`, `Identity`), актуализировать и покрыть тестами/документацией по правилу завершённости выше.

### Phase 2 — Storage ✅

**Правило реализации (защита ADR-020 от размывания на практике).** Желание изменить `ports/` во время работы над `adapters/bbolt` сначала считается ошибкой реализации, а не ошибкой интерфейса. Фильтр перед любой правкой порта:

1. Можно реализовать внутри адаптера без изменения контракта? → Да: меняется адаптер, не порт.
2. Если нет — это ограничение конкретно bbolt или подтверждённая потребность ядра? → Только bbolt: адаптер адаптируется (даже ценой более сложного кода внутри `adapters/bbolt`). Подтверждённая потребность ядра: кандидат на новый ADR.
3. Только после проверки первых двух пунктов — рассматривается изменение `ports/`, через обычный процесс ADR (ADR-020).

Рабочий журнал по ходу реализации — не ADR, обычный список (см. `adapters/bbolt/IMPLEMENTATION_LOG.md`): что потребовалось и решено внутри адаптера, что потребовалось и решено без изменения порта, что осталось кандидатом на архитектурное обсуждение. **Результат: список кандидатов пуст** — ни один случай (включая находки из внешнего ревью: копирование в `ForEach`/`ForEachPrefix`, проверка дыр в версиях миграций) не потребовал рассмотрения правки `ports/storage.go`. Сильное свидетельство того, что ADR-010/011/013 сработали как задумано.

- [x] `adapters/bbolt` — базовая реализация (`Storage`, `readTx`/`writeTx`, namespace→bucket маппинг)
- [x] Транзакции (`View`/`Update`, откат при ошибке — покрыто тестом)
- [x] Миграции схемы (версионирование через `_meta` bucket, идемпотентность, порядок применения, обязательная последовательность версий без дыр/дублей — покрыты тестами)
- [x] Тесты адаптера — 18 тестов: round-trip, `ErrNotFound`/`ErrNamespaceNotFound`, запрет неявного создания namespace, откат транзакции, идемпотентность и порядок миграций, поведение после `Close`, копирование данных в `Get`/`ForEach`/`ForEachPrefix` за пределами транзакции, дыры/дубликаты в версиях миграций, отмена контекста для `View`/`Update`

**Кэш поверх хранилища — намеренно вне критерия закрытия этой фазы.** Не реализован: нет подтверждённой потребности (ADR-013), нет профилирования, показывающего необходимость. Это не часть контракта `ports.Storage` (кэш — decorator/wrapper поверх порта, а не метод самого порта), поэтому его отсутствие не блокирует "реализовано + тесты + документировано" для Phase 2. Остаётся кандидатом на будущее — если/когда появится измеренная потребность, реализуется отдельно, не задним числом меняя эту фазу.

Compile-time проверка соответствия интерфейсу (пункт из Phase 1) выполнена здесь: `var _ ports.Storage = (*Storage)(nil)`, аналогично для `readTx`/`writeTx` — см. `adapters/bbolt/storage.go`, `tx.go`.

### Phase 3.5 — Account & Device Management ✅

Модель доверия (Trust Model) уже зафиксирована архитектурным решением — см. ADR-021, ARCHITECTURE.md раздел 9.1. Эта фаза — не о самой модели, а о сервисах вокруг неё: интеграция с внешним IdP, реестр устройств, отзыв, API и UI управления. Не переименовывать в "Google OAuth" — Google сегодня один из возможных Identity Provider, не постоянная часть архитектуры.

**Подготовка (сделана до начала кода сервиса, по принципу "сначала документ, потом код" для бизнес-логики):**

- [x] `docs/account-device-flow.md` — пять сценариев (первый вход, обычное подключение, новое устройство, отзыв, переустановка) с диаграммами
- [x] `ports/identityprovider.go` — девятый порт, `VerifyIDToken`, `ExternalIdentity{Provider, Subject, Email}` (ADR-022→ADR-023)
- [x] `docs/account-storage-model.md` — модель данных и Storage-схема до начала кода сервиса (ADR-024)

**Реализация:**

- [x] `adapters/googleoidc` — реализация `IdentityProvider` для Google: JWT/JWKS-верификация, только стандартная библиотека (без внешних зависимостей — тот же принцип, что `adapters/ed25519`)
- [x] Account Service (`services/account`, поверх `Storage`+`Identity`+`IdentityProvider`, без нового порта под сам сервис — см. ADR-017/018) — `LoginOrRegister`, `PhotonID` присваивается при создании (ADR-024: точка реализации ADR-018 наступила)

- [x] Регистрация устройства (`RegisterDevice`, привязка нового `PublicKey` к аккаунту)
- [x] Отзыв устройства (`RevokeDevice` — атомарно из обоих namespace, покрыто тестом на согласованность)
- [x] Device List API (`ListDevices`, покрыто тестом на отсутствие утечки между аккаунтами)
- [x] Transport Authentication (`AuthenticateDevice` — challenge-response через `Identity.Verify`, обновление `LastSeen`); проверяется подпись под **доменным представлением** `"photon-device-auth:" ‖ challenge`, не под сырым challenge — ADR-037, реализовано отдельной правкой `1c5e679`
- [ ] Device Management UI (Developer Tools и/или ENGRAM) — **намеренно вне критерия закрытия этой фазы.** Не потому что не нужен, а потому что структурно не может быть построен раньше своего хоста: и Developer Tools (Phase 16), и ENGRAM (Phase 18) сами ещё не существуют. Это не решение "низкий приоритет", а зависимость по порядку фаз — UI появится, когда появится хотя бы один из двух возможных хостов, тогда и будет реализован поверх уже готового и протестированного `services/account` (`ListDevices`/`RevokeDevice` уже дают всё нужное API). Остаётся открытым пунктом в этой фазе как напоминание, не как блокер.
- [x] Тесты `services/account` — **21 тест** на mock `IdentityProvider` + реальных `adapters/bbolt`/`adapters/ed25519` (18 исходных плюс 3 на ADR-037: подпись под сырым challenge отвергается, подпись в домене `plugin-sign` не аутентифицирует устройство, доменный литерал закреплён побайтово); `IMPLEMENTATION_LOG.md`: кандидатов на архитектурное обсуждение нет
- [x] Тесты `adapters/googleoidc` — 13 тестов (валидный токен, обе формы issuer, неверная подпись, просрочен, неверный issuer/audience, отсутствующий subject, некорректный формат, неизвестный kid, alg=none отклонён, отмена контекста, недоступность JWKS не путается с невалидным токеном), compile-time проверка `var _ ports.IdentityProvider = (*Adapter)(nil)`; `IMPLEMENTATION_LOG.md`: кандидатов на архитектурное обсуждение нет

### Phase 5 — Bindings 🟡

- [x] `photon_core.h` — черновик официального ABI-контракта готов (см. `photon-bindings/c/photon_core.h`)
- [x] **Блокер перед заморозкой закрыт (ADR-025):** action-коды и wire-структуры перенесены из `photon-quic-bridge/server/protocol.go` в `photon-core/protobuf/` (`enum Action`, 40 кодов); Bridge теперь импортирует канонические определения через алиасы (`const ActionCreatePost = int(photonpb.Action_ACTION_CREATE_POST)`), не объявляет их заново. **Ограничение на момент записи (Phase 5, ADR-025), снято позже — см. ниже:** полная сборка всего `photon-quic-bridge` тогда не проверялась, и причина была названа неверно («Mattermost SDK недоступен без обычного Go module proxy»); проверено было то, что можно: `photon-core` целиком (build+test+vet+gofmt чистые), паттерн миграции — в изолированном мини-проекте, `protocol.go`/`plugin.go` — синтаксис и форматирование. **Текущий статус: сборка Bridge проверена и воспроизводится здесь.** `GOTOOLCHAIN=auto` (значение по умолчанию) подставляет **go1.24.7** по директиве `toolchain` из `go.mod` Bridge — то есть Go 1.22 в `PATH` препятствием не был, и настоящей причиной была версия Go, а не прокси. `go build ./server/...`, `go vet ./server/...`, `go test ./server/...` проходят; впервые это зафиксировал **ADR-035** при переносе ADR-025, повторно подтверждено аудитом после Phase 13.5. Перенос влит в `main` Bridge.
- [x] `photon_core.h` — ревью и заморозка v1 завершены (ADR-026: 7 пунктов аудита — минимальность поверхности, ownership `payload_json`/`config_json`, callback lifetime, MAJOR.MINOR versioning, `PHOTON_ERR_INVALID_ACTION`, protobuf-граница подтверждена, JSON vs protobuf bytes решено в пользу JSON). **С этого момента действует ABI Freeze Policy (ARCHITECTURE.md, раздел 7.5.1)** — любое изменение сигнатуры требует отдельного ADR, а не обычного коммита.
- [x] `bindings/c` — реализация `photon_core.h` поверх ядра (cgo/c-shared): все 12 функций ABI, `-buildmode=c-shared` собирается, 12 символов `Photon_*` экспортированы. Opaque handles через `cgo.Handle`, хранимый в реальной C-памяти (не приведение Handle к `unsafe.Pointer` — прямо запрещено документацией `runtime/cgo`)
- [x] `bindings/jvm` — JVM/JNI мост реализован: `PhotonNative.java` (7 native-методов), `photon_jni.c` (компилируется `-Wall -Wextra` чисто против настоящего `jni.h` JDK 21, линкуется с реальной `libphoton_core.so`), Kotlin-обёртка `Photon.kt` (`Closeable`, исключения, проверка ABI MAJOR). Сигнатуры сгенерированы `javac -h`, коды `PhotonResult` сверены Java↔C 10 compile-time assert'ами. Граница ABI подтверждена машинно (`nm -D`: 0 обращений к Go-символам). **E2E на JVM: Java 32/32 PASS, Kotlin 14/14 PASS**, включая ownership (destroy ×3, destroy(0), create→destroy→create, вызовы на уничтоженном handle) и конкурентность (8 потоков × 500 и × 200 циклов)
- [ ] `bindings/jvm` — **Android-специфика не проверена:** native build под ARM (`arm64-v8a`/`armeabi-v7a`), поведение на ART, реальное устройство/эмулятор, Gradle/CMake интеграция. Причина: Android NDK/SDK недоступны в среде разработки (`dl.google.com` заблокирован). JVM-тесты подтверждают JNI-контракт и логику моста, но **не** ART-специфику — см. `photon-bindings/android/README.md`

### Phase 6 — Transport Engine ✅

**Главный результат фазы — не количество тестов, а то, что `ports.Transport` не изменился ни на строку.**

```
                 ports.Transport  (заморожен, ADR-020)
                        │
            ┌───────────┴───────────┐
            ▼                       ▼
      adapters/quic           adapters/tcp
            │                       ├── framing (свой wire-format)
            │                       ├── multiplexing (TCP его не имеет)
            │                       └── stream lifecycle
            │                       │
      native QUIC streams           │
            │                       │
         QUIC / UDP                TCP
```

Два транспорта с принципиально разной моделью потоков реализовали один и тот же
интерфейс: QUIC даёт мультиплексирование нативно, TCP — не имеет его вообще и
адаптеру пришлось построить его с нуля поверх собственного кадрирования. Порт при
этом не потребовал ни одной правки. Это и есть проверка, ради которой вводилась
hexagonal architecture (ADR-002) и заморозка контракта (ADR-020) — граница выдержала
столкновение с реальностью, а не только с одной удобной реализацией.

Сводка: QUIC 20/20 + race ✅ · TCP 35/35 + race + 843 404 fuzz-итераций ✅ · `ports.Transport` не изменён ✅


- [x] `adapters/quic` — реализует замороженный `ports.Transport` поверх `quic-go v0.48.2`. ### Параллельная ветка — quic-go fork + uTLS ⏸️ DEFERRED

**Статус: отложено до появления конкретного требования, которого stock `quic-go` не покрывает.**

Не «отменено» и не «когда дойдут руки» — отложено по инженерной причине: сейчас
весь Photon работает на обычном `quic-go`, и это ценная базовая линия. Если
сначала сделать форк, а потом обнаружить проблему в Transport или Autodial,
неизбежен вопрос «это баг Photon или наша модификация QUIC?». Пока базовая линия
чистая, ответ на такой вопрос очевиден.

Правильный порядок:

```
stock quic-go → Photon работает и протестирован   ← мы здесь
                        ↓
              появилось конкретное требование
                        ↓
                   fork quic-go
                        ↓
        заменить ТОЛЬКО реализацию транспорта
                        ↓
              сравнить с базовой линией
```

**Критерий возврата к этой ветке** — любой из:

- измеренная блокировка, которую не обходит `adapters/tcp` и которую решает изменение TLS-отпечатка;
- конкретное требование к маскировке трафика от реального развёртывания (не гипотетическое);
- обнаруженное ограничение upstream `quic-go`, мешающее работе Photon.

До тех пор задача не начинается: цель (uTLS, изменение TLS-отпечатка) понятна,
но потребность не подтверждена измерением — тот же критерий, что применяется к
портам (ADR-013).

План работы, когда критерий сработает: форк → найти места создания `tls.Config` →
интегрировать uTLS → пройти тесты `quic-go` без регрессий → проверить между двумя
минимальными примерами отдельно от `photon-core` → заморозить форк.

### Phase 7.5 — Интеграция quic-go fork в Transport ⏸️ DEFERRED

Зависит от ветки выше — отложено вместе с ней.

Когда форк появится, интеграция должна свестись к замене зависимости в
`adapters/quic`, без правки `ports/transport.go`: контракт заморожен (ADR-020) и
уже доказал, что выдерживает два транспорта с разной моделью потоков (Phase 6).
Расхождения в поведении форка, если появятся, проходят тем же фильтром, что в
Phase 2/3 — сначала решаются внутри адаптера или форка, и только при
невозможности становятся кандидатом на ADR.

**Reality** — отдельная большая тема (маскировка, совместимость с реальными
клиентами, свои требования к TLS). Не начинается «потому что записана в roadmap»:
до неё нужен и рабочий форк, и подтверждённое требование. `services/autodial` уже
готов принять её как ещё один `TransportEntry` без правок — то есть отсрочка
ничего не блокирует.

Это **единственное место в планах и коде, где Reality названа по имени**, и
названа она здесь потому, что речь о конкретном механизме — изменении
TLS-отпечатка, ради которого и заведён форк. Везде ещё последняя ступень
цепочки autodial называется по роли («транспорт с маскировкой»): продуктом,
занимающим эту роль, Reality не выбрана, и планом её присутствие в цепочке не
является.

Одно исключение вне планов: **ADR-016** упоминает Reality как пример адаптера
поверх байтового потока. Запись не правится — `DECISIONS.md` фиксирует
рассуждение на момент принятия решения и не редактируется задним числом
(процесс описан в конце файла). Само решение ADR-016 (`UniStream` обязателен
для всех адаптеров) от переименования не зависит.

### Phase 8 — Security Foundation ✅

**Переформулирована по итогам аудита.** Изначально фаза была списком из четырёх
каталогов (`security/permissions`, `signatures`, `trust`, `sandbox`) — то есть
планом «написать четыре пакета». Аудит показал, что проблема не в отсутствии
реализации, а в неудачной границе фазы: две из четырёх областей уже реализованы в
других пакетах, а две другие не могут существовать без своего субъекта — Plugin
Runtime (Phase 9).

Результат фазы — не новый код, а **проверка, что криптографическая идентичность,
доверие к устройствам и модель авторизации имеют единую основу и не дублируются.**

| Область | Статус | Где реализовано |
|---|---|---|
| Подписи | ✅ закрыто | `ports/identity.go` + `adapters/ed25519` (15 тестов), реально используется в `services/account:230` для challenge-response |
| Доверие к устройствам | ✅ закрыто | ADR-021 реализован в `services/account`: Device Registry (`RegisterDevice`/`RevokeDevice`/`ListDevices`), Transport Authentication (18 тестов) |
| Контракт авторизации | ✅ закрыто | `ports.Authorizer` + `ports.Permission`, заморожен (ADR-020) |
| Реализация permission enforcement | ↪ Phase 9 | субъект — Plugin Runtime |
| Sandbox (изоляция) | ↪ Phase 9 | субъект — Plugin Runtime |

**`security/signatures` и `security/trust` не требуют отдельных реализаций.**
Соответствующие обязанности уже принадлежат `Identity` и `services/account`.
Создавать их только потому, что такие каталоги перечислены в `REPOSITORY.md`,
означало бы написать второй механизм подписей рядом с работающим `Identity.Verify`
и второй реестр устройств рядом с работающим Device Registry — прямое дублирование
вместо переиспользования.

**Реализация permission enforcement и sandbox намеренно отложена до Phase 9,
поскольку их субъектом является Plugin Runtime.** Permission без объекта, которому
права выдаются, — абстракция; sandbox без процесса, который нужно изолировать, —
тоже. В Phase 9 оба получают реальное назначение:

```
Plugin → Manifest → requested permissions → Authorizer → Sandbox → IPC → Photon Core
```

- [x] Подписи — закрыто через `Identity` (отдельная реализация не нужна)
- [x] Доверие к устройствам — закрыто через `services/account` (отдельная реализация не нужна)
- [x] Контракт авторизации — `ports.Authorizer` заморожен

### Phase 9 — Plugin Architecture (+ permissions, sandbox) ✅

Включает две области, перенесённые из Phase 8: реализацию `ports.Authorizer`
(permission enforcement) и sandbox — здесь у них появляется субъект, которого не
было раньше.

**Это работа НЕ в `photon-core`** (ADR-030). Ядро содержит только контракт
`ports.Authorizer` + `ports.Permission`; вся реализация — в отдельном репозитории
`photon-plugin-runtime`, который ещё не создан. Направление зависимости:
`plugin-runtime → photon-core`, никогда наоборот (ADR-005).

**Порядок работы — спецификации до кода** (тот же принцип, что сработал с
`adapters/tcp`: `WIRE_FORMAT.md` до реализации):

- [x] 1. ADR на границу ответственности `photon-core` ↔ `photon-plugin-runtime` — **ADR-030**, `REPOSITORY.md` и структура каталогов приведены в соответствие (`security/sandbox` удалён из ядра)
- [x] 2. **Threat model** — `docs/plugin-threat-model.md`. Написана на уровне security properties, не механизмов (`seccomp`/`cgroups` — способы, не требования). Содержит: 10 угроз с решением по каждой; **6 пунктов «что намеренно НЕ обещаем»** (компрометация Runtime/ОС/Core, side-channels, защита от самого пользователя, одинаковая изоляция на всех платформах); базовый инвариант «плагин не получает возможностей просто потому, что запущен»; **манифест = запрос, а не разрешение**; двухуровневая модель гарантий (Layer 1 Photon — везде одинаково, Layer 2 OS — платформо-зависимо, на Android слабее и требует проверки на устройстве); разделение sandbox ≠ authorization; trust levels как верхняя граница, не замена Authorizer
- [x] 3. **Plugin lifecycle** — `docs/plugin-lifecycle.md`. State machine из 7 состояний (`STOPPED`/`STARTING`/`RUNNING`/`STOPPING`/`TERMINATING`/`FAILED`/`DISABLED`). Три ранее открытых вопроса закрыты: **процесс запускает Supervisor внутри Runtime** (ядро не знает PID/путь/счётчик перезапусков — следствие ADR-030); **при падении — экспоненциальный backoff с обязательным jitter**, 6 различаемых типов завершения вместо одного `ERROR`, `protocol_violation` не перезапускается автоматически (это не сбой, а поведение); **плагин переживает перезапуск ядра регистрацией и состоянием, но не процессом** — прозрачное продолжение активных операций явно не обещается. Плюс: правило `Runtime restart ≠ Plugin identity reset`, single-instance по умолчанию, handshake-протокол, раздел «что из этого следует для манифеста»
- [x] 4. **Manifest specification** — `docs/plugin-manifest.md`. Пять блоков (`identity`/`runtime`/`permissions`/`capabilities`/`integrity`) вместо примера из трёх полей в `ARCHITECTURE.md`. Ключевое: **`granted` не записывается обратно в манифест** (выданные права — состояние Runtime в `ports.Storage`; запись в пакет означала бы изменение подписанных автором данных и не позволила бы разным пользователям иметь разные права на один пакет); **`entrypoint` только относительно корня пакета** — абсолютные пути, `..` и symlink за пределы отвергаются, иначе манифест становится способом запустить произвольный файл хоста; **три независимые оси версий** (`manifest_version`/`protocol_version`/`version` плагина) — обновление версии не создаёт новую identity; **неизвестные `required_*` поля → `UNSUPPORTED_MANIFEST`**, обычные неизвестные игнорируются (неизвестное обязательное — вопрос безопасности, необязательное — удобства); `instance_policy: multi` объявлен, но отклоняется в текущей версии; семантика проверки подписи явно **deferred** до спецификации trust/distribution policy. `ports/plugin.go` не менялся
- [x] 5. **IPC specification** — `docs/plugin-ipc.md`. Семантика зафиксирована до выбора wire-format. Базовый принцип: **IPC transport сам по себе не authorization boundary** — `IPC connected ≠ permission granted`, каждый запрос проверяется заново, поэтому новый транспорт можно добавить не переписывая модель безопасности. Ключевое: **идентичность определяется каналом, не содержимым сообщения** (`plugin_id` внутри запроса → `protocol_violation`, а не «проигнорировать»); `UNAUTHORIZED` (субъект не установлен) и `FORBIDDEN` (прав нет) не смешиваются; отмена и дедлайны двусторонние; events отдельным направлением с ограниченной очередью (неограниченная = DoS через память ядра); 7 случаев `protocol_violation` → закрытие сессии без попыток «починить» недоверенный поток. 8 типов сообщений; намеренно нет heartbeat/reconnect/стриминга. Wire-format: предварительный кандидат protobuf (схема уже есть, ADR-025), решение отдельно при написании скелета — смена формата не должна затрагивать семантику
- [x] 6. Скелет репозиториев — **два модуля, а не один**: `photon-plugin-runtime` (6 пакетов: `manifest`/`permissions`/`ipc`/`host`/`supervisor`/`sandbox`, каждый только с `doc.go` — границей ответственности и ссылкой на спецификацию) и **`photon-plugin-sdk` отдельным модулем**, потому что это разные trust boundaries: код SDK исполняется внутри недоверенного процесса плагина, код Runtime — снаружи и принимает решения о правах. ### Phase 10 — Plugin SDK ✅

**Принцип фазы (ADR-031):** SDK — клиент уже существующего IPC-протокола, а не окно
во внутренности runtime. Главный вопрос, вокруг которого проектируется фаза: как
сделать разработку плагина максимально простой, **не позволяя SDK обходить security
model runtime**.

- [x] **Граница SDK ↔ Runtime** — `photon-plugin-runtime/docs/sdk-boundary.md`. Механика IPC (handshake, идентификация, correlation, отмена, дедлайны, события, shutdown, нарушения протокола) **не переопределяется**: она уже зафиксирована в `docs/ipc.md` и реализована (49 тестов), и второй документ на ту же тему со временем разошёлся бы с первым. Зафиксировано то, чего не было: **каталог операций v1** (`storage.*`, `identity.*`, `crypto.*`, `log.*` — только то, что уже поддержано работающим кодом ядра) и **форма SDK как тонкой обёртки** с явным списком антипаттернов (не кэшировать, не повторять запросы, не валидировать права локально, не склеивать операции). Ключевые ограничения: namespace принудительно ограничен `plugin.<id>.*` **на стороне runtime**, иначе `storage.read` означало бы «читать всё»; приватный ключ не выдаётся ни одной операцией (ADR-021); таблица «операция → право» живёт в runtime, потому что в SDK её можно было бы подменить
- [x] **Публичный API v1** — `photon-plugin-sdk/api.go`: `Plugin` + `Storage`/`Identity`/`Crypto` + `Log`/`OnEvent`/`OnStop`. Только интерфейсы, каждый метод — **ровно одна** операция каталога. Классификация ошибок (`errors.go`) повторяет коды `ipc.md`, а не упрощает их: `ErrUnauthorized` («не знаю, кто ты» — повтор бессмыслен) отделён от `ErrForbidden` («знаю, но нельзя» — плагин может сообщить пользователю). Неизвестный код протокола → `ErrInternal`, а не игнорируется: он означает рассинхрон версий
- [x] **Структурная защита ADR-031** — 3 теста, проверены негативно (специально ломал, чтобы убедиться, что ловят). **Два независимых барьера**: (1) добавление запрещённого импорта ломает сборку раньше теста — `go.mod` не содержит нужной `require`, модуль не резолвится; (2) `TestADR031_NoForbiddenImports` парсит импорты и даёт внятное объяснение, если кто-то добавит и импорт, и зависимость сразу. Плюс `TestADR031_NoModuleDependencies` (любой `require`/`replace` в `go.mod` → падение) и `TestOperationCatalogCoverage` (маппинг API↔каталог строго один-к-одному в обе стороны)
- [x] **IPC-клиент** — `wire.go` (кодек, зеркальный к runtime, но **реализованный независимо**: общий пакет означал бы кусок доверенного кода в линковочном графе недоверенного процесса), `client.go` (handshake, correlation, отмена, события, shutdown), `operations.go` (реализации интерфейсов). Все методы проходят через единственный `call` — это структурно исключает появление собственной логики у отдельной операции
- [x] **E2E через настоящий runtime** — `photon-plugin-runtime/tests/integration/sdk_e2e_test.go`, **11 top-level тестов PASS** (без под-тестов; один из них, `TestE2E_AllCatalogOperations`, разворачивается в 10 под-тестов — по одному на операцию каталога, но методика подсчёта их не учитывает отдельно, см. CLAUDE.md), `-race` чист. Не мок IPC: реальный `ipc.Session` + реальный `permissions.Authorizer`. Успешный handshake сам по себе доказывает, что два независимых кодека совпадают побайтово. Проверено: `storage.read` выдан → `Get` работает, `Put` → `ErrForbidden`; все 10 операций каталога проходят полную цепочку; `log.write` работает без единого права; **отзыв права действует на той же сессии без переподключения** (SDK не кэширует авторизацию); неизвестная операция → ошибка, а не тихий успех; события доходят; отмена контекста возвращает управление плагину

**E2E-тест поймал реальный архитектурный пробел.** `sdk-boundary.md` раздел 4 требовал таблицу «операция → право», но `ipc.Session` передавал `m.Op` прямо в `Authorizer` как имя права — то есть маппинг был описан в спецификации и **нигде не реализован**, а `log.write` без права не работал вовсе. Исправлено: `ipc/operations.go` с таблицей на стороне runtime (в SDK её можно было бы подменить), три различимых исхода (`известна+требует права` / `известна+без права` / `неизвестна → UNSUPPORTED`), и `FORBIDDEN` теперь сообщает **право**, а не операцию — плагину полезнее знать, чего просить. Заодно вскрылось, что старые тесты `ipc`/`host` использовали имена прав как имена операций — приведены в соответствие

**Phase 10 закрыта.** Найденный пробел зафиксирован как **ADR-032** (маппинг «операция → право» принадлежит runtime, три различимых исхода вместо двух), решения SDK — в `photon-plugin-sdk/IMPLEMENTATION_LOG.md`. Граница ADR-031 перепроверена после роста кода: `go.mod` без единого `require`, импорты только из стандартной библиотеки, три структурных теста зелёные

**Итог фазы.** Пять плагинов нашли три реальных бага в коде Phase 9 —
`host.Stop()` убивал процесс раньше, чем тот успевал выйти сам (`hello`);
гонка порядка записи в `ipc.handshake()`, воскрешающая закрытую сессию
(`hello`); `kill()` не использовал `Setpgid`, несмотря на то что тот
специально проставлен именно ради этого (`stress`/`fork-bomb`) — плюс
ловушку в публичном API SDK, дедлок при блокирующем вызове из
`OnEvent`/`OnStop` (найдена `permission`, исправлена на уровне SDK, не
точечно в тестовом плагине). Все шесть — на границах, невидимых для
in-process тестов Phase 9–10: `fakeSpawner` и `net.Pipe` не порождают
настоящих процессов, не имеют кодов возврата и не воспроизводят тайминги
реального завершения, поэтому разница между «процесс убит» и «процесс
вышел сам» была для них неразличима.

Отдельно: `crash`, `permission` и `storage` новых багов не нашли — и это
результат, а не пустой прогон. Каждый подтвердил, что правки, сделанные по
итогам `hello`, оказались достаточными: `crash` — что классификация
`host.classify()` верна для всех четырёх способов падения без
дополнительных правок; `permission` — что security boundary держится под
семью настоящими атаками, а не только в юнит-тестах `Authorizer`; `storage`
— что namespace-изоляция прозрачна для двух честно авторизованных плагинов,
не только непроницаема для одного нечестного.

### Phase 12 — Protobuf Protocol 🟡 В РАБОТЕ

**Начата 2026-09-07. Критерий возврата выполнен:** потребитель доменных
сущностей появился — им оказался не UI, а слой синхронизации (ADR-046).

**Цель переформулирована.** Не «довести семь сущностей до финального вида», а
дать протоколу форму, пригодную для синхронизации: курсорную пагинацию и
версии. Сущности доводятся ровно в той мере, в какой требует срез.

**Первый вертикальный срез выполнен** — «открыть один канал и пролистать
историю назад», полный путь `server → cursor → local storage → ordered read →
load more → offline reopen`. Ответы на восемь вопросов среза, измерения и
находки — `photon-core/services/localfeed/IMPLEMENTATION_LOG.md`.

Главный результат — **измеренная стоимость существующего `ports.Storage`**:
открытие канала дёшево независимо от размера (50 просмотрено, 0 выброшено при
100 / 1 000 / 5 000 записей), глубокое пролистывание линейно по глубине
(страница №100 просматривает 5 000 ради 50). Решение о расширении порта
**не принято** и принимается отдельно.

**Форма закрыта двумя решениями.** **ADR-052** заморозил курсор — позицию
`{OrderKey, ID}`, раскладку ключа, **инверсию сравнения `ID`** (при равном
`OrderKey` свежее та запись, у которой `ID` МЕНЬШЕ — иначе сравнение
разошлось бы с байтовым обходом молча), сегменты как утверждение о полноте,
направления и провод `before`/`after`/`limit`. **ADR-053** заморозил
семантику `Version` и механизм обнаружения удаления.

**Живой прогон дважды исправлял сценарий, а не код**, и это записано как
находка метода: сначала окно после удаления оказалось пустым и `Vanished` не
проверился вовсе — понадобились опорные записи, держащие диапазон покрытым;
затем правка приходила первой встречей, потому что окно читалось до создания
записи. Оба — дефекты измерителя того же класса, что находили Phase 13.5 и
Media MVP.

- [x] **Политика локального удаления `Vanished` — ЗАКРЫТА, ADR-054.**
      Принята после узкого живого эксперимента
      (`photon-core/docs/deletion-oracle.md`), а не по рассуждению.
      `Vanished` **не имеет права автоматически удалять** локальную запись;
      адресный `Get` — **диагностический оракул живости**: `ok:true`
      подтверждает существование и снимает ложную тревогу, `forbidden` **не
      трактуется как `deleted`**, при отсутствии однозначного сигнала запись

- [x] **измерено до реализации:** подтверждение стоит **72.1 мс** на

      ADR-053 менять не потребовалось
- [x] **зафиксирована слепая зона:** удаление самой новой или самой старой
      записи блока `Vanished` **не замечает** — диапазон сжимается вместе с

плагин снаружи «здоровым» (health-check ходит по другому стриму). Плюс четыре
**ложных PASS в самом прогоне**: проверки отказов принимали любую ошибку и
потому зеленели на сервере, который не мог принять ни одного решения.
Исправлено требованием контрактной причины отказа, живым свидетелем и порогом
времени у проверки дедлайна.

**Две проверки остались невыполненными, и они разной природы** — смешивать их
нельзя:

- **E3** («сервер не буферизует файл целиком») — **закрыто отдельным замером
  2026-09-10, после прогона.** Прежнее доказательство было слабым: структурный
  тест запрещает `io.ReadAll`, то есть одно написание, а не свойство. Замер —
  относительный, два размера через живой Bridge: файл вырос в **8.0 раза**, а
  прирост RSS плагина не вырос вовсе (1 056 kB против 1 508 kB, отношение
  0.70), и `VmHWM` после 96 MiB — 24 972 kB, вчетверо меньше самого файла.
  Накопления `O(file_size)` нет. Не покрыто замером: параллельные передачи и
  направление 701. Подробности — `photon-core/services/media/IMPLEMENTATION_LOG.md`;
- ~~**N6** («недоступный объект отвергается как `unavailable`») — стимула не
  существует~~ — **КРИТЕРИЙ ВОЗВРАТА ВЫПОЛНЕН, N6 исполняется** (2026-09-13,
  ADR-055). Стимул дала уборка C: удаление поста переводит media в `DELETED`.
  Вместе с N6 добавлена симметричная **N7** — тот же ответ на пути `701`.
  Обе сверяют **точную** причину `unavailable`: сервер, снёсший метаданные
  вместе с байтами, ответил бы `forbidden`, и проверка «пришла какая-то
  ошибка» приняла бы это за успех. `MediaExpired` производителя по-прежнему
  не имеет — планировщика нет (ADR-049 §11).

### Media lifecycle cleanup (реапер) 🟡 — уборки C и C-2 закрыты, четыре открыты

Заведена находкой Media MVP, в его объём **не входит** и его закрытию не
мешает. **Первая из пяти уборок ADR-048 §12 выполнена** (2026-09-13,
ADR-055); остальные четыре открыты и по-прежнему не смешиваются.

**Дефект, ради которого задача заводилась, — устранён.** Удаление поста
оставляло медийный объект живым: хука на удаление не было, состояние не
менялось. По ADR-048 **§7** `ATTACHED` означает «объект назван в
`photon_media` ЖИВОГО поста» — значит инвариант нарушался штатным действием
пользователя. (Прежняя редакция ссылалась на §11 — это «Совместимость»,
ссылка была неверной.)

**Уточнение состояния, которое прежняя редакция называла неверно:** штатный
`Attach` завершается в **`AVAILABLE`**, а не в `ATTACHED` — он делает два
`PutMeta` подряд, и `ATTACHED` остаётся лишь при неудачной пробе блоба.
Правило уборки поэтому названо через **оба** состояния; написанное только про
`ATTACHED` промахивалось бы мимо основного случая.

Последствия были конкретны: такой объект уже не прикрепить (сработает
`already attached`), освободить его нечем, он остаётся навсегда — и, что
существеннее размера на диске, **остаётся читаемым**: `objMedia` резолвит
канал из метаданных MediaStore, а не из поста. На стенде после прогонов —
5 объектов, 37 МБ, ноль живых постов в тестовом канале. Найдено не ревью и не
тестом, а уборкой самого прогона.

### Phase 12.5 — Bridge Session ✅

**Следующая фаза. Идёт перед Phase 13, и это не перестановка ради удобства.**

Фаза заведена по итогам discovery-прохода перед Phase 13, который нашёл вещь,
не описанную ни одним документом: **`Photon_Create` не подключается к серверу**.
Не «подключается неправильно» — не подключается вовсе: реализация
(`photon-bindings/c/photon.go`) разбирает `config_json` и создаёт пустой
`&core{}`. При этом `photon_core.h` — **замороженный** ABI, по которому будут
писать клиенты, — обещал обратное: «Photon_Create — создать инстанс (включает
подключение транспорта согласно config_json)».

Это не «дырка в одну строку», а отсутствующий слой. Между `ports.Transport`
(умеет открывать стримы) и Dispatcher (умеет исполнять action) нет ничего, что
знает протокол: как аутентифицироваться, в каком порядке слать фреймы, чем
`action`-режим отличается от `subscribe`, что делать при обрыве. Начав Phase 13
без него, Dispatcher пришлось бы писать так, чтобы он сам открывал стримы и сам
писал в них JSON — та самая ошибка «код повторяет форму транспорта, а не модель
системы», от которой `CLAUDE.md` предостерегает в разделе «Метод работы».

Спецификация написана до кода: **`photon-core/docs/bridge-session.md`**.
Решение о формате — **ADR-034** (JSON на проводе, protobuf как схема).

- [x] ADR-034 — wire-format Bridge-границы зафиксирован
- [x] `photon.proto` — шапка исправлена (обещала `PhotonRequest` на проводе), оба конверта помечены как «не сериализуются»
- [x] `photon_core.h` — убрано обещание подключения транспорта в `Photon_Create`

- [x] Вывод `resource` из action-кода (следствие ADR-026 п.1 — на ABI убран, на проводе требуется)
- [x] Handshake: auth-фрейм, mode-фрейм, ack

формата), `json_codec.go`, `resource.go`, `session.go`, `errors.go`,
`IMPLEMENTATION_LOG.md`. Порт `ports.Transport` не менялся (ADR-020) —
шестой подряд компонент без правки контракта.

**Найдено при реализации:** дедлок в `WriteRequest` — payload и завершающий
`"\n"` уходили двумя `Write`, и на небуферизованном соединении обе стороны
начинали писать одновременно. Формат на проводе при этом получался
байт-в-байт верным, ошибка была только в числе системных вызовов — ревью
такое не ловит, поймал тест T-7 (висел до таймаута). Подробности —
`IMPLEMENTATION_LOG.md`.

**Почему не часть Phase 13.** Dispatcher отвечает на вопрос «что исполнить»,
сессия — «как доставить». Это разные оси: сессия не знает, что внутри
payload'а, Dispatcher не знает, JSON на проводе или protobuf (в этом и смысл
`Codec`). Слив их в одну фазу дал бы компонент, который знает и то и другое —
и который пришлось бы разделять при первом же втором транспорте.

**Реализация — через замороженный `ports.Transport`/`adapters/quic`, не через
`quic-go` напрямую.** Проверено при написании спецификации: порт покрывает
потребность целиком, правок не требует (`bridge-session.md`, §7) — шестой
подряд компонент без правки контракта (ADR-020). `test-client/test_photon.go`
дёргает `quic.DialAddr` сам, и это нормально для тест-клиента, проверяющего
сервер, но не образец для Core.

**Прогон против живого сервера состоялся — и оправдал требование.** Опасение
было записано заранее: `net.Pipe` проверяет логику протокола, но не
воспроизводит ни таймингов сети, ни поведения QUIC при обрыве. Так и вышло —
живой прогон нашёл то, чего не находил ни один из 29 тестов:

1. **Подписка умирает через 30 с простоя** (idle-timeout QUIC; keep-alive не
   слала ни одна сторона). Для action-соединения незаметно — его держит трафик
   запросов; для подписки тишина и есть норма, поэтому обрыв наступает
   **штатно**. Исправлено на сервере: `KeepAlivePeriod: 15s`.
2. **Об обрыве не сообщала ни одна сторона.** Переход `Ready → Failed` был
   обещан спецификацией (§6) и комментарием в коде, но не реализован нигде:
   `StateFailed` выставлялся только при неудачном `Connect`. Подписчик висел в
   `AcceptPush`, считая себя подписанным. Исправлено: `ErrConnectionLost`,
   тесты T-18, проверено на настоящем idle-timeout (30 с, цепочка причин
   сохранена до исходной ошибки quic-go).
3. **`user_id` верхнего уровня в push-событии обычно отсутствует** —
   `omitempty` плюс один заполняющий хук из восьми. Комментарий в `codec.go`
   утверждал «пустой = широковещательное событие»; неверно, автор в
   `data.user_id`. Исправлено вместе с §2.3.

Заодно подтверждено фактом то, что раньше выводилось разбором: авторизация по
**Session ID**, а не по токену логина; `event` приходит **строкой**, несмотря
на `enum EventType` (ADR-034); расхождение версий quic-go (Core v0.48.2 против
сервера v0.59.0) на проводе действительно ничего не меняет.

**Что осталось открытым — за рамками чек-листа фазы**, записано в
`bridge-session.md` §9:

- поведение при **аварийном** обрыве (потеря сети, убитый процесс) в отличие
  от штатного idle-timeout — порядок ошибок там может отличаться;
- ~~`KeepAlivePeriod: 15s` на сервере не проверен вживую~~ — **проверен**:
  после установки сборки с ним соединение пережило 150 с молчания, тогда как
  до неё обрыв приходил на 30-й секунде воспроизводимо. Обратная проверка,
  подтверждающая отсутствие события;
- буфер push на 64 события и молчаливый сброс в `Broadcast` — требует
  всплеска событий и подъёма `net.core.rmem_max`, иначе потери на приёме
  смешаются со сбросом на отправке.

### Phase 13 — Core Operations Handler ✅

**Идёт после Phase 12.5** (Bridge Session, заведена выше) — без слоя сессии
Dispatcher не к чему подключить. Phase 12 отложена (DEFERRED) —
оставшиеся в ней доменные сущности не могут быть спроектированы без клиента,
который бы ими пользовался. Phase 13 — обратный случай: она не добавляет
предположений, а разблокирует три уже существующих, открытых прямо сейчас
места, у каждого из которых уже есть код или тест, ожидающий именно её:

- `Photon_SendAction` в C ABI (`photon-bindings/c/photon.go`) возвращает
  честную заглушку `"action not yet implemented: dispatcher (Phase 13) does
  not exist"` — вместо неё появится настоящий исполнитель;
- каталог операций (`storage.*`, `identity.*`, `crypto.*`) уже описан в
  `photon-plugin-runtime/docs/sdk-boundary.md` и проверен E2E-тестами, но
  исполняется тестовыми `Handler`'ами лаборатории Phase 11, а не ядром — сам
  каталог не изменится, изменится только то, что стоит за ним;
- оговорка 🟡 у пункта «восстановление после сбоя» в Phase 11: persistence в
  `storage`-тесте смоделирована общим in-memory store; с Dispatcher её можно
  будет перепрогнать против настоящего `ports.Storage` (`adapters/bbolt`), не
  заменяя существующий тест, а дополняя его — см. `IMPLEMENTATION_LOG.md`,
  «Phase 11: `storage`».

**Спецификация написана до кода:**
`photon-plugin-runtime/docs/core-operations.md`.

**Исполнитель операций каталога поверх портов ядра.** Реализация `ipc.Handler`
над `ports.Storage`/`ports.Identity`/`ports.Crypto`. Сейчас единственная
нетестовая реализация `ipc.Handler` во всём дереве — `HandlerFunc`
(`ipc/session.go:78`), адаптер функции к интерфейсу, а не исполнитель: каталог
описан, проверен E2E и проверен на настоящих процессах Phase 11, но за ним не
стоит ничего, кроме тестовой оснастки.

**Живёт в `photon-plugin-runtime`, не в Core.** `ipc.Handler` — интерфейс
runtime; реализация его ядром означала бы импорт runtime ядром, прямое
нарушение ADR-030. Зависимость идёт в обратную сторону: runtime уже импортирует
`photon-core` ради `ports.Authorizer`.

**Сессии не требует** — работает с портами, не с сетью. Прежняя редакция этого
раздела связывала его с `Photon_SendAction` общим предусловием (создание сессии
в `Photon_Create`); это неверно, предусловие есть только у Phase 13.5. Отсюда
разделение фаз.

**Центральный вопрос проектирования — идентичность вызывающего.** Текущая форма
`ipc.Handler` её не даёт: ни `plugin_id`, ни публичного ключа, и `ctx` пуст
(`context.WithValue` в `ipc/session.go` не встречается ни разу). Идентичность
достоверна, но живёт в `Config.Caller`/`Config.ExpectedPluginID` и до handler'а
не доходит; тесты Phase 11 обходят это захватом `plugin_id` в замыкание.

`ports.Authorizer`, — и обосновывает почему: замыкание превращает
namespace-изоляцию в соглашение о конструировании, а не в свойство типа.

### Phase 13.5 — Action Routing ✅

**Маршрутизация C ABI → сессия.** `Photon_SendAction` разбирает action-код
(100–602), выводит `resource` (`services/session/resource.go`, готово с Phase
12.5), зовёт `session.Do`, возвращает ответ. Живёт в
`photon-core/services/dispatcher`.

**Идёт после Phase 13** — не потому что зависит от неё (не зависит), а потому
что `Photon_SendAction` — единственная операция замороженного ABI,
возвращающая заглушку `"action not yet implemented: dispatcher (Phase 13) does
not exist"`. `photon-bindings/c` и JNI стоят готовые и непригодные, пока она
там.

**Спецификация написана до кода:** `photon-core/docs/action-routing.md`.
Четыре решения приняты в ней (D-1…D-4 ниже); одно из них, D-2, потребовало
отдельной записи — **ADR-038**.

**Предусловие, решение по которому принято при спецификации этой фазы:**
инстанс не держит сессию. `core struct`
(`photon-bindings/c/photon.go:77-83`) — `mu`, `lastError`, `callback`,
`userData`, `destroyed`, и ничего больше. Выбор стоял между **созданием
сессии в `Photon_Create`** и **ленивым при первом вызове**; принято D-1 —
объекты в `Photon_Create`, подключение по требованию.

Что уже известно и должно учитываться при выборе:

- `photon_core.h` **заморожен** (ADR-008), `Photon_Connect` не существует,
  экспортируемых функций ровно двенадцать;
- заголовок прямо говорит «`Photon_Create` НЕ подключается к сети», и там же
  записано, что прежнее обещание обратного было неверным и убрано;
- `bridge-session.md` §6 п. 5: `Do` намеренно не подключается неявно —
  подключение под общей блокировкой превратило бы каждый первый вызов в
  непредсказуемо долгий;
- **`session.New` тоже сети не касается** — то же правило, что у
  `Photon_Create`. Значит создание сессии в `Photon_Create` заголовку не
  противоречит; вопрос только в том, где происходит `Connect`.

Из формы `photon-quic-bridge/server/dispatcher.go` применимо: синхронность,
маршрутизация по диапазону кодов, неизвестный код — явная ошибка. Не применимо:
шесть resource-handler'ов (доменные сущности Mattermost, ADR-003, Phase 12
DEFERRED), `userID` первым аргументом (у Core сессия своя), `json.RawMessage` в
сигнатуре (payload обязан остаться непрозрачным `[]byte`, ADR-034 п. 4).

**Решения спецификации:**

- **D-1 — ленивое подключение.** Объекты (транспорт + `session.Session`)
  создаются в `Photon_Create`, `Connect` — по требованию, вне `session.Do` и
  без удержания блокировки инстанса. Синглфлайт обязателен: без него N
  параллельных `SendAction` на свежем инстансе дадут N соединений, а часть
  вызовов получит `ErrConnectInProgress` не по делу. `Photon_Connect` не
  заводится (правило минимальности: адрес всё равно в `config_json`); фоновая
  горутина в `Photon_Create` отвергнута как гонка с обещанием «ни одного
  пакета до возврата». Фоновый коннектор станет обязателен вместе с push —
  это записанный критерий, а не «когда-нибудь».
- **D-2 — `PHOTON_OK` = вызов состоялся, вердикт операции в конверте**
  (**ADR-038**). `ok:false` доходит до клиента телом ответа, а не кодом:
  кодов ошибок на проводе нет, классификация по тексту запрещена (ADR-033), а
  заголовок запрещает `response_out` при не-`OK` — альтернатива теряет `error`
  сервера, единственный источник причины. Цена названа явно: клиент,
  проверяющий только `rc`, примет отказ за успех.
- **D-3 — enum `PhotonResult` не расширяется.** `ErrNotReady` и
  `ErrConnectionLost` → `PHOTON_ERR_NOT_CONNECTED`: оба ведут клиента к одному
  решению — повторить вызов. Различие сохраняется в `Photon_GetLastError`.
  `ErrSessionClosed` → `INVALID_ARGUMENT` (`NOT_CONNECTED` подсказал бы
  «повтори» на уничтожаемом хендле). Критерий возврата и полная цена
  добавления десятого кода — `action-routing.md` §7.1.
- **D-4 — один инстанс, один адресат.** Адресат — сам `PhotonHandle`:
  многобэкендность уже выразима двумя вызовами `Photon_Create` с разным
  `config_json`, правки ABI не требует. Вместо решения — проверяемое
  ограничение «никакого пакетного состояния», с тестом и мутацией.

- **Ожидание «число соединений поймает поломку синглфлайта» неверно.**
  Измерено: с убранным синглфлайтом `Transport.Connect` вызывается ровно один
  раз, потому что `session.Connect` защищает себя сам — второй параллельный
  вход получает `ErrConnectInProgress`, а не второе соединение. Тест,
  полагавшийся бы только на счётчик, был бы зелёным всегда. Ловят поломку
  другие утверждения того же теста; счётчик ловит две другие мутации.
- **Результат попытки подключения нельзя хранить в поле диспетчера** — узкая

- **`setError` тёк после `Photon_Destroy`** — вызов в полёте аллоцировал
  `lastError` уже после того, как `Destroy` его освободил. До этой фазы
  фоновой работы, переживающей возврат из вызова, не существовало.
- **Тест на `Destroy` над висящим вызовом мог оказаться пустым** (проходит за
  время собственного `sleep`). Проверено мутацией: без закрытия диспетчера он
  висит 10 с и падает.

- **Подтверждено на живой сети:** ленивое подключение (0 → 1 → 1 подключение,

**Почему 207/208/209 потребовали переработки oracle.** Правило у всех трёх —
`{objNone, isSelf()}`, а резолвер `objNone` ставит `o.isSelf = true`
**безусловно**: «цели нет — self по построению». Композиция тождественно
истинна, субъектов не различает, и строка матрицы «A → ALLOWED, B → ALLOWED»
не измеряла бы ничего. Настоящая инварианта — *действие нельзя перенаправить
на чужой аккаунт payload'ом*; она и проверялась: в запрос вкладывался ложный
`user_id`, а доказательством служило то, что **изменился только вызывающий**.
Структурного чтения кода здесь недостаточно — прецедент `ownerSel` в этой же
фазе показал, что таблица правил и развёрнутая сборка расходятся молча.

**Почему 209/A — INTENTIONALLY_NOT_TESTED, а не FAIL и не INCONCLUSIVE.**
Три независимых довода: изменение аватара необратимо (ни REST, ни `mmctl` не
дают «удалить», только заменить); A — единственный `system_admin` стенда, через
который идут все живые проверки; относительно 209/B прогон от A не даёт
дополнительного доказательства, поскольку правило субъекта не различает.
Сознательный отказ, а не пропуск.

**Почему 306/B и 308/B избыточны.** `permSys` игнорирует `objectRef` — ни
субъект, ни цель на решение не влияют, право есть у любого `system_user`. К
тому же 306 и 308 идут в **один обработчик**
(`case ActionGetOrCreateDirectChannel: return h.createDirectChannel(...)`).
Прогон от B повторил бы тот же путь и создал ещё один неудаляемый DM.

**Почему 308 всё же получил отдельный smoke.** `TestAuthzCoversEveryAction`
итерирует `photonpb.Action_name` и сверяет полноту **таблицы правил** —
маршрутизацию он не проверяет. У `ChannelHandler` есть ветка
`default: "unknown action %d"`, и регрессия диспетчеризации вернула бы
`ok:false`, не будучи пойманной ни одним машинным тестом. M6 подтвердил:
действие доходит до обработчика, возвращает тот же `channel_id`, что 306, и
нового DM не создаёт.

**Почему 310/B отвергнут именно как не-член.** Роль `channel_user` по
умолчанию **имеет** `manage_public_channel_members` и
`manage_private_channel_members`, поэтому «B не может снимать участников» как
общее утверждение неверно. Проверено контрольным экспериментом: **та же
операция** (B снимает C) отвергнута, пока B не член канала, и разрешена сразу
после добавления B в канал. Отказ определяется членством и канальной ролью, а
не отсутствием глобального права; правило не выродилось в deny-all.

**Качество oracle: эпизод M3.** Первый прогон QUIC-плеча вернул
`{"ok":true,"data":{"updated":true}}`, а `users.lastpictureupdate` не
изменился. Разбор показал, что это не расхождение плеч: повтор **того же**
изображения по HTTP тоже не обновляет отметку — Mattermost не пишет её при
идентичных байтах. Окончательный тест использовал **разные изображения на
разных плечах**, и запись подтвердилась (`0 → …619611 → …709564` у C при
неизменном `0` у B). Эпизод записан намеренно: приняв `ok:true` за
доказательство, прогон дал бы фиктивный PASS.

### Phase 15 — P2P Layer 🟡

**Чек-лист исправлен.** Прежняя редакция перечисляла API `ConnectPeer()`,
`CreateSession()`, `SendData()` — такого API нет ни в замороженном
`ports/p2p.go`, ни где-либо в коде, и появиться он не может без изменения
контракта (ADR-020). Порт определяет согласование
(`CreateOffer`/`AcceptOffer`/`CompleteSession`/`Close`), а данные идут через
`Session`, которая расширяет `Connection` — то есть через уже существующие
`OpenStream`/`AcceptStream`/`OpenUniStream`. Отдельного «отправить данные» в
P2P-порте нет намеренно: иначе P2P дублировал бы Transport.

Цель фазы — **валидировать замороженный порт реализацией до появления первого
потребителя** (первый клиент — Phase 16). Ошибку контракта дешевле найти
сейчас.

- [x] ADR-043 — обход NAT и выбор механизма: ICE + DTLS + SCTP без
      WebRTC-стека (путь B+). Написан **до** кода; `pion` в комментарии порта
      был предположением, а не решением (ADR-011/013)
- [x] ADR-041 — аутентификация peer'а: `Session.Peer()` возвращает только
      криптографически подтверждённый ключ
- [x] ADR-041 §3 — защита от replay и привязка handshake к сессии: подписывается
      transcript с обоими ключами, обоими nonce и channel binding
- [x] ADR-042 — signaling вне P2P-порта, блобы непрозрачны, доставка на
      вызывающем
- [x] ADR-043 §8 — direct/relay-политика и семантика `ErrSessionFailed`
- [x] ADR-044 — жизненный цикл, отмена, таймауты, конкурентные сессии, `Close`
- [x] Спецификация `photon-core/docs/p2p-session.md` — написана **до** кода
- [x] Адаптер порта `ports.P2P`; compile-time `var _ ports.P2P` и

`adapters/pion` — **25 тестов**, race чист. `photon-core` целиком: **256**
(было 231).

**Acceptance отдельно от loopback.** Согласование двух агентов в одном
процессе доказывает работу протокола, но **не обход NAT** — смешивать нельзя,
это тот же класс ошибки, что зелёный тест на фиктивном транспорте
(Phase 12.5). Настоящий NAT traversal, TURN-relay через внешний сервер и две
физические машины — отдельные проверки со своим критерием, и они **открыты**.

Relay-**тесты** в `go test` доказывают путь, а не сетевые условия: TURN-сервер
свой, в том же процессе, на loopback. Прежде `ForceRelay` был флагом, который
не исполнял никто. Внешний acceptance выполнен отдельно и заменой этим тестам
не является — как и они ему.

**Что нашла фаза** (подробности — `adapters/pion/IMPLEMENTATION_LOG.md`):

1. Ошибка контракта — **до единой строки кода**: комментарий `AcceptOffer`
   содержал два разных контракта в одном предложении. Устранено ADR-044 §1 без
   правки сигнатур.
2. `establish` игнорировал контекст вызывающего (`context.Background()`) —
   нарушение ADR-044 §2. Loopback этого не показывал: там согласование
   завершается раньше, чем кто-либо отменит. Нашёл сетевой прогон.
3. **Регрессионный тест на находку п. 2 был зелёным на самой находке.**
   Обнаружено проверкой мутациями: тест отменял контекст *до* вызова, а
   `CompleteSession` отвергает такой контекст первой строкой и до фонового
   согласования не доходит. Тот же класс, что
   `TestAuthzOwnerSelectorIsSelector` в Phase 14 — только там его нашёл живой
   прогон после развёртывания.
4. Потолок согласования покрывал только шаг после `CompleteSession`.
   Незавершённый offer держал ICE-агент и сокеты до `Close()` адаптера; поле
   `negotiation.cancel` под это существовало и не присваивалось никогда.
5. Handshake — единственный шаг, не подчинявшийся контексту: чтение из
   SCTP-потока блокируется до прихода данных. Молчащая сторона подвешивала бы
   согласование навсегда, мимо обязательного потолка.
6. Два тихих отказа стали громкими: `ForceRelay` без TURN (теперь отвергается
   на построении) и сбор с нулём кандидатов (теперь отказ на месте, а не
   истечение потолка на противоположной стороне).

**Ловушка, оставленная контрактом и записанная явно** (`p2p-session.md` §6.1):
согласование живёт на контексте вызывающего и продолжается после возврата из
вызова, поэтому привычное `defer cancel()` вокруг одного шага **убивает
сессию**. Смягчать это адаптеру запрещено — иначе отменить согласование нечем
вовсе. Правило: один контекст на всё согласование, живущий до его исхода.

**Вне фазы:** peer discovery; домен `p2p.*` в каталоге операций SDK (шесть
условий `sdk-boundary.md` не выполнены); P2P-функции в C ABI; P2P-действия в
`photon.proto`; включение P2P в лестницу Autodial; развёртывание coturn как
инфраструктурная задача; mesh и multi-hop.

- [x] **Live acceptance против развёрнутого Bridge — 9 проверок выполнено**
- [x] **Сквозной P2P E2E под двумя разными аккаунтами Mattermost**

`services/dispatcher` — **51 тест** (было 28), `photon-bindings/c` — **44**
(было 35). `photon-core` целиком: **279**. Race чист. `ports/*.go` не
менялись; в `photon_core.h` изменён только устаревший комментарий — сигнатуры
и `PHOTON_ABI_MINOR` не тронуты.

**Live acceptance — 9 выполненных проверок:**

1. `CONNECTED` от реального Bridge (604 мс);
2. реальный `MESSAGE`: пост создан через action-соединение, доставлен
   подпиской и отдельно подтверждён на границе ABI, через собранную `.so`;
3. порядок событий и отсутствие параллельных вызовов колбэка;
4. **настоящий сетевой обрыв** пути → `NETWORK_CHANGED` → reconnect →
   `CONNECTED`;
5. два последовательных восстановления;
6. независимость action-соединения и подписки;
7. `Destroy` во время колбэка, во время паузы backoff и в ожидании push;
   реентерабельный и повторный `Destroy`;
8. колбэк → `SendAction` (`ok:true` от живого сервера) и `GetLastError`;
9. отсутствие колбэков после возврата `Destroy`; стабильность OS-потока
   доставки.

**Находка прогона.** Первый способ вызвать обрыв — отодвинуть клиентский
keep-alive за idle-timeout — **не сработал**: keep-alive шлёт сам сервер
(`KeepAlivePeriod: 15s`, правка Phase 12.5). Метод заменён на разрыв сетевого
пути через локальный UDP-ретранслятор. Записано как находка, а не
переформулировано задним числом.

**Cross-account P2P E2E — доказанный результат.** Две личности Photon под
**разными** аккаунтами Mattermost (`wiloris` и `photon-test-b`), у каждого своя
Bridge-сессия: публикация ключей в props, discovery через `getUser`, offer и
answer настоящим push, `CompleteSession`, криптографически подтверждённый
`Peer()` с ожидаемыми ключами, двунаправленный payload, `Close`.

Это **proof of composition, а не traversal и не расширение P2P API**. Обвязка,
которой нет в Photon (генерация ключа устройства, публикация в props, маркер
служебного сообщения), живёт в инструменте — тот же приём, что TCP-рандеву в
`p2pcheck`, и иллюстрация ADR-042. Границы P2P-порта не двигаются: P2P в C ABI
и SDK, а также включение в лестницу Autodial остаются **вне фазы**.

**Открыто и намеренно не закрывается:**

- **malformed push против настоящего Bridge — NOT EXECUTED, и таким остаётся.**
  Стимул недостижим: Bridge всегда шлёт валидный JSON, внутрь QUIC не
  вклиниться. **Инвариант клиента закрыт отдельно 2026-09-07** — см. ниже;
- **переполнение буфера `PushRegistry` (64) — ИЗМЕРЕНО 2026-09-07: 165
  событий**, теряется хвост. **Доставка событий lossless не является и таковой
  не заявляется**;
- оба процесса E2E работали на одной машине; traversal доказан отдельно, в
  acceptance Phase 15;
- отзыв опубликованного ключа существующими действиями не выражается:
  `patchMe` на Bridge сливает props и удалить ключ не может.

#### Два открытых пункта закрыты после фазы — 2026-09-07

Статусы на момент закрытия Phase 15.5 оставлены выше как были: переписывать их
задним числом нечестно. Здесь — что удалось выяснить позже.

**Буфер: порог 165 событий, теряется хвост.** Два независимых прогона (230 и
200 отправленных) дали одинаковый результат — доставлены номера 1..165, **ни
одного пропуска внутри диапазона**. Порог объясняется целиком: `100`
(`DefaultMaxIncomingUniStreams` quic-go) + `64` (буфер `PushRegistry`) + `1`
(в полёте в `sendEvent`).

Важнее числа — **форма потери**: `select … default` роняет **новое** событие,
поэтому отстающий клиент сохраняет самые **старые** и теряет самые **свежие**.
Для будущего кеша это худший из возможных вариантов.

Прежний прогон (99 из 180) оказался **дефектом измерителя**, а не сервера:
события генерировались параллельно через один диспетчер. Последовательная
генерация даёт 230/230 и 200/200; ограничение частоты на стенде выключено.

**Второе ограничение, более сильное, чем буфер.** В конверте push нет ни
номера, ни версии: `PushEvent` — это `{event, user_id, data}`, а порядок и
версии живут внутри `data`, которую Core намеренно не разбирает (ADR-025/034).
Значит **пропуск нельзя обнаружить по самому потоку** — только сверкой с
сервером. Отсюда следствие, определяющее архитектуру будущего кеша: **push —
ускоритель, а не источник истины** (см. ADR-046).

**Malformed push: свойство клиента доказано, поведение Bridge — нет.** Развёрнутый
Bridge для стимула непригоден, поэтому поднимался собственный QUIC-сервер,
говорящий по протоколу Photon: настоящий QUIC, настоящий TLS, настоящий
клиентский код. Последовательность «валидное → битое → валидное» дала ровно
один `CONNECTED`, оба валидных события доставлены, битое — нет. Мутация,
трактующая битый кадр как обрыв, проверку роняет. Статусы разделены намеренно.

**Вне фазы:** identity как продуктовая сущность, discovery и signaling внутри
ядра, P2P в C ABI и SDK, Autodial, симметричный NAT.

**Оснастка acceptance** остаётся в репозитории, как `tests/livecheck` и
`tests/p2pcheck`: `photon-core/tests/eventcheck` (проверки доставки,
UDP-ретранслятор, сквозной сценарий) и `photon-bindings/c/livecheck_events.c`
(граница ABI через собранную `.so`). Ни credentials, ни секретов не содержат —
сессия и канал передаются флагами. В `go test ./...` не участвуют.

### Phase 16 — Photon Developer Tools 🟡

**Реализуемое закрыто; четыре пункта заблокированы архитектурно, а не не
сделаны.** Закрыты: Dashboard, Network Lab, Protobuf Inspector, Performance и
Logging в клиентской части. Остаются: Storage Lab, Crypto Lab, Plugin Lab и
централизованный лог ядра — у каждого своя развилка, названная в своём
разделе; ни одна не решается реализацией инструмента. Первый настоящий клиент
Photon существует и работает через публичный путь.

Первый **настоящий клиент** Photon — Linux Desktop, `Compose Desktop → JNI →
C ABI → Photon Core`. Не вспомогательный Debug Client, а среда разработки и
исследования платформы: наблюдать состояние, воспроизводить сценарий, мерить,
нагружать, находить дефект.

**Ограничение, определяющее форму фазы.** Инструмент ходит **тем же публичным
путём**, которым пойдут настоящие приложения, и **C ABI ради него не растёт**.
Фактическая поверхность на сегодня (`photon-bindings/c/photon_core.h`,
`PHOTON_ABI_MAJOR 1` / `PHOTON_ABI_MINOR 0`) — одиннадцать символов:

```
Photon_GetABIVersion
Photon_Create   Photon_Destroy   Photon_SendAction   Photon_GetLastError
Photon_SetEventCallback  (колбэк отдаёт event_json)
Photon_StringData  Photon_StringLen  Photon_FreeString
Photon_BytesData   Photon_BytesLen   Photon_FreeBytes
```

То есть наружу отдаются: **исход вызова** (`PhotonResult` + конверт в
`response_json`), **текст последней ошибки** и **события** трёх типов —
`CONNECTED`, `MESSAGE`, `NETWORK_CHANGED` (ADR-045). Всё остальное —
`ports.Storage`, `Identity`, `Crypto`, `P2P`, `Transport`, Plugin Runtime —
публичного пути **не имеет**, и каталог действий это подтверждает: **60
значений `enum Action`, из них 59 реальных кодов** — целиком доменные (user,
channel, post, file, engram, wall, media), ни одного служебного. Прежняя
редакция называла 62: число было артефактом подстрочного совпадения — `grep`
по `.pb.go` ловил `REACTION_ADDED`/`REACTION_REMOVED` из `enum EventType` как
`ACTION_ADDED`/`ACTION_REMOVED`. Каноническое значение теперь читается
инструментом из дескриптора, а не пересчитывается вручную.

Поэтому ниже каждая лаборатория разделена на то, что **выполнимо сегодня**, и
то, что **требует будущей диагностической поверхности**. Второе — не
недоделка чек-листа, а честная граница: обещать доступ, которого нет,
значило бы проектировать C ABI под нужды дашборда.

#### Protobuf Inspector ✅

Не потребовал новых возможностей: только канонические определения и то, что
инструмент отправляет сам. Режим `--protobuf-inspector`, сети и native не
требует. ADR не заводился.

**Способ получения каталога — вариант C1:**
`photon.proto` → `protoc --descriptor_set_out --include_source_info` →
`FileDescriptorSet` → Inspector.

- [x] источник истины ровно один — `photon-core/protobuf/photon.proto`;
      дескриптор **выводится** из него задачей Gradle в `build/` и **не
      коммитится**: иначе появилась бы вторая вещь, способная отстать
- [x] `protoc` — предусловие среды, как `go` и `cc` (ADR-051). Отсутствие даёт
      внятный отказ задачи `checkProtoc` с указанием, чего не хватает, а не
      стек Exec-задачи — проверено прогоном с PATH без `protoc`
- [x] кодогенерация Java **не используется**: 154 файла и 3.2 МБ классов ради
      трёх enum'ов. Единственная зависимость — `protobuf-java:3.21.12`, ровно
      той версии, которой сгенерирован `photon.pb.go`
- [x] показываются `Resource` (8), `Action` (60 значений / 59 кодов),
      `EventType` (12), сообщения (75) с полями, типами и номерами, плюс
      комментарии схемы из source info
- [x] сверка контракта: коды, которые шлёт сам клиент, проверяются по
      каталогу. Магических чисел в коде инструмента больше нет — места
      отправки и проверка пользуются одним перечнем `UsedActions`
- [x] **8 тестов по содержимому**, а не по факту наличия файла: опорные
      номера каждого диапазона, состав `Resource`, доступность комментариев,
      75 сообщений, и структурная проверка — в исходниках инструмента **нет
      ни одного имени вида `ACTION_*`**, то есть второй копии каталога

**`EventType` схемы и типы событий подписки C ABI — разные словари, и
Inspector их разделяет.** В `photon.proto` имён `CONNECTED`, `MESSAGE`,
`NETWORK_CHANGED` нет вовсе (их источник — `photon_core.h`, ADR-045), а
`EventType` — доменные события Bridge. Inspector перечисляет только первый и
печатает врезку о втором: вписать его список руками значило бы завести ту
самую вторую копию, которой вариант C1 и избегает. Отдельный тест требует,
чтобы имена C ABI **не** оказались среди значений `EventType`.

- ⛔ инспектор **не является** новым транспортом и новым API: он показывает то,
      что прошло через `Photon_SendAction`, и ничего сверх

#### Logging 🟡 — выполнено всё, что не требует решения

Режим `--logging`. Имена действий берутся из канонического каталога
(FileDescriptorSet), своей таблицы у инструмента нет — проверяется тестом.

- [x] события `CONNECTED` / `MESSAGE` / `NETWORK_CHANGED` и журнал действий
      инструмента одним хронологическим потоком; порядок задаёт номер записи,
      а не отметка времени — у соседних записей она совпадает до миллисекунды
- [x] уровень **выводится из исхода**, а не назначается: `ok:true` — INFO,
      вердикт `ok:false` — WARN (вызов состоялся), несостоявшийся вызов —

- [x] фильтрация по источнику, уровню, компоненту и подстроке
- [x] корреляция «действие → событие» по доменному ключу (id поста) —

- [x] **7 тестов**, включая регрессию на дефект живого прогона

**Что нашёл живой прогон.** Push приходит в ту же миллисекунду, что и ответ
на вызвавшее его действие, и **иногда раньше**, чем ответ разобран:
подписное соединение независимо от action-соединения. Корреляция, ищущая
связь в момент прихода события, теряла её — цепочек было 0 при совпадающих
id. Переделано на соединение **после факта**: обе стороны запоминают ключ,
связь собирается при отчёте. В повторном прогоне `MESSAGE` записан раньше
`ACTION_CREATE_POST` — и цепочка всё равно собралась.

- [ ] ⛔ **централизованного лога ядра нет, и взять его неоткуда.** Разведка
      2026-09-11: во всём `photon-core` **ни одного** импорта
      `log`/`slog`/`logrus`/`zap` (кроме тестов), и среди десяти портов нет
      порта логирования. Прежняя формулировка здесь — «ядро пишет в свой
      логгер, наружу он не выведен» — **была неверна**: писать нечем.
      Появление такого потока означает сначала завести логирование в ядре
      (новый порт либо колбэк), то есть **архитектурное решение**, а не
      отсутствующую реализацию инструмента. Здесь оно не принимается
- ⛔ сквозного идентификатора запроса протокол не передаёт: в конверте push
      нет ни номера, ни версии (ADR-046). Корреляция возможна только по
      доменному ключу

#### Performance ✅

Режим `--performance`. Новых возможностей платформы не потребовал: только уже
существующие символы (`Photon_GetABIVersion`, `Photon_SendAction`) и обычные
средства ОС и JVM. ADR не заводился.

**Разделение слоёв опирается на факт из кода, а не на догадку:** неизвестный
код действия отсекается **локально**, в `services/session/resource.go`
(`ResourceFor` проверяет `photonpb.Action_name`), до того как что-либо уходит
в сеть. Отсюда три зонда, каждый добавляет ровно один слой.

- [x] задержка по слоям, перцентили nearest-rank (общая реализация с Network
      Lab — вторая запрещена тестом), обязательный прогрев перед каждым
      замером: без него измеряется работа JIT, а не путь
- [x] пропускная способность развёрткой потоков 1 → 2 → 4 → 8 с
      коэффициентом масштабирования
- [x] память: куча JVM и RSS процесса **раздельно**
- [x] **7 тестов**, включая проверки честности величин

**Измерено вживую** (150 замеров после прогрева, живой Bridge):

| зонд | что проходит | p50 |
|---|---|---|
| `abiVersion()` | JNI + cgo | **0.001 мс** |
| `sendAction(неизвестный код)` | + `c.mu`, диспетчер, валидация | **0.009 мс** |
| `sendAction(getMe)` | + QUIC + Bridge + Mattermost | **81.6 мс** |

**Главный вывод:** весь локальный путь Desktop → JNI → C ABI → Core стоит
**9 микросекунд — 0.011% полного вызова**. Граница JVM↔native не является
узким местом и близко; всё остальное — сеть и сервер.

Масштабирование: 1 поток 12.1 оп/с → 8 потоков 78.8 оп/с (**×6.53**),
сублинейно, потому что вызовы делят одно QUIC-соединение и один инстанс.
Память за прогон: куча JVM 6.4 → 16.4 МиБ, RSS 53 → 69 МиБ.

- ⚠️ **доля сети и сервера (81.6 мс, 100.0% полного) — ПРОИЗВОДНАЯ величина,**
      разность медиан двух разных вызовов. Измеренным RTT она не является:
      отделить сеть от работы сервера клиенту нечем. Отрицательной быть не
      может — «локальный дороже полного» означало бы шум измерения, и такой
      случай даёт ноль (проверено тестом)
- ⚠️ **RSS включает и кучу JVM, и память Go-ядра:** оно живёт в том же

      счётчики горутин), бенчмарки `ports.Storage` и `ports.Transport` в
      отрыве от действий
- ⛔ воспроизводимы **условия** замера (прогрев, число измерений, метод

#### Мост событий — реализован (первый шаг фазы)

Разведка до кода нашла то, на чём фаза встала бы посреди GUI: путь
`Compose Desktop → JNI → C ABI` **не нёс событий вовсе** — `SetEventCallback`
в мост выведен не был, хотя в C ABI существует с Phase 15.5. На событиях
стоят Dashboard и Logging.

Спецификация до кода — `photon-bindings/docs/jni-events.md`. Решения:
**D1** — синхронная доставка на потоке доставки ядра, без исполнителя и
очереди; **D2** — `AttachCurrentThread`/`DetachCurrentThread` на каждое
событие, `JNIEnv*` не кэшируется, постоянного присоединения нет;
**D4** — исключение слушателя фиксируется и гасится, доставка продолжается,
слушатель не отцепляется. **D3, D5, D6 остаются открытыми и молча не
приняты.**

Обоснование D1 оказалось не вкусовым: реентерабельный `Photon_Destroy`
опознаётся сравнением идентификаторов OS-потока, поэтому исполнитель JVM
сломал бы уже замороженное поведение. Обоснование D2 — факт из кода: насос
берёт `runtime.LockOSThread`, но снимает его через `defer`, поэтому поток
возвращается **в пул Go**, и постоянное присоединение накапливало бы
attached-потоки по одному на каждый созданный инстанс.

- [x] `jni/photon_jni.c` — мост событий; существующие функции не тронуты
- [x] `PhotonEventListener` + два `native`-объявления; `destroy(long)`
      сохранил сигнатуру
- [x] `Photon.kt` — `setEventListener`, освобождение контекстов **после**
      `Destroy`
- [x] `kotlin/PhotonEventsTest.kt` — **23 PASS, 0 FAIL** на живом Bridge,
      включая порядок событий, «доставки не параллельны», исключение
      слушателя, `close()` из колбэка и отсутствие вызовов после `close()`
- [x] **C ABI не изменён**: `photon_core.h` нетронут, `PHOTON_ABI_MAJOR`/
      `MINOR` = `1`/`0`; добавился ровно один линкуемый символ —
      `Photon_SetEventCallback`, уже существовавший в ABI

Размещение и сборка определены **ADR-051**; C ABI не затрагивается.

      `go build -buildmode=c-shared` **только в `photon-bindings/c/build/`**,
      затем `libphoton_jni.so` через `cc` с заголовками JDK
- [ ] запуск: `java.library.path` выставляет Gradle; ручной
      `LD_LIBRARY_PATH` из инструкции исчезает
- [ ] Dashboard в объёме Phase 16: версия ABI, состояние подписки по
      `CONNECTED` / `NETWORK_CHANGED`, журнал действий, различение
      `PhotonResult` и вердикта в конверте

Go и C-компилятор — документированные предусловия среды, а не то, что Gradle
добывает сам. Кроссплатформенная упаковка, публикация артефактов и релизы
этим шагом **не проектируются** (ADR-051, «что остаётся нерешённым»).

**Измеренное ограничение, записанное явно:** замена слушателя не освобождает
прежний контекст сразу — ABI не даёт дождаться уже начавшейся доставки со
старым `user_data`. N замен удерживают N `GlobalRef` до `close()`; проверено
на 200 (до `close()` живы все, после — ни одного). Безопасный момент раннего
освобождения выводится из последовательности доставок, но требует отдельного
решения и здесь не принят.

#### Public API constraint / future diagnostic surface

**C ABI v1.0 остаётся минимальным намеренно:** создание и уничтожение
инстанса, `SendAction`, события, последняя ошибка, версия ABI и помощники
управления памятью. Расширение возможностей идёт **внутрь `payload_json`
одного действия**, а не через рост числа экспортируемых символов — это прямо
записано в `photon_core.h` и является свойством контракта, а не привычкой.

**Developer Tools не обходят эту границу прямыми импортами внутренних пакетов
Photon Core.** Инструмент, дотянувшийся до `services/*`, `adapters/*` или
`ports/*` мимо C ABI, перестаёт быть первым настоящим клиентом и становится
вторым ядром: он начнёт проверять не то, чем пользуются приложения, а то, что
доступно только ему, — и расхождение между этими двумя картинами обнаружится
позже и дороже.

Если для полноценного Storage Inspector, статистики Transport, диагностики
криптографии, управления Plugin Runtime или профилирования потребуется новая
возможность, она появляется **отдельным архитектурным решением и публичным
API** — ADR, затем поверхность, затем инструмент. Не скрытой зависимостью
Developer Tools от внутренних пакетов и не действием, добавленным в каталог
ради красивого пункта в чек-листе.
