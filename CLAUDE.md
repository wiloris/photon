## Что это за проект

**Photon** — платформа (ядро, транспорт, плагины, безопасность).
**ENGRAM** — приложение поверх неё.

Разделение принципиально: если функциональность может понадобиться другому
приложению — она в Photon; если специфична для ENGRAM — она в ENGRAM или в плагине
(ADR-003).

## Метод работы (соблюдать)

Порядок, который сработал во всех завершённых фазах:

```
спецификация → код → тесты (включая failure-oriented) → IMPLEMENTATION_LOG → ROADMAP
```

**Спецификация до кода** — не формальность. `WIRE_FORMAT.md` перед `adapters/tcp`,
`sandbox.md` перед sandbox, `sdk-boundary.md` перед SDK. Обратный порядок даёт
протокол, повторяющий возможности выбранной библиотеки, а не модель системы.

**Failure-oriented тесты обязательны.** Три реальных бага Phase 9–10 найдены
тестами отказов, не ревью:
- double-free в `ipc.closeWith` при двойном вызове;
- вечное зависание `host.Stop` на неотвечающем плагине;
- воскрешение плагина после `Stop` во время backoff.

Ни один не проявлялся при нормальной работе.

**Тесты должны ловить нарушения.** Проверять это специально: сломать правило и
убедиться, что тест падает. Зелёный тест, который проходит всегда, хуже
отсутствующего.

**IMPLEMENTATION_LOG фиксирует «почему», а не «что»** — особенно то, что намеренно
не реализовано, и по какой причине.

## Границы, которые нельзя нарушать

Каждая закреплена ADR и проверена тестами. Нарушение — не стилистическая ошибка.

### ADR-020: порты заморожены

`photon-core/ports/*.go` не меняются без нового ADR. Четыре компонента подряд
(bbolt, ed25519, aesgcm, quic, tcp) реализованы без единой правки контракта — в том
числе TCP, где мультиплексирования нет вообще и его пришлось строить с нуля.

При желании изменить порт — сначала фильтр: (1) решается внутри адаптера?
(2) ограничение конкретной библиотеки или потребность ядра? (3) только потом ADR.

### ADR-030: `photon-core` не знает о плагинах

```
photon-core            ← ports.Authorizer (контракт)
     ▲
photon-plugin-runtime  ← реализация, manifest, sandbox
     ▲  (IPC, не импорт!)
photon-plugin-sdk
     ▲
  Plugin
```

### ADR-031: SDK не может обходить runtime

**Проверяется структурно, не тестом поведения:**
- `photon-plugin-sdk/go.mod` — **ни одного `require`**, только стандартная
  библиотека;
- не импортирует `photon-plugin-runtime` и `photon-core`;
- нет API для изменения собственных прав, состояния, жизненного цикла;
- нет «режима разработки», ослабляющего проверки.

Добавление запрещённого импорта **ломает сборку** раньше теста: зависимости нет в
`go.mod`, модуль не резолвится.

### ADR-032: маппинг «операция → право» в runtime

Таблица в `photon-plugin-runtime/ipc/operations.go`. В SDK её можно было бы
подменить — плагин объявил бы, что `storage.put` требует `storage.read`.

Три различимых исхода: известна+требует права / известна+без права / неизвестна →
`UNSUPPORTED`.

### ADR-021: приватный ключ не покидает устройство

Операции «получить приватный ключ» не существует и не будет. `identity.sign`
подписывает на стороне runtime.

## Что честно не проверено

Записывать такое явно — часть метода. Не «дореализовывать» молча:

| Не проверено | Причина |
|---|---|
| Android ARM/ART, native build | NDK/устройство недоступны |
| `photon-quic-bridge` целиком | Локальный Go 1.22 младше требуемого им 1.24.6 — собрать нечем; Mattermost не установлен |
| Valgrind/ASan для C ABI | Valgrind недоступен; leak-check сделан через RSS |
| Windows/macOS bindings | Нет toolchain |
| Sandbox P3/P4/P5/P8 | Требуют привилегий либо cgo между fork и exec |

## Полнота репозитория: что здесь неполное по замыслу

Прежде чем решить, что файлы потеряны — сверить с этим разделом.

### Документы верхнего уровня — только в корне

Пять документов — `CLAUDE.md`, `ARCHITECTURE.md`, `ROADMAP.md`,
`REPOSITORY.md`, `DECISIONS.md` — существуют в единственном экземпляре, в
корне репозитория. Дублировать их в подкаталоги (например, `photon-core/`)
нельзя: копия начинает отставать сразу же, молча, без единого сигнала об
этом — до аудита, который её найдёт и сверит цифры с оригиналом. Ровно так и
произошло: вложенная копия `CLAUDE.md`/`ROADMAP.md`/`DECISIONS.md` в
`photon-core/` разошлась с корнем по трём числам (32 ADR вместо 33,
compile-time проверки 3 из 9 вместо 6 из 9, «196 тестов» вместо актуальных к
тому моменту) и была удалена; следом за ней — `ARCHITECTURE.md` и
`REPOSITORY.md`, ещё не успевшие разойтись текстом, но неверные по смыслу:
оба описывают платформу целиком (`ARCHITECTURE.md` — plugin runtime,
транспорт, bindings, не только ядро; `REPOSITORY.md` — структуру всех
репозиториев), а не то, что специфично для `photon-core`. Формулировка
Phase 0 в `ROADMAP.md`, требовавшая «прикрепить» три из них в `photon-core`,
писалась для однорепозиторной структуры и с тех пор устарела — исправлена
там же.

`photon-core/` содержит только то, что относится к самому ядру — `docs/`,
`IMPLEMENTATION_LOG.md` внутри пакетов — не копии документов верхнего
уровня.

### `photon-quic-bridge/` — два разных дерева, и это важно различать

Есть **два** места с этим именем, и они находятся в разных состояниях.

**1. `~/projects/photon-quic-bridge/` — полный репозиторий, состояние ДО
ADR-025.** Отдельный репозиторий со своей историей, поэтому живёт отдельным
каталогом, а не внутри этого дерева. Один коммит `dc9418a "feat: core v0.3.0
stable"`, дерево чистое. Полный плагин Mattermost: `server/handler_*.go`,
`webapp/`, `build/`, `Makefile`, собранный `plugin-linux-amd64`.

**Переноса ADR-025 в нём нет.** `go.mod:1` — всё ещё
`module github.com/mattermost/mattermost-plugin-starter-template`,
`server/protocol.go:23-91` — action-коды объявлены литералами, `photonpb` не
импортируется, `test-client/` отсутствует.

**2. `photon-quic-bridge/` в этом дереве — четыре файла, единственное место, где
перенос ADR-025 существует:**

```
photon-quic-bridge/
├── go.mod                      ← переименован модуль
├── server/protocol.go          ← action-коды теперь алиасы на photon-core/protobuf
├── server/plugin.go            ← обновлены импорты
└── test-client/test_photon.go  ← есть ТОЛЬКО здесь
```

**Перенос ADR-025 — незакрытая задача, а не выполненная работа.** Прежняя
редакция этого раздела утверждала обратное («полный репозиторий существует,
развёрнут и работает», четыре файла — «то, что менялось в рамках ADR-025»).
Формально второе верно, но вместе они читались как «перенос применён к рабочему
репозиторию». Это не так: перенос сделан в песочнице, в изолированном проекте, и
до `~/projects/photon-quic-bridge/` не доехал. Что осталось сделать:

- применить четыре файла к полному репозиторию;
- заменить `replace github.com/wiloris/photon-core => /home/claude/photon-core-scaffold`
  и `replace google.golang.org/protobuf => /home/claude/protobuf-go`
  (`photon-quic-bridge/go.mod:68-72`) — это пути машины, где делался перенос, на
  любой другой машине мусор;
- проверить конфликт версий: подмножество требует `protobuf v1.34.2`, Mattermost
  SDK тянет `v1.36.10`. По MVS выиграет 1.36.10, но сборку надо прогнать;
- **не потерять `test-client/test_photon.go`** — в полном репозитории его нет.

Сборка Bridge **не проверена ни разу**, ни при переносе, ни сейчас: см.
«Расхождение окружений» ниже — локальный Go для него слишком старый. Прежняя
формулировка про «десятки транзитивных зависимостей» указывала не на ту причину.

**`test-client/test_photon.go` — не черновик, а рабочий референс.** Клиент
проверен против живого сервера и прогоняет все шесть ресурсов (48 вызовов
`action(...)`, `PostResource`/`UserResource`/`ChannelResource`/`EngramResource`/
`FileResource`/`WallResource`) плюс подписку на push. Он остаётся хорошим
источником о проводе, но **больше не единственным**: теперь есть сам сервер, и
при расхождении прав он. Разбор сервера уже дал то, чего в тест-клиенте нет:
handshake-ответ на самом деле `{"ok":true,"data":{"status":"ready"}}`, а не
`{"ok":true}` — тест-клиент это поле просто не читает. `photon.proto` в этом
вопросе неверен (объявляет `status` полем верхнего уровня), см. ADR-034 и
`photon-core/docs/bridge-session.md` §2.1.

Прямая зависимость тест-клиента от `quic-go` (`quic.DialAddr` напрямую, минуя
`ports.Transport`) — нормальна для клиента, проверяющего сервер, и **не образец
для Core**: код ядра ходит через порт (ADR-020).

Адрес и токен в `test_photon.go` (`anichavpn.ru:4443`) **неактуальны** — сервер,
против которого он гонялся, не существует. Диагностику сети по ним не делать.

### Развёртывание Bridge: две ловушки, которые стоят часов

Обе найдены разбором кода, обе тихие — плагин при них выглядит работающим.

**1. Отказ TLS не мешает активации, но роняет плагин при первом же сообщении.**

`server/plugin.go:75-81`: если `getTLSConfig` вернул ошибку, пишется `LogError` и
`OnActivate` возвращает **`nil`**. Плагин считается активированным, System
Console показывает его включённым, `p.quicListener` остаётся `nil`.

Дальше `server/hooks.go:20, 30, 44, 58, 71, 84, 98, 108` — каждый хук зовёт
`p.quicListener.Push(...)`, что даёт nil-dereference. `recover` в хуках нет.
**Первое же сообщение, отправленное любым пользователем Mattermost, роняет
процесс плагина.** То же на HTTP-входе: `server/api.go:67`.

Симптом («плагин падает при отправке сообщений») отстоит от причины («не нашёлся
сертификат») настолько, что искать будут где угодно. Поэтому:

> **Сразу после активации проверить лог на `[Photon] Failed to build TLS config`.**
> Признак успеха — `[Photon] QUIC listener bound` с `addr=:4443`
> (`quic_listener.go:207`).

**2. Сертификат Caddy процессу Mattermost не прочитать.**

`server/quic_listener.go:92-119` ищет сертификат в трёх местах по порядку:
Caddy по домену из `SiteURL` → любой домен в каталоге Caddy → 
`ServiceSettings.TLSCertFile`/`TLSKeyFile`. Каталог Caddy захардкожен:
`quic_listener.go:19`.

Caddy кладёт `certificates/` с правами `0600 caddy:caddy`. Читает их процесс
плагина, то есть пользователь Mattermost. Без добавления его в группу `caddy` и
`chmod g+rX` на дерево `tls.LoadX509KeyPair` (`:52`) вернёт permission denied,
**оба пути через Caddy молча провалятся**, останется только третий — а если
`TLSCertFile` не заполнен, сработает ловушка №1.

**Прочее по развёртыванию:**

- **Порт `:4443` — константа** (`quic_listener.go:18`), не настройка. QUIC — это
  **UDP**; в firewall нужен `udp/4443`, TCP не используется.
- **System Console не управляет ничем.** `plugin.json:18-28` содержит одну
  настройку `DebugMode`; `server/configuration.go:10-19` — три поля. **Ни одно
  не читается**: `getConfiguration()` (`configuration.go:26`) не вызывается во
  всём `server/`. Переключатель «Debug logging» не делает ничего,
  `SSEKeepAliveSec`/`ClientBufferSize` — остатки прежней SSE-реализации (буфер
  push-клиента захардкожен: `push.go:60`).
- `SiteURL` должен быть заполнен — от него зависит и поиск сертификата (`:94`), и
  построение URL файлов (`handler_file.go:183-191`).
- Сборка: `make dist`. Требует Go ≥ 1.24.6 **и** npm/node — цель `dist` зависит
  от `webapp` (`Makefile:278`), хотя webapp-бандл в `plugin.json` не объявлен.
- `plugin-linux-amd64` в корне репозитория — посторонний артефакт: `Makefile:262`
  берёт бинарники из `server/dist/`, туда он не попадёт.
- `README.md` — неправленый boilerplate starter-template. Про Photon, QUIC и
  сертификаты там нет ничего.

### Расхождение окружений: Core и Bridge не собираются вместе

| | `photon-core` | `photon-quic-bridge` |
|---|---|---|
| Go | 1.22.2 (`go.mod:3`) | 1.24.6, `toolchain go1.24.7` (`go.mod:3-4`) |
| quic-go | v0.48.2 | **v0.59.0** |

Это **разные поколения API** quic-go: в v0.48 `Connection`/`Stream`/`Listener` —
интерфейсы, в v0.59 — структуры-указатели, и сервер использует именно новую
форму (`quic_listener.go:171, 233, 300`).

Практические следствия:

- **Общий `go.work` для Core и Bridge не соберётся.** «Прогон против живого
  Bridge» — это два процесса на разных toolchain'ах, а не один проект.
- Локальный Go здесь — 1.22.12, то есть **Bridge в этой среде собрать нельзя**:
  `go build` упирается в `toolchain go1.24.7 not available`. Это, а не
  «недоступные зависимости Mattermost SDK», настоящая причина того, что сборка
  Bridge не проверялась ни разу.
- Требование «Go 1.22 обязателен» (см. «Замечания по окружению») относится
  **только к Core** и вызвано `syscall.SysProcAttr`. К Bridge оно не применимо и
  ему прямо противоречит.
- На проводе расхождение ничего не меняет: QUIC v1 с обеих сторон, ALPN
  `photon-quic-v1` совпадает.

### Пустые каталоги с `.gitkeep`

`photon-core/adapters/pion/`, `services/dispatcher/`, `security/permissions/`,
`security/signatures/`, `security/trust/`, `photon-plugin-runtime/tests/{ipc,
lifecycle,manifest,permissions}/` — намеренно пустые.

Для `security/*` причина в ADR-029: `signatures` и `trust` **не будут** созданы,
их ответственность уже принадлежит `Identity` и `services/account`.
`security/sandbox` удалён из `photon-core` по ADR-030 — sandbox живёт в
`photon-plugin-runtime`.

### `photon-bindings/`

`c/` — реализация есть (`photon.go`, `internal_cgo_types.h`, тесты, leak-check).
`android/` — Java/JNI/Kotlin есть, но **собранных `.so` нет**: они строятся из
исходников, а ARM-версии вообще не собирались (нет NDK).

## С чего продолжать (важно)

**Не с первой фазы, которая выглядит незакрытой в `ROADMAP.md`.** Порядок статусов
там не совпадает с порядком работы:

| Фаза | Выглядит как | На самом деле |
|---|---|---|
| Phase 0 🔲 | «не начата» | Структура каталогов существует; пункт закрывается сам собой по мере работы, отдельной задачи нет |
| Phase 1 🟡 | «недоделана» | Порты **заморожены** (ADR-020). Открыто: `docs/ports.md` и compile-time проверки для оставшихся 3 портов (`media`, `p2p`, `notification`) — они появятся вместе с первыми адаптерами этих портов, а не отдельной задачей |
| Phase 5 🟡 | «недоделана» | C ABI и JNI готовы и протестированы. Открытое — **Android ARM/ART**, требует NDK и устройства |
| Phase 7.5 ⏸️ | «отложена» | DEFERRED **с критерием возврата**. Не начинать без выполнения критерия (см. `ROADMAP.md`) |
| Phase 12 ⏸️ | «недоделана» | DEFERRED **с критерием возврата** (тот же формат, что у quic-go fork'а выше). Протокол перенесён в `photon-core/protobuf` (ADR-025) и работает; оставшиеся доменные сущности (`User`/`Message`/`Channel`/`File`) принадлежат ENGRAM/Bridge и не могут быть сведены к финальному виду без клиента, который бы ими пользовался — см. `ROADMAP.md` |
| Phase 12.5 ✅ | закрыта | Прогон против живого сервера выполнен. Открытое, что он оставил, — за рамками фазы: аварийный обрыв, непроверенный `KeepAlivePeriod` на сервере, буфер push на 64. Список — `bridge-session.md` §9 |

**Реально следующая задача — Phase 13** (Dispatcher). Phase 11 и 12.5 закрыты
(`ROADMAP.md`), Phase 12 отложена намеренно (см. выше).

Phase 12.5 заведена не «по порядку», а по находке discovery-прохода:
`Photon_Create` не подключается к серверу, и между `ports.Transport` и
Dispatcher нет слоя, знающего протокол. Начав Phase 13 первой, Dispatcher
пришлось бы писать открывающим стримы и пишущим в них JSON самостоятельно —
ошибка «код повторяет форму транспорта, а не модель системы».

Phase 13 после неё разблокирует три уже существующих открытых места
(`Photon_SendAction`'s заглушка, каталог операций SDK без настоящего
исполнителя, оговорка 🟡 у persistence в Phase 11), тогда как Phase 12 без
клиента добавила бы только предположения.

Общее правило: `🟡` и `⏸️` означают «частично сделано» или «сознательно отложено»,
а не «здесь работа». Прежде чем брать фазу — прочитать её раздел целиком: там
записано, что именно открыто и почему.

## Phase 11 закрыта

Все пять тестовых плагинов (`hello`, `crash`, `permission`, `storage`,
`stress`) реализованы и прошли — см. `ROADMAP.md` для полного описания и
`photon-plugin-runtime/IMPLEMENTATION_LOG.md` для деталей каждой находки.
Итог: пять плагинов нашли три реальных бага Phase 9 (`host.Stop()` убивал
процесс раньше времени, гонка порядка записи в `ipc.handshake()`, `kill()` не
использовал `Setpgid` несмотря на то, что тот специально проставлен) плюс
ловушку в публичном API SDK (дедлок `OnEvent`/`OnStop`) — все шесть на
границах, невидимых для in-process тестов Phase 9–10 (`fakeSpawner` и
`net.Pipe` не порождают процессов, не имеют кодов возврата, не воспроизводят
тайминги реального завершения). `crash`, `permission`, `storage` новых багов
не нашли — подтверждение достаточности правок по итогам `hello`, а не пустой
прогон.

Открыто: 🟡 «восстановление после сбоя» частично — persistence в
`storage`-тесте смоделирована, не проверена против настоящего `ports.Storage`.
Закроется вместе с Phase 13.

## Phase 12.5 закрыта

Сделано: **ADR-034** (JSON на проводе, protobuf как схема), спецификация
`photon-core/docs/bridge-session.md`, правки `photon.proto` и `photon_core.h`,
реализация `photon-core/services/session/` — **34 теста**, race чист,
`ports.Transport` не менялся (шестой компонент подряд без правки контракта).

**Прогон против живого сервера выполнен** (`vpn.wiloris.ru:4443`) и выполнен
именно `services/session`, а не только тест-клиентом Bridge: subscribe с
приёмом push, action (`getMe`), обрыв по idle-timeout. Всё через
`ports.Transport`/`adapters/quic`.

Требование прогона себя оправдало — `net.Pipe` не воспроизводит того, что
нашлось за первые минуты:

- **подписка умирает через 30 с простоя** (idle-timeout QUIC; keep-alive не
  слала ни одна сторона). Для action-соединения незаметно, для подписки тишина
  и есть норма — исправлено `KeepAlivePeriod: 15s` на сервере;
- **об обрыве не сообщала ни одна сторона**: переход `Ready → Failed` был
  обещан спецификацией и комментарием в коде, но не реализован нигде.
  Исправлено — `ErrConnectionLost`, тесты T-18;
- **`user_id` верхнего уровня в push обычно отсутствует** (`omitempty`, один
  хук из восьми); комментарий «пустой = широковещание» был неверен.

Открытое, что прогон оставил, — **за рамками фазы**, список в
`bridge-session.md` §9: аварийный обрыв в отличие от штатного idle-timeout,
непроверенный вживую `KeepAlivePeriod` на сервере (развёрнутый бандл собран до
этого коммита), буфер push на 64 события.

Phase 13 (Dispatcher) идёт следующей и разблокирует три уже существующих
открытых места:

- `Photon_SendAction` в C ABI возвращает заглушку «dispatcher (Phase 13) does
  not exist» — появится настоящий исполнитель;
- каталог операций (`storage.*`, `identity.*`, `crypto.*`) уже описан в
  `sdk-boundary.md` и проверен E2E, но исполняется тестовыми `Handler`'ами
  Phase 11, а не ядром;
- оговорка 🟡 у «восстановления после сбоя» в Phase 11 — persistence можно
  будет перепроверить против настоящего `ports.Storage`.

Подробное обоснование и полный список задач — `ROADMAP.md`, раздел Phase 13.

## Сборка после переноса: что нужно сделать один раз

**Модули не соберутся сразу — это ожидаемо, а не поломка.**

`photon-plugin-runtime` и `photon-plugin-sdk` ссылаются друг на друга и на
`photon-core` версией `v0.0.0`, которой нет ни в одном registry:

```
require (
	github.com/wiloris/photon-core v0.0.0
	github.com/wiloris/photon-plugin-sdk v0.0.0
)
```

`replace`-директивы были **намеренно убраны** перед переносом: они содержали пути
конкретной машины, где велась разработка, и на другой машине были бы мусором.

**Что сделать:** прописать `replace` на локальные пути (или `go.work`):

```sh
# в photon-plugin-runtime/go.mod
replace github.com/wiloris/photon-core => ../photon-core
replace github.com/wiloris/photon-plugin-sdk => ../photon-plugin-sdk
```

Внешние зависимости (`bbolt v1.3.11`, `quic-go v0.48.2`, `protobuf v1.34.2`,
`x/sys v0.23.0`) тянутся обычным способом при наличии интернета — версии выбраны
осознанно, см. «Замечания по окружению» ниже. **Не обновлять их произвольно**:
`bbolt` HEAD требует Go 1.25, `x/sys` ниже v0.23.0 не содержит `unix.UDP_SEGMENT`,
нужного `quic-go`.

**`photon-plugin-sdk/go.mod` не трогать.** Отсутствие в нём `require` — не
недоделка, а структурная гарантия ADR-031, проверяемая тестом
`TestADR031_NoModuleDependencies`. Добавление любой зависимости туда сломает тест,
и это правильное поведение.

## Правила первого запуска (аудит)

Первый запуск — **аудит, а не реализация**. Результат: отчёт о фактическом
состоянии и расхождениях с документацией, без изменений в проекте.

**Запрещено:**
- менять исходники, документацию, `ROADMAP.md`, `DECISIONS.md`;
- делать commit/push;
- устанавливать или удалять системные пакеты, менять конфигурацию системы;
- начинать реализацию Phase 11.

**Разрешено — иначе аудит невозможен:**
- `go build`, `go test`, `go vet`, `gofmt -l` (пишут в `go.sum` и кэш модулей —
  это нормально);
- добавление `replace`-директив, если без них сборка не идёт (см. раздел выше) —
  **с явным упоминанием в отчёте**, что было добавлено;
- создание временных файлов вне репозитория.

Различие существенно: без запуска тестов аудит становится сверкой документов между
собой, а не проверкой того, что код соответствует написанному.

**Отчёт должен ответить:**
1. Что физически присутствует в рабочем дереве.
2. Что соответствует документации, что нет.
3. Собирается ли код, проходят ли тесты (с числами).
4. Какие расхождения найдены.
5. Что действительно является следующей задачей.
6. Какие `replace`/побочные изменения пришлось внести для проверки.

## Замечания по окружению

- Go 1.22 обязателен **для Core и runtime**: `NoNewPrivs` отсутствует в
  `syscall.SysProcAttr` этой версии (проверено по исходникам — не предполагать
  наличие). На `photon-quic-bridge` это НЕ распространяется и прямо ему
  противоречит: он требует Go ≥ 1.24.6 и quic-go v0.59.0 — см. «Расхождение
  окружений: Core и Bridge не собираются вместе».
- `bbolt` брать `v1.3.11`; HEAD требует Go 1.25.
- `x/sys` — `v0.23.0`: `quic-go` использует `unix.UDP_SEGMENT`, которого нет в
  v0.4.0.
- Тесты `supervisor` идут ~6 с под `-race` — без явного таймаута прогон выглядит
  как зависание.
