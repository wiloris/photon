# AGENT_WORKFLOW.md — как агенты работают в этом репозитории

**Статус:** операционный документ. Не ADR и не источник архитектуры: здесь —
кто что делает, в каком порядке и как проверяется результат. Архитектура —
только в принятых ADR (`DECISIONS.md`) и спецификациях, на которые они
ссылаются.

---

## 1. Роли

| роль | что делает | чего не делает |
|---|---|---|
| **Человек / Codex** | принимает архитектурные решения и ADR; утверждает срезы и их порядок; даёт доступ к серверам | — |
| **Claude Session** | долгоживущий управляющий контур: читает текущее состояние, формирует задание на следующий срез, проверяет результат Claude Code, решает «принято / доработать / остановиться» | не принимает архитектурных решений; не расширяет утверждённый список срезов; не пишет production-код вместо Claude Code |
| **Claude Code** | основной исполнитель: реализует задание, запускает проверки, делает коммит после прохождения acceptance, отчитывается | не выходит за scope задания; не меняет принятые ADR; не трогает серверы без явного разрешения человека |

---

## 2. Источники истины — по порядку

1. **`DECISIONS.md` (корень)** — сквозной журнал ADR. Действуют только записи
   со статусом **ПРИНЯТО**; принятые записи не редактируются, изменение —
   новой записью-поправкой. `photon-quic-bridge/DECISIONS.md` — отдельный
   журнал серверных ADR с общей нумерацией (не копия корневого).
2. **Спецификации и implementation contracts**, на которые ссылаются ADR.
   Для групповых разговоров (900–931):
   - `photon-quic-bridge/docs/conversation-implementation-contract.md` —
     мост от ADR к коду: scope, поверхности, acceptance;
   - `photon-quic-bridge/docs/conversation-storage.md` — схема, шаги
     операций, блокировки, распределитель служебных команд (§6.0);
   - `photon-quic-bridge/docs/ap1-ordering-research.md` — исследование AP-1
     (основание ADR-101, ADR-102).
3. **`CURRENT_TASK.md`** — текущее состояние работы: сделанные срезы,
   следующий срез, открытые вопросы. При расхождении с другими документами
   **о текущей работе** прав `CURRENT_TASK.md`.
4. **`CLAUDE.md`** — точка входа и постоянные правила проекта (метод,
   границы, окружение, команды). Его сводные таблицы фаз и счётчики могут
   отставать от `CURRENT_TASK.md` — при расхождении о текущей работе прав
   `CURRENT_TASK.md`, об архитектуре — принятые ADR.
5. `ROADMAP.md`, `ARCHITECTURE.md`, `IMPLEMENTATION_LOG.md` пакетов — история
   и контекст решений.

Раздел CLAUDE.md «Правила первого запуска (аудит)» относится к прогону,
который явно назван аудитом. Обычная работа идёт по заданиям Session (§3).

---

## 3. Цикл работы

1. **Session** читает `CURRENT_TASK.md` (раздел «Сейчас») и contract
   следующего среза.
2. **Session** формирует задание Claude Code по шаблону §4. Следующий срез
   берётся **только** из утверждённого списка срезов в `CURRENT_TASK.md`.
   Срез вне списка, новый срез или изменение порядка — к человеку.
3. **Claude Code** реализует, запускает проверки §6, обновляет
   `CURRENT_TASK.md` (состояние среза) и делает **один коммит на срез** —
   только после прохождения acceptance.
4. **Claude Code** отчитывается: что сделано, решения реализации, проверки с
   числами, мутации, `git diff --check`, хеш коммита, `git status`.
5. **Session** проверяет отчёт по чек-листу §5 и решает: принято → следующий
   срез; доработать → уточнённое задание; конфликт → остановка (§7).

Session продолжает по следующему срезу без нового ручного промпта, пока
список срезов не исчерпан и не возникло условие остановки.

---

## 4. Шаблон задания Claude Code

```
Срез N — <название>
Источники: <ADR, разделы contract/спецификации>
Scope: <что реализуется>
Вне scope: <что не трогать: другие коды, ADR, proto, Android, 217/218, серверы>
Acceptance: <тесты и критерии из contract §6 / спецификации §10>
Проверки: <команды §6>, мутации для новых правил
Коммит: один, только файлы среза; CURRENT_TASK.md обновить
При противоречии с принятым ADR — остановиться и сообщить, не обходить кодом.
```

---

## 5. Чек-лист приёмки (Session)

- изменения в пределах scope; ADR, proto, Android и 217/218 не тронуты, если
  задание этого не предусматривало;
- все проверки §6 зелёные, кроме известных падений §8 — и отчёт явно отделяет
  их от новых;
- для каждого нового правила есть тест и **мутация**: правило ломается
  нарочно, тест падает (CLAUDE.md, «Тесты должны ловить нарушения»); мутация,
  которая не ловится, объяснена (эквивалентна на этом срезе или закрыта
  усилением теста);
- решения реализации, которых нет в ADR/спецификации, перечислены в отчёте;
- `git diff --check` чист; в коммите нет `privatekey`, `publickey`,
  локальных правок `CLAUDE.md`, секретов, бинарников;
- `CURRENT_TASK.md` отражает новое состояние.

## 6. Проверки

Из корня репозитория; каждая строка независима.

```sh
# photon-core
(cd photon-core && go build ./... && go vet ./... && go test -timeout 500s ./...)

# photon-plugin-runtime (supervisor медленный — таймаут обязателен)
(cd photon-plugin-runtime && go test -timeout 300s ./...)

# photon-plugin-sdk (структурные проверки ADR-031)
(cd photon-plugin-sdk && go test ./...)

# photon-bindings/c (cgo)
(cd photon-bindings/c && go test .)

# photon-quic-bridge: Go ≥ 1.24.6; GOTOOLCHAIN=auto подставит go1.24.7
(cd photon-quic-bridge && GOTOOLCHAIN=auto go vet ./... && GOTOOLCHAIN=auto go test -count=1 ./...)
```

**PostgreSQL-тесты Bridge** (DM v2 и разговоры 900–931) без
`PHOTON_DM_PG_DSN` пропускаются (`SKIP`). Запуск на временном PostgreSQL
18.3 — `tools/pgtest` (отдельный модуль, только для тестов):

```sh
(cd tools/pgtest && go build -o "${TMPDIR:-/tmp}/pgtest" .)
(cd photon-quic-bridge && "${TMPDIR:-/tmp}/pgtest" env GOTOOLCHAIN=auto go test -count=1 -run 'TestConv' ./server/)
(cd photon-quic-bridge && "${TMPDIR:-/tmp}/pgtest" env GOTOOLCHAIN=auto go test -count=1 -race -run 'TestConv' ./server/)
```

Первый запуск скачивает бинарники PostgreSQL (нужна сеть). Тесты работают во
временных схемах и удаляют их.

**Регенерация `photon.pb.go`** — только `protoc` 3.21.12 и `protoc-gen-go`
v1.34.2 (версии в заголовке файла); перегенерация из неизменённого `.proto`
обязана давать файл байт в байт.

**Сборка плагина Bridge** — `make apply` (генерирует `server/manifest.go`,
в git не входит), затем `MM_SERVICESETTINGS_ENABLEDEVELOPER=1 make server`.

## 7. Остановка и эскалация к человеку / Codex

Работа останавливается, вопрос передаётся с конкретикой (цитаты источников,
варианты, рекомендация), если:

- задание противоречит принятому ADR или спецификации;
- для реализации нужно решение, которое ADR оставил открытым или
  спецификация не задаёт (прецедент — распределитель служебных команд,
  conversation-storage.md §6.0: остановка, раздел спецификации, одобрение,
  код);
- падает тест, которого нет в §8;
- нужен доступ к серверу, развёртывание или изменение инфраструктуры;
- в изменениях оказываются секреты или чужие локальные файлы;
- срез не укладывается в утверждённый scope.

---

## 8. Известные падения, существовавшие до текущей работы

Не регрессия, если падение совпадает с описанием; любое другое падение —
новое.

| где | что | как отличить |
|---|---|---|
| `photon-quic-bridge/server` | `TestLostClaimDoesNotAllocateExtraReservation` (реестр ADR-077) — флейк в полном прогоне пакета, с `-race` и без (наблюдалось 2–5 из 8–10 прогонов); в изоляции не падает; на `8805e43` (до кода разговоров) падал так же | только этот тест; остальные зелёные |
| `photon-core/tests/p2pslice` | `TestCleanShutdownHalfClose` — редкое зависание до таймаута под нагрузкой полного прогона, в изоляции проходит (по записям; в последних прогонах не воспроизводилось) | таймаут именно этого теста |
| `photon-core/adapters/tcp` | `TestUniStream_ServerPush` — редкая паника «send on closed channel» (по записям) | именно эта паника |
| `photon-quic-bridge/server` | `gofmt -l` показывает `handler_file.go`, `handler_wall.go` — форматирование до текущей работы | только эти два файла |

Флейки — отдельные задачи; внутри среза их не чинят и не расследуют.

---

## 9. Коммиты

- один коммит на срез; ADR — отдельными коммитами (ПРЕДЛОЖЕНО → принятие);
  спецификация пишется до кода;
- сообщение: `тип(область): суть` по-русски (`feat(conversation): …`,
  `fix(…)`, `docs(adr): …`, `docs(bridge): …`), тело — что и почему,
  проверки, мутации;
- в конце — строка `Co-Authored-By: …` агента, сделавшего коммит;
- в коммит добавляются **только** файлы задания (`git add <файлы>`, не
  `git add -A`): локальные файлы владельца (`privatekey`, `publickey`,
  незакоммиченные правки `CLAUDE.md`) не трогаются;
- push в GitHub — по решению человека.

---

## 10. Серверы и секреты

- тестовые серверы и их назначение — в CLAUDE.md («Тестовая
  инфраструктура»); любые изменения на них — только по явному заданию
  человека;
- пароли, токены, session ID, приватные ключи и DSN с паролями в репозиторий
  не попадают; live-оснастка принимает их флагами или переменными окружения.
