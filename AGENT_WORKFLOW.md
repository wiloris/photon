# AGENT_WORKFLOW.md — как агенты работают в этом репозитории

**Статус:** операционный документ. Не ADR и не источник архитектуры: здесь —
кто что делает, в каком порядке, что важнее чего и когда остановиться.
Архитектура — только в принятых ADR (`DECISIONS.md`) и в спецификациях, на
которые они ссылаются. Этот документ ADR не пересказывает и не дополняет.

---

## 1. Роли

**Claude Code — главный исполнитель проекта.**
- исследует код в пределах задания;
- реализует утверждённые задачи: production-код, документацию, тесты;
- запускает проверки (§10);
- исправляет найденные им реализационные ошибки;
- делает коммиты — только после прохождения acceptance;
- отчитывается фактическим результатом: что сделано, проверки с числами,
  мутации, `git diff --check`, хеш коммита, `git status`.

**Claude Session — долгоживущий управляющий контур. Не архитектор и не
второй исполнитель.**
- читает состояние репозитория (§4);
- определяет следующий шаг **только** из утверждённого списка срезов в
  `CURRENT_TASK.md`;
- формирует конкретные задания Claude Code (§5);
- проверяет результат и контролирует acceptance (§8);
- при обычной реализационной ошибке сам возвращает Claude Code исправляющее
  задание (§6);
- после acceptance выбирает следующий утверждённый срез;
- не пишет production-код вместо Claude Code, не меняет ADR и спецификации,
  не придумывает новый roadmap.

**Человек / Codex — архитектура.** Принимают ADR, утверждают срезы и их
порядок, решают вопросы, по которым агенты остановились (§7), дают доступ к
серверам.

## 2. Иерархия источников истины

При конфликте более высокий уровень побеждает **всегда**. Нижний уровень не
меняет верхний ради удобства реализации: P0 и P1 агенты не правят, вопрос
уходит человеку (§7).

| уровень | что | где |
|---|---|---|
| **P0** | принятые ADR и архитектурные инварианты | `DECISIONS.md` — только записи со статусом **ПРИНЯТО**; изменение — новой записью-поправкой, принятые не редактируются. `photon-quic-bridge/DECISIONS.md` — отдельный журнал серверных ADR с общей нумерацией. Инварианты платформы — CLAUDE.md, «Границы, которые нельзя нарушать» |
| **P1** | утверждённые implementation contracts и спецификации, если не противоречат P0 | для групп 900–931: `photon-quic-bridge/docs/conversation-implementation-contract.md`, `photon-quic-bridge/docs/conversation-storage.md`; основание — `photon-quic-bridge/docs/ap1-ordering-research.md` |
| **P2** | acceptance criteria текущего среза | contract §6 и раздел среза в `CURRENT_TASK.md` |
| **P3** | текущий код и тесты — фактическое состояние реализации | дерево репозитория |
| **P4** | roadmap и следующий утверждённый срез | `CURRENT_TASK.md`, «Сейчас» |
| **P5** | технические улучшения, рефакторинг, предложения агентов | только как предложения в отчёте |

`CLAUDE.md` — точка входа и постоянные правила проекта (метод, окружение,
команды). Его сводки фаз и счётчики могут отставать: о текущей работе
сверяться с `CURRENT_TASK.md`, об архитектуре — с P0/P1. `ROADMAP.md`,
`ARCHITECTURE.md`, `IMPLEMENTATION_LOG.md` пакетов — история и контекст.

Раздел CLAUDE.md «Правила первого запуска (аудит)» относится только к
прогону, явно названному аудитом.

## 3. Приоритеты работы

| приоритет | что | правило |
|---|---|---|
| **0 — архитектурная целостность** | принятые ADR, инварианты, границы владения, протоколы, границы безопасности и доверия, границы Photon Core, правила ENSTOR, зафиксированные семантики | никогда не нарушать; если реализации нужно изменить P0/P1 — **STOP** (§7) |
| **1 — текущий утверждённый срез** | довести до acceptance | не переходить к следующему; ничего «заодно» |
| **2 — регрессии текущего среза** | новые падения тестов, гонки, непойманные мутации, нарушения acceptance, ошибки, вызванные текущими изменениями | исправлять; не превращать в общий cleanup |
| **3 — обязательная проверка** | проверки §10 и acceptance среза, `git diff`, `git status` | результат проверяем фактами, а не заявлением |
| **4 — следующий утверждённый срез** | только после acceptance текущего | Session формирует задание сам, из списка в `CURRENT_TASK.md` |
| **5 — проблемы, существовавшие до среза** | §11 и любые иные, доказуемо предшествующие срезу | не блокируют; фиксируются в отчёте как pre-existing; исправлять — только если срез от них зависит или человек поручил |
| **6 — улучшения** | рефакторинг, переименования, архитектурные улучшения, оптимизация без требования acceptance, UI polish, уборка несвязанных файлов | не выполнять; можно предложить отдельно |

## 4. Перед началом любой работы

Агент отвечает себе на семь вопросов — по репозиторию, а не по памяти:

1. Какой сейчас утверждённый срез? (`CURRENT_TASK.md`, «Сейчас»: первый
   незавершённый в списке утверждённых)
2. Какой у него точный scope?
3. Какие ADR и спецификации его определяют?
4. Каковы acceptance criteria?
5. Что обязательно?
6. Что явно вне scope?
7. Какие падения уже известны как pre-existing? (§11)

Нет ответа в репозитории — сначала читать документы. Не повторять
исследование, закрытое принятым ADR или contract; не исследовать Mattermost
заново без конкретного открытого вопроса; не искать альтернативную
архитектуру после принятого решения.

## 5. Цикл работы

**Алгоритм Session на каждом шаге:**

1. Определить состояние: последние коммиты (`git log`), `CURRENT_TASK.md`,
   нет ли незавершённого среза.
2. Ответить на вопросы §4.
3. Сформировать задание Claude Code по шаблону ниже.
4. Получить отчёт Claude Code и проверить его по §8, при необходимости
   повторив проверки §10 самостоятельно.
5. Решить:
   - **принято** → следующий утверждённый срез (шаг 1);
   - **реализационная ошибка** → исправляющее задание (§6);
   - **условие STOP** → вопрос человеку/Codex (§7), работа по срезу стоит.

Session продолжает без нового ручного промпта, пока список утверждённых
срезов не исчерпан и не возникло условие STOP. Срезы сверх списка, новые
срезы и изменение порядка — решение человека.

**Шаблон задания Claude Code:**

```
Срез N — <название>
Источники (P0/P1): <ADR, разделы contract/спецификации>
Scope: <что реализуется>
Вне scope: <другие коды/срезы, ADR, proto, Android, 217/218, серверы, улучшения>
Acceptance (P2): <тесты и критерии из contract §6 / спецификации §10>
Проверки: <команды §10>; мутации для каждого нового правила
Pre-existing: <§11>
Коммит: один, только файлы среза; CURRENT_TASK.md обновить в том же коммите
STOP: противоречие с P0/P1 — не обходить кодом, сообщить (§7)
```

**Claude Code** на задание: §4 → реализация → проверки §10 → обновление
`CURRENT_TASK.md` → коммит (если acceptance пройден) → отчёт.

## 6. Исправляющие задания

Обычная реализационная ошибка при ясной архитектуре — Session сам формирует
исправляющее задание Claude Code и не передаёт её человеку.

```
Исправление среза N
Найдено: <что не так, со ссылкой на P0/P1/P2 — например, «нет проверки
владельца ключа ADR-102 §2 перед поиском повтора»>
Ожидание: <какое поведение требует источник>
Проверка: <тест, который должен упасть до исправления и пройти после>
Scope: только это исправление; коммит — отдельный или вместе со срезом
```

Если исправление требует изменить P0 или P1 («для этого нужно поменять
ADR-102») — это не исправление, а **STOP** (§7).

---

## 7. STOP — вопрос человеку / Codex

Работа по срезу останавливается, если:

- найдено противоречие между ADR;
- contract или спецификация противоречат принятому ADR;
- реализация требует изменить принятую семантику;
- нужен новый архитектурный компромисс или решение, которое ADR оставил
  открытым, а спецификация не задаёт (прецедент — распределитель служебных
  команд, conversation-storage.md §6.0: остановка → раздел спецификации →
  одобрение человека → код);
- непонятно, какой из двух принятых документов актуален;
- обнаружено нарушение границы безопасности или доверия;
- есть риск потери данных или нарушения гарантий идемпотентности и порядка;
- нужен доступ к серверу, развёртывание или изменение инфраструктуры;
- в изменениях оказываются секреты или чужие локальные файлы.

Вопрос формулируется точно: что найдено, цитаты источников, варианты,
рекомендация. **Не угадывать правильный вариант.**

Не STOP, а исправляющее задание (§6) или pre-existing (§11): обычная ошибка
реализации, падение известного теста из §11.

---

## 8. Срез завершён, только если

- реализация соответствует contract (P1);
- acceptance tests проходят (P2);
- регрессионные проверки §10 проходят;
- для каждого нового правила есть тест и **мутация**: правило ломается
  нарочно, тест падает (CLAUDE.md, «Тесты должны ловить нарушения»);
  непойманная мутация объяснена — эквивалентна на этом срезе или закрыта
  усилением теста;
- pre-existing падения отделены от новых и названы;
- решения реализации, которых нет в P0/P1, перечислены в отчёте;
- `git diff` проверен: нет незапланированных изменений, вне scope ничего не
  тронуто; `git diff --check` чист;
- `git status` проверен: в коммите нет `privatekey`, `publickey`, локальных
  правок `CLAUDE.md`, секретов, бинарников;
- `CURRENT_TASK.md` отражает новое состояние;
- коммит создан только после всего перечисленного.

Только после этого Session переходит к следующему срезу.

---

## 9. Серверы и секреты

- тестовые серверы и их назначение — в CLAUDE.md («Тестовая
  инфраструктура»); любые действия на них — только по явному заданию
  человека (STOP, §7);
- пароли, токены, session ID, приватные ключи и DSN с паролями в репозиторий
  не попадают; live-оснастка принимает их флагами или переменными окружения.

## 10. Проверки

Из корня репозитория; каждая строка независима.

```sh
# photon-core
(cd photon-core && go build ./... && go vet ./... && go test -timeout 500s ./...)

# photon-plugin-runtime (supervisor медленный — таймаут обязателен)
(cd photon-plugin-runtime && go test -timeout 300s ./...)

# photon-plugin-sdk (структурные проверки ADR-031)
(cd photon-plugin-sdk && go test ./...)

# photon-bindings/c (cgo)
(cd photon-bindings/c && go test .)

# photon-quic-bridge: Go ≥ 1.24.6; GOTOOLCHAIN=auto подставит go1.24.7
(cd photon-quic-bridge && GOTOOLCHAIN=auto go vet ./... && GOTOOLCHAIN=auto go test -count=1 ./...)
```

**PostgreSQL-тесты Bridge** (DM v2 и разговоры 900–931) без
`PHOTON_DM_PG_DSN` пропускаются (`SKIP`). Запуск на временном PostgreSQL
18.3 — `tools/pgtest` (отдельный модуль, только для тестов):

```sh
(cd tools/pgtest && go build -o "${TMPDIR:-/tmp}/pgtest" .)
(cd photon-quic-bridge && "${TMPDIR:-/tmp}/pgtest" env GOTOOLCHAIN=auto go test -count=1 ./server/)
(cd photon-quic-bridge && "${TMPDIR:-/tmp}/pgtest" env GOTOOLCHAIN=auto go test -count=1 -race -run 'TestConv' ./server/)
```

Первый запуск скачивает бинарники PostgreSQL (нужна сеть). Тесты работают во
временных схемах и удаляют их.

**Регенерация `photon.pb.go`** — только `protoc` 3.21.12 и `protoc-gen-go`
v1.34.2 (версии в заголовке файла); перегенерация из неизменённого `.proto`
обязана давать файл байт в байт.

**Сборка плагина Bridge** — `make apply` (генерирует `server/manifest.go`,
в git не входит), затем `MM_SERVICESETTINGS_ENABLEDEVELOPER=1 make server`.

## 11. Известные падения, существовавшие до текущей работы

Не регрессия, если падение совпадает с описанием; любое другое падение —
новое (приоритет 2).

| где | что | как отличить |
|---|---|---|
| `photon-quic-bridge/server` | `TestLostClaimDoesNotAllocateExtraReservation` (реестр ADR-077) — флейк в полном прогоне пакета, с `-race` и без (наблюдалось 2–5 из 8–10 прогонов); в изоляции не падает; на `8805e43` (до кода разговоров) падал так же | только этот тест; остальные зелёные |
| `photon-core/tests/p2pslice` | `TestCleanShutdownHalfClose` — редкое зависание до таймаута под нагрузкой полного прогона, в изоляции проходит (по записям; в последних прогонах не воспроизводилось) | таймаут именно этого теста |
| `photon-core/adapters/tcp` | `TestUniStream_ServerPush` — редкая паника «send on closed channel» (по записям) | именно эта паника |
| `photon-quic-bridge/server` | `gofmt -l` показывает `handler_file.go`, `handler_wall.go` — форматирование до текущей работы | только эти два файла |

Флейки — отдельные задачи (приоритет 5); внутри среза их не чинят и не
расследуют.

## 12. Коммиты

- один коммит на срез; исправление — отдельным коммитом или в составе среза;
  ADR — отдельными коммитами (ПРЕДЛОЖЕНО → принятие); спецификация пишется до
  кода;
- сообщение: `тип(область): суть` по-русски (`feat(conversation): …`,
  `fix(…)`, `docs(adr): …`, `docs(bridge): …`), тело — что и почему,
  проверки, мутации;
- в конце — строка `Co-Authored-By: …` агента, сделавшего коммит;
- в коммит добавляются **только** файлы задания (`git add <файлы>`, не
  `git add -A`): локальные файлы владельца (`privatekey`, `publickey`,
  незакоммиченные правки `CLAUDE.md`) не трогаются;
- push в GitHub — по решению человека.
