# Разработка плагина Photon

Практическое руководство для того, кто пишет плагин, а не для того, кто пишет
платформу. Здесь только то, что уже работает и проверено настоящими процессами;
обещаний будущих возможностей в этом документе нет.

Архитектурные обоснования сюда не переписываются — на них стоят ссылки.

---

## Зрелость: на что можно опираться

**Stable v1 — можно писать код прямо сейчас**

- запуск плагина отдельным процессом и весь IPC — делает SDK;
- манифест: `plugin_id`, `version`, `protocol_version`, `entrypoint`;
- одиннадцать операций: `storage.*`, `identity.*`, `crypto.*`, `log.write`,
  `work.complete`;
- собственное хранилище плагина и его сохранность между запусками;
- подпись данных ключом устройства;
- доставка событий плагину, доклад о завершении работы и штатная остановка.

**Deferred — существует, но контрактом ещё не является**

- семантика `permissions.requested` против фактически выданных прав;
- `integrity` и политика доверия к пакету;
- изоляция сверх «отдельный процесс»;
- `instance_policy: multi`;
- соглашение об именовании исполняемого файла на Android;
- доменные события (каталога нет);
- обращение хоста к плагину с ответом (`host → plugin request/response`).

Пункты из второго списка **не следует закладывать в архитектуру плагина**: они
либо не реализованы, либо реализованы, но не закреплены.

## 1. Что такое плагин Photon

Плагин — **отдельный исполняемый файл**, который запускает **хост** и с которым
он разговаривает по стандартным потокам ввода-вывода. Плагин не является
библиотекой, не линкуется в приложение и не работает в его процессе.

```
приложение
   └── запускает  engram-plugin-host          ← продакшн-хост
            └── запускает  ваш плагин          ← отдельный процесс
                     ↕ IPC (stdin/stdout)
```

Пять вещей, которые нужно знать сразу:

| Понятие | Что это |
|---|---|
| **Хост** | `cmd/engram-plugin-host` — он запускает плагин, выдаёт права и исполняет его запросы |
| **SDK** | `photon-plugin-sdk` — единственное, что импортирует плагин. У модуля нет ни одной внешней зависимости (ADR-031) |
| **Манифест** | `manifest.json` — заявление плагина о себе: идентификатор, версия, точка входа |
| **PackageRoot** | каталог пакета плагина; `entrypoint` указывается **относительно него** |
| **plugin_id** | идентичность плагина: по нему выдаются права и называется его хранилище |

Плагин **не может** объявить себе права, изменить своё состояние в рантайме или
обойти хост: таблица «операция → право» живёт в хосте, а не в SDK (ADR-032), а
сам SDK физически не способен обратиться к ядру мимо него — в его `go.mod` нет
ни одного `require` (ADR-031).

## 2. Первый плагин

### 2.1 Модуль

```sh
mkdir hello && cd hello
go mod init example.com/hello
```

SDK подключается как обычная зависимость. Пока модуль не опубликован,
используйте `replace` на каталог с исходниками:

```
// go.mod
module example.com/hello

go 1.22

require github.com/wiloris/photon-plugin-sdk v0.0.0

replace github.com/wiloris/photon-plugin-sdk => ../photon/photon-plugin-sdk
```

### 2.2 Скелет плагина

Минимальный работающий плагин целиком:

```go
package main

import (
	"context"
	"fmt"
	"os"

	sdk "github.com/wiloris/photon-plugin-sdk"
)

func main() {
	ctx := context.Background()

	// 1. Подключение и handshake. Conn не задаётся: по умолчанию
	//    используются stdin/stdout — именно так хост запускает плагин.
	p, err := sdk.Connect(ctx, sdk.Config{
		PluginID:        "com.example.hello",
		ProtocolVersion: 1,
	})
	if err != nil {
		fmt.Fprintln(os.Stderr, "connect:", err)
		os.Exit(2)
	}

	// 2. Run ОБЯЗАН работать до первого вызова: он и доставляет ответы.
	//    Поэтому — в отдельной горутине.
	runDone := make(chan error, 1)
	go func() { runDone <- p.Run(ctx) }()

	// 3. Работа плагина.
	if err := p.Storage().Put(ctx, "state", "greeting", []byte("привет")); err != nil {
		fmt.Fprintln(os.Stderr, "put:", err)
		os.Exit(3)
	}
	value, err := p.Storage().Get(ctx, "state", "greeting")
	if err != nil {
		fmt.Fprintln(os.Stderr, "get:", err)
		os.Exit(4)
	}
	_ = p.Log(ctx, sdk.LogInfo, "прочитано: "+string(value))

	// 4. Работа закончена — докладываем. Это НЕ остановка: плагин
	//    продолжает жить, а решение о STOP принимает хост.
	if err := p.WorkComplete(ctx); err != nil {
		fmt.Fprintln(os.Stderr, "work complete:", err)
		os.Exit(5)
	}

	// 5. Ждём завершения сессии. Возврат Run без запроса остановки хост
	//    считает падением, а не чистым выходом.
	if err := <-runDone; err != nil {
		fmt.Fprintln(os.Stderr, "run:", err)
		os.Exit(6)
	}
}
```

Пункт 2 — не стилистика. `Run` читает входящие сообщения, включая ответы на
ваши собственные запросы; если его не запустить, первый же вызов `Storage()`
будет ждать ответа, которому неоткуда прийти.

Пункт 4 — тоже не формальность. Хост ждёт доклада, чтобы знать, что работу
можно прерывать: без него он остановит плагин, как только сочтёт нужным, и
незаконченная работа пропадёт. Подробности — раздел 5.

### 2.3 Манифест

Рядом с исходниками — `manifest.json`:

```json
{
  "manifest_version": 1,
  "identity": {
    "plugin_id": "com.example.hello",
    "version": "0.1.0"
  },
  "runtime": {
    "protocol_version": 1,
    "entrypoint": "hello",
    "instance_policy": "single"
  },
  "permissions": {
    "requested": ["storage.read", "storage.write"]
  }
}
```

`plugin_id` в манифесте и в `sdk.Config` обязаны совпадать: хост сверяет их при
handshake и закрывает сессию при расхождении.

### 2.4 Сборка и каталог пакета

`entrypoint` — путь **относительно корня пакета**, поэтому собирать надо внутрь
этого каталога:

```sh
mkdir -p /tmp/hello-pkg
go build -o /tmp/hello-pkg/hello .
```

Манифест может лежать где угодно — его путь передаётся хосту отдельно.

### 2.5 Запуск

```sh
mkdir -p /tmp/hello-data

engram-plugin-host \
  -db   /tmp/hello-data/engram.db \
  -keys /tmp/hello-data/keys \
  -manifest    ./manifest.json \
  -package-root /tmp/hello-pkg \
  -grants "storage.read,storage.write" \
  -init -install
```

Подробнее о каждом флаге — раздел 10.

## 3. Манифест

| Поле | Обязательно | Значение | Назначение |
|---|---|---|---|
| `manifest_version` | **да** | ровно `1` | версия формата самого манифеста |
| `identity.plugin_id` | **да** | `^[a-z0-9]+(\.[a-z0-9][a-z0-9-]*)+$`, минимум два сегмента | идентичность плагина: права, хранилище, handshake |
| `identity.version` | **да** | semver `1.2.3` | версия плагина; идентичность не меняет |
| `runtime.protocol_version` | **да** | ровно `1` | версия IPC-протокола, не версия плагина |
| `runtime.entrypoint` | **да** | относительный путь внутри `PackageRoot` | что запускать |
| `runtime.instance_policy` | нет | пусто или `single` | сколько экземпляров |
| `permissions.requested` | нет | имена вида `domain.action` | что плагин просит |
| `capabilities.provided` | нет | имена вида `domain.action` | что плагин умеет предоставлять |
| `integrity` | нет | `signature`, `signing_key_id` | метаданные подписи пакета |

Правила проверяет `manifest/validator.go`; полная спецификация формата —
`docs/manifest.md`.

**Честно о четырёх полях:**

- **`permissions.requested` сегодня декларативен.** Ни одна строка рабочего кода
  его не читает: фактические права приходят хосту флагом `-grants`. Указывать
  его всё равно следует — это заявление автора о потребностях плагина, и именно
  оно станет основой, когда появится выдача прав. Подробнее — раздел 7.
- **`capabilities.provided` участвует в handshake.** То, что плагин объявит в
  `sdk.Config.Capabilities`, обязано быть подмножеством объявленного здесь,
  иначе сессия закрывается (`ipc/session.go`). Но **вызвать** объявленную
  capability сегодня некому: направления «хост просит плагин» в протоколе нет.
  Пустое поле означает, что плагин не вправе объявить ни одной capability.
- **`integrity` — пока структурное поле.** Валидатор проверяет форму, но **не
  проверяет подпись**: кто вправе подписывать плагины и каким ключам доверять,
  не решено (`manifest/types.go`, `docs/manifest.md` §5).
- **`instance_policy: multi` не поддерживается** и отвергается явно, а не
  выполняется молча в режиме `single` (`manifest/types.go`).

**`entrypoint` — относительный путь, а не имя программы.** Абсолютные пути,
`..` и символические ссылки за пределы корня отвергаются валидатором. Имя файла
ничем не ограничено — **кроме Android**, см. раздел 11.

## 4. SDK

Импортируется один пакет; весь публичный API — в `photon-plugin-sdk/api.go`.

### Жизненный цикл

| Вызов | Что делает |
|---|---|
| `sdk.Connect(ctx, cfg) (Plugin, error)` | устанавливает сессию и выполняет handshake. `Conn` в `Config` не задавайте: по умолчанию stdin/stdout, как и запускает хост |
| `p.Run(ctx) error` | обслуживает сессию: читает сообщения, доставляет ответы и события. Запускайте **в горутине до первого вызова**. Возвращается, когда хост закрыл соединение или запросил остановку; переподключения нет |
| `p.OnEvent(handler)` | регистрирует обработчик событий |
| `p.OnStop(handler)` | регистрирует обработчик штатной остановки |
| `p.Close() error` | завершает сессию со стороны плагина |

`Config`: `PluginID`, `ProtocolVersion` — обязательны и сверяются с манифестом;
`Capabilities` — необязательны, ограничены манифестом.

### Storage

Все вызовы — `p.Storage()`.

| Вызов | Операция | Право | Возвращает и чем отказывает |
|---|---|---|---|
| `Get(ctx, ns, key)` | `storage.get` | `storage.read` | значение; **`ErrNotFound`**, если ключа нет |
| `Put(ctx, ns, key, val)` | `storage.put` | `storage.write` | ошибку или `nil` |
| `Delete(ctx, ns, key)` | `storage.delete` | `storage.write` | удаление отсутствующего ключа — **не ошибка** |
| `List(ctx, ns, prefix)` | `storage.list` | `storage.read` | список ключей с префиксом |

### Identity

| Вызов | Операция | Право | Примечание |
|---|---|---|---|
| `PublicKey(ctx)` | `identity.public_key` | `identity.read` | публичный ключ устройства |
| `Sign(ctx, data)` | `identity.sign` | `identity.sign` | подпись выполняется **хостом**; приватного ключа плагин не получает (ADR-021) |
| `Verify(ctx, pk, data, sig)` | `identity.verify` | `identity.read` | неверная подпись — это `(false, nil)`, **а не ошибка** |

### Crypto

| Вызов | Операция | Право | Примечание |
|---|---|---|---|
| `Encrypt(ctx, plaintext, binding)` | `crypto.encrypt` | `crypto.use` | `binding` аутентифицируется, но не шифруется; нечего привязывать — `nil` |
| `Decrypt(ctx, ciphertext, binding)` | `crypto.decrypt` | `crypto.use` | любая причина сбоя — **`ErrDecryptionFailed`**, без уточнения |

Ключ выводит хост по домену плагина; выбрать или увидеть его нельзя — поэтому
один плагин не расшифрует данные другого.

### Журнал

`p.Log(ctx, level, message)` — операция `log.write`, права **не требует**:
плагин должен уметь сообщить о проблеме, даже не получив ничего
(`docs/sdk-boundary.md` §3). Уровни: `LogDebug`, `LogInfo`, `LogWarn`,
`LogError`.

### Доклад о завершении работы

`p.WorkComplete(ctx)` — операция `work.complete`, тоже **без права**
(ADR-072).

Означает: **«текущая единица работы, ради которой хост ведёт этот жизненный
цикл, завершена»**. Чем она не является — перечислено, потому что каждое из
этого выглядит правдоподобно и неверно:

| Не является | Почему |
|---|---|
| командой остановиться | решение о `STOP` принимает **только хост** |
| завершением плагина | после доклада плагин продолжает работать и обязан дождаться `STOP` |
| закрытием сессии или процесса | ни `Close`, ни `os.Exit` доклад не выполняет |
| однократным событием | **вызов повторяем**: обработали событие — доложите снова |

Права не требует по той же причине, что и `Log`: плагин, которому не выдали
ничего, обязан остаться управляемым. Иначе «право не выдано» означало бы «хост
не дождётся завершения», то есть зависание вместо отказа.

Полный каталог операций и их прав — `ipc/operations.go`, описание —
`docs/sdk-boundary.md` §3.

## 5. Жизненный цикл и главная ловушка

```
Connect            установление сессии, HELLO / HELLO_ACK
   ↓
Run                работает всё время жизни плагина
   ↓
работа             ваши REQUEST → RESPONSE хоста
   ↓
WorkComplete       ВЫ докладываете: текущая работа закончена
   ↓
хост решает        например: прислать событие — или остановить
   ↓
[EVENT → работа → WorkComplete]        столько раз, сколько событий
   ↓
STOP               хост попросил остановиться
   ↓
OnStop             ваш обработчик; время ограничено хостом
   ↓
STOP_ACK           отправляет SDK, не вы
   ↓
завершение процесса
```

Кто чем распоряжается: **запуск, события и остановку инициирует хост; работу и
доклад о её завершении — плагин**. Плагин не останавливает себя сам: процесс,
ушедший до `STOP`, классифицируется как падение, а не как штатный выход.

**Кадры протокола вы не пишете.** HELLO, HELLO_ACK, REQUEST, RESPONSE, EVENT,
STOP, STOP_ACK, CANCEL — всё это формирует и разбирает SDK. Ваш код — это
`Connect`, `Run`, обработчики и вызовы API.

### Ловушка: обработчики выполняются в потоке `Run`

`OnEvent` и `OnStop` вызываются **синхронно тем же потоком**, который читает
ответы на ваши запросы. Блокирующий вызов SDK прямо из обработчика поэтому
зависает: ответу неоткуда прийти, пока `Run` занят обработчиком.

SDK ловит этот случай и возвращает **`ErrReentrantCall`** вместо зависания —
**но только если вызов использует переданный обработчику `ctx`** (или его
потомок). Подмена на `context.Background()` обходит проверку, и вызов зависнет
молча (`api.go`).

Правильный приём — обработчик только сигналит, работа идёт снаружи:

```go
reports := make(chan struct{}, 8)

p.OnEvent(func(_ context.Context, ev sdk.Event) error {
	if ev.Type == "com.example.hello.report" {
		select {
		case reports <- struct{}{}:
		default: // сигнал уже есть, второй в очередь не нужен
		}
		return nil
	}
	return nil
})

go func() { runDone <- p.Run(ctx) }()

for {
	select {
	case <-reports:
		value, err := p.Storage().Get(ctx, "state", "greeting") // вне обработчика
		...
	case err := <-runDone:
		return
	}
}
```

Так устроен `examples/counter`, и по этой же причине.

## 6. Хранилище

У плагина есть **собственное пространство имён**, и назначает его хост:
`plugin.<plugin_id>` (ADR-068 §4). Плагин это пространство не выбирает и не
видит.

Параметр `namespace` в вызовах — **суффикс внутри собственного пространства
плагина**, а не произвольное пространство ядра:

```go
p.Storage().Put(ctx, "state", "count", []byte("1"))
//                    ^^^^^^^ ваш суффикс; хост подставит префикс сам
```

Обратиться к данным другого плагина невозможно — не потому, что SDK это
проверяет, а потому что префикс подставляет хост (`docs/sdk-boundary.md` §3).

**Сохранность.** Данные переживают завершение процесса: следующий запуск
плагина видит то, что записал предыдущий. Это проверено сквозным прогоном на
настоящих процессах, в том числе на Android.

**Что не является частью контракта:** чем хранилище реализовано внутри. Ключи и
значения — байты; никаких транзакций, итераторов и запросов сверх
`Get/Put/Delete/List` плагину не предоставляется.

## 7. Права — раздел, который важно прочитать целиком

**Существующие права** (полный список, `ipc/operations.go`):

| Право | Что открывает |
|---|---|
| `storage.read` | `storage.get`, `storage.list` |
| `storage.write` | `storage.put`, `storage.delete` |
| `identity.read` | `identity.public_key`, `identity.verify` |
| `identity.sign` | `identity.sign` |
| `crypto.use` | `crypto.encrypt`, `crypto.decrypt` |
| — | `log.write` и `work.complete` права не требуют |

Проверка **точная**: `storage.read` не даёт `storage.write`
(`permissions/policy.go`). Отказ приходит плагину как **`ErrForbidden`**.

**Как права выдаются сегодня — честно:**

1. Плагин объявляет `permissions.requested` в манифесте. Это **заявление о
   намерении**, и сегодня **никто его не читает**.
2. Фактические права хост получает **флагом `-grants`** при запуске.
3. Проверки «выданное ⊆ запрошенного» **нет**.
4. Выданные права **не сохраняются** между запусками: их нужно передавать при
   каждом запуске.

**Что это значит для вас:** плагин может получить право, которого не просил, и
не получить права, которое просил, — и узнает об этом только по `ErrForbidden`
в рантайме. Поэтому: **обрабатывайте отказ по праву как штатный исход**, а не
как сбой. `examples/counter` так и делает — без `identity.sign` он продолжает
считать и сообщает об отсутствии подписи в журнал.

Это неудобно для разработчика, и это признаётся прямо. Контракт зафиксирован
**ADR-073**: манифест объявляет, вызывающий выдаёт, runtime проверяет на каждый
запрос, persistence в v1 нет. Проверка «выданное ⊆ запрошенного» и экран
согласия пользователя — post-v1: сегодня и манифест, и права задаёт один и тот
же человек, и проверять их друг против друга не для кого.

## 8. События

**Механизм есть, каталога нет.**

Хост может доставить плагину событие: тип (строка) и непрозрачное тело
(`sdk.Event`). Доставка **последовательная, по одному событию за раз**;
возвращённая обработчиком ошибка логируется, но доставку следующих событий не
отменяет — событие уже произошло.

**У события нет подтверждения доставки, и его не будет.** Подтверждением того,
что событие **обработано**, служит ваш доклад:

```
EVENT  →  работа плагина  →  WorkComplete  →  хост решает, что дальше
```

Доклад здесь — не конец жизни плагина, а конец **этой** единицы работы: хост
вправе прислать следующее событие или остановить плагин.

Чего нет:

- **универсального каталога событий** — какие типы существуют, не описано
  нигде, потому что их перечень не определён;
- **доменных событий платформы** — `chat.*`, `user.*` и подобное относятся к
  приложению и Bridge, а не к ядру (`docs/sdk-boundary.md`);
- **ответа на событие** — событие одностороннее.

Практический вывод: пока события полезны как **сигнал от вызывающего вашему
плагину**, и тип события — это соглашение между ними. `counter` реагирует на
собственную строку `engram.counter.report`, которую ему передают при запуске, и
после обработки докладывает `WorkComplete`.

## 9. Ошибки и типичные ловушки

| Ошибка | Когда | Что делать |
|---|---|---|
| `ErrNotFound` | `Storage().Get` по отсутствующему ключу | **не ошибка логики**: обычно это первый запуск |
| `ErrForbidden` | право не выдано | штатный исход, см. раздел 7 |
| `ErrDecryptionFailed` | `Crypto().Decrypt` | причина не уточняется намеренно: реакция одна |
| `ErrReentrantCall` | блокирующий вызов из `OnEvent`/`OnStop` | вынесите работу из обработчика |
| `ErrSessionClosed` | сессия закрыта | переподключения нет — завершайте процесс |
| `ErrUnsupported` | операция неизвестна хосту | проверьте версию протокола |
| Несовпадение `plugin_id` | `sdk.Config` ≠ манифест | сессия закрывается при handshake |
| Несовпадение версии протокола | `protocol_version` ≠ 1 | валидатор отвергает манифест |
| `entrypoint does not exist` | файл не собран в `PackageRoot` | соберите бинарь внутрь каталога пакета |
| Манифест не разбирается | синтаксис или неизвестное поле `required_*` | см. `docs/manifest.md` §6 |
| «плагин не доложил о завершении работы» | плагин не вызвал `WorkComplete` за отведённое `-timeout` | доложите по окончании работы — см. раздел 5 |

Полный перечень ошибок — `photon-plugin-sdk/errors.go`.

## 10. Сборка и запуск

```sh
engram-plugin-host \
  -db   <файл хранилища> \
  -keys <каталог ключей> \
  -manifest     <файл манифеста> \
  -package-root <корень пакета> \
  -grants "storage.read,storage.write,identity.sign" \
  [-init] [-install] [-events "тип1,тип2"] [-timeout 15s]
```

| Флаг | Значение |
|---|---|
| `-db` | файл хранилища. **Один и тот же путь между запусками** — плагин видит своё прежнее состояние; другой путь — не видит |
| `-keys` | каталог ключевого материала; по умолчанию — каталог хранилища |
| `-manifest` | путь к манифесту плагина. Источник истины для `plugin_id` и `entrypoint` (ADR-071) |
| `-package-root` | корень пакета; `entrypoint` из манифеста отсчитывается от него |
| `-grants` | права, выдаваемые плагину; см. раздел 7 |
| `-init` | **только для первого запуска**: создать идентичность устройства. На существующей — ошибка, а не «ничего не делать» (ADR-069) |
| `-install` | **только для первого запуска**: зарегистрировать плагин. Без регистрации запуск отвергается — установка является явным событием (ADR-068 §6.2) |
| `-events` | события, отправляемые плагину после старта |
| `-timeout` | предел ожидания доклада плагина |

Есть и режим `-plugin <путь к бинарю>` — он выводит корень и точку входа из
пути и манифеста не требует. Он взаимоисключающий с `-manifest` и существует
для локальных прогонов.

> **Эти флаги — сегодняшний способ запуска, а не стабильный публичный
> интерфейс.** Контрактом зафиксирован способ передачи манифеста и корня
> (ADR-071); остальные флаги могут измениться вместе с композицией хоста.

### Чего хост ждёт от плагина

Ровно одного: **доклада `WorkComplete` по окончании работы** — и, если заданы
`-events`, ещё по одному докладу на каждое обработанное событие. Без доклада
запуск завершится ошибкой «плагин не доложил о завершении работы» по истечении
`-timeout`.

Никаких требований к содержимому журнала у хоста нет.

> **Если вы читали раннюю редакцию этого руководства:** там было сказано, что
> продакшн-хост ждёт строку `count:<число>` и без неё отказывает. Это было
> правдой и перестало ею быть с ADR-072: `count:` был форматом журнала
> `examples/counter` и служил хосту барьером синхронизации. Теперь барьер —
> явная операция `work.complete`, а `count:` не влияет ни на успех запуска, ни
> на момент остановки.

## 11. Android

Доказанный путь:

```
plugin APK
   ↓ установка средствами Android
nativeLibraryDir пакета плагина        ← PackageRoot
   ↓
приложение запускает продакшн-хост
   ↓
процесс плагина
```

Что зафиксировано (ADR-070):

- **плагин поставляется отдельным APK**; один APK — один плагин;
- **исполняемый файл лежит в `nativeLibraryDir`** — единственном каталоге, из
  которого Android разрешает исполнение;
- **копия в каталоге данных не используется и не может быть использована**:
  исполнение оттуда запрещено политикой платформы;
- **`PackageRoot` получается при каждом запуске и не сохраняется**: путь
  меняется при каждом обновлении APK;
- **корень пакета доступен только на чтение** — пишите в своё хранилище;
- **манифест** временно материализуется приложением в файл, чтобы передать его
  хосту через `-manifest`, и удаляется после завершения хоста.

**Соглашение об именовании исполняемого файла на Android пока не закрыто**
(ADR-070 §12). Практически: имя должно быть таким, чтобы упаковщик APK положил
файл в `lib/<abi>/`. До принятия соглашения ориентируйтесь на существующий
пример пакета плагина.

## 12. Безопасность: минимум, который нужно знать

- **Приватный ключ устройства плагину не выдаётся** — такой операции нет и не
  будет (ADR-021). `Identity().Sign` выполняет подпись **на стороне хоста**.
- **Подписываемые данные доменно разделены** по `plugin_id`: подпись, сделанную
  для одного плагина, нельзя предъявить от имени другого (ADR-037).
- **Хранилище и ключ шифрования — свои у каждого плагина**; доступ к чужим
  данным невозможен по построению, а не по проверке в SDK.
- **Права проверяются на каждый запрос** на стороне хоста; отказ приходит
  `ErrForbidden`.
- **Плагин — отдельный процесс.** Память приложения ему недоступна.

Чего **не** обещано: изоляция сверх отдельного процесса. Ограничения ресурсов,
сетевые ограничения и прочие механизмы песочницы существуют в коде, но **ни
одна текущая композиция их не включает** (`docs/sandbox.md`). Не полагайтесь на
них.

## 13. Чего плагин сегодня не может

| Нельзя | Пояснение |
|---|---|
| Ходить в сеть | домена `network.*` в каталоге операций нет |
| Быть вызванным хостом | направление «хост → плагин с ответом» в протоколе отсутствует; есть только односторонние события |
| Устанавливать и удалять пакеты | установка — дело платформы, не плагина |
| Перечислять установленные плагины | API обнаружения нет |
| Полагаться на проверку подписи пакета | `integrity` не проверяется |
| Управлять своими правами и жизненным циклом | запрещено (ADR-031) |
| Запускаться в нескольких экземплярах | `instance_policy: multi` отвергается |
| Рассчитывать на песочницу | см. раздел 12 |
| P2P, медиа, уведомления | адаптеры есть, операции для плагинов не спроектированы |

Список неприятный, но точный. Он нужен именно затем, чтобы плагин не
проектировался вокруг возможностей, которых нет.

## 14. Как получить новый домен операций

Если вашему плагину нужна возможность, которой нет, порядок известен и жёсток
(`docs/sdk-boundary.md`, «Порядок добавления домена операций»):

```
конкретный потребитель  →  модель прав  →  ADR  →  спецификация и маппинг
                        →  реализация   →  тест настоящим процессом
```

Ключевое правило оттуда: **домен добавляется по потребности, а не по плану**.
«Полезно иметь» и «адаптер всё равно есть» потребителем не считаются. Первый
пункт — назвать плагин и задачу, которым операция нужна **сейчас**.

## 15. Пример для сверки: `counter`

`examples/counter` — первый настоящий плагин, написанный только на публичном
SDK. Не шаблон и не фреймворк: смотреть на него стоит как на образец приёмов.

| Код плагина | API SDK | Операция | Что делает хост |
|---|---|---|---|
| `sdk.Connect(ctx, Config{PluginID, ProtocolVersion})` | `Connect` | HELLO/HELLO_ACK | сверяет `plugin_id` и версию с манифестом |
| `go func() { p.Run(ctx) }()` | `Run` | — | ведёт сессию, доставляет ответы и события |
| `p.Storage().Get(ctx, "state", "count")` | `Storage.Get` | `storage.get` | проверяет `storage.read`, читает из namespace плагина |
| `p.Storage().Put(ctx, "state", "count", …)` | `Storage.Put` | `storage.put` | проверяет `storage.write`, пишет туда же |
| `p.Identity().Sign(ctx, value)` | `Identity.Sign` | `identity.sign` | подписывает ключом устройства с доменным разделением |
| `p.Log(ctx, sdk.LogInfo, "count:"+value)` | `Log` | `log.write` | права не требует; строка попадает в журнал хоста |
| `p.WorkComplete(ctx)` | `WorkComplete` | `work.complete` | фиксирует доклад и решает, слать событие или останавливать |
| `p.OnEvent(…)` — только сигнал в канал | `OnEvent` | — | доставляет событие синхронно, см. раздел 5 |

Отсутствие права `identity.sign` counter обрабатывает как штатный исход:
продолжает считать и пишет предупреждение в журнал.

**Про строки `count:` и `signature:`.** Это **диагностические данные
reference-прогона**, а не часть контракта плагина. Продакшн-композиция читает
их, чтобы показать в отчёте счётчик и проверить подпись ключом устройства; на
успех запуска и на момент остановки они не влияют, и ни одна платформенная
часть — `host`, `ipc`, `coreops`, SDK — о них не знает. Своему плагину
придумывать похожие строки незачем: барьером служит `WorkComplete`.

## ENSTOR и будущие расширения платформы

ENSTOR — магазин расширений — по этой модели может быть **обычным плагином**,
и это полезная проверка контракта: если он собирается без особых прав, без
внутренних импортов Photon и без обходных путей, значит API плагина
действительно сложился.

Сегодня для него уже есть: хранилище каталога (`storage.*`), проверка подписей
как криптографическая операция (`identity.verify`), шифрование локальных данных
(`crypto.*`).

Сегодня для него **нет двух вещей**:

- **сетевых операций** — домена `network.*` в каталоге не существует;
- **обращения приложения к плагину с ответом** — в протоколе есть только
  односторонние события.

Поэтому ENSTOR становится **первым законным потребителем** по процедуре
раздела 14: именно он должен сформулировать, какие расширения контракта нужны,
и пройти путь «потребитель → модель прав → ADR → реализация → тест». Настоящий
документ этих расширений не проектирует и не предрешает.
