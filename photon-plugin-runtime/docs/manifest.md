# Plugin Manifest Specification

Спецификация манифеста плагина для `photon-plugin-runtime`. Написана **до** кода
загрузчика — тот же порядок, что сработал с `adapters/tcp` (`WIRE_FORMAT.md` до
реализации).

Опирается на:
- `docs/plugin-threat-model.md` — манифест есть **запрос**, а не разрешение
- `docs/plugin-lifecycle.md` — раздел 11 выводит обязательные поля из модели
  жизненного цикла
- ADR-030 — манифест целиком принадлежит Runtime; `photon-core` о нём не знает

---

## Основной принцип

> **Манифест описывает идентичность, совместимость и намерения плагина.
> Фактические возможности определяет Runtime.**

Манифест — часть пакета плагина, то есть данные, предоставленные недоверенной
стороной. Всё, что в нём написано, — это заявление автора плагина, а не факт.
Реализация, трактующая манифест как источник полномочий, ломает базовый инвариант
threat model.

---

## Структура

```
manifest
├── identity
│   ├── plugin_id
│   └── version
│
├── runtime
│   ├── protocol_version
│   ├── entrypoint
│   └── instance_policy
│
├── permissions
│   └── requested[]
│
├── capabilities
│   └── provided[]
│
└── integrity
    ├── signature
    └── signing_key_id
```

Пример:

```json
{
  "manifest_version": 1,
  "identity": {
    "plugin_id": "com.engram.ssh",
    "version": "1.4.2"
  },
  "runtime": {
    "protocol_version": 1,
    "entrypoint": "bin/plugin",
    "instance_policy": "single"
  },
  "permissions": {
    "requested": ["network.connect", "storage.read"]
  },
  "capabilities": {
    "provided": ["ssh.session"]
  },
  "integrity": {
    "signature": "...",
    "signing_key_id": "..."
  }
}
```

---

## 1. `identity`

### `plugin_id`

Стабильный идентификатор, **не зависящий от имени файла, пути установки или
версии**. Обратная DNS-нотация:

```
com.engram.ssh
com.engram.github
com.engram.vless
```

Требования:
- неизменен на протяжении всей жизни плагина;
- ключ single-instance policy (`docs/plugin-lifecycle.md`, раздел 10);
- ключ пространства имён в `Storage` (`plugin.<id>.*`) и в политике прав.

### `version`

Версия самого плагина, например `1.4.2`. **Обновление версии не создаёт новую
идентичность.** Плагин `com.engram.ssh` версии `2.0.0` — тот же плагин, что и
`1.4.2`: те же выданные права, то же persistent-состояние, тот же trust level.

Это прямое следствие правила `Runtime restart ≠ Plugin identity reset`
(lifecycle, раздел 9), распространённое на обновления.

---

## 2. `runtime`

### `protocol_version`

Версия **IPC-протокола Runtime ↔ Plugin**, не версия плагина. Разные вещи:

```
protocol_version: 1        ← как плагин говорит с Runtime
version: "2.7.0"           ← версия самого плагина
```

Плагин версии `2.7.0` может общаться по протоколу `1`. Это позволяет обновлять
Runtime и SDK независимо от плагинов и наоборот. Проверяется при handshake
(lifecycle, раздел 3); несовместимость → `FAILED`.

### `entrypoint`

**Путь относительно корня пакета, никогда абсолютный.**

```
package/
├── manifest.json
├── bin/
│   └── plugin          ← entrypoint: "bin/plugin"
└── ...
```

Runtime разрешает `entrypoint` **внутри корня установленного пакета** и обязан
отвергнуть манифест, если результат разрешения выходит за его пределы.

Требования к валидации:

| Запрещено | Пример | Почему |
|---|---|---|
| Абсолютные пути | `/home/user/anything`, `/bin/sh` | Запуск произвольного исполняемого файла хоста |
| Выход за корень пакета | `../../../bin/sh` | То же самое обходным путём |
| Символические ссылки за пределы пакета | `bin/plugin → /bin/sh` | То же самое ещё одним обходным путём |

Без этой проверки манифест становится способом заставить Runtime запустить любой
файл в системе от своего имени — то есть путь обхода sandbox, созданный
собственными руками. Проверка symlink обязательна отдельно: разрешение пути и
проверка целевого файла — разные операции, и первая не гарантирует вторую.

### `instance_policy`

```
"single"   — один экземпляр на plugin_id (значение по умолчанию)
"multi"    — зарезервировано, НЕ реализуется сейчас
```

Значение `multi` объявлено в спецификации, но Runtime обязан отвергать его как
неподдерживаемое до тех пор, пока multi-instance не будет спроектирован явно
(lifecycle, раздел 10: при нескольких экземплярах немедленно возникают вопросы о
том, чьё состояние авторитетно и кто получает событие).

Резервирование значения сейчас — чтобы позже не пришлось менять формат поля.

## 3. `permissions.requested`

Список прав, которые плагин **просит**:

```json
"permissions": { "requested": ["network.connect", "storage.read"] }
```

Означает: *«я хочу эти права»*. **Не означает:** *«Runtime выдал мне эти права»*.

```
Manifest
   │
   ├── requested_permissions        ← заявление плагина
   │
   ▼
Authorizer  (+ trust level + политика пользователя)
   │
   └── granted permissions          ← решение Runtime
```

### `granted` не записывается обратно в манифест

Выданные права — это **состояние Runtime**, а не характеристика пакета. Причины:

- манифест — часть пакета, подписанного автором плагина; запись туда решений
  Runtime означала бы изменение подписанных данных;
- одному и тому же пакету у разных пользователей могут быть выданы разные права —
  в манифесте им негде разойтись;
- при переустановке пакета права не должны сбрасываться до заявленных автором.

Хранилище выданных прав — состояние Runtime в `ports.Storage`, отдельно от пакета.

### Формат значений

Capability-ориентированные строки вида `домен.действие`: `chat.send`,
`storage.read`, `network.connect`. Не ролевые (`trusted`, `admin`) — threat model,
раздел 8, пункт 4: роли начали бы подменять авторизацию.

Соответствует уже существующему `ports.Permission` (плоская строка), менять его не
требуется.

## 4. `capabilities.provided`

Что плагин **умеет предоставлять**:

```json
"capabilities": { "provided": ["ssh.session"] }
```

Не то же самое, что `permissions.requested`:

| | Значение |
|---|---|
| `permissions.requested` | «Я хочу обращаться к этим возможностям платформы» |
| `capabilities.provided` | «Я умею предоставлять эти функции другим» |

Сверяется с `capabilities` из `HELLO_ACK` при handshake (lifecycle, раздел 3):
плагин, заявивший в рантайме больше, чем в манифесте, — `FAILED`. Расхождение
означает либо подмену исполняемого файла, либо ошибку сборки пакета; в обоих
случаях продолжать нельзя.

---

## 5. `integrity`

```json
"integrity": {
  "signature": "...",
  "signing_key_id": "..."
}
```

**Поля объявлены сейчас, семантика проверки отложена.**

> ⚠ **Verification semantics deferred until plugin trust/distribution policy is
> specified.**

Почему нельзя определить прямо сейчас: подпись бессмысленна без ответов на
вопросы, которых пока нет:

- **Кто подписал?** Автор плагина, ENSTOR, или оба?
- **Какому ключу доверяем?** Один корневой ключ платформы или набор?
- **Кто имеет право публиковать плагины?** Открытая публикация или allowlist?
- **Как отзывается ключ?** Скомпрометированный ключ автора должен инвалидировать
  уже установленные плагины — механизма отзыва нет.
- **Как соотносится с trust levels?** Подпись официальным ключом даёт `official`
  автоматически или это отдельное решение?

Эти вопросы относятся к политике распространения плагинов (ENSTOR, Phase 19), а не
к формату манифеста.

**Что уже решено:** проверка подписи будет использовать существующий
`Identity.Verify` (`ports/identity.go` + `adapters/ed25519`). Новый механизм
подписей **не создаётся** — ADR-029. Но из этого не следует, что Runtime должен
автоматически доверять пользовательскому `Identity` как ключу публикации: «чем
проверяем» и «кому доверяем» — разные вопросы, и второй остаётся открытым.

## 6. Правила совместимости

### `manifest_version`

Версия формата самого манифеста. Отличается от `protocol_version` (IPC) и
`version` (плагин) — три независимых счётчика, каждый со своим смыслом.

### Неизвестные поля

| Тип поля | Реакция Runtime |
|---|---|
| Неизвестное **необязательное** | Игнорировать → forward compatibility |
| Неизвестное **обязательное** | `UNSUPPORTED_MANIFEST`, отказ загрузки |

Обязательные поля помечаются префиксом `required_`:

```json
{
  "required_new_security_mode": "strict"
}
```

Старый Runtime, встретив `required_*`, которого не знает, обязан **отказать**, а не
молча проигнорировать. Иначе манифест, объявляющий более строгий режим
безопасности, на старом Runtime тихо превратится в отсутствие этого режима — то
есть новая защитная настройка молча перестанет действовать именно там, где старее
код и выше риск.

Это единственный способ добавлять обязательные настройки безопасности в будущем,
не ломая уже установленные плагины и не создавая тихих дыр.

## 7. Валидация: обязательный порядок

Загрузчик обязан отвергнуть манифест до любого запуска процесса:

1. `manifest_version` известен;
2. нет неизвестных `required_*` полей;
3. `plugin_id` синтаксически корректен и совпадает с ожидаемым для этого пакета;
4. `protocol_version` поддерживается Runtime;
5. `entrypoint` — относительный путь, разрешается внутри корня пакета, целевой
   файл существует и не выводит за пределы пакета (включая symlink);
6. `instance_policy` — поддерживаемое значение (сейчас только `single`);
7. `permissions.requested` — синтаксически корректные capability-строки;
8. `capabilities.provided` — то же;
9. `integrity` — присутствие полей (проверка подписи — отложена, см. раздел 5).

Любая неудача → плагин не запускается, состояние `FAILED` с типом
`startup_failure` (lifecycle, раздел 5).

Порядок важен: проверка `entrypoint` (5) идёт **до** запуска процесса, а не после —
иначе смысл проверки теряется.

## 8. Граница ответственности

```
        MANIFEST
            │
   ┌────────┴────────┐
   ▼                 ▼
compatibility      intent
   │                 │
   │        requested permissions
   │                 │
   ▼                 ▼
Runtime ────────► Authorizer
   │
   ▼
Supervisor
   │
   ▼
 Plugin
```

Манифест целиком принадлежит `photon-plugin-runtime` (ADR-030). `ports/plugin.go`
для его поддержки **не меняется**: `ports.Permission` (плоская строка) уже подходит
под формат `permissions.requested`, а `ports.Authorizer` принимает решение на
основании данных, которые Runtime добывает сам.

`protocol_version`, состояний lifecycle и семантики permissions.
