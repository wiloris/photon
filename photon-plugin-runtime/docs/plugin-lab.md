# Plugin Lab на настоящем `coreops` — спецификация (B4b)

Спецификация написана **до кода**. Основание — принятый **ADR-058**, который
дополняет **ADR-057**. Доказательство свойств S1–S7 — срез **B4a**
(`tests/lifecycle/sdkscenario_test.go`, `921e5ba`); этот документ его не
повторяет.

---

## 1. Границы среза

**Входит:**

- замена заглушки исполнителя в `cmd/devtools-runtime` настоящим `coreops`
  поверх `adapters/bbolt`, `adapters/aesgcm`, `adapters/ed25519` (ADR-058 п. 1);
- одноразовый ключевой материал и временное хранилище (ADR-058 пп. 2–4);
- закрытый каталог сценариев и его выбор через канал управления (пп. 6–7);
- показ наблюдаемых результатов в Plugin Lab (п. 8);
- сборка второй фикстуры в Gradle;
- структурная проверка, тесты и мутации из §10–§12.

**Не входит и не меняется:** SDK, IPC, Authorizer, `coreops`, адаптеры, порты,
C ABI; `core-operations.md` §11.1 и §11.2 для продакшна; `cmd/photon-core-server`;
общий пакет композиции; произвольная загрузка плагинов; оракулы S1–S7.

**Не входит и требовало бы отдельного решения:** несколько загрузок в одном
экземпляре (см. §4.3) и уборка остатков чужих запусков (см. §6.3).

## 2. Канал управления

### 2.1 Кадрирование — без изменений

Как в ADR-057: по одному JSON-объекту в строке в обе стороны, stdout занят
протоколом целиком, человекочитаемое — в stderr. Первая строка — готовность.

### 2.2 Запрос

```json
{"id": 1, "cmd": "load", "scenario": "sdk-sign-forbidden"}
```

| поле | тип | где допустимо |
|---|---|---|
| `id` | число | везде |
| `cmd` | строка | везде |
| `scenario` | строка | **только** в `load`; в прочих командах — отказ |

**Разбор строгий:** неизвестное поле — отказ кадра (`DisallowUnknownFields`),
канал остаётся жив. Это не стилистика: без строгого разбора кадр
`{"cmd":"load","grants":["identity.sign"]}` молча принимался бы как обычный
`load`, и отсутствие управления правами держалось бы на том, что поле просто не
читается, — ни одна проверка этого не заметила бы (ADR-058 п. 7).

### 2.3 Команды

| команда | было | в B4b |
|---|---|---|
| `status` | есть | без изменений |
| `scenarios` | — | **новая, только чтение:** закрытый каталог (§3) |
| `load` | запускает `hello` | принимает необязательный `scenario`; **без него — `hello`**, как прежде |
| `diagnose` | права, изоляция, операции | + сценарий, результаты плагина, граница лаборатории (§9) |
| `shutdown` | есть | + уборка временного хранилища (§6) |

`scenarios` — не расширение возможностей, а часть выбора (п. 7): Kotlin-сторона
читает каталог из канала и **не держит своей копии** — то же правило, что у
Protobuf Inspector.

**Чего в канале нет и быть не может:** команд и полей про ключи, `Grant`,
`Revoke`, права, путь к плагину, режим фикстуры, переменные окружения,
namespace. Сценарий — единственный вход; всё остальное из него **выводится**.

### 2.4 Ответы

`ready` — после того как временное хранилище и ключи созданы (§5):

```json
{"ok": true, "cmd": "ready", "runtime_state": "ready",
 "lab": {"key_material": "ephemeral", "storage": "temporary",
         "storage_dir": "/tmp/photon-plugin-lab-XXXX",
         "production_composition": false}}
```

Если композиция не собралась (нет каталога, bbolt не открылся), первая строка —
`{"ok": false, "cmd": "ready", "error": "..."}`, процесс выходит с ненулевым
кодом. Частично собранная лаборатория не объявляет готовность.

`scenarios`:

```json
{"ok": true, "cmd": "scenarios",
 "scenarios": [{"id": "hello", "fixture": "hello",
                "plugin_id": "com.engram.test.hello",
                "granted": ["storage.read"], "description": "..."}]}
```

`load` — дополнительно `scenario`, `fixture`, `plugin_id`, `granted`,
`namespace`. Неизвестный `scenario` — `ok:false`, `unknown scenario: <id>`,
плагин не запускается.

`diagnose` — дополнительно `scenario`, `results` (§9.2), `lab` (как в `ready`).
Поля `plugin_state`, `granted`, `isolation`, `operations` — прежние.

## 3. Закрытый каталог сценариев

Каталог задан кодом `devtools-runtime`. Строка каталога полностью определяет
запуск: фикстуру, идентичность, выданные права, режим фикстуры, namespace и
правила показа результатов.

| id | фикстура | идентичность | права | режим | что наблюдается |
|---|---|---|---|---|---|
| `hello` | `hello` | `com.engram.test.hello` | `storage.read` | — | чтение заранее записанного значения (§3.1) |
| `sdk-storage-roundtrip` | `sdkscenario` | `…sdkscenario-a` | набор A | `storage-roundtrip` | put → get → list → delete → get на настоящем bbolt |
| `sdk-sign` | `sdkscenario` | `…sdkscenario-a` | набор A | `sign` | ключ устройства и подпись от настоящего исполнителя; см. §8 |
| `sdk-sign-forbidden` | `sdkscenario` | `…sdkscenario-b` | набор B | `sign` | отказ без `identity.sign`; `identity.sign` не дошла до исполнителя |

Набор A: `storage.read`, `storage.write`, `identity.read`, `identity.sign`,
`crypto.use`. Набор B — тот же без `identity.sign`. Идентичности и наборы
совпадают с B4a.

**Допустимы только строки таблицы.** Любая другая комбинация фикстуры,
идентичности и режима невыразима: в канале нет полей, из которых её можно
собрать.

### 3.1 `hello` на настоящем исполнителе

Фикстура `hello` читает `greeting/message` и при любой ошибке выходит с кодом 2
(`tests/plugins/hello/main.go:41-42`). Заглушка отдавала константу; в пустом
временном хранилище будет `NOT_FOUND`, и плагин упадёт.

**Решение — bootstrap fixture, лабораторная предзагрузка.** Перед запуском
`hello` `devtools-runtime` записывает значение `hello-value` вызовом
`coreops.Handler.Handle` **от имени идентичности `hello`**, `storage.put`.

Что это такое и чем не является:

- **назначение одно** — создать исходное состояние закрытой фикстуры `hello`.
  Для других сценариев каталога предзагрузки нет;
- **выполняется до запуска пользовательского сценария** — до `host.Start`,
  когда процесса плагина ещё не существует;
- **Authorizer и наблюдатель обходятся намеренно**: это действие доверенного
  владельца экземпляра, а не запрос плагина, и проверять его правами плагина
  или показывать среди операций плагина было бы неверно;
- **это не модель обычного пути исполнения плагина.** Обычный путь —
  `процесс плагина → SDK → IPC → Authorizer → coreops`; предзагрузка его не
  иллюстрирует и образцом для него не служит;
- **это не изменение SDK, Authorizer или `coreops`** — используется
  существующий публичный `Handle` — **и не прецедент для продакшна**: хост,
  которому понадобится начальное состояние плагинов, решает это сам.

Следствия:

- вызов идёт **мимо наблюдателя** и в `operations` не попадает — список
  операций по-прежнему означает «что сделал плагин»;
- вызов идёт **мимо Authorizer** — у `hello` нет `storage.write`, и
  предоставлять его не нужно: плагин только читает;
- формат ключа `coreops` не повторяется — используется его же `Handle`.

Фикстура `hello` не меняется, поэтому B4a и Phase 11 не затронуты.

### 3.2 Крипто-сценарий в каталог не входит

Шифрование в одном запуске наблюдать нечем: режимы `encrypt` и `decrypt`
фикстуры — отдельные процессы. Для `decrypt` нужен шифртекст прошлого запуска,
а ключ между запусками не сохраняется (ADR-058 п. 2). Добавить в фикстуру
режим `crypto-roundtrip` можно, но это расширение B4a-фикстуры ради показа, а
свойство S5 уже доказано B4a. **В B4b не делается.**

## 4. Композиция `coreops`

### 4.1 Где

Только `cmd/devtools-runtime`, `package main`. Общего пакета композиции нет
(ADR-058 п. 1). Код композиции — функция внутри этого бинаря; импортировать её
нечем.

### 4.2 Что собирается и когда

**При старте процесса, до `ready`:**

1. `os.MkdirTemp("", "photon-plugin-lab-*")` — временный каталог;
2. `bbolt.New(<каталог>/lab.db, миграция v1)`, где миграция создаёт bucket'ы
   **обеих** фикстур: `lab.hello`, `lab.sdkscenario`;
3. `Migrate(ctx, 1)` — вызывает сам `devtools-runtime` (ADR-058 п. 4);
4. `ed25519.Generate` — пара ключей устройства;
5. `aesgcm.GenerateKey` — мастер-ключ.

**При `load`:**

6. `coreops.New(Config{Storage, StorageNamespace: <namespace фикстуры>,
   Identity, DeviceKey, Crypto, DeriveKey: DeriveKey(master, domain),
   Log: <сборщик результатов>})`;
7. наблюдатель — существующий `record()` — оборачивает `coreops.Handler`;
8. для `hello` — запись значения (§3.1);
9. переменные окружения фикстуры (§4.4);
10. `host.New` / `host.Start`, как сейчас.

### 4.3 Один экземпляр — одна загрузка

Сохраняется поведение ADR-057: второй `load` отвергается, выгрузки нет. Поэтому
сценарии, которым нужны **две идентичности в одном хранилище** (изоляция S2,
невзаимозаменяемость S4, чужая расшифровка S5), в Plugin Lab **не показываются**:
их доказательство — B4a. Выгрузка или последовательные загрузки — изменение
жизненного цикла канала, за рамками ADR-058 п. 7, и потребовали бы отдельного
решения.

### 4.4 Окружение фикстуры

Сценарий передаётся фикстуре окружением, как в `tests/lifecycle`:
`PHOTON_TEST_MODE`, `PHOTON_TEST_PLUGIN_ID`, `PHOTON_TEST_VALUE`,
`PHOTON_TEST_BINDING`, `PHOTON_TEST_DOMAIN_INPUT`.

**Все пять выставляются явно при каждом `load`** — пустыми, если сценарий
значение не задаёт. Иначе значение из окружения родителя (JVM) пришло бы в
плагин через наследование, и сценарий зависел бы не только от каталога.
`host` и спавнер не меняются: `exec.Command` наследует окружение процесса,
загрузка одна, поэтому `os.Setenv` перед `Start` достаточно.

### 4.5 Пути к фикстурам

Флаг `-plugin` заменяется двумя: `-fixture-hello` и `-fixture-sdkscenario`.
Пути передаёт доверенный родитель (Gradle), это не канал управления.
`PackageRoot` и `Entrypoint` выводятся из пути, как сейчас.

## 5. Ключевой материал

| материал | создаётся | живёт | на диск |
|---|---|---|---|
| пара ed25519 устройства | при старте процесса, до `ready` | до выхода процесса | никогда |
| мастер-ключ AES | при старте процесса, до `ready` | до выхода процесса | никогда |
| производные ключи плагинов | при каждом `crypto.*`, `DeriveKey` | время вызова | никогда |

**Это локальное исключение композиции Plugin Lab** (ADR-058 п. 2): требования
§11.1 не меняются, продакшн-вариантом это не является. Следствие проверяется
тестом: два экземпляра лаборатории показывают **разные** публичные ключи
устройства (§12, T11).

Приватный ключ и мастер-ключ **не попадают** ни в один ответ канала, ни в
stderr, ни в результаты. Обнуление памяти при выходе — best-effort: Go не даёт
гарантии, и спецификация её не обещает.

## 6. Временное хранилище и уборка

### 6.1 Штатное завершение — уборка гарантирована

Путь один для команды `shutdown` и для закрытия stdin (ADR-058 п. 9):

1. остановить плагин (`host.Stop`, как сейчас);
2. закрыть хранилище (`Storage.Close`);
3. `os.RemoveAll(<каталог>)`;
4. выйти.

Уборка выполняется после остановки плагина: удалять файл базы под работающим
исполнителем нельзя.

### 6.2 Аварийное завершение — уборка не гарантирована

`kill -9`, OOM killer, падение самого `devtools-runtime`: процесс не получает
управления, каталог **может остаться**. Спецификация этого не скрывает и не
обещает обратного (ADR-058 п. 3). Ключей в остатке нет; шифртексты `crypto.*`
без мастер-ключа не читаются; значения `storage.put` лежат как есть — это
тестовые данные закрытого каталога.

Путь к каталогу печатается в `ready`, поэтому остаток можно найти глазами.

### 6.3 Уборка остатков прошлых запусков — не делается

Удаление каталогов по шаблону `photon-plugin-lab-*` при старте означало бы
удалять файлы, созданные не этим процессом, — в том числе каталог
параллельно работающей лаборатории. В B4b не делается; остатки убирает ОС.

## 7. Namespace

- **Отдельный namespace на фикстуру:** `lab.hello`, `lab.sdkscenario`
  (ADR-058 п. 5). Фикстуры не делят namespace.
- **Внутри `sdkscenario` изоляцию идентичностей обеспечивает `plugin_id`** в
  ключе `coreops` — так `coreops` устроен сегодня (`Config.StorageNamespace`
  один на исполнитель).
- **Namespace на каждую идентичность не заводится.** Он потребовал бы
  исполнителя на идентичность или изменения `coreops`, а при одной загрузке на
  экземпляр (§4.3) ничего бы не показал.

## 8. Сценарий подписи и доверенный вход ADR-037

Plugin Lab **не строит** доменный вход ADR-037 (ADR-058 п. 8). Фикстура
`sdkscenario` в режиме `sign` всегда сообщает четыре значения; без доверенного
входа они значат разное:

| значение фикстуры | что означает без доверенного входа | показывать |
|---|---|---|
| `pub` | публичный ключ устройства, выданный исполнителем | **да** |
| `sig` | подпись, выданная исполнителем | **да**, длина и начало в base64 |
| `verify_raw` | `identity.verify` по сырым данным | **да, с подписью «наблюдение, не доказательство»** |
| `verify_domain` | проверка по **пустому** входу — вход не передан | **нет** |

Почему так:

- **`verify_domain` скрывается.** Без доверенного входа это проверка по пустым
  байтам, и её `false` читался бы как «домен не работает» — ложный вывод из
  значения, которое ничего не измеряло;
- **`verify_raw:false` показывается, но не как доказательство.** Этот `false`
  совместим и с доменным разделением, и с испорченной подписью: отличить их
  может только доверенный вход. Поэтому рядом печатается ссылка на
  `TestSDKScenario_SignIsDomainSeparated`;
- **для `sdk-sign-forbidden`** показываются `pub`, `sig:FORBIDDEN` и то, что в
  `operations` есть `identity.public_key` и **нет** `identity.sign`. Это прямое
  наблюдение исполнителя, а не оракул: список операций лаборатория ведёт и
  сейчас.

Правило фильтрации задаётся **строкой каталога** (§3), а не Kotlin-стороной:
значения, не разрешённые сценарию, в `results` не попадают вовсе.

## 9. Что показывает Plugin Lab

### 9.1 После `load`

- сценарий: id и описание;
- фикстура, `plugin_id`, выданные права, namespace;
- состояние плагина.

### 9.2 После `diagnose`

- **операции, дошедшие до исполнителя**, по порядку — как сейчас;
- **результаты плагина** (`results`) — только разрешённые сценарию значения
  (§8), в виде `имя → значение`;
- применённая изоляция — как сейчас;
- **граница лаборатории**, всегда, отдельным блоком:
  - «ключи устройства и мастер-ключ одноразовые, созданы при старте, на диск
    не пишутся»;
  - «хранилище временное: `<каталог>`; удаляется при штатном завершении, после
    `kill -9` может остаться»;
  - «это не продакшн-композиция и не образец для `cmd/photon-core-server`»;
  - «свойства доказаны B4a: `tests/lifecycle/sdkscenario_test.go`».

### 9.3 Чего Plugin Lab не показывает и не утверждает

- приватный ключ и мастер-ключ — их нет в канале;
- `verify_domain` и любые выводы вида «ADR-037 доказан», «изоляция доказана»,
  «приватный ключ не выходит»;
- сравнение сценариев между собой как доказательство.

## 10. Структурная граница импортов

Правило: в не-тестовом коде модуля `photon-plugin-runtime` пакеты
`github.com/wiloris/photon-core/adapters/...` импортируются **только** в
`cmd/devtools-runtime`.

Проверка — Go-тест, обходящий `.go`-файлы модуля без `_test.go` и разбирающий
импорты `go/parser`, а не подстрокой. Нарушение — любой такой файл вне
`cmd/devtools-runtime`. Отдельно проверяется, что пакет `cmd/devtools-runtime`
— `main`: общий пакет композиции так завести нельзя, не уронив проверку.

## 11. Тесты

### 11.1 Go, `cmd/devtools-runtime` — настоящие процессы

Существующие шесть тестов остаются; `load` без `scenario` по-прежнему
запускает `hello`, теперь на настоящем исполнителе.

| # | тест | проверяет |
|---|---|---|
| T1 | `hello` на настоящем исполнителе | плагин `running`, `storage.get` в `operations`, записи §3.1 в `operations` нет |
| T2 | `scenarios` | каталог ровно из четырёх строк §3 |
| T3 | неизвестный сценарий | `ok:false`, плагин не запущен, канал жив |
| T4 | лишние поля | `load` с `grants`, `plugin`, `key`, `mode` — отказ кадра, канал жив, права не изменились |
| T5 | `sdk-sign-forbidden` | `sig:FORBIDDEN`; `identity.public_key` в `operations`, `identity.sign` — нет |
| T6 | `sdk-sign` | в `results` есть `pub`, `sig`, `verify_raw`; **нет** `verify_domain` |
| T7 | `sdk-storage-roundtrip` | `roundtrip:OK`, `after_delete:NOT_FOUND`, четыре операции хранилища в `operations` |
| T8 | уборка по `shutdown` | каталог из `ready` удалён |
| T9 | уборка по закрытию stdin | каталог из `ready` удалён |
| T10 | окружение родителя | `PHOTON_TEST_MODE` в окружении `devtools-runtime` не меняет сценарий |
| T11 | одноразовые ключи | два экземпляра, `sdk-sign`: публичные ключи различаются |
| T12 | namespace | `load` сообщает `lab.hello` и `lab.sdkscenario` для своих фикстур |
| T13 | структура импортов | §10 |

Для `kill -9` отдельного теста **нет**: удаление в этом случае не
гарантируется, и тест, утверждающий любое поведение, закрепил бы то, что
спецификация не обещает. Существующие `TestOrphan_*` продолжают проверять, что
плагин не переживает родителя.

### 11.2 Kotlin, `PluginLabTest`

| # | тест |
|---|---|
| K1 | разбор `scenarios`, `results`, `lab` |

## 13. Что остаётся открытым

Архитектурного решения для B4b в объёме этой спецификации **не требуется** —
всё выведено из ADR-057 и ADR-058. Вне объёма и потребовали бы решения:

- **несколько загрузок в одном экземпляре** — изменение жизненного цикла канала
  (§4.3);
- **уборка остатков прошлых запусков** — удаление файлов, созданных не этим
  процессом (§6.3).

Нужен ваш выбор — не архитектурный, а объёма:

- **`scenarios` как отдельная команда** (§2.3) или каталог в ответе `ready`;
- **крипто-сценарий** (§3.2): вне B4b, как предложено, или расширение фикстуры
  режимом `crypto-roundtrip`.
