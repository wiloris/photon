# Sandbox Properties

Спецификация изоляции процесса плагина. Написана **до** кода — тот же порядок,
что сработал с `WIRE_FORMAT.md` для TCP и `plugin-manifest.md`.

Опирается на:
- `threat-model.md` — раздел 4 (два уровня гарантий), раздел 5 (sandbox ≠ authorization)
- `lifecycle.md` — sandbox вписывается в уже определённый жизненный цикл, не задаёт свой
- ADR-030 — sandbox живёт в `photon-plugin-runtime`, не в ядре

---

## 1. Sandbox не управляет жизненным циклом

Порядок отношений задан supervisor'ом и уже реализован:

```
Supervisor
    │
    ├── start ──→ Sandbox.Prepare ──→ Plugin process
    │
    ├── stop ───→ Sandbox.Terminate
    │
    └── crash ←── process exit
```

Sandbox **не** решает, когда запускать, перезапускать или останавливать плагин. Он
применяет ограничения к процессу, который запускает `host`, и освобождает
захваченные ресурсы, когда процесс завершился.

Практическое следствие: интерфейс sandbox не содержит `Start`, `Restart`,
`IsAlive`. Если такой метод понадобится — значит, sandbox начал дублировать
supervisor, и это ошибка проектирования, а не недостающая функция.

---

## 2. Свойства, а не механизмы

Требования формулируются как **свойства**, потому что механизмы платформо-зависимы.
`seccomp` — способ достичь свойства на Linux, а не само требование: записав его в
спецификацию, мы сделали бы Android-реализацию невозможной по формальным причинам.

| ID | Свойство | Формулировка |
|---|---|---|
| **P1** | Отдельный процесс | Плагин исполняется вне адресного пространства Runtime |
| **P2** | Нет доступа к памяти Runtime | Плагин не может читать/писать память ядра и других плагинов |
| **P3** | Ограниченная файловая система | Нет произвольного доступа к ФС хоста |
| **P4** | Ограниченная сеть | Сетевой доступ выдаётся как capability, не по умолчанию |
| **P5** | Ограниченные ресурсы | CPU/RAM/дескрипторы ограничены; плагин не может исчерпать ресурсы хоста |
| **P6** | Единственный канал наружу | IPC — единственный путь взаимодействия с Runtime |
| **P7** | Завершаемость | Процесс может быть принудительно завершён в ограниченное время |
| **P8** | Отсутствие эскалации | Плагин не получает привилегий выше, чем у процесса Runtime |

## 3. Два уровня гарантий

Из `threat-model.md`, раздел 4. Уровни различаются принципиально, и смешивать их
нельзя:

```
Layer 1 — Photon        одинаково на всех платформах
  ├── P1 отдельный процесс
  ├── P6 единственный канал (IPC)
  ├── P7 завершаемость
  └── enforcement прав (Authorizer)

Layer 2 — OS            зависит от платформы
  ├── P2 изоляция памяти
  ├── P3 ограничение ФС
  ├── P4 ограничение сети
  ├── P5 лимиты ресурсов
  └── P8 отсутствие эскалации
```

**Photon гарантирует Layer 1 везде. Layer 2 — настолько, насколько позволяет
платформа.** Обещание одинаковой изоляции на всех платформах было бы ложным (N6 в
threat model).

## 4. Матрица платформ

Что реально достижимо. Столбец «проверено» отражает состояние **этой** рабочей
среды, а не теоретические возможности.

| Свойство | Linux (потенциально) | Android (потенциально) | Проверено здесь |
|---|---|---|---|
| P1 отдельный процесс | ✅ `fork/exec` | ⚠️ требует отдельного `:process` в манифесте приложения | ✅ Linux |
| P2 память | ✅ следствие P1 | ⚠️ следствие P1, если P1 достигнут | ✅ Linux |
| P3 файловая система | ✅ namespaces, chroot, отдельный uid | ⚠️ ограничено моделью приложения | ❌ нет прав в среде |
| P4 сеть | ✅ network namespace | ❌ на уровне приложения, не процесса | ❌ |
| P5 ресурсы | ✅ cgroups, `setrlimit` | ⚠️ частично, через ОС | ⚠️ частично (`setrlimit`) |
| P6 единственный канал | ✅ закрытие лишних дескрипторов | ✅ | ✅ |
| P7 завершаемость | ✅ `SIGKILL` | ✅ | ✅ |
| P8 без эскалации | ✅ `NoNewPrivs`, отдельный uid | ⚠️ | ⚠️ частично |

### Почему Android отдельно, а не «как Linux»

Android — это Linux-ядро, но модель приложения другая:

```
Android OS sandbox
      │
      ▼
  ENGRAM process
      ├── Plugin Runtime
      │     └── Plugin  ← НЕ изолирован от Runtime по умолчанию
      └── Android permissions
```

Приложение уже изолировано ОС от **других приложений**. Но плагин **внутри**
процесса приложения от него не изолирован. Запуск плагина отдельным процессом
на Android требует объявления `android:process` в манифесте приложения и работает
иначе, чем `fork/exec` — это не деталь реализации, а другая модель.

`seccomp`/`cgroups` на Android доступны ядру, но приложению — ограниченно и
зависит от версии и производителя.

**Честный статус: Android-реализация не написана и не может быть проверена в этой
среде** (NDK/устройство недоступны — см. `photon-bindings/android/README.md`).
Заглушка, притворяющаяся изоляцией, была бы хуже её отсутствия.

## 5. Чего sandbox НЕ гарантирует

Симметрично разделу «что намеренно не обещаем» из threat model:

| Не гарантирует | Почему |
|---|---|
| Защиту от компрометации ядра ОС | Ни одно свойство не сохраняется при root-эксплойте |
| Защиту от компрометации самого Runtime | Sandbox применяется Runtime; скомпрометированный Runtime применит его как угодно |
| Side-channel изоляцию | Тайминги, кэш, энергопотребление — вне модели |
| Одинаковый уровень на всех платформах | См. раздел 4 |
| Защиту от вредоносного кода **внутри** разрешённых capability | Плагин с `network.connect` может подключиться куда угодно из разрешённого — это задача permissions, не sandbox |

Последний пункт — прямое следствие «sandbox ≠ authorization»: sandbox не даёт
обойти Runtime, permissions решают, что разрешено через Runtime.

## 6. Деградация: как ведём себя, когда свойство недостижимо

Свойства делятся на две категории, и это определяет поведение при невозможности
их обеспечить:

| Категория | Свойства | Поведение при недостижимости |
|---|---|---|
| **Обязательные** | P1, P6, P7 | **Отказ запуска.** Без них изоляции нет вообще |
| **Best-effort** | P3, P4, P5, P8 | Запуск с явным сообщением о том, какие свойства не применены |

**Тихая деградация запрещена.** Если Runtime не смог применить ограничение ФС, он
обязан сообщить об этом, а не запустить плагин, создавая ложное впечатление
защищённости. Ровно то же правило, что для неизвестных `required_*` полей манифеста.

## 7. Интерфейс

Минимальный, следующий из разделов 1 и 6:

```go
type Sandbox interface {
    // Prepare применяет ограничения к процессу ДО запуска.
    Prepare(spec Spec) (Applied, error)

    // Cleanup освобождает ресурсы после завершения процесса.
    Cleanup() error
}

type Applied struct {
    Properties map[Property]bool  // что реально применено
    Warnings   []string           // что не удалось и почему
}
```

Нет `Start`, `Stop`, `Restart` — жизненным циклом владеет supervisor (раздел 1).

`Applied` возвращается наружу намеренно: вызывающий обязан иметь возможность
узнать, какие свойства реально действуют. Без этого честная деградация (раздел 6)
невозможна — Runtime не смог бы отличить «изоляция применена» от «изоляция
пропущена молча».

---

## 8. Что должно быть покрыто тестами

1. Свойство недостижимо → соответствующая реакция (отказ для обязательных, warning для best-effort)
2. `Applied` честно отражает реальность, а не то, что запрашивали
3. Тихая деградация невозможна: нет пути, где ограничение не применилось и об этом не сообщили
4. `Cleanup` идемпотентен и не висит
5. Sandbox не мешает `SIGKILL` (P7 не должно ломаться другими свойствами)
6. Отсутствие sandbox явно отличимо от «sandbox применён»
7. Платформо-специфичные тесты пропускаются (`t.Skip`) с явной причиной, а не молча проходят
