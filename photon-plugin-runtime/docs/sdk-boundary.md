# SDK ↔ Runtime Boundary

Граница между `photon-plugin-sdk` (недоверенный процесс) и
`photon-plugin-runtime` (доверенная сторона).

**Этот документ НЕ переопределяет IPC-протокол.** Механика — handshake,
идентификация, correlation, отмена, дедлайны, события, shutdown, нарушения
протокола, wire-format — уже зафиксирована и реализована в
[`ipc.md`](ipc.md) (13 разделов, 49 тестов). Дублировать её здесь означало бы
создать второй документ, который со временем разойдётся с первым.

Здесь фиксируется то, чего в `ipc.md` нет:

1. **Каталог операций первой версии** — `ipc.Handler` принимает произвольный
   `op string`, но список допустимых операций не определён нигде.
2. **Форма SDK API** — как типизированный вызов превращается в IPC-запрос,
   оставаясь тонкой обёрткой.

Опирается на ADR-031 (SDK — клиент протокола, не окно во внутренности runtime).

---

## 1. Границы ответственности

```
┌───────────────────────────────┐
│        Plugin process         │  НЕдоверенный
│                               │
│   photon-plugin-sdk           │
│   ├── Plugin API              │  типизированные вызовы
│   ├── Event API               │  подписка на события
│   └── IPC client              │  сериализация в протокол
└───────────────┬───────────────┘
                │ IPC (ipc.md)
                ▼
┌───────────────────────────────┐
│      photon-plugin-runtime    │  доверенный
│   validation                  │
│   authorization               │
│   lifecycle                   │
│   supervision                 │
│   sandbox                     │
└───────────────┬───────────────┘
                ▼
           OS boundary
```

**Чего SDK не решает** (ADR-031):

| Вопрос | Кто решает |
|---|---|
| Можно ли выполнить операцию | `permissions.Authorizer` |
| Каким транспортом она выполняется | `services/autodial`, ядро |
| Где хранятся данные | `ports.Storage`, ядро |
| Как устроена авторизация | `permissions` |
| Как устроен sandbox | `sandbox` |
| Как Host запускает плагин | `host` + `supervisor` |

SDK превращает вызов в IPC-запрос и разбирает ответ. Больше ничего.

## 2. SDK — тонкая обёртка, а не библиотека

> Чем меньше кода внутри недоверенного процесса, тем лучше.

Каждый метод SDK обязан быть прямым отображением одной IPC-операции:

```go
// SDK
result, err := plugin.Storage.Get(ctx, "key")

// эквивалентно ровно одному:
REQUEST { op: "storage.get", payload: {"key":"key"} }
```

**Что SDK делать НЕ должен:**

| Антипаттерн | Почему запрещён |
|---|---|
| Кэшировать результаты | Кэш в недоверенном процессе — источник рассинхрона; отзыв права не подействует на закэшированное |
| Повторять запросы при ошибке | Retry-логика в плагине обходит дедлайны runtime; повторять решает вызывающий |
| Валидировать права локально | Дублирует Authorizer и создаёт иллюзию, что проверка уже была |
| Собирать несколько операций в одну | Runtime авторизует каждую операцию отдельно; склейка скрыла бы часть от проверки |
| Хранить состояние между вызовами | Кроме идентификатора сессии — всё состояние на стороне runtime |

Допустимо: типизация, сериализация, удобные сигнатуры, обработка ошибок
протокола.

### `OnEvent`/`OnStop` выполняются в потоке `Run`, не в отдельном

Оба обработчика вызываются СИНХРОННО из того же цикла чтения, что доставляет
RESPONSE на запросы самого плагина (`Run`, `sdk-boundary.md` не описывает
внутреннее устройство `Run`, но это следствие последовательной доставки,
которую он гарантирует — см. `api.go`, `EventHandler`). Блокирующий вызов SDK
(`Storage`/`Identity`/`Crypto`/`Log`) прямо из тела `OnEvent`/`OnStop` поэтому
не просто медленный — он тупиковый: ответу неоткуда прийти, пока цикл занят
вызовом обработчика, а обработчик ждёт этот самый ответ.

Правильно — сигнал через канал, вызов SDK из отдельной горутины:

```go
retry := make(chan struct{}, 1)
plugin.OnEvent(func(ctx context.Context, ev sdk.Event) error {
    select {
    case retry <- struct{}{}:
    default:
    }
    return nil // возврат немедленный — цикл Run свободен
})

go func() {
    <-retry
    plugin.Storage().Get(ctx, "ns", "key") // здесь, не в обработчике
}()
```

SDK обнаруживает прямой блокирующий вызов и возвращает `ErrReentrantCall`
вместо зависания — но только если вызов сделан с тем же `ctx` (или его
потомком через `context.With*`), что передан обработчику. Замена на
`context.Background()` или любой независимый `ctx` обходит проверку: вызов
зависнет молча, как и до этой защиты. `ErrReentrantCall` — подстраховка от
типичной ошибки (передать полученный `ctx` дальше, что естественно для
идиоматичного Go), а не гарантия от любого способа её обойти.

## 3. Каталог операций v1

`ipc.md` определяет **механику** запроса, но не список операций. Здесь —
исчерпывающий каталог первой версии.

Принцип отбора: операция входит в v1, только если она **уже поддержана
работающим кодом ядра**. Заявлять операции «на будущее» значит обещать API,
который вернёт `UNSUPPORTED` — хуже, чем его отсутствие.

**Единственное исключение — `p2p.*`, и оно ограничено по времени и по
механике.** Порядок добавления домена (§ниже) требует вносить операции в этот
раздел и в `ipc/operations.go` **одновременно**, то есть на условии 4, когда
исполнителя по условию 5 ещё нет. Возникающее промежуточное состояние названо
в самом разделе `p2p.*`: там сказано, что и почему сейчас возвращает
`UNSUPPORTED`. Обещания плагину при этом не возникает — метода в SDK нет, а
обобщённого вызова произвольной операции SDK не предоставляет (`client.call`
не экспортируется). Исключение снимается выполнением условия 5.

### storage.*

Поверх `ports.Storage` (реализован, `adapters/bbolt`, 18 тестов).

| Операция | Permission | Payload → Response |
|---|---|---|
| `storage.get` | `storage.read` | `{namespace, key}` → `{value}` либо `NOT_FOUND` |
| `storage.put` | `storage.write` | `{namespace, key, value}` → `{}` |
| `storage.delete` | `storage.write` | `{namespace, key}` → `{}` |
| `storage.list` | `storage.read` | `{namespace, prefix}` → `{keys[]}` |

**Namespace принудительно ограничен.** Плагин не указывает произвольный
namespace: runtime подставляет `plugin.<plugin_id>.<suffix>`, где `suffix` —
то, что передал плагин. Без этого плагин читал бы данные ядра и других
плагинов, а `storage.read` означал бы «читать всё» вместо «читать своё».

Это **не** проверка в SDK (она была бы обходима), а преобразование на стороне
runtime.

### identity.*

Поверх `ports.Identity` (реализован, `adapters/ed25519`, 15 тестов).

| Операция | Permission | Payload → Response |
|---|---|---|
| `identity.public_key` | `identity.read` | `{}` → `{public_key}` |
| `identity.sign` | `identity.sign` | `{data}` → `{signature}` |
| `identity.verify` | `identity.read` | `{public_key, data, signature}` → `{valid}` |

**Приватный ключ плагину не выдаётся никогда.** `identity.sign` подписывает
ключом устройства на стороне runtime; операции «получить приватный ключ» не
существует и не будет — это прямое следствие ADR-021 (ключ не покидает
устройство), и отсутствие такой операции здесь не пробел, а требование.

**`identity.sign` подписывает НЕ то, что прислал плагин (ADR-037).**
Подписывается доменно-разделённое представление:

```
plugin_sign_input = "plugin-sign:" ‖ uint32be(len(plugin_id)) ‖ plugin_id ‖ ":" ‖ data
```

Следствие, которое выглядит как дефект и им не является: **наивный внешний
верификатор — взять `data` и `signature` и проверить — получит `false`.** Это
желаемое поведение. Плагин, проверяющий подпись от `identity.sign`, обязан
собрать представление сам; схема публична и секретом быть не может.

`identity.verify` остаётся **сырой** и потому асимметрична `identity.sign`:
ею проверяют в том числе подписи, сделанные вне Photon, и префикс в ней сломал
бы это применение.

Симметричный домен существует с другой стороны границы — в
`services/account.AuthenticateDevice`:

```
device_auth_input = "photon-device-auth:" ‖ challenge
```

Без него подпись, полученная плагином, годилась бы как аутентификация
устройства. **Любой новый формат, подписываемый ключом устройства, обязан
иметь собственный домен** — это требование ADR-037, а не рекомендация.

### crypto.*

Поверх `ports.Crypto` (реализован, `adapters/aesgcm`, 23 теста).

| Операция | Permission | Payload → Response |
|---|---|---|
| `crypto.encrypt` | `crypto.use` | `{plaintext, binding_data}` → `{ciphertext}` |
| `crypto.decrypt` | `crypto.use` | `{ciphertext, binding_data}` → `{plaintext}` |

Ключ выводится runtime через `DeriveKey` из мастер-ключа по домену
`plugin.<plugin_id>` — плагин не выбирает и не видит ключ. Иначе один плагин
расшифровал бы данные другого.


### p2p.*

Поверх `ports.P2P` (реализован, `adapters/pion`, 28 тестов; кадрирование —
`p2pmsg`, ADR-075, доказано на двух настоящих процессах). Решение о домене —
**ADR-076**.

> **СОСТОЯНИЕ: имена внесены, исполнителя нет.** Это условие 4 из шести
> (см. «Порядок добавления домена операций»). Плагин **без** права
> `p2p.connect` получает отказ в правах; плагин **с** правом получает
> `UNSUPPORTED` от `coreops`, потому что ветки исполнителя ещё не существует.
> Состояние временное и громкое: молчаливого поведения здесь нет ни в одном
> из двух случаев. Снимается выполнением условия 5.

| Операция | Permission | Payload → Response |
|---|---|---|
| `p2p.create_offer` | `p2p.connect` | `{peer_pubkey}` → `{negotiation_id, offer}` |
| `p2p.accept_offer` | `p2p.connect` | `{peer_pubkey, offer}` → `{session_id, answer}` |
| `p2p.complete` | `p2p.connect` | `{negotiation_id, answer}` → `{session_id}` |
| `p2p.peer` | `p2p.connect` | `{session_id}` → `{peer_pubkey}` |
| `p2p.send` | `p2p.connect` | `{session_id, payload}` → `{}` |
| `p2p.close` | `p2p.connect` | `{session_id}` → `{}` |

События (Runtime → Plugin, `MsgEvent`; ответами на запрос **не являются** и
`RequestTimeout` не подчинены):

| Событие | Payload |
|---|---|
| `p2p.message` | `{session_id, payload}` |
| `p2p.closed` | `{session_id, reason}`, `reason` ∈ `local` / `remote` / `failed` / `plugin_stopped` / `slow_consumer` |

**Право одно на весь домен.** «Согласовать, но не отправлять» не является
осмысленным состоянием: сессия без обмена бесполезна, обмен без сессии
невозможен. Пара `p2p.connect`/`p2p.send` создала бы различие, за которым не
стоит ни одного сценария (ADR-076 §3.5).

**Потоки наружу не выводятся.** ADR-075 фиксирует один двунаправленный поток
на разговор, и runtime открывает либо принимает его сам. `OpenStream` и
`AcceptStream` в каталоге отсутствуют намеренно: мультиплексирование стало бы
вторым понятием без потребителя.

**`negotiation_id` и `session_id` непрозрачны.** Из них ничего не выводится и
в них ничего не кодируется — ни адрес, ни ключ, ни имя плагина. Чужой,
неизвестный и уже закрытый handle дают **`NOT_FOUND`**, а не `FORBIDDEN` и не
отдельный `SESSION_CLOSED`: любой из двух подтверждал бы существование сессии
и давал бы перебором оракул о соседях (ADR-076 §3.7). Цена принята осознанно —
плагин не отличает свою закрытую сессию от чужой живой.

**Что остаётся за Photon и плагину недоступно:** ICE, DTLS, SCTP, handshake
ADR-041, подтверждение `Peer()`, кадрирование. Плагин не может провести
handshake сам даже имея сокеты: он не способен подписаться в домене
`photon-p2p-auth:` — `identity.sign` подписывает в домене `plugin-sign:`
(ADR-037). Это аргумент корректности, а не изоляции.

**Что принадлежит вызывающему:** discovery и matchmaking, доставка
`offer`/`answer` любым своим каналом (ADR-042), схема `payload`. Платформа
`payload` не разбирает.

### log.*

| Операция | Permission | Payload → Response |
|---|---|---|
| `log.write` | *(не требуется)* | `{level, message}` → `{}` |

Одна из двух операций без права: плагин должен иметь возможность сообщить о
проблеме, даже не получив никаких прав. Объём ограничен runtime (иначе это
DoS через диск).

### work.*

| Операция | Permission | Payload → Response |
|---|---|---|
| `work.complete` | *(не требуется)* | `{}` → `{}` |

**Доклад о завершении текущей единицы работы (ADR-072).** Плагин сообщает, что
работа, ради которой Runtime ведёт этот жизненный цикл, закончена.

Чем эта операция **не** является: командой остановиться, самостоятельным
завершением плагина, закрытием сессии, завершением процесса. Решение о `STOP`
принимает Runtime, и только он.

Операция **не терминальна и повторяема**: после доклада плагин продолжает
работать и обязан дождаться `STOP`; обработав событие, он докладывает снова —
у `EVENT` подтверждения нет, и `work.complete` является единственным способом
сообщить, что событие обработано.

Права не требует по той же причине, что и `log.write`: плагин без единого
права обязан остаться управляемым. Право на доклад превратило бы «право не
выдано» в «Runtime не дождётся завершения», то есть в зависание вместо отказа.

### Чего в v1 НЕТ и почему

Строка про `p2p.*` отсюда **убрана**: она устарела дважды — `adapters/pion`
реализован в Phase 15, а домен внесён ADR-076 и описан выше. Оставлять её
значило бы держать в документе утверждение, опровергнутое и кодом, и решением.

| Не входит | Причина |
|---|---|
| `network.*` | `ports.Transport` реализован, но операции для плагинов не спроектированы: неясно, плагин открывает соединение или просит runtime |
| `media.*` | Адаптер не реализован |
| `notification.*` | Адаптер не реализован |
| `chat.*`, `user.*` | Относятся к ENGRAM/Bridge, не к ядру |
| `plugin.*` (управление собой) | Запрещено ADR-031, п.3 |

### Порядок добавления домена операций

Таблица выше — не список задач. **Домен добавляется по потребности, не по
плану.** `network.*` не появится оттого, что `ports.Transport` заработал, и
`p2p.*` появился **не** оттого, что появился `adapters/pion`: он ждал первого
названного потребителя полторы фазы и вошёл только вместе с ним (Chat
Roulette, ADR-076 §1.1). Пример сохранён именно потому, что правило на нём
сработало.

Пока не выполнены все шесть пунктов — домена нет:

1. **Конкретный потребитель.** Плагин или приложение, которому операция нужна
   сейчас, с именем и задачей. «Полезно иметь», «раз адаптер всё равно есть» и
   «для симметрии со `storage.*`» потребителем не являются. Без этого пункта
   остальные пять — формальная процедура: права для воображаемого потребителя
   можно спроектировать как угодно, и проверить эту модель нечем.
2. **Модель прав спроектирована.** Что право разрешает, что остаётся
   недоступным и почему граница проходит здесь. Не «`network.write`», а ответ
   на вопрос, дотянется ли плагин с этим правом до соседнего.
3. **ADR на домен** — отдельный, с отклонёнными вариантами.
4. **Операции описаны в разделе 3 и внесены в маппинг** `ipc/operations.go` —
   одновременно. Операция, известная одной стороне и неизвестная другой, — это
   расхождение спецификации и кода, ровно то, что нашёл E2E-тест Phase 10.
5. **Реализация.**
6. **Тестовый плагин Phase 11 на невозможность обхода** — настоящим процессом
   (`tests/lifecycle`). In-process тест здесь не считается: `net.Pipe` не
   порождает процесс и не воспроизводит границу.

**Критерий готовности** — не «код написан», а: право выдаётся и отзывается,
обход невозможен, и это проверено на реальном процессе.

**Фазу в `ROADMAP.md` под домен не заводить.** Фаза возвращает «по
потребности» обратно в «по плану»: пункт в roadmap сам становится причиной его
закрыть — тот случай, который CLAUDE.md называет «писать код ради закрытия
пункта roadmap».

## 4. Соответствие операций и прав

Право проверяется по **имени операции**, без вычислений и иерархий:

```
op "storage.get"  → permission "storage.read"
op "storage.put"  → permission "storage.write"
```

Таблица соответствия живёт **в runtime**, не в SDK: маппинг на стороне
недоверенного процесса позволил бы объявить, что `storage.put` требует
`storage.read`.

`storage.read` не даёт `storage.write` — точное совпадение строк, без
wildcard (`permissions`, проверено тестами).

Одно право может покрывать весь домен, если дробить его не за что:
`p2p.connect` требуется всеми шестью операциями `p2p.*` (ADR-076 §3.5).
Это не исключение из точного совпадения — совпадение по-прежнему точное, просто
правая часть у шести строк одна и та же.

Две операции права не требуют вовсе — `log.write` и `work.complete`. Обе по
одной причине: плагин обязан оставаться наблюдаемым и управляемым, не получив
ничего. Список закрытый и живёт в `ipc/operations.go`
(`opsWithoutPermission`); неизвестная операция даёт `UNSUPPORTED`, а не
молчаливое исполнение.

## 5. Что происходит при разрыве IPC

Механика — `ipc.md`, разделы 9–10. Со стороны SDK:

| Событие | Поведение SDK |
|---|---|
| Соединение закрыто | Активные вызовы завершаются ошибкой; новые сразу возвращают ошибку |
| Получен `STOP` | SDK вызывает обработчик завершения плагина, отвечает `STOP_ACK` |
| Нарушение протокола | Сессия закрыта runtime; SDK не переподключается |

**SDK не переподключается.** Сессия не переживает разрыв: новый процесс —
новый handshake (`ipc.md`, раздел 11). Reconnect в SDK означал бы попытку
восстановить идентичность, которую устанавливает runtime.

## 6. Версионирование

Три независимые оси уже определены (`manifest.md`):

| Ось | Что версионирует |
|---|---|
| `manifest_version` | Формат манифеста |
| `protocol_version` | IPC-протокол (проверяется при handshake) |
| `version` | Сам плагин |

Каталог операций версионируется вместе с `protocol_version`: добавление
операции — минорное изменение (старый плагин её не вызывает), удаление или
изменение семантики — мажорное.

Неизвестная операция → `UNSUPPORTED` (`ipc.md`, раздел 5). Молча игнорировать
нельзя: плагин решит, что операция выполнена.

## 7. Что должно быть покрыто тестами

1. Каждая операция каталога → корректный IPC-запрос
2. Операция без права → `FORBIDDEN`, вызов не достигает ядра
3. Неизвестная операция → `UNSUPPORTED`
4. Namespace принудительно ограничен: плагин не читает чужие данные, даже
   указав чужой namespace явно
5. Приватный ключ недоступен ни одной операцией
6. SDK не кэширует: отзыв права действует на следующем вызове
7. Разрыв IPC → активные вызовы завершаются, переподключения нет
8. SDK не импортирует `photon-plugin-runtime` и `photon-core` (проверяется
   статически)

Пункт 8 — единственный, который проверяется не тестом, а анализом импортов:
это структурное требование ADR-031, и нарушение должно ломать сборку, а не
падать в рантайме.
