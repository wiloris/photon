# Plugin Lifecycle

Спецификация жизненного цикла плагина в `photon-plugin-runtime`. Написана **до**
реализации supervisor и **до** спецификации манифеста — потому что часть полей
манифеста (`protocol_version`, `plugin_id`, instance policy, entrypoint) является
следствием этой модели, а не самостоятельным решением.

Опирается на:
- ADR-005 — плагин не живёт внутри ядра, IPC-граница
- ADR-030 — граница `photon-core` ↔ `photon-plugin-runtime`
- `docs/plugin-threat-model.md` — плагин недоверенный, Runtime доверенный

---

## 1. State machine

```
                    ┌─────────────┐
                    │   STOPPED   │
                    └──────┬──────┘
                           │ start
                           ▼
                    ┌─────────────┐
                    │  STARTING   │──── handshake failure ──┐
                    └──────┬──────┘                         │
                           │ handshake ok                   │
                           ▼                                │
                    ┌─────────────┐                         │
              ┌────►│   RUNNING   │                         │
              │     └──────┬──────┘                         │
              │            │                                │
              │      ┌─────┴─────┬──────────────┐           │
              │      │ stop      │ crash        │ protocol  │
              │      ▼           │              │ violation │
              │ ┌──────────┐     │              ▼           │
              │ │ STOPPING │     │       ┌─────────────┐    │
              │ └────┬─────┘     │       │ TERMINATING │    │
              │      │           │       └──────┬──────┘    │
              │      ▼           │              │           │
              │ ┌─────────┐      ▼              ▼           ▼
              │ │ STOPPED │  ┌─────────────────────────────────┐
              │ └─────────┘  │            FAILED               │
              │              └──────────────┬──────────────────┘
              │                             │
              │            ┌────────────────┴──────────────┐
              │            │ backoff                       │ limit reached
              └────────────┘                               ▼
                                                    ┌─────────────┐
                                                    │  DISABLED   │
                                                    └─────────────┘
```

**Состояния:**

| Состояние | Значение |
|---|---|
| `STOPPED` | Плагин установлен, процесс не запущен. Нормальное состояние покоя |
| `STARTING` | Процесс запущен, handshake не завершён. Плагин ещё не имеет права ни на что |
| `RUNNING` | Handshake успешен, плагин обслуживает запросы |
| `STOPPING` | Запрошена штатная остановка, процесс ещё не завершился |
| `TERMINATING` | Runtime принудительно завершает процесс (нарушение протокола) |
| `FAILED` | Процесс завершился нештатно; ожидается решение о перезапуске |
| `DISABLED` | Исчерпан лимит перезапусков либо запрет администратора. Автоматический перезапуск не производится |

`STOPPING` и `TERMINATING` — не украшение: между решением остановить и фактическим
завершением процесса проходит время, в течение которого Runtime обязан отвечать на
запрос статуса чем-то определённым, а не «ещё RUNNING» или «уже STOPPED».

## 2. Владение процессом

> **Runtime — единственный владелец жизненного цикла процесса плагина.**

```
Photon Core
     │  (ports.Authorizer — контракт, ADR-030)
     ▲
     │ implements
Plugin Runtime
     │
     ▼
 Supervisor
     │ spawn
     ▼
Plugin Process
```

Процесс запускает **Supervisor** внутри Runtime. Не Photon Core и не сам плагин.

Ядро не знает и не должно знать PID, путь к исполняемому файлу, счётчик
перезапусков или файловую систему плагина — это прямое следствие ADR-030 и
ADR-005 («ядро не хранит списка известных плагинов»).

**Плагин не имеет права:**

| Запрещено | Почему |
|---|---|
| Самостоятельно регистрироваться в Core | В обход Runtime не проходит проверка прав (threat model, T6) |
| Запускать второй свой экземпляр | Обход single-instance policy (раздел 10) |
| Изменять собственные permissions | Манифест — запрос, а не разрешение (threat model, раздел 3) |
| Объявлять себя `RUNNING` | Состояние определяет Runtime по факту handshake, не по заявлению недоверенной стороны |
| Подключаться к Core в обход Runtime | Основание для `TERMINATING` |

Последний пункт — не теоретический: если бы плагин мог сам открыть соединение к
ядру, весь enforcement обходился бы одной строкой в коде плагина.

## 3. Startup и handshake

```
Runtime → Plugin   HELLO
                     protocol_version
                     runtime_instance      (идентификатор запуска Runtime)
                     plugin_instance       (идентификатор запуска плагина)

Plugin → Runtime   HELLO_ACK
                     protocol_version
                     plugin_id
                     capabilities          (что плагин умеет — НЕ что ему разрешено)
```

Переход `STARTING → RUNNING` происходит **только** после успешного handshake.

**Проверки при handshake, любая неудача → `FAILED`:**

- `protocol_version` несовместим → нет смысла продолжать: стороны не поймут друг друга;
- `plugin_id` не совпадает с ожидаемым из манифеста → запущен не тот плагин;
- handshake не завершён за отведённое время → плагин завис на старте;
- `capabilities` содержит то, чего нет в манифесте → плагин заявляет больше, чем декларировал при установке.

`capabilities` в `HELLO_ACK` — это **что плагин умеет**, не что ему разрешено.
Разрешения определяет Authorizer на основании манифеста, trust level и политики
(threat model, раздел 3). Плагин, приславший `capabilities: [chat.send]`, не
получает права отправлять сообщения — он лишь сообщает, что такой обработчик у
него есть.

## 4. Clean shutdown

```
RUNNING → STOPPING → STOPPED
```

1. Runtime отправляет запрос остановки.
2. Плагину даётся ограниченное время на завершение текущих операций.
3. Если по истечении срока процесс жив → принудительное завершение, состояние
   всё равно `STOPPED` (штатная остановка была запрошена, значит результат
   ожидаемый).

Разница со `TERMINATING`: там причина — нарушение протокола, и итог `FAILED`.

---

## 5. Классификация завершений

Разные причины требуют разной реакции, поэтому одного состояния `ERROR`
недостаточно:

| Тип | Что произошло | Реакция |
|---|---|---|
| `clean_stop` | Штатная остановка по запросу | `STOPPED`, перезапуск не нужен |
| `startup_failure` | Процесс не запустился (нет файла, нет прав на исполнение) | `FAILED`, перезапуск обычно бессмысленен — считается против лимита агрессивнее |
| `handshake_failure` | Процесс запустился, handshake не прошёл | `FAILED`, перезапуск с backoff |
| `crash` | Процесс завершился ненулевым кодом или по сигналу | `FAILED`, перезапуск с backoff |
| `protocol_violation` | Некорректный кадр IPC, обращение в обход Runtime, заявка неразрешённых capabilities | `TERMINATING` → `FAILED`. **Перезапуск не автоматический**: это не сбой, а поведение, требующее внимания |
| `authorization_failure` | Плагин систематически запрашивает то, на что не имеет прав | Не завершение само по себе; при превышении порога — основание для `DISABLED` |

`protocol_violation` намеренно не перезапускается автоматически: сбой можно
пережить перезапуском, а нарушение протокола повторится с той же вероятностью —
и может быть попыткой атаки, а не багом.

## 6. Restart policy

**Не «упал → сразу перезапустить».** Багнутый плагин в таком цикле превращается
в `crash → restart → crash → restart` и выедает CPU.

Экспоненциальный backoff с jitter:

```
crash #1 → 1s
crash #2 → 2s
crash #3 → 4s
crash #4 → 8s
crash #5 → 16s
...      → до максимума (например, 5 минут)
```

**Jitter обязателен** (случайное отклонение к каждой задержке): без него несколько
плагинов, упавших одновременно по общей причине (перезапуск сети, обновление
ядра), будут синхронно перезапускаться одной волной.

Счётчик сбрасывается после того, как плагин продержался в `RUNNING` достаточно
долго — иначе плагин, стабильно работающий неделю и упавший однажды, окажется
ближе к `DISABLED`, чем заслуживает.

---

## 7. Disable policy

Переход в `DISABLED` при:

- достижении лимита последовательных перезапусков;
- `protocol_violation` (без автоматического перезапуска);
- превышении порога `authorization_failure`;
- явном запрете пользователем или политикой.

Из `DISABLED` выход только по явному действию (пользователь, политика,
переустановка) — автоматического возврата нет. Это состояние означает «система
решила не пытаться дальше», и молчаливый выход из него обесценил бы решение.

---

## 8. Persistent state

Разделение, которое определяет всё остальное:

| Живёт в процессе | Переживает перезапуск |
|---|---|
| Активные IPC-запросы | `plugin_id` |
| Открытые соединения | Манифест |
| Состояние в памяти | Собственное persistent-состояние плагина |
| PID | Счётчик перезапусков, `DISABLED`-статус |
| **Выданные permissions** | |

Хранилище — `ports.Storage` (namespace вида `plugin.<id>.*`), тот же механизм, что
уже используется `services/account`. Отдельного хранилища для плагинов не заводится.

**Выданные permissions перезапуск НЕ переживают** (ADR-073). Их выдаёт
вызывающий при каждом запуске, и хранилища прав не существует: `granted` —
результат вычисления политики, а не запомненная величина
(`permissions/policy.go`). Прежняя редакция этой таблицы утверждала обратное и
расходилась с кодом.

**Trust level из таблицы убран по той же причине** — в коде его нет вовсе
(`docs/threat-model.md` §6 описывает уровни доверия в будущем времени).
Persistence прав и trust levels — post-v1, ADR-073 §5.

## 9. Runtime restart semantics

**Процесс плагина умирает вместе с Runtime. Регистрация и состояние — нет.**

```
Photon starts
   ↓
Runtime starts
   ↓
discover installed plugins        (из persistent state)
   ↓
restore configuration / permissions / trust
   ↓
authorize
   ↓
start plugin process
   ↓
handshake
   ↓
RUNNING
```

**Прозрачное продолжение активных операций не обещается.** Если плагин выполнял
операцию в момент падения Runtime:

```
operation #184
      ↓
Runtime dies
      ↓
operation LOST
```

Плагин может определить состояние после восстановления через собственное
persistent-состояние, но Runtime **не обязан** магически продолжить незавершённый
IPC-запрос. Попытка обещать это потребовала бы журналирования каждого запроса и
протокола восстановления — цена, несопоставимая с пользой, и источник тонких
багов в случае, когда «продолженная» операция уже была частично выполнена.

> **Runtime restart ≠ Plugin identity reset.**

`plugin_id`, манифест, permissions, trust level и persistent-конфигурация не
зависят от PID процесса. Это правило понадобится при проектировании IPC и
манифеста: идентичность плагина не может быть привязана к номеру процесса.

## 10. Single-instance policy

**По умолчанию: один экземпляр на `plugin_id`.**

```
plugin_id = com.example.ssh

instance #1 → RUNNING
instance #2 → DENY
```

Multi-instance, если когда-нибудь понадобится, должен быть **явной возможностью**,
объявленной в манифесте и поддержанной Runtime — а не случайным следствием того,
что кто-то запустил второй процесс.

Причина строгости: при нескольких экземплярах немедленно возникают вопросы, на
которые сейчас нет ответа — чьё persistent-состояние авторитетно, как делятся
permissions, какой экземпляр получает событие. Запретить сейчас и разрешить
осознанно позже дешевле, чем разгребать это постфактум.

## 11. Что из этого следует для манифеста

Поля манифеста, которые являются **следствием** этой модели, а не свободным
выбором:

| Поле | Откуда следует |
|---|---|
| `plugin_id` | Раздел 9: идентичность не привязана к процессу; раздел 10: ключ single-instance |
| `protocol_version` | Раздел 3: проверяется при handshake |
| `entrypoint` | Раздел 2: Supervisor должен знать, что запускать |
| `requested_permissions` | Threat model, раздел 3: манифест — запрос |
| `instance_policy` | Раздел 10: multi-instance только явно |
| `capabilities` | Раздел 3: сверяется с `HELLO_ACK` |

Следующий документ — спецификация манифеста, затем IPC (в этом порядке: IPC должен
отражать модель lifecycle и capabilities, а не наоборот).
