# Plugin Test Laboratory

Спецификация тестовых плагинов для Phase 11. Написана **до** кода — тот же порядок,
что сработал с `WIRE_FORMAT.md`, `sandbox.md`, `sdk-boundary.md`.

---

## Принцип

> **Каждый тестовый плагин существует, чтобы доказать конкретное свойство
> безопасности или устойчивости. Плагин без такого утверждения не нужен.**

Тестовый плагин — не демонстрация возможностей SDK и не пример для документации.
Это исполнитель атаки или отказа, который должен провалиться предсказуемым образом.

Отсюда следует, чего в лаборатории **нет**:

| Не входит | Почему |
|---|---|
| Плагин, показывающий «как пользоваться SDK» | Это документация, а не проверка. Демонстрационный код обычно happy-path и ничего не доказывает |
| Плагин, дублирующий существующий unit-тест | Если свойство уже проверено на уровне пакета, повторение через процесс добавляет время сборки, но не уверенность |
| Плагин «на все случаи сразу» | При провале непонятно, какое свойство нарушено |

---

## Ключевое отличие от предыдущих фаз

До Phase 11 всё проверялось **внутри одного процесса**: `net.Pipe`, тестовые
двойники, `fakeSpawner`. Это корректно проверяло логику, но обходило целый слой:

```
Phase 9-10 (in-process)          Phase 11 (real process)
─────────────────────────        ────────────────────────
net.Pipe                         stdin/stdout настоящего процесса
fakeSpawner                      exec.Command
имитация краха                   реальный os.Exit / паника
имитация зависания               реальный процесс, который не читает канал
                                 SIGKILL, process group, Pdeathsig
```

Свойства, которые **невозможно** проверить in-process и которые появляются здесь:

- реальный краш процесса не роняет runtime;
- зависший процесс действительно убивается, а не «помечается убитым»;
- `Setpgid` работает: потомки плагина не переживают его смерть;
- `Pdeathsig` работает: смерть runtime не оставляет сирот;
- сериализация переживает реальный поток байт, а не идеальный `net.Pipe`.

## Каталог плагинов

Пять плагинов, каждый с одним утверждением.

### 1. `hello` — базовый путь работает end-to-end

**Утверждение:** плагин, запущенный как настоящий процесс, проходит handshake,
выполняет разрешённую операцию и штатно завершается.

**Зачем нужен, если есть E2E из Phase 10:** тот работал через `net.Pipe` в одном
процессе. Здесь впервые проверяется вся цепочка запуска: `exec.Command` →
stdin/stdout → handshake → операция → `STOP` → `STOP_ACK` → завершение процесса.

**Провал означает:** сломан базовый путь; остальные плагины бессмысленно
запускать.

**Проверяется:**
- процесс запускается и проходит handshake;
- `storage.get` с выданным правом возвращает значение;
- `STOP` приводит к штатному завершению с кодом 0;
- `ExitCleanStop`, перезапуска не происходит.

---

### 2. `crash` — падение плагина не роняет runtime

**Утверждение:** процесс плагина, аварийно завершившийся любым способом, не
нарушает работу runtime и классифицируется как `ExitCrash`.

**Режимы (выбираются переменной окружения):**

| Режим | Что делает | Что проверяет |
|---|---|---|
| `exit` | `os.Exit(1)` сразу после handshake | Обработку ненулевого кода |
| `panic` | Паника в обработчике | Крах во время выполнения операции |
| `mid-request` | Падение, не ответив на запрос | Что вызывающий получает ошибку, а не висит |
| `before-handshake` | Падение до `HELLO_ACK` | `ExitHandshakeFailure` вместо `ExitCrash` |

**Провал означает:** недоверенный код может уронить платформу — прямое нарушение
T10 threat model.

**Проверяется:**
- runtime остаётся работоспособным после каждого режима;
- классификация верна для каждого режима;
- `crash` перезапускается с backoff, `before-handshake` — тоже, но обе серии
  ограничены `MaxAttempts`;
- другие плагины, запущенные параллельно, продолжают работать.

---

### 3. `permission` — enforcement нельзя обойти из недоверенного кода

**Утверждение:** плагин, активно пытающийся получить доступ к тому, на что не имеет
прав, получает отказ на каждой попытке.

Это **не** повторение unit-тестов авторизации. Там проверялось, что `Authorizer`
корректно отвечает на корректно заданные вопросы. Здесь плагин задаёт вопросы
**некорректно** — так, как это сделал бы злоумышленник:

| Атака | Ожидаемый ответ |
|---|---|
| Операция без права (`storage.put` без `storage.write`) | `FORBIDDEN` |
| Право есть на чтение, запрашивается запись | `FORBIDDEN` (не выводится из `storage.read`) |
| Обращение к чужому namespace явным указанием | Данные другого плагина недоступны |
| Несуществующая операция | `UNSUPPORTED`, не `FORBIDDEN` |
| `plugin_id` другого плагина в теле запроса | Игнорируется; идентичность из канала |
| Операция после отзыва права на живой сессии | `FORBIDDEN` немедленно |
| Тысяча запросов подряд без прав | Все отклонены; runtime не деградирует |

**Провал означает:** security boundary дырявый — самый серьёзный из возможных
результатов Phase 11.

---

### 4. `storage` — изоляция данных между плагинами реальна

**Утверждение:** два плагина с одинаковыми ключами не видят данные друг друга.

**Сценарий:** два процесса, оба пишут по ключу `secret`, оба читают `secret`.
Каждый должен получить **своё** значение.

**Почему отдельный плагин, а не подтест `permission`:** здесь проверяется не отказ
в доступе, а **невидимость**. Плагин A не получает `FORBIDDEN` при чтении своего
`secret` — он получает своё значение, не подозревая о существовании чужого.
Namespace-префикс `plugin.<id>.*` (ADR-032, `sdk-boundary.md` раздел 3) должен
работать прозрачно.

**Проверяется:**
- данные не пересекаются при одинаковых ключах;
- `list` не показывает чужие ключи;
- перезапуск плагина сохраняет его данные (persistent state, lifecycle §8);
- удаление плагина не затрагивает данные другого.

---

### 5. `stress` — нагрузка и злоупотребление не роняют runtime

**Утверждение:** плагин, ведущий себя как DoS-источник, не выводит runtime из
строя.

| Режим | Атака | Что проверяет |
|---|---|---|
| `flood` | Тысячи запросов без пауз | Runtime отвечает, не растёт неограниченно |
| `large-payload` | Сообщения на границе и за границей лимита | `maxMessageSize` соблюдается, аллокации нет |
| `slow-reader` | Не читает ответы и события | Очередь событий ограничена (T9), runtime не блокируется |
| `hang` | Зависает, не отвечая на `STOP` | Принудительное завершение за ограниченное время |
| `fork-bomb` | Порождает дочерние процессы | `Setpgid`: потомки умирают вместе с плагином |

**Провал означает:** один плагин может испортить работу всей платформы — нарушение
T9 и главного инварианта «ни один компонент не может навечно остановить Runtime».

## Матрица покрытия

Какое свойство доказывает какой плагин:

| Свойство | Источник требования | Плагин |
|---|---|---|
| Базовый путь работает | — | `hello` |
| T10: падение не роняет систему | threat-model | `crash` |
| T5: enforcement на каждый запрос | threat-model | `permission` |
| T6: обход IPC невозможен | threat-model | `permission` |
| T4: изоляция данных | threat-model | `storage` |
| T9: DoS не проходит | threat-model | `stress` |
| P7: завершаемость | sandbox §2 | `stress` (`hang`) |
| P1 + `Setpgid` | sandbox | `stress` (`fork-bomb`) |
| Классификация завершений | lifecycle §5 | `crash` |
| Restart policy и лимиты | lifecycle §6 | `crash` |
| Namespace-изоляция | sdk-boundary §3 | `storage` |
| Маппинг операция→право | ADR-032 | `permission` |

Свойство без плагина в этой таблице означает, что оно не проверено на реальном
процессе — и это должно быть видно, а не подразумеваться.

## Как устроен запуск

Тестовые плагины — **настоящие исполняемые файлы**, собираемые из исходников в
`tests/plugins/<name>/`. Они используют `photon-plugin-sdk` как обычный плагин: без
привилегий, без доступа к внутренностям runtime.

```
go build -o <tmpdir>/hello ./tests/plugins/hello
                    ↓
        host.Config{Entrypoint: ...}
                    ↓
            exec.Command → stdin/stdout
                    ↓
              настоящий процесс
```

**Плагины не должны требовать сети, файлов вне пакета или особых прав** — иначе
тест начнёт падать по причинам, не связанным с проверяемым свойством.

Поведение задаётся переменными окружения (`PHOTON_TEST_MODE`), а не аргументами:
аргументы командной строки видны в `ps` и создали бы у теста зависимость от
конкретного способа запуска процесса runtime'ом.

---

## Что должно быть покрыто

1. Каждый плагин из каталога собирается и запускается как реальный процесс
2. Каждое утверждение из раздела «Каталог» проверено отдельным тестом
3. Провал плагина даёт понятное сообщение о том, **какое свойство** нарушено
4. Тесты не зависят от порядка выполнения и могут идти параллельно
5. Ни один тест не оставляет живых процессов после завершения
6. Время выполнения ограничено: зависший плагин валит тест по таймауту, а не
   останавливает прогон
