# Plugin IPC Specification

Спецификация протокола между `photon-plugin-runtime` и процессом плагина.

**Сначала семантика, wire-format в конце.** Порядок не случаен: выбор
protobuf/JSON/сокетов — это способ передать сообщения, а не решение о том, какие
сообщения существуют и кто кому доверяет. Обратный порядок привёл бы к протоколу,
повторяющему возможности выбранной библиотеки, а не модель системы.

Опирается на:
- `docs/plugin-threat-model.md` — плагин недоверенный, Runtime доверенный
- `docs/plugin-lifecycle.md` — состояния, handshake, классификация нарушений
- `docs/plugin-manifest.md` — `plugin_id`, `protocol_version`, requested vs granted
- ADR-005, ADR-030 — граница ядро ↔ runtime ↔ плагин

---

## Базовый принцип

> **IPC transport сам по себе не является authorization boundary.
> Authorization происходит на уровне каждого semantic request.**

```
IPC connected  ≠  permission granted
```

Установленное соединение означает только «канал есть». Каждый отдельный запрос
проходит проверку прав заново, независимо от того, что соединение уже открыто и
handshake давно пройден.

Практическое следствие: новый IPC-транспорт (unix socket, named pipe, что угодно
на Android) можно добавить позже, не переписывая модель безопасности — она не
опирается на свойства канала.

## 1. Handshake

```
Runtime → Plugin   HELLO
                     protocol_version      предлагаемая версия
                     runtime_instance      идентификатор запуска Runtime
                     plugin_instance       идентификатор запуска плагина

Plugin → Runtime   HELLO_ACK
                     protocol_version      подтверждённая версия
                     plugin_id
                     capabilities[]        что плагин УМЕЕТ
```

Переход `STARTING → RUNNING` — **только** после успешного handshake
(lifecycle, раздел 3).

**Проверки, любая неудача → `FAILED`:**

| Проверка | Причина отказа |
|---|---|
| `protocol_version` совместим | Стороны не поймут друг друга |
| `plugin_id` совпадает с манифестом | Запущен не тот плагин |
| `capabilities` ⊆ `capabilities.provided` из манифеста | Плагин заявляет больше, чем декларировал при установке |
| Handshake уложился в отведённое время | Плагин завис на старте |

До завершения handshake плагин **не имеет права ни на один запрос**. Любое
сообщение, кроме `HELLO_ACK`, в состоянии `STARTING` — нарушение протокола.

---

## 2. Identity: откуда Runtime знает, кто звонит

> **Runtime никогда не доверяет `plugin_id`, присланному внутри запроса.**

Идентичность вызывающего определяется **каналом**, а не содержимым сообщения:

```
IPC-канал  ──►  Runtime уже знает:
                  runtime_instance
                  plugin_id
                  plugin_instance
                  granted permissions
```

Runtime сам запустил этот процесс (lifecycle, раздел 2) и сам открыл этот канал —
значит однозначно знает, кто на другом конце.

**Поле `plugin_id` внутри обычного запроса запрещено.** Если оно там появится:

```
request { plugin_id: "com.other.plugin", op: "storage.read" }
   → protocol_violation
```

Не «проигнорировать и продолжить»: наличие такого поля означает либо баг SDK, либо
попытку выдать себя за другой плагин. Оба случая требуют разбирательства, а не
тихого исправления.

Это прямое следствие threat model, T6 (обход IPC) и правила из lifecycle: плагин
не имеет права объявлять что-либо о себе — состояние и идентичность определяет
Runtime.

---

## 3. Request / Response correlation

Каждый запрос несёт `request_id`, уникальный в пределах сессии:

```
Plugin → Runtime   REQUEST   request_id=42  op="storage.read"  payload=...
Runtime → Plugin   RESPONSE  request_id=42  result=... | error=...
```

Требования:

- Десятки операций могут быть в полёте одновременно; ответы сопоставляются строго
  по `request_id`.
- Повторное использование активного `request_id` → `protocol_violation`
  (иначе ответ на один запрос доставится другому — с непредсказуемыми
  последствиями для плагина, который считает, что читает свои данные).
- `request_id` не переживает перезапуск: он уникален в пределах сессии, а не
  плагина. После рестарта нумерация начинается заново — соответствует правилу
  «активные IPC-запросы не переживают перезапуск» (lifecycle, раздел 8).
- Ответ на неизвестный `request_id` (Runtime не отправлял такого запроса) →
  `protocol_violation`.

---

## 4. Permission enforcement

**Порядок обязателен:**

```
Plugin
   ↓ IPC Request
Runtime
   ↓
Identity        (из канала, не из сообщения — раздел 2)
   ↓
Authorizer      (ports.Authorizer + trust level + политика)
   ↓
Core operation
```

**Не так:**

```
Plugin → Core                      ← нет проверки
Plugin → "у меня есть право X"     ← права заявляет недоверенная сторона
```

Проверка выполняется на стороне Runtime **на каждый запрос**, а не один раз при
подключении. Плагин не передаёт свои права в запросе и не может на них ссылаться —
он передаёт только то, что хочет сделать.

Отдельно: изменение политики во время работы плагина применяется немедленно к
следующему запросу. Права, проверенные при handshake, не кэшируются как
«выданные навсегда» — иначе отзыв права требовал бы перезапуска плагина.

## 5. Классификация ошибок

Машинные категории, а не текстовые сообщения:

| Код | Значение |
|---|---|
| `INVALID_REQUEST` | Синтаксически корректно, но семантически бессмысленно (нет обязательного поля, недопустимое значение) |
| `UNAUTHORIZED` | Субъект **не установлен**: handshake не пройден, сессия не аутентифицирована |
| `FORBIDDEN` | Субъект установлен, но **capability отсутствует** |
| `NOT_FOUND` | Запрошенный объект не существует |
| `INVALID_STATE` | Операция невозможна в текущем состоянии (например, запрос после `STOPPING`) |
| `UNSUPPORTED` | Операция или её версия не поддерживается этим Runtime |
| `INTERNAL_ERROR` | Сбой на стороне Runtime, не вина плагина |

**`UNAUTHORIZED` и `FORBIDDEN` не смешиваются.** Разница принципиальна:

- `UNAUTHORIZED` — «я не знаю, кто ты» → проблема сессии, повтор запроса
  бессмыслен;
- `FORBIDDEN` — «я знаю, кто ты, и тебе нельзя» → проблема прав, повтор
  бессмыслен до изменения политики, но плагин может осмысленно сообщить об этом
  пользователю.

Слияние их в один код лишило бы плагин возможности различить «переподключись» и
«попроси права» — и подтолкнуло бы SDK к неверной обработке.

## 6. Cancellation

```
Plugin → Runtime   REQUEST  request_id=42  op="long.operation"
Plugin → Runtime   CANCEL   request_id=42
Runtime → Plugin   RESPONSE request_id=42  error=CANCELLED
```

Обязательно с обеих сторон:

- **Плагин отменяет свой запрос** — пользователь закрыл экран, операция больше не
  нужна;
- **Runtime отменяет исполнение** — плагин переходит в `STOPPING`, отзвано право,
  истёк deadline.

Без отмены длинная операция переживает закрытие клиента и продолжает занимать
ресурсы — а на стороне Runtime это ресурсы **ядра**, не плагина.

`CANCEL` на неизвестный или уже завершённый `request_id` — не ошибка (гонка:
ответ мог быть отправлен, пока `CANCEL` летел).

---

## 7. Deadlines

> Runtime не позволяет плагину бесконечно удерживать запрос.

Каждый запрос имеет дедлайн: либо явный в самом запросе, либо из политики Runtime
по умолчанию. При истечении — `RESPONSE` с ошибкой `DEADLINE_EXCEEDED` и отмена
исполнения на стороне Runtime.

Плагин **не может** назначить дедлайн больше максимума, разрешённого политикой:
иначе ограничение обходится одной строкой в запросе.

Симметрично: Runtime, отправивший событие или запрос плагину, тоже не ждёт
бесконечно — иначе зависший плагин блокирует Runtime, что нарушает T10 (падение
или зависание плагина не должно ронять систему).

---

## 8. Events: Runtime → Plugin

Отдельное направление, **не** моделируется как response:

```
Runtime → Plugin   EVENT  event_id=...  type="chat.message"  payload=...
```

Почему не response: событие не является ответом на запрос плагина — оно приходит
по инициативе Runtime, в произвольный момент, и может не иметь никакого отношения
к тому, что плагин сейчас делает. Попытка уложить их в модель request/response
потребовала бы фиктивных «долгих запросов» и сломала бы correlation.

**Events тоже проходят проверку прав:** событие доставляется только плагину,
имеющему соответствующее право на подписку. Отзыв права прекращает доставку — без
перезапуска плагина.

Обработка отставания: если плагин не успевает читать события, Runtime **не** копит
их бесконечно (это DoS через память ядра — T9). Политика переполнения (отбрасывать
старые/новые, разрывать сессию) — параметр реализации, но неограниченная очередь
запрещена.

---

## 9. Shutdown

```
Runtime → Plugin   STOP
                     ↓
Plugin → Runtime   STOP_ACK           (плагин завершает текущие операции)
                     ↓
              graceful timeout
                     ↓
          force termination            (если не завершился)
```

> **Runtime не зависает вместе с плагином.**

Если `STOP_ACK` не пришёл за отведённое время или процесс не завершился —
принудительное завершение. Итоговое состояние всё равно `STOPPED`: штатная
остановка была запрошена, значит результат ожидаемый (lifecycle, раздел 4).

---

## 10. Protocol violation

Все перечисленные случаи → **закрытие IPC-сессии** и перевод плагина в
`protocol_violation` (lifecycle, раздел 5):

| Нарушение |
|---|
| Некорректный кадр (malformed frame) |
| Неизвестный тип сообщения |
| Невозможный переход состояния (запрос до handshake, `HELLO_ACK` дважды) |
| Повторное использование активного `request_id` |
| Ответ на несуществующий `request_id` |
| Несовместимая версия протокола после handshake |
| Наличие `plugin_id` в обычном запросе (раздел 2) |

> **Runtime не пытается «починить» недоверенный поток.**

Попытка восстановиться после рассинхрона означает продолжение разбора данных, в
корректности которых уже нет уверенности — ровно тот класс уязвимостей, ради
которого в `adapters/tcp` протокольные ошибки отделены от I/O и всегда ведут к
закрытию соединения.

Напоминание из lifecycle: `protocol_violation` **не перезапускается
автоматически** — в отличие от `crash`. Сбой можно пережить перезапуском,
нарушение протокола повторится с той же вероятностью и может быть попыткой атаки.

## 11. Сводка типов сообщений

| Сообщение | Направление | Назначение |
|---|---|---|
| `HELLO` | Runtime → Plugin | Начало handshake |
| `HELLO_ACK` | Plugin → Runtime | Подтверждение handshake |
| `REQUEST` | Plugin → Runtime | Запрос операции |
| `RESPONSE` | Runtime → Plugin | Результат или ошибка |
| `CANCEL` | обе стороны | Отмена запроса по `request_id` |
| `EVENT` | Runtime → Plugin | Событие по инициативе Runtime |
| `STOP` | Runtime → Plugin | Запрос штатной остановки |
| `STOP_ACK` | Plugin → Runtime | Подтверждение остановки |

Восемь типов. Намеренно нет: heartbeat (живость определяется по состоянию
процесса — это забота Supervisor, а не протокола), reconnect (сессия не переживает
разрыв — новый процесс, новый handshake), потоковой передачи (не подтверждена
потребность; добавляется отдельным решением, если появится).

## 12. Wire-format: выбор после семантики

Семантика выше не зависит от формата сериализации. Кандидаты:

| Формат | За | Против |
|---|---|---|
| **Protobuf** | Уже в проекте (`photon-core/protobuf`, ADR-025); схема строгая; кодогенерация для Go и других языков SDK | Требует protobuf-runtime в каждом SDK |
| **JSON** | Отлаживается глазами; поддерживается везде без зависимостей | Слабая типизация; больше объём |

**Предварительный кандидат — protobuf**, по той же логике, что в ADR-025: схема
уже есть, кодогенерация решает вопрос SDK на разных языках, а IPC — внутренняя
граница, не публичный ABI (в отличие от `photon_core.h`, где JSON был выбран
именно чтобы не тащить protobuf-runtime в каждый binding — ADR-026, п.7).

**Решение принимается отдельно**, при написании скелета `photon-plugin-runtime`.
Здесь важно другое: смена формата не должна затрагивать разделы 1–11 — если
затронет, значит семантика была описана в терминах формата, и это ошибка.

---

## 13. Что из этого следует для реализации

1. **Идентичность привязана к каналу** — структура сессии должна хранить
   `plugin_id`/`plugin_instance`/granted permissions рядом с соединением, а не
   извлекать из сообщений.
2. **Таблица активных `request_id`** нужна с обеих сторон: для correlation, для
   отмены и для обнаружения повторного использования.
3. **Каждый обработчик запроса вызывает `Authorizer`** — не «проверить один раз
   при подключении».
4. **Очередь событий ограничена** — неограниченная равна DoS через память ядра.
5. **Все таймауты двусторонние** — Runtime не ждёт плагина бесконечно ни в одном
   сценарии.
