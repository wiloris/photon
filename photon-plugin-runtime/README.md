# photon-plugin-runtime

Runtime для плагинов Photon: загрузка манифеста, проверка прав, запуск и надзор
за процессом плагина, IPC.

**Статус: skeleton.** Структура ответственности и границы зафиксированы, **ни один
механизм не реализован.** Собирается с нулевой функциональностью — это осознанная
контрольная точка: архитектура Runtime существует, но ничего ещё не считается
работающим.

---

## Границы доверия

```
Photon Core          ← ports.Authorizer (контракт), ports.Storage, ports.Identity
     ▲
     │ uses
photon-plugin-runtime  ← ДОВЕРЕННАЯ сторона: принимает решения о правах
     ▲
     │ IPC (не импорт!)
photon-plugin-sdk      ← отдельный модуль
     ▲
     │
  Plugin               ← НЕдоверенный сторонний код
```

**SDK — отдельный репозиторий/модуль, а не подпакет.** Разделение физическое,
потому что это разные trust boundaries: код SDK исполняется внутри недоверенного
процесса плагина, код Runtime — снаружи и принимает решения о правах. Без
физического разделения со временем неизбежно появляется цикл
`runtime → sdk → runtime` либо случайный импорт Runtime API в код плагина.

**Направление зависимостей (обязательное):**

| Кто | Может импортировать | Не может |
|---|---|---|
| `photon-core` | — | **не знает о runtime вообще** (ADR-005, ADR-030) |
| `photon-plugin-runtime` | `photon-core/ports` | — |
| `photon-plugin-sdk` | — | runtime implementation, photon-core |
| Plugin | `photon-plugin-sdk` | всё остальное |

Runtime и Plugin общаются **исключительно через IPC**.

## Внутренняя структура

```
manifest ───────┐
permissions ────┤
                ▼
            supervisor
                │
          ┌─────┴─────┐
          ▼           ▼
        host        sandbox
          │
          ▼
       process
          │
         IPC
```

| Пакет | Ответственность | Спецификация |
|---|---|---|
| `manifest/` | Парсинг и валидация манифеста | `docs/manifest.md` |
| `permissions/` | Политика прав, реализация `ports.Authorizer` | `docs/threat-model.md` |
| `ipc/` | Протокол Runtime ↔ плагин | `docs/ipc.md` |
| `host/` | Запуск процесса, окружение | `docs/lifecycle.md` §2 |
| `supervisor/` | State machine, restart policy, registry | `docs/lifecycle.md` |
| `sandbox/` | Платформенная изоляция | `docs/threat-model.md` §4–5 |

## Спецификации (написаны до кода)

Тот же порядок, что сработал с `adapters/tcp` — `WIRE_FORMAT.md` до реализации:

1. **`docs/threat-model.md`** — от чего защищаемся (10 угроз) и **что намеренно НЕ
   обещаем** (6 пунктов). Базовый инвариант: плагин не получает возможностей
   просто потому, что запущен.
2. **`docs/lifecycle.md`** — state machine из 7 состояний, владение процессом,
   handshake, классификация завершений, restart policy с jitter.
3. **`docs/manifest.md`** — 5 блоков; манифест это **запрос**, а не разрешение.
4. **`docs/ipc.md`** — 8 типов сообщений; `IPC connected ≠ permission granted`.

Порядок не произволен: IPC проектировался последним, потому что должен отражать
модель lifecycle и capabilities, а не наоборот.

---

## Что НЕ реализовано (весь список)

На этапе skeleton намеренно отсутствуют:

- настоящий sandbox (любой платформы);
- spawn процессов;
- IPC wire-format и транспорт;
- база выданных прав;
- restart/backoff;
- SDK.

Каждый пакет содержит только `doc.go` с описанием границы ответственности и
ссылкой на спецификацию.
