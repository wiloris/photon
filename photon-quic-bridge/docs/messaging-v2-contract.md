# Implementation contract: ADR-104 … ADR-107 (Messaging v2)

**Статус:** P1, выведен orchestrator из принятых ADR-104–107 (решение владельца 2026-10-05: «не запрашивай
дополнительные решения, если они следуют из принятых ADR»). Каждое решение ниже либо цитирует ADR, либо
отмечено «реализация» — выбор, который ADR оставил исполнителю и который не меняет семантику.
База: `messaging/adr-104-107` @ `540830d` (линия slice-6 `957ded3` + fix215 `d51ac8b`).
Образец формы и правил: `conversation-implementation-contract.md` (900–931) — всё, что здесь не сказано, —
как там (порядок проверок ADR-099 §11, идемпотентность §10.2, X/S-блокировки ADR-101 §5.2/5.3, ошибки §12,
`temporarily_unavailable` при сбое хранилища, никаких идентификаторов Mattermost в ответах).

## 2. M2 — `direct` (ADR-104)

- **Схема v3:** `engram_direct_pair (low_pid text, high_pid text, conversation_id text NOT NULL UNIQUE,
  PRIMARY KEY (low_pid, high_pid))`; `low_pid < high_pid` (строки канонического PhotonID).
- **905 OPEN_DIRECT** `{request_id, peer_photon_id}` → `{conversation: Snapshot, created: bool}`
  (ADR-104 §3.2). Порядок: формат PhotonID → `invalid_photon_id`; свой → `invalid_request`; peer не найден /
  деактивирован → `photon_id_not_found` (как `resolveExisting`). Идемпотентность — **по паре**: под
  транзакционной advisory-блокировкой ключа пары (реализация) найти строку пары → вернуть разговор
  (`created:false`); иначе создать как 900 (носитель — распределитель §6.0 контракта 900–931; `kind:"direct"`,
  `title:""`, `history_policy:"full"`, оба участника `member`, события `created` + `member_added` пира) и
  вставить пару. `request_id` записывается (§10.2), но на результат не влияет: повтор и встречный вызов
  дают тот же `conversation_id`.
- **Права `direct`** (ADR-104 §3.1): обоим — `messages.send`, `messages.read`; 903, 904, 910, 911, 912, 920, 921
  на `direct` → `invalid_request` (после проверки доступа, ADR-099 §11). 900 с `kind:"direct"` →
  `invalid_request` (создаёт только 905).
- **902**: возвращает все виды; ListItem получает `last_item` (последний **видимый** вызывающему элемент ленты,
  форма Item ADR-099 §9.3, `null` если ленты нет) и для `direct` — `peer_photon_id` (реализация: форма, без
  новой семантики — второй участник ADR-104 §3.1). Порядок и курсор — как были (ADR-099 §6).
- **Тесты:** гонка двух встречных 905 → один разговор (PG, параллельно); повтор; свой/неизвестный/
  деактивированный; 930/931 на `direct` (P-тесты как у групп); запреты; 902 со смесью видов, `last_item`
  при since_join не раскрывает чужие периоды.

## 3. M3 — история назад (ADR-105)

- **940** `{conversation_id, before:{created_at,id}, limit?}` → `{items, at_start}`: доступ как 931 (S-блокировка,
  `callerAccess`, архив §8.1), видимость — периоды since_join; элементы строго старше якоря, ближайшие к нему,
  в порядке ленты; `limit` 1..200 (иначе `invalid_limit`), по умолчанию 60; `at_start` — нет видимых элементов
  старше выданных. Барьер не нужен (ADR-105 §1.4), но надгробия и неопубликованные резервы не выдаются.
- **219** `{with_photon_id, before:{created_at,id}, limit?}` → `{items, at_start}` по DM-каналу пары
  (как 218: S1-чтение, порядок ADR-092 §2.1, форма сообщения 218, `client_msg_id` только своих); окна нет
  (ADR-105 §1.3).
- **Тесты:** граница якоря (равный `created_at`, разные id), `at_start`, since_join-разрывы не раскрываются,
  `limit` вне диапазона, поздний пост в окне (219) находит проход 218 вперёд.

## 4. M4 — жизненный цикл (ADR-106)

- **Схема v4:** `engram_member_state (conversation_id, photon_id, hidden_at bigint NULL, pinned_at bigint NULL,
  muted_until bigint NULL, updated_at bigint NOT NULL, PRIMARY KEY (conversation_id, photon_id))`.
- **906 UNARCHIVE** `{request_id, conversation_id, expected_version?}` → `{conversation: Snapshot}`: под X, право
  `conversation.archive`; не архивный → `changed`-эквивалент: возвращается снимок без события и без версии
  (реализация, как «нет изменения» §6.2); иначе событие `unarchived`, версия +1. Разговор без участников в
  периоде `active` разархивировать некому (ADR-106 §2.1): любой вызывающий получает `no_access` /
  `conversation_not_found` по порядку проверок ADR-099 §11 — отдельного кода нет.
- **907 MEMBER_STATE_SET** `{conversation_id, hidden?, pinned?, muted_until?}` → `{member_state}`; доступ —
  участник `active` или бывший участник архивного разговора; без X (не меняет разговор); `pinned:true` при уже
  5 других закреплённых → `invalid_request` (ADR-106 Q4; отдельного кода в ADR нет — клиент знает число из 902).
- **«Возврат скрытого» — правило чтения, а не запись в 930** (реализация; 930 заморожен): разговор скрыт, если
  `hidden_at IS NOT NULL AND (last_activity_at <= hidden_at OR muted_until > now)`.
- **902**: `member_state` в ListItem; порядок — закреплённые первыми (`pinned_at` убыв.), затем
  `last_activity_at`; скрытые не возвращаются без `include_hidden:true`. Курсор keyset расширяется
  закреплением (реализация: закреплённые — первая страница целиком, ≤5).
- **Тесты:** 906 право/событие/версия/повтор; 907 идемпотентность, невидимость другим, версия не меняется;
  скрытый возвращается после нового сообщения и не возвращается при `muted_until`; предел 5.

## 5. M5 — приглашения (ADR-107 этап 1)

- **Схема v5:** `engram_invite (invite_id text PK, conversation_id text NOT NULL, token_hash bytea NOT NULL UNIQUE,
  created_by text, created_at bigint, expires_at bigint NULL, max_uses int NULL, uses int NOT NULL DEFAULT 0,
  revoked_at bigint NULL)`; хранится SHA-256 токена.
- **913** создать (`members.add`, ключ §10.2) → токен 128 бит, base64url, только в этом ответе и в сохранённом
  ответе ключа идемпотентности (повтор отдаёт тот же токен); **914** отозвать; **915** список без токенов.
- **916 JOIN_BY_INVITE** `{request_id, token}`: найти по хэшу под X разговора; недействителен (нет / отозван /
  истёк / `uses >= max_uses`) → `invite_invalid` (один код); архив → `conversation_archived`; уже участник →
  снимок без события; иначе новый период `member`, `uses+1`, событие `member_joined` (`actor` — вступивший,
  `invite_id`), версия +1.
- **Ограничение частоты** 916: 20 попыток в минуту на пользователя в памяти процесса (реализация,
  эксплуатационный параметр ADR-107 §3).
- **Тесты:** гонка двух вступающих при `max_uses=1` → ровно один; все причины → один код; токен не в логах
  (проверка журнала теста); хэш в таблице; since_join для вступившего.

## 5a. M6 — публичные разговоры (ADR-107 этап 2)

Добавлено 2026-10-06 по решению владельца ADR-107 Q1 («этап 2 — следующим»), Q3, Q4; выведено orchestrator, новых
решений не содержит. Отмечено «реализация» — то, что ADR оставил исполнителю.

- **Коды:** 917 `DIRECTORY_SEARCH`, 918 `JOIN_PUBLIC` в `enum Action` (резерв ADR-099 §2.3, свободны; как M1 —
  без oneof-payload, перегенерация `photon.pb.go` тем же protoc), `ResourceFor` → ConversationResource, authz
  «аутентифицирован», `TestAuthzCoversEveryAction` зелёный.
- **Схема v6:** `engram_conversation.visibility text NOT NULL DEFAULT 'private'`, ограничение
  `visibility IN ('private','public')`; существующие строки — `private`.
- **900:** необязательное `visibility` (`private` по умолчанию); при `public` поле `history_policy` можно опустить —
  тогда `full` (ADR-107 Q3); при `private` `history_policy` обязательно, как было (запросы без `visibility` —
  байт в байт прежнее поведение, тесты 900 без изменений). `visibility` входит в хэш ключа §10.2 только когда
  передано (реализация: хэш прежних запросов не меняется).
- **903:** необязательное `visibility`; право `conversation.update`; изменение — в событии `metadata_changed`
  (поле `visibility`), версия +1; на `direct` 903 уже `invalid_request` (M2). **Snapshot** и ListItem 902
  получают `visibility`. 905 создаёт `private`.
- **917** `{query, cursor?, limit?}` → `{conversations:[{conversation_id, title, description, member_count}],
  next_cursor?}`: только `public` и не архивные; без состава и ленты (ADR-107 §2.5); подстрока названия без учёта
  регистра (Q4); `query` после обрезки 1..64 символа, иначе `invalid_request`; `limit` 1..50, по умолчанию 20,
  иначе `invalid_limit`; порядок `(created_at DESC, conversation_id)`, курсор непрозрачный keyset (реализация).
  Вызывающему участие не нужно; закрытые не видны никогда.
- **918** `{request_id, conversation_id}` → `{conversation: Snapshot}`: как 916 (ключ §10.2, X, новый период
  `member`, событие `member_joined` без `invite_id`, версия +1, уже участник — снимок без события), но для
  `public`; `private` или нет такого → `conversation_not_found` (ADR-107 §2.6, ADR-098 §8); архив →
  `conversation_archived`. Ограничение частоты — общее с 916 (ADR-107 §3).
- **Тесты:** 900/903 без `visibility` — прежние тесты без изменений; `public` без `history_policy` → `full`;
  917 не возвращает `private`/архивные, регистр, курсор без дублей; 918 на `private` неотличим от несуществующего;
  гонка двух 918 — два разных периода, `member_count` +2; since_join для вступившего по 918.

### 5b.1. M7 — непрочитанное (ADR-108)

- **Схема v7:** `engram_read_state (conversation_id text, photon_id text, read_created_at bigint NOT NULL,
  read_id text NOT NULL, updated_at bigint NOT NULL, PRIMARY KEY (conversation_id, photon_id))` (реализация:
  отдельная таблица, а не столбцы `engram_member_state` — у них разный смысл `updated_at`).
- **908 CONVERSATION_MARK_READ** `{conversation_id, up_to:{created_at, id}}` → `{read_up_to:{created_at,id},
  unread_count}` (ADR-108 §2.2). Доступ — как 931 (`callerAccess`: участник `active` либо бывший участник
  архивного, ADR-099 §8.1); без X (разговор не меняется) и без ключа идемпотентности. `up_to` новее последнего
  **видимого** вызывающему элемента обрезается до него. Позиция только растёт: запись — UPSERT, обновляющий
  строку только если `(created_at, id)` нового больше хранимого (реализация; гонка двух 908 не уменьшает
  позицию). Меньшая/повторная отметка — тот же ответ с хранимой позицией. Разговор без видимых элементов —
  `read_up_to: null`, `unread_count: 0`.
- **Непрочитанное** (ADR-108 §2.3, Q2): элементы `item_kind = message` **других** участников, опубликованные
  (не надгробия резервов и не удалённые по ADR-109), в периодах вызывающего (since_join), с позицией новее
  `read_up_to`; события и свои сообщения не считаются. Счёт ограничен `999` (Q3): запрос `LIMIT 1000`, ответ
  `min(n, 999)` — клиент показывает «999+» при 999.
- **902:** ListItem получает `read_up_to` (`null`, если отметки нет) и `unread_count`. Порядок и курсор 902 не
  меняются (ADR-106 §2.4). `direct` — так же (ADR-104).
- **Не входит:** видимость `read_up_to` других участников (Q1 — отдельное решение), уведомления (D6).
- **Тесты:** монотонность (меньшая не уменьшает, повтор — тот же ответ, две параллельные 908 — максимум);
  обрезка `up_to`; счётчик — только чужие опубликованные в видимых периодах, события и свои не считаются,
  since_join-разрыв не считается; предел 999 (1000+ сообщений); второй вызывающий (устройство того же
  аккаунта) видит тот же `read_up_to` в 902; доступ бывшего участника архива; чужой → `conversation_not_found`.

### 5b.2. M8 — правка, удаление, ответ, пересылка (ADR-109 без реакций)

- **Схема v8** (реализация): `engram_position` получает `deleted_at bigint NULL` (удаление для всех) и
  `edit_version int NOT NULL DEFAULT 0`; текущий текст после правки — `engram_item_edit (conversation_id,
  item_id text PRIMARY KEY, text text NOT NULL, edit_version int NOT NULL, updated_at bigint NOT NULL)`.
  Пост-носитель при правке **не** меняется (ADR-109 §2.1 — правка есть событие; исходный элемент сохраняет
  исходный текст, клиент применяет событие, ADR-109 §2.6).
- **932 MESSAGE_EDIT** `{request_id, conversation_id, item_id, text}` → `{event: Item}`: ключ §10.2 первым, X
  разговора (ADR-101 §5.2), проверки ADR-099 §11 (доступ → архив → право `messages.send` → авторство:
  не автор → `forbidden`); элемент не сообщение этого разговора / не видим автору → `invalid_request`;
  удалённый → `message_deleted` (новый код ADR-109 §2.7); текст — те же проверки и коды, что у 930
  (`message_empty`/`message_too_long`/`message_too_many_links`). Событие `message_edited {target_id, text,
  edit_version}` на новой позиции (как прочие события, `flushEvents`), `edit_version` = прежний + 1. Без
  ограничения времени (Q2). Конкурентные правки — последняя по позиции события выигрывает (Q4): X
  сериализует, `expected_version` нет. Версия разговора **не** меняется: ADR-099 §10.1 увеличивает её только
  при изменении метаданных, участия, ролей или состояния; событие несёт текущую версию. Ключ хранения события в
  `engram_event` сейчас строится из версии (`<conv>:<version>:<i>`, `conversation_change.go`) — для событий
  элементов он расширяется так, чтобы два события одной версии не совпали (реализация).
- **933 MESSAGE_DELETE** `{request_id, conversation_id, item_id}` → `{event: Item}`: как 932, право — автор
  своё, иначе новое право `messages.delete_any` (в таблице ролей: `owner`, `admin`; ADR-099 §7.4 — таблица
  данные) → иначе `forbidden`; повтор по уже удалённому (другим ключом) → `message_deleted`. Отмечает
  `deleted_at`, событие `message_deleted {target_id}`, удаляет пост-носитель в Mattermost (мягкое удаление
  Mattermost; медиа — ADR-055). Порядок «отметка в БД → событие → удаление поста» (реализация: при сбое
  удаления поста элемент уже не выдаётся — надгробие из `deleted_at`; повтор ключа отдаёт сохранённый ответ).
- **Надгробие** (ADR-109 §2.2): 931 и 940 выдают удалённое сообщение на его позиции как `{kind:"message", id,
  created_at, deleted:true}` — без автора, текста и полей ответа/пересылки. 902 `last_item` — так же.
- **Ответ** (ADR-109 §2.4, Q1): 930 получает необязательное `reply_to` (id элемента-сообщения **того же**
  разговора, видимого автору и не удалённого на момент отправки; иначе `invalid_request`). Элемент сообщения
  получает `reply_to` (omitempty). Отдельного кода 935 нет.
- **Пересылка** (ADR-109 §2.5): 930 получает необязательное `forwarded_from: {author_photon_id, created_at}`;
  проверка только формы (канонический PhotonID, `created_at > 0`, иначе `invalid_request`); ссылки на исходный
  разговор нет. Элемент получает `forwarded_from` (omitempty). Хранение `reply_to`/`forwarded_from` — в
  props поста-носителя (реализация, как `engram_event`).
- **Новые события** `message_edited`, `message_deleted` проходят `convItemOf` (поля `target_id`, `text`,
  `edit_version`); неизвестные старому клиенту события он пропускает (ADR-099 §9.3).
- **Тесты:** чужое редактировать нельзя; удалить чужое — только `messages.delete_any` (owner/admin да, member
  нет); повтор ключа 932/933; правка удалённого → `message_deleted`; две параллельные правки — обе события,
  `edit_version` 1 и 2, последняя по позиции; 931/940/902 отдают надгробие; since_join — события о невидимом
  элементе не раскрывают текст вне периода (событие `message_edited` о сообщении вне периода вызывающего не
  выдаётся — реализация, иначе правка раскрыла бы текст до вступления); 930 без новых полей — прежние тесты
  без изменений (diff = 0); `reply_to` на элемент другого разговора → `invalid_request`; `forwarded_from`
  неверной формы → `invalid_request`; `direct` — так же, как группа.

### 5b.3. M9 — серверный поиск (ADR-110)

- **Схема v9:** `engram_item_text (item_id text PRIMARY KEY, conversation_id text NOT NULL, created_at bigint NOT
  NULL, text_norm text NOT NULL)` + индекс `(conversation_id, created_at DESC, item_id)`. Индекс текста — в
  таблице Bridge (Q2). Нормализация: нижний регистр, `ё → е` (как локальный поиск). Заполнение: 930 (в той же
  транзакции, что позиция), 932 заменяет текст, 933 удаляет строку. Миграция v9 заполняет таблицу для уже
  опубликованных сообщений из постов-носителей (S1-чтение). Расширение `pg_trgm` не требуется — пользователь
  БД Mattermost может не иметь права `CREATE EXTENSION` (реализация; поиск — `LIKE` по `text_norm` в пределах
  разговоров вызывающего).
- **941 CONVERSATION_SEARCH** `{query, conversation_id?, before?:{created_at,id}, limit?}` → `{hits:[{conversation_id,
  item: Item}], next_before?}` (ADR-110 §2.1, Q1: все разговоры вызывающего + необязательный фильтр). Доступ — как
  931/940: только разговоры, где вызывающий участник или бывший участник архивного; только элементы в его
  периодах; без надгробий и удалённых; текст — актуальный после правок (ADR-109). `query` после обрезки — не
  меньше 2 символов (ADR-110 §2.3) и не больше 64 (реализация, как 917), иначе `invalid_request`; `limit`
  1..50, по умолчанию 20, иначе `invalid_limit`; порядок — свежие первыми `(created_at DESC, id DESC)`,
  `next_before` — позиция последнего выданного, если есть ещё. Чужой `conversation_id` →
  `conversation_not_found`. Legacy DM не покрывается (ADR-110 §2.4).
- **Тесты:** since_join — не находит вне периодов; не находит чужие разговоры, удалённое, старый текст
  отредактированного; находит новый текст; регистр и `ё`; страницы назад без дублей и пропусков; миграция v9
  заполняет существующие сообщения; замер на 100 000 сообщениях — время ответа записать в commit (без порога,
  ADR-110 §4.2).

### 5b.4. M10 — блокировки и бан (ADR-111)

- **Схема v10:** `engram_user_block (blocker_pid text, blocked_pid text, created_at bigint NOT NULL, PRIMARY KEY
  (blocker_pid, blocked_pid))`; `engram_member_period.state` допускает `banned`; `engram_conversation_ban
  (conversation_id text, photon_id text, banned_at bigint NOT NULL, banned_by text NOT NULL, PRIMARY KEY
  (conversation_id, photon_id))`.
- **220 USER_BLOCK / 221 USER_UNBLOCK** `{photon_id}` → `{blocked: bool}`; **222 USER_BLOCK_LIST** `{}` →
  `{blocked:[photon_id]}`. Идемпотентны без ключа (ADR-111 §2.1). Свой PhotonID → `invalid_request`; формат →
  `invalid_photon_id`; незарегистрированный → `photon_id_not_found` (как 212 — 212 не меняется, §2.2).
- **Последствия** (A заблокировал B; ADR-111 §2.2, Q1, Q2): `direct` A–B: 930 и 905 от B → `conversation_not_found`
  (причина не раскрывается; 905 от B — тот же код и при отсутствии разговора); 930 от A → новый код `blocked`
  (Q2); 931/940 — история видна обоим как была. Группы: 910 от B, добавляющий A → `photon_id_not_found`
  (неотличимо от несуществующего, ADR-111 §4.1); в общих группах сообщения B видны A (Q1) — 931/940/941 не
  фильтруют. 212 не меняется.
- **919 CONVERSATION_MEMBER_BAN** `{request_id, conversation_id, photon_id, ban: bool}` → `{conversation: Snapshot}`:
  ключ §10.2, X, проверки ADR-099 §11, право `members.remove` и правило «роль ниже» (ADR-099 §7.3; `owner`
  забанить нельзя → `forbidden`; цель без активного периода — допустимо, роль не сравнивается). `ban:true`:
  запись в `engram_conversation_ban`; активный период цели закрывается состоянием `banned`, событие
  `member_banned` (actor, target), версия +1; цель без активного периода — только запись, без события и версии
  (реализация). `ban:false`: удаляет запись; без события и без версии (реализация: ADR называет только
  `member_banned`); в разговор не возвращает (ADR-111 §2.3). На `direct` → `invalid_request` (как 910/911).
- **Запрет повторного вступления** забаненного: 916 → `invite_invalid`, 918 → `conversation_not_found` (те же
  неразличающие коды, что для прочих причин — ADR-107 §2.6); 910 администратором → `forbidden` (реализация:
  администратор знает о бане).
- **Тесты:** блокировка двусторонне закрывает `direct` по §2.2; B не может отличить блокировку от отсутствия
  разговора; A получает `blocked`; 910 по заблокировавшему неотличим от несуществующего; в общей группе
  сообщения видны; бан закрывает период `banned`, повторное вступление по ссылке/каталогу/910 отвергнуто;
  снятие бана не добавляет обратно; «роль ниже»; повтор ключа 919; since_join забаненного закрыт.

### 5b.5. M11 — реакции (ADR-109 §2.3) — ЖДЁТ СОСТАВ НАБОРА

### 5b.6. C1 — Core 813 (ADR-112)

- `813 ACTION_LOCAL_FEED_CLEAR {channel_id}` → `{removed: n}` (`photon-core/services/dispatcher` + `localfeed`):
  одной транзакцией `ports.WriteTx.Delete` удаляет записи, сегменты полноты и курсор канала; канал исчезает из
  804; повтор — `removed: 0`. Outbox (ADR-093) не трогается (Q1: исходящие отменяет клиент через 811). Bridge
  уже отвечает отказом на сотню 800 (ADR-064 §2) — проверить тестом, не менять. `ports/*` не меняются; C ABI
  не меняется (код идёт через `Photon_SendAction`). SDK (`photon-sdk`) — типизированный примитив `clear`
  рядом с локальной лентой (ADR-066), если в нём есть примитивы 800–812 (реализация).
- **Тесты** (ADR-112 §4): после 813 — 800 пусто, 805 без курсора, 804 без канала; соседние каналы целы; повтор —
  0; outbox цел; ошибка записи посреди транзакции не оставляет половины (инъекция ошибки в фиктивный
  `ports.Storage`); мутации — удаление без сегментов / без курсора ловится.
- **База:** вершина линии Bridge после M10 (не `main`): 813 добавляется в тот же `enum Action`, что коды M1–M10, и
  Bridge обязан получить правило-отказ на 813 в `authz.go` (`TestAuthzCoversEveryAction` перечисляет все коды
  enum) — отдельная линия от `main` разошлась бы с ней в `photon.proto`/`photon.pb.go`. Ветка
  `claude/engram-messaging-c1-<n>`.

## 7. Найдено при выводе контракта

- **Очистка локальной ленты** («удалить у себя», ADR-106 §2.5) требует локального действия Core, которого нет
  (`localfeed` не удаляет; действия 800–812 вводились ADR-064/065). Нужна поправка — отдельное решение D11
  (проект ADR). До него A3 реализует скрытие, но не очистку.
- **Live acceptance** требует выкладки Bridge на стенд — отдельное разрешение владельца.
- **2026-10-06:** очистка локальной ленты решена ADR-112 (813, §5b.6); A3 по-прежнему только скрывает — очистка в A10.
- **2026-10-06:** состав набора реакций (ADR-109 Q3 «8 эмодзи») в ADR не назван — M11/A11 ждут его (§5b.5).
- **2026-10-06:** `forwarded_from` — утверждение отправителя: Bridge проверяет только форму (ADR-109 §2.5 без ссылки на источник), подлинность автора пересылки не гарантируется.
- **2026-10-06:** Core проверяет код действия по своему `enum Action` до отправки (`photon-core/services/session/resource.go`
  `ResourceFor`: код вне enum → `ErrUnknownAction`, `PHOTON_ERR_INVALID_ACTION`). engram-android A1–A5 собирают
  Core из `photon` @ `27bb483`, где кодов 905–940 нет, — на устройстве эти вызовы будут отвергнуты Core до сети.
  Unit-тесты A1–A5 этого не видят (транспорт подменён). Закрывается сборкой клиента против Core с полным enum
  (линия M-срезов; A10 — первым, §5b.6) и проверяется в live acceptance.
