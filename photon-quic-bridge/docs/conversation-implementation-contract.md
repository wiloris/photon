# Implementation contract: групповые разговоры ENGRAM, действия 900–931

**Статус:** УТВЕРЖДЁН (2026-10-05) как P1 для срезов 900–931 (AGENT_WORKFLOW.md §2). Мост от принятых ADR к коду; **новых архитектурных
решений не принимает**. Если формулировка этого документа расходится с
первоисточником, прав первоисточник, а расхождение — дефект контракта.

## 0. Scope и источники

таблицы Bridge в PostgreSQL-базе Mattermost, реестровые изменения в

**Сверка трёх формулировок запроса с первоисточниками** (до написания
контракта):
- правило позиции `P = max(часы Bridge, H + 1)` **есть** в принятом

## 2. Storage

### 2.1. Источник DDL

Таблицы, столбцы, ограничения и индексы — **спецификация §2** (`840d49c`)
— единственный источник DDL. Контракт её не копирует: копия молча
расходится с оригиналом. Ниже — сводка и **единственная дельта** контракта.

| таблица | роль | ключевое |
|---|---|---|
| `engram_schema` | версия схемы Bridge | миграции под `photon:schema` (ADR-100 §2.6) |
| `engram_service_team` | служебные команды носителей | `reserved → created → full` |
| `engram_conversation` | разговор + привязка носителя | `version`; **`position_h`** — счётчик `H` (ADR-101 §5.1), не уменьшается; `carrier_*` (S3) |
| `engram_member_period` | периоды участия, роли | один `active` на пару (S2) |
| `engram_request` | ключи идемпотентности 900–921 | срок хранения — Q1, не выбран |
| `engram_event` | события ленты | `at` = позиция резерва; `pending → written` |
| **`engram_position`** | резерв на каждую выданную позицию (ADR-101 §5.1a) | `PRIMARY KEY (conversation_id, pos)`; `item_kind`, `item_key`, `state ∈ {reserved, published, aborted}`, `sender`, `payload_hash`, `reserved_at`, `post_id` |

Индексы `engram_position` по спецификации §2:
- `engram_position_key_live` — `UNIQUE (conversation_id, item_key) WHERE
  state <> 'aborted'`: не более одного неотменённого резерва на ключ
  (ADR-101 §5.6);
- `engram_position_open` — `(conversation_id, pos) WHERE state =
  'reserved'`: барьер (ADR-101 §5.1b);
- `engram_position_open_age` — `(reserved_at) WHERE state = 'reserved'`:
  сверка.

### 2.2. Дельта контракта: индекс для проверки владельца ключа

Проверка ADR-102 §2 смотрит резервы ключа **во всех состояниях**, включая
надгробия; `engram_position_key_live` надгробий не покрывает (спецификация
§6.3 шаг 2 это фиксирует). Контракт добавляет:

```sql
CREATE INDEX engram_position_key_all
  ON engram_position (conversation_id, item_key);
```

Это техническое средство исполнения ADR-102, не решение. При реализации
спецификацию §2 привести к этому индексу тем же изменением.

### 2.3. Правила хранилища

- доступ — только `*sql.DB` из `pluginapi` `Store.GetMasterDB()`; реплика не
  используется (ADR-100 §2.1);
- каждый шаг, меняющий состояние Bridge, — одна транзакция (ADR-100 §2.5);
  атомарности «состояние Bridge + пост» нет — её заменяют резерв и сверка;
- посты носителя — только через Plugin API `CreatePost`; прямой SQL к
  таблицам Mattermost — только чтение `Posts` (ADR-100 §2.3, ADR-092 §5);
  DDL над объектами Mattermost не выполняется;
- миграции — при активации под advisory lock `photon:schema`, только
  вперёд; проверка схемы, включая `engram_position` и индексы §2.1–§2.2; при
  отказе 900–931 → `temporarily_unavailable`, остальной Bridge работает
  (ADR-100 §2.6);
- только транзакционные advisory locks (`pg_try_advisory_xact_lock*`):
  сессионная блокировка через `pluginapi` Store после падения плагина не
  снимается (исследование R7; ADR-101 §5.11).

### 2.4. Инварианты хранилища (спецификация §3, S1–S13)

Обязательны к проверке тестами; особенно S7–S13 позиций:
- **S7–S8:** `position_h` только растёт; продвигается `UPDATE` строки
  `engram_conversation` в транзакции, которая в ней же пишет резерв;
  блокировка строки держится **до фиксации** этой транзакции;
- **S9:** последовательности PostgreSQL (`nextval`) и выдача позиций блоками
  **запрещены** (ADR-101 §5.1);
- **S10:** позиция выдаётся один раз; поста носителя группы без резерва или с
  `CreateAt = 0` нет;
- **S11:** переходы только `reserved → published | aborted`, условные;
  надгробие постоянно и не переиспользуется;
- **S12:** опубликованная позиция не переназначается;
- **S13:** события не отменяются.

## 3. 930 SEND — детальный контракт

Источники: ADR-101 §5.1, §5.1a, §5.3, §5.6, §5.10; ADR-102 §2; ADR-103 §2;
спецификация §6.3. Форма запроса и ответа, пределы текста, ошибки — ADR-099
§9.1, §12.

### 3.1. Допуск

1. Разбор payload строго (ADR-099 §3); текст — пределы 217
   (`message_empty`, `message_too_long`, `message_too_many_links`).
2. Под **S(разговор)** (попытка с бюджетом, иначе `temporarily_unavailable`):
   существование и участие (`conversation_not_found` / `no_access`) →
   состояние (`conversation_archived`) → право `messages.send`
   (`forbidden`) — по таблицам Bridge (ADR-099 §11).
3. S держится **как минимум до фиксации транзакции резерва** (§3.3): иначе
   удаление участника может зафиксироваться между проверкой права и
   резервом, и сообщение встанет после `member_removed` (ADR-101 §5.3).
4. Блокировка отправки ADR-092 §2.5.1 (транзакционная, ключ
   `photon:conv-send:` + sender + `client_msg_id`) — сохраняется
   (спецификация §5).

### 3.2. Владелец ключа, затем повтор

1. **Сначала — ADR-102.** `SELECT 1 FROM engram_position WHERE
   conversation_id = $c AND item_kind = 'message' AND item_key = $k AND
   sender <> $s LIMIT 1` по `engram_position_key_all` — **во всех
   состояниях**, включая `aborted`. Найдено →
   - ответ `idempotency_conflict`;
   - новая позиция **не** резервируется, `CreatePost` **не** вызывается;
   - чужой резерв или надгробие **не** изменяется (ни переходов, ни
     сверки в ходе этого запроса).
2. **Иначе — повтор** среди своих резервов ключа **не в состоянии
   `aborted`** (`engram_position_key_live`):
   - `published`, тот же `payload_hash` → ответ с его позицией (I6);
     другой → `idempotency_conflict`;
   - `reserved` → `message_in_progress`;
   - нет (или только свои надгробия) → §3.3. Пост с этим ключом на позиции
     с надгробием **не** считается найденным.

### 3.3. Резерв

Одна транзакция:
```sql
UPDATE engram_conversation
   SET position_h = GREATEST($bridge_now_ms, position_h + 1)
 WHERE conversation_id = $c
RETURNING position_h;                          -- P (ADR-101 §5.1)
INSERT INTO engram_position
  (conversation_id, pos, item_kind, item_key, state, sender, payload_hash, reserved_at)
VALUES ($c, P, 'message', $k, 'reserved', $s, $hash, $now);
COMMIT;                                        -- блокировка строки до COMMIT (S8)
```
- нарушение `engram_position_key_live` (параллельный повтор того же
  отправителя или одновременная отправка другого с тем же ключом) →
  повторить §3.2: свой резерв найдётся, чужой даст `idempotency_conflict`
  (ADR-102 §2 п. 4);
- `nextval`, выдача блоками, вычисление позиции по `Posts` — запрещены;
- после `COMMIT` S можно отпускать.

### 3.4. Публикация

- `CreatePost` с явным `CreateAt = P`, `Props.engram_client_msg_id = k`;
- `PendingPostId` — **либо не задаётся, либо** `k` + `P`; задавать только
  `k` запрещено (ADR-101 §5.6: `deduplicateCreatePost` в 9.11 30 с
  возвращает прежний пост с тем же `PendingPostId` как успех и `CreateAt`
  не сверяет);
- `CreateAt` возвращённого поста сверяется с `P`. Расхождение →
  `reserved → aborted` своего резерва, успех **не** сообщается (ADR-101
  §5.6);
- `CreatePost` вернул **однозначную подтверждённую ошибку создания** (пост
  не создан) → так же `reserved → aborted`, успех **не** сообщается;
- **неопределённый результат** — тайм-аут, потерянный ответ, обрыв RPC,
  смерть исполнителя после отправки `CreatePost` — **не** ведёт к
  `aborted` у владельца: резерв остаётся `reserved` и закрывается сверкой по
  §3.6 (ADR-101 §5.10), которая сначала ищет пост с `CreateAt = P` и
  ключом.

### 3.5. Закрытие и ответ

- условный `UPDATE engram_position SET state = 'published', post_id = $id
  WHERE conversation_id = $c AND pos = P AND state = 'reserved'`;
- 0 строк (резерв уже отменён сверкой) → успех **не** сообщается; клиент
  повторяет через исходящие Core (ADR-093) и получает новую позицию;
- успех → `last_activity_at = GREATEST(…, P)`; ответ ADR-099 §9.1,
  `created_at = P` (ADR-103 §1);
- доставка — **at-least-once** на стороне отправителя через существующие
  исходящие Core; Bridge exactly-once не обещает.

### 3.6. Неопределённость после `CreatePost`

Если результат `CreatePost` не определён — тайм-аут, потерянный ответ,
обрыв RPC, смерть исполнителя (R1: сервер доводит пост до конца после
смерти плагина):
- владелец резерв сам **не** отменяет; резерв остаётся `reserved` и держит
  барьер;
- сверка (§4.5) закрывает его одним условным оператором: пост с
  `CreateAt = P` и ключом найден → `published`; иначе → `aborted`;
- повтор клиента до закрытия получает `message_in_progress`, после —
  найденную позицию (`published`) или новую (`aborted`).

## 4. 931 SYNC — детальный контракт

Источники: ADR-101 §5.1b, §5.5, §5.11; ADR-103 §3; ADR-099 §9.2–§9.4;
спецификация §6.4, §7.2.

### 4.1. Допуск

Под **S**: существование и участие, периоды вызывающего (ADR-099 §9.4); в архиве —
по ADR-099 §8.1. Курсор: непрозрачен, привязан к `conversation_id`
(`invalid_cursor`); `limit` 1–200 (`invalid_limit`). Формат курсора —
реализация.

### 4.2. Один оператор: барьер + страница

**Один оператор SQL через master**, в одном снимке:
- **барьер** = `min(pos)` резервов разговора в состоянии `reserved`; если
  открытых нет — `position_h + 1`;
- страница `Posts` носителя: `type IN ('', 'custom_engram_event')`,
  `deleteat = 0`, `CreateAt < барьер`, границы видимых периодов;
- **надгробия исключены**: `NOT EXISTS` резерва с `state = 'aborted'` на
  позиции поста;
- **один пост на позицию** — с наименьшим `PostID` (дубль поста-события,
  дубль одной попытки);
- оператор возвращает и значение барьера.

Форма — спецификация §7.2 (раздел «Под ADR-101»), включая зеркальную форму
первичной синхронизации. `since_join` по нескольким периодам — внутри того
же оператора.

Запрещено: барьер и страница разными операторами, разными соединениями, с
реплики (ADR-101 §5.1b; контроль стенда AP-1 «страница, затем барьер» —
918–1237 пропусков на прогон).

### 4.3. Курсор, порядок, полнота

- **W = 0**: окна нет — ни ADR-092 §2.3, ни иного (ADR-101 §5.5, ADR-103
  §3); «окно» в ADR-099 §9.2/§9.4 читается как 0;
- курсор ответа **не проходит барьер**;
- выдаётся опубликованный префикс ленты ниже барьера; элементы выше
  барьера придут продолжением после закрытия резерва;
- порядок — `(created_at, id)` по ADR-052; позиции уникальны (S10), равные
  `created_at` после схлопывания дублей не встречаются — порядок
  детерминирован;
- `at_end`, якорь, `from` — ADR-092 §2.2 и ADR-095 п. 2.7 относительно
  видимой ленты ниже барьера;
- 931 события **не дописывает** и `pending` не проверяет.

### 4.4. Типы и форма

Типы `''` → `kind:"message"`, `custom_engram_event` → `kind:"event"`;
прочие посты не выдаются. Элемент — ADR-099 §9.3; `created_at` — позиция.

### 4.5. Сверка (не 931)

Спецификация §8: незаписанные события дописываются под X с сохранённой
позицией (E2–E4); брошенные резервы сообщений закрываются §3.6. Кто и когда
запускает проход и порог отмены — **открыто** (Q2; живость, ADR-101
§5.11). Безопасность от момента отмены не зависит.

## 5. Изменения участия и события; конкурентность и идемпотентность

### 5.1. S/X и события (ADR-101 §5.2, §5.3)

- изменение (900 шаги 4–5, 903–921) — под **X** одной транзакцией:
  ключ идемпотентности, разговор `FOR UPDATE`, проверки, `expected_version`,
  изменение, `version + 1`, позиции событий `P..P+k−1` из `H` (E1), их
  резервы и `engram_event`; затем запись постов событий (E2–E4) и снятие X;
- X **обязательна до фиксации транзакции изменения**; держать её до записи
  постов событий — текущее правило записи событий (писать события без X
  запрещено), но не условие порядка и видимости;
- открывающий элемент периода — `created` или `member_added`; закрывающий
  — `member_left` или `member_removed` (ADR-099 §9.4); их позиции — из `H`,
  поэтому сообщения, начатые после фиксации изменения, всегда позже, а
  завершённые до — раньше (I1, I2);
- прежняя модель «930/931 под S видят `pending` → отпускают S → берут X →
  дописывают» **не реализуется** (устарело по ADR-101 §5.1a; спецификация
  §5). Незаписанное событие держит барьер.

### 5.2. Конкурентность — обязательные сценарии

| сценарий | ожидание | основание |
|---|---|---|
| один отправитель, N одновременных повторов одного `client_msg_id` | один неотменённый резерв, один видимый пост; остальные — найденная позиция или `message_in_progress` | ADR-101 §5.6; стенд S5 |
| два отправителя, один `client_msg_id`, резервов нет | один резерв; второй — `idempotency_conflict` | ADR-102 §2 п. 4 |
| B с ключом A при `reserved` / `published` / `aborted` резерве A | `idempotency_conflict`; резервы A не изменены; `CreatePost` не вызван | ADR-102 §2 |
| повтор A после отказа B | обычный повтор ADR-101 | ADR-102 §2 п. 3 |
| неопределённость после `CreatePost` (исполнитель умер, ответ потерян) | резерв держит барьер; сверка → `published` или `aborted`; повтор — по результату | §3.6 |
| поздний пост на отменённой позиции | никогда не выдаётся | ADR-101 §5.10 |
| повтор после отмены | новая позиция больше прежней; пост на надгробии не найден | ADR-101 §5.6 |
| повтор в пределах 30 с кэша `PendingPostId` | без потери: `PendingPostId` с позицией или не задан | ADR-101 §5.6 |
| удаление участника параллельно с его 930 | сообщение либо до `member_removed`, либо `no_access` / `forbidden` | ADR-101 §5.3 |
| параллельные изменения одного разговора | последовательные версии; `version_conflict` по `expected_version` | ADR-099 §10.3–§10.4; C2, C2b |
| переиспользование позиции | невозможно: PK `(conversation_id, pos)`, `H` растёт | S7, S10, S11 |

### 5.3. Идемпотентность (сводка)

| операция | ключ | повтор | конфликт |
|---|---|---|---|
| 900, 903, 904, 910–912, 920, 921 | `(PhotonID, код, request_id)` | `data` первого исполнения | другое каноническое содержание → `idempotency_conflict` |
| 930 | `(разговор, client_msg_id)`, владелец — `sender` | свой `published` → та же позиция; свой `reserved` → `message_in_progress` | другой текст или чужой `sender` в любом состоянии → `idempotency_conflict` |

## 6. Acceptance

**Правило:** у каждой проверки — отрицательный контроль: правило ломается
нарочно, проверка обязана упасть (CLAUDE.md, «тесты должны ловить
нарушения»). Порогов производительности ADR не задают — контракт их не
вводит: L3/L4 и замер владельца фиксируют **план и число**, критерий —
форма плана, не время.

### 6.1. Unit и интеграционные (настоящий PostgreSQL, фиктивный Mattermost)

- C1–C5, K1–K5, M1–M8, L1–L2 — спецификация §10 (как есть);
- контрактные тесты формы запроса и ответа каждого кода; правило
  авторизации на каждый код (`TestAuthzCoversEveryAction`);
- ADR-099 §17 и ADR-103 §5 целиком: атомарность 900, идемпотентность
  изменяющих, 930 без дублей, одна шкала 931 по ADR-052, `since_join`
  включая `left → active`, коды доступа, последовательные версии, 902 без
  состава, ни одного идентификатора Mattermost.

### 6.2. Регрессия AP-1 (отрицательные контроли остаются тестами)

Из исследования и ADR-101 §5.12 (стенд AP-1 — PASS; реализация обязана
повторить на своём коде):

| # | проверка | ожидание | контроль (обязан упасть) |
|---|---|---|---|
| P1 | барьер + страница одним оператором, конкурентные отправители со сбоями | 0 пропусков ниже курсора, 0 постов на надгробии | «страница, затем барьер»; без барьера |
| P2 | порядок фиксации резервов, детерминированное чередование | вторая транзакция ждёт первую | `nextval` вместо строки `H` |
| P3 | надгробие: поздний пост через 3 и 8 с, задержка в хуках, потеря X посреди записи события | поздний пост не выдан; один пост-событие | отмена без фильтра надгробия |
| P4 | повтор 930 после отмены: 7 сценариев + конкурентный | 0 потерь при «успехе», ≤ 1 опубликованной позиции на ключ | поиск мимо надгробий; `PendingPostId` = ключ без сверки `CreateAt` |

### 6.3. Live: настоящий Mattermost

На тестовом стенде проекта (Mattermost 9.11, Bridge) — **по отдельному
заданию** на работы со стендом:
- явный `CreateAt` сохраняется через `CreatePost` плагина (F2);
- `PendingPostId` с позицией: попадания в кэш между разными позициями нет;
  со сверкой `CreateAt` повтор после отмены доходит;
- барьер + страница через RPC-драйвер одним оператором: проверено по коду
  (`app/plugin_db_driver.go:98`), прогоном — нет;
- `CreatePost`, начатый перед падением плагина, доводится до конца (R1), и
  сверка закрывает резерв;
- транзакционная блокировка после падения плагина снимается через 15–60 с
  (R7) — наблюдается и записывается;
- 900 при `DriverName ≠ postgres` и при непроверенной схеме —
  `temporarily_unavailable`, активация не падает;
- посты носителя не уходят ENGRAM-клиентам через push (push вне v1, ADR-099
  §15): наблюдается и записывается, решения не принимается.

Кластер Mattermost и корпоративная лицензия **не требуются**: всё выше
выполнимо на одном узле.

  902) — спецификация §12, как есть;

  семантики групп в Core нет.
