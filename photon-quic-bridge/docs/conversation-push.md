# Push разговоров ENGRAM — спецификация

Статус: **ПРИНЯТО** вместе с ADR-123 (2026-10-18). Написана до кода. Описывает весь путь
«новое сообщение → системное уведомление» поверх уже существующих механизмов:
QUIC-подписки Bridge (`push.go`, ADR-040), насоса событий Core (ADR-045,
`photon-core/docs/event-delivery.md`) и списка разговоров 902 (ADR-104, ADR-108).
Firebase, второй канал доставки, брокер и очередь не вводятся.

---

## 1. Что было до этой работы (разведка 2026-10-18)

| звено | состояние |
|---|---|
| `ports.Notifier` | интерфейс без реализаций и вызовов; ни одного адаптера |
| хуки Mattermost → `PushRouter` | работают; аудитория — `read(C)` по членству Mattermost (ADR-040, вариант A) |
| сообщения разговоров ENGRAM (930) | пишутся постами в **приватный канал-носитель** служебной команды (`c-<conversation_id>`); участники ENGRAM **не** члены канала Mattermost (членство — таблицы `engram_member_period`, ADR-100) |
| следствие | хук `MessageHasBeenPosted` для поста-носителя срабатывает, `canReadChannel` отказывает каждому подписчику — **событие не получает никто**. Утечки нет, но и доставки нет |
| Core в ENGRAM | без секции `bridge` (ADR-094 §4.5): подписку открыть не к кому |
| ENGRAM Android | к Bridge — только HTTP; QUIC-подписки, `NotificationManager`, каналов уведомлений и разрешения `POST_NOTIFICATIONS` нет; приём новых сообщений — опрос видимым экраном раз в 5 с |

Итог: push-уведомлений в ENGRAM не существовало ни на одном звене после хука.

## 2. Решение в одной схеме

```
930 SEND (успех, reserved → published)          908 READ (успех)
        │                                              │
        ▼                                              ▼
 аудитория = активные участники разговора        аудитория = сам читатель
   − автор − заблокировавшие автора                (другие его устройства)
        │                                              │
        └──────────► PushEvent{conversation_activity, to=<mm_user_id>}
                               │   (поле to на провод не идёт)
                               ▼
                  PushRegistry.sendTo → QUIC uni-stream подписчика
                               │
          ┌────────────────────┘
          ▼
 Core ENGRAM: насос подписки (ADR-045), цель задаёт действие 814
          │  MESSAGE{event:"conversation_activity", data:{conversation_id, reason}}
          │  CONNECTED (после каждого (пере)подключения)
          ▼
 ENGRAM: PushNotifier — 902 (источник истины) → план уведомлений → NotificationManager
```

**Push сообщает о событии, а не о состоянии.** В событии нет ни текста, ни
автора, ни позиции — только `conversation_id` и повод. Всё, что показывает
уведомление, клиент берёт из ответа 902 по своей сессии, то есть через ту же
авторизацию, что и обычное чтение. Повторное, потерянное или переставленное
событие поэтому не может испортить состояние: худший исход — лишний запрос 902.

## 3. Bridge

### 3.1. Событие

```json
{"event":"conversation_activity","data":{"conversation_id":"<id>","reason":"message"}}
```

- `reason`: `message` — опубликовано новое сообщение (930); `read` — участник
  отметил прочтение (908). Неизвестный `reason` клиент обязан трактовать как
  «что-то изменилось» (тот же запрос 902).
- `user_id` верхнего уровня **не заполняется**: адресат задаётся служебным
  полем `PushEvent.To` (`json:"-"`). Клиенту ENGRAM `mm_user_id` не выдаётся
  (ADR-081 §2.5), в том числе свой.
- Тела, текста, автора, позиции в событии нет (ADR-040, вариант C — для этого
  класса событий; хуки Mattermost остаются на варианте A без изменений).

### 3.2. Аудитория (fail-closed)

Для `message`:

```
audience = { p : активный период участия p в разговоре (state='active') }
           − { автор }
           − { p : p заблокировал автора (engram_user_block) }
```

Тот же предикат, что разрешает чтение 931 (`callerAccess`): активный участник.
Каждый `photon_id` переводится в пользователя Mattermost через
`AccountRegistry.FindByPhotonID`; не найден, не связан, ошибка — **этому
получателю ничего не отправляется**. Ошибка SQL — не отправляется никому.
Ошибки push не влияют на исход 930: сообщение уже опубликовано, push —
ускоритель (ADR-046 §1).

Для `read`: только сам вызывающий 908 (`callerID` сессии). Остальные участники
о чужом прочтении событий не получают.

### 3.3. Момент отправки

После **условного** перехода `reserved → published` (`markMessagePublished`
вернул `true`). Раньше — нельзя: клиент, пришедший с 902 по событию, мог бы не
увидеть сообщение за барьером резерва. Повтор 930 тем же ключом (`slot.found`)
события не повторяет.

### 3.4. Что не меняется

- `PushRouter.Route` для событий хуков: аудитория по `read(C)`, как в ADR-040.
  Пост-носитель по-прежнему не доставляется никому: участники не члены канала.
  Это закрепляется тестом, чтобы будущая «помощь» (добавить участников в канал
  Mattermost) не открыла полный пост с текстом подписчикам.
- Буфер 64 на подписчика и молчаливое отбрасывание при переполнении
  (`bridge-session.md` §9 п. 6). Потеря события здесь не теряет сообщения:
  `CONNECTED` и следующий повод снова опрашивают 902.

## 4. Core: цель подписки — действие 814

Core в ENGRAM создаётся до входа и живёт весь процесс (ADR-094 §5.1); сессия
появляется, меняется и отзывается позже. Секция `bridge` в `Photon_Create`
этого не выражает: её токен фиксируется при создании. Поэтому цель подписки
задаётся локальным действием.

**`ACTION_LOCAL_EVENTS_TARGET = 814`** — локальное, на провод не выходит,
Bridge отвечает отказом (ADR-064 п. 2.5).

| payload | смысл |
|---|---|
| `{"endpoint":"host:4443","session_token":"…"}` | задать или заменить цель |
| `{}` или оба поля пустые | снять цель (выход, отзыв сессии) |
| отсутствует или пусто ровно одно из двух полей | отказ вызова `PHOTON_ERR_INVALID_ARGUMENT` (ADR-065 §8); цель не меняется |

Ответ: `{"ok":true,"data":{"target":"set"}}` / `{"target":"cleared"}`.

Правила:

1. Подписка по-прежнему одна на инстанс, насос один (event-delivery.md §5).
2. Установка цели при уже установленном колбэке запускает насос; колбэк,
   установленный раньше цели, запоминается (`StartEvents` возвращает
   `ErrNoEndpoint`, как и прежде, но адресат доставки сохранён).
3. Смена цели прерывает текущую подписку и её паузу восстановления сразу и
   подключается к новой без паузы. Одно событие, уже принятое старой
   подпиской, может быть доставлено после возврата 814: вызов допустим из
   колбэка события, то есть с потока насоса, и ждать насос он не может.
   Событие — лишь повод перечитать 902, поэтому это безопасно.
4. Снятие цели закрывает подписку; насос ждёт новой цели, не переподключаясь.
5. Action-соединение 814 **не создаёт**: запросы ENGRAM остаются HTTP
   (ADR-094 §6.1). Транспорт QUIC создаётся лениво при первой цели и
   закрывается в `Close` после выхода насоса.
6. Цель с `Photon_Create` (`bridge.endpoint` + `session_token`) — начальное
   значение той же цели; поведение инстансов с секцией `bridge` не меняется.
7. Токен в журналы и ответы не попадает.

## 5. ENGRAM Android

### 5.1. Подписка

- `PushLink`: при подтверждённой сессии — 814 с `endpoint` = хост
  `BRIDGE_URL` + `:4443` (константа Bridge, `quic_listener.go`) и токеном
  сессии; при выходе, `401`, смене аккаунта — 814 `{}`.
- Слушатель событий Core: `MESSAGE/conversation_activity` и `CONNECTED` →
  повод `PushNotifier`; `NETWORK_CHANGED` → журнал.
- Повод при старте процесса и при появлении сети — тоже: пропущенное за время
  отсутствия связи находится через 902, а не через историю push.

### 5.2. План уведомлений (чистая функция, тесты без Android)

Вход: ответ 902, сохранённые «уже показано до позиции» по разговорам, открытый
на экране разговор, текущее время. Для каждого разговора:

| условие | действие |
|---|---|
| `unread_count = 0` или `read_up_to ≥ показанной позиции` | снять уведомление разговора |
| разговор открыт на экране | не показывать; снять показанное |
| `muted_until > now` | не показывать |
| последний элемент — свой или не сообщение | не показывать |
| позиция последнего сообщения ≤ уже показанной | не показывать повторно |
| иначе | показать/обновить одно уведомление разговора, запомнить позицию |

Одно уведомление на разговор (идентификатор — от `conversation_id`),
обновляется на месте; несколько разговоров — несколько уведомлений и сводка
группы. Повтор события с той же позицией ничего не показывает.

### 5.3. Уведомление

- Канал `messages` (важность высокая); на экране блокировки — публичная версия
  «Новое сообщение» без текста (`VISIBILITY_PRIVATE`).
- Нажатие открывает тот же экран, что и список чатов (`GroupActivity` с
  `conversation_id`); после открытия разговор помечается прочитанным
  существующим путём 908.
- Android 13+: `POST_NOTIFICATIONS` запрашивается на главном экране; отказ —
  уведомлений нет, подписка и синхронизация работают.

### 5.4. Фон

- `PushService` — foreground service типа `specialUse` (Android 14+) с
  постоянным уведомлением канала `connection` низкой важности: держит процесс,
  а с ним насос Core. Запускается главным экраном при подтверждённой сессии и
  после загрузки устройства (`BOOT_COMPLETED`); останавливается при выходе.
- Без foreground service процесс в фоне замораживается или выгружается,
  и QUIC-подписка гибнет вместе с ним. С ним — Doze не отключает сеть процессу
  с foreground service, но не гарантирует доставки: keep-alive QUIC в глубоком
  сне может не уйти, отображение NAT для UDP истечёт, push потеряется до
  пробуждения. Потерянное находит `CONNECTED` после восстановления (902).
  Что из этого подтверждено на устройстве — в отчёте, а не здесь.

## 6. Тесты

Bridge: аудитория (получатель, автор, посторонний, ушедший, заблокировавший,
не найден в реестре, ошибка SQL), отсутствие повтора при повторе 930, 908 —
только себе, `To` не уходит на провод, пост-носитель не уходит участникам.
Core: 814 — установка, смена (старая подписка закрыта, события только новой),
снятие, неполный payload, колбэк до цели, токен вне ответа.
Android: планировщик §5.2 целиком, разбор события, проводка `PushLink`.
